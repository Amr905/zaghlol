## Design-note conformance (§4 S-2 redesign), traced
- **One winner:** the claim runs `DELETE expired`, then `INSERT … ON CONFLICT DO NOTHING`, then a live read, all in one READ COMMITTED transaction. A concurrent insert waits on the unique index and then sees the conflict. The loser's live read sees `status 0` and answers 429. Tested by `ConcurrentClaimsOfOneKeyHaveExactlyOneWinner` and the e2e 200/429 test. ✔
- **Lease takeover / lease lost:** `CompleteAsync` deletes only `claim_id = mine AND status = 0`, and inserts the final row only when that delete hit exactly 1 row. Otherwise it returns false and records `lease_lost`. Tested by `AClaimWhoseLeaseExpiredIsTakenOver…` at both the filter and the store level. ✔
- **Release:** the claim is released on 429/5xx (`!IsStored`), on any exception, on the handler timeout, on a KMS or DB failure after the handler, and on the S-3 rotation backstop. Release is best-effort and the lease backs it up. ✔
- **Handler timeout < lease:** 30 s vs 60 s, pinned by `TheHandlerTimeoutIsShorterThanTheClaimLease`. `RequestAborted` and the bound `CancellationToken` are swapped for the call. ✔ (see finding 2 on the budget inside 30 s)
- **No transaction across the handler:** the pool test shows 0 `idle in transaction` sessions under a 3-connection cap, and the negative proof shows the test catches the old design. ✔
- **S-3:** an architecture test (`IdempotentHandlersNeverTakeTheInstallTokenRotator`) plus a top-level JSON scan. The scan throws in Development/Testing and logs only the type in Production. ✔
- **S-4:** `EXISTS … FOR SHARE` on the install row, ordered against `DeleteAsync` (it updates the install, then deletes the records, in one transaction). ✔
- **S-6:** the envelope context is `idem/v2/<install>/<op>/<b64u(SHA-256(key))>`, and a swapped body fails to decrypt. ✔
- **Migration:** adds a nullable `claim_id`, a status CHECK and a claim-iff-status-0 CHECK. Existing rows (final, no claim) satisfy both, and `Down` is symmetric. The EF config and `backend-schema.md` match. ✔

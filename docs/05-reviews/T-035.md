## Design-note conformance
- **Evaluation order** (§4 steps 0–5): matches `CaptureGuard._decide`. That includes global drop for generic and user kinds, no ignore rules for `share`, `shortcut_message` checked against `sms` rules, the apple_pay longest-name rule with no institution on a tie, and the first last-4 pattern whose group 1 is exactly 4 ASCII digits. The `decide` function is pure, and an exception maps to a drop.
- **Portability:** `portableRegexProblems` covers the §3 list plus nested classes, `&&`/`--` and a leading `]`. Exporter and loader compile the same text (`guardPatternText` → `RegExp(unicode: true)`), so stage 0 and the Guard agree. The parity test runs every golden case through `ParsingPipeline`. I also flipped the lookaround check; the lint tests failed. The NEL change is correct: ICU and Java `.` exclude U+0085 and Dart's does not. Folding U+0085 to a space removes the difference. It also affects `normalizeText` (display), which is harmless.
- **Golden format** uses only JSON and wire strings. The harness needs a `configs` map, `userError` and `dropped`. Modes are expected as `baseOnly`, `full` and `invalid` strings. Natives can consume all of it.
- **Q1–Q6:** each has a single decision point and is labelled provisional in `guard_policy.dart` and the task file. Q2 and Q6 are data rules, with markers only (nit 7).
- **Performance:** worst case in my probe was about 0.8 ms per decision on a 4,000-character adversarial body (repeated `رمز`). Config load is well under budget. The patterns are bounded; there are no nested unbounded quantifiers.
- **Docs:** platform-channels §1.1/§1.2/§2/§3, parsing-engine and the ADR-005 *Threats* section match the code, except the line 93 wording (finding 1) and nits 6 and 9.

### Findings

**1. major — a newline is not a boundary, and the drop reaches ordinary reference lines.** `guard_policy`/`shared.json` pattern 1 and 2 (`t1_base.json` drop.global[0..1]), residual `residual.newline_not_a_sentence_end`. The builder documents `Do not share your OTP` + `Available balance: 23456`; the real reach is wider, because any `: <4-8 digit number>` next to a security word across a line break matches. All of these real-looking transactions are dropped with the new config (verified):
- `Debit EGP 100.00 at SHOP.` / `Ref: 482913` / `PIN is never requested by the bank`
- `Purchase EGP 100.00 at SHOP` / `Ref: 482913` / `Password is never requested`
- `Never share your PIN` / `Txn: 123456` / `Purchase EGP 100.00`
- `Transfer received EGP 500.00. Ref: 482913` / `OTP never required`
- Arabic `لا تشارك كلمة المرور` / `رقم المرجع: 482913` / `تم خصم 300.00 جنيه`

Why it is a major: a dropped transaction is unrecoverable (no spool entry, and the catch-up scan runs the same Guard), while a kept OTP is stored encrypted on the device, has no amount so it cannot auto-save as a transaction, and lands in review as unrecognised (security M-1 rated this Medium only because it persists, not because it spends money). The cost is asymmetric, so the Guard must prefer the keep on structural doubt, and the previous round's own principle was "keep a real transaction". Reference numbers (`Ref:`, `Txn:`, `Auth:`) of 4-8 bare digits are normal in bank and wallet SMS, and security lines on their own line are the usual layout; the residual should not be accepted as written. The 6-8 digit reference code with `:` is not a rare shape.
Required change: treat a line break as a sentence end for the **gap** and for the **code-first prefix/connector** parts (keyword on one line, code after a lead-in on the next; `Ref: 482913` newline `PIN ...`), but not for the tight form (`OTP:` newline `482913`, `Verification code` newline `482913` still drop; both are in golden today). That needs the Guard to keep a line break through step 0 for the global-drop match (a private marker or `\n` kept by a Guard-specific fold; the portable lint then permits that one literal) and the same in Kotlin and Swift, so decide it now, before T-038/T-061 port it. Add goldens for the five bodies above (keep) and keep `Verification code`/`482913` and `OTP:`/`482913` as drops. If the Lead decides to defer, the minimum is a PO decision recorded in ADR-005 plus a T-036 AC that every registry fixture with a multi-line layout runs through the Guard; I do not recommend deferring.

**2. minor — kept OTP wording.** `استخدم الرمز 482913` and `الرمز هو 482913` (bare `الرمز`, no `التحقق`) are kept, as is `Fawry code is`. Add `الرمز`/`رمز` with a lead-in or a confirm verb to the Arabic patterns, or list them in the residuals. Follow-up for T-036 (not blocking).

**3. nit — task file text.** T-035.md says `Do not share your OTP` + line is "residual"; update it to the line-break rule once finding 1 is settled. Other docs match the patterns.

### Performance

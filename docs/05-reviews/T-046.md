### Design-note conformance (checked)
- Pipeline order: parse, hash and key building before the transaction (`_prepare`); step 0 reads once per batch inside the transaction; Guard re-check → stage-0 drop → dedupe 1 → per-message savepoint → dedupe 2 → pending → account → categorize → raw + txn → balance → review → hooks. Matches §2.
- One `BEGIN IMMEDIATE` per batch (`inWriteTransaction` = drift `transaction`), nested `transaction` = SAVEPOINT; accounts repo, rules categorizer and store share the same `AppDatabase`, so all dedupe/merge reads are inside the write lock. The barrier test is real (pauses A after its dedupe-2 read; B must wait).
- Commit → `_finish` (diag, one `TransactionsChanged`) → return; the cycle acks only after return. Nothing emitted on failure.
- Merge: fill-NULL only; user-verified and soft-deleted targets attach-only (balance still recorded); `parse_confidence` max; account move only when T0 has no last-4. Settled: user-verified P status-only + `settledAmountDiffers`. Symmetric late pending implemented; ±5 % integer arithmetic; smallest diff then oldest then id.
- `body_hash`: tag `zg.raw.v1`, NUL-separated, receive time excluded, `hashNorm` independent of the parser (see CR-4 for the sender part); golden vectors present.
- FU-078: sign accepted only for `balance`/`available`, one leading `-`/`−`, informational reason factor 1000; amount with a sign stays a problem.
- FU-080: every `ParseGeneric` goes through `genericDisposition`; auto-save only with direction, background origin and the Q3 policy; `confirmed_count` never written (no write path to `capture_senders` exists in the use case).
- Failure classification: transient (`DB_WRITE_FAILED`/`DB_READ_FAILED`) → `RETRY`; constraint/accounts/money errors → message stored as `review` (`ingestFailed`); everything else → whole batch non-transient. Nothing is ever silently lost or deleted; the gap is availability (CR-1).

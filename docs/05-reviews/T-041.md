## Focus areas checked
- **Work lifecycle.** Live `zaghlol.ingest` expedited (`RUN_AS_NON_EXPEDITED_WORK_REQUEST`), `APPEND_OR_REPLACE`, no constraints, always `Result.success()`. Retry `zaghlol.ingest.retry` not expedited, delay series 10…900 s, input = attempt only, stops after 8. **Deviation 1** traced: a retry run's successor is appended to its own running work (`KEEP` would drop it, correct); a live run uses `KEEP`, so at most one retry waits; the process `Mutex` serialises runs, and a live run that cancels the retry work while a retry run waits on the mutex only cancels a run that would find an empty spool. No path drops a pending entry: every exit is EMPTY, NO_RETRY with a documented resumer (next live enqueue / app open), or RETRY. Duplicates are runs, not data (see m-2). No `setForeground` (source test + grep); the 60 s loop budget sits well under the 10-minute stop; a stop runs `afterRun(stopped = true)` under `NonCancellable` → `shutdown()`, never `destroy` (`CaptureRuntimeTest.aStoppedWorkerRun…`).
- **Headless engine / ShutdownSequence.** One `FlutterEngineGroup`, allowlist (instrumented allowlist test green), never reuses a closing engine (waits for `gone`), F3 re-check on the main thread returns `UI_TOOK_OVER`. `close` is sent at once even with a drain pending; destroy only after both replies or the 55 s + 5 s bound; `teardown` is exactly-once via `State.GONE`. Edge case in m-1.
- **Close after current batch.** Dart `_stop` is checked before each `drainSpool`; `_close` awaits `_running`, then the store close; deviation 2 (close before the first batch starts none) is harmless: the reply is OK/drained 0, the loop then polls the UI or retries.
- **Held entries (FU-105) / deviation 5.** Hold = rename after the ack of the rest; only ids this host drained; claim released only for ids actually moved; cap 50 → stays pending (stuck path); held counts towards caps, not towards pending; release only on a version change or an absent/unreadable version file (never a delete). T-046's test now expects the hold, and the old stuck path is kept as the hold-failure case. Data is never lost.
- **F4.** `ProviderIngestStore.open` invalidates `appDatabaseProvider` on both failure branches.
- **FU-104.** #2 drain stops at the first key-related `Unavailable` and after 5 s (monotonic, production clock injected); #6 `Cipher.init` inside `SpoolKey.withKey` and the device probe recorded per API; #8 `DrainScope` → one `recordDrain` in the host `finally`; #9 `secretKeyOrNull` → `UnusableKeyEntryException` → ladder; I-1 production-graph test by identity; I-7 release `androidx.test` check in the placement script; #5 recorded for T-047/T-078 in the task file.
- **Placement.** WorkManager is `implementation` (all variants); `DiagnosticsReceiver` removed with `tools:node="remove"`; the placement script checks it, FGS type permissions, `foregroundServiceType`, release `androidx.test`, and spike classes/strings outside devSms; prod release `libapp.so` grep for `5550100` green. Spike code left in `src/devSms` is the receiver, intake, Guard, metrics and initializer only.
- **Inbox wiring.** `newHost(headless)` passes `uiInbox()` only to the UI host; `CaptureRuntimeTest.theUiHostGetsTheInboxReaderAndTheHeadlessHostAnswersNotAvailable` drives the real Pigeon `queryInbox` handler registered by `attachUi` and the headless factory's host (`NOT_AVAILABLE`, no reader built). Merge resolution of the `AndroidCaptureHost` constructor is clean (`inbox` last, named).
- **FU-081 F6.** Conditions sampled at receive in devSms `SpikeMetrics`; devSms-only.

## Notes for the Lead
- **T-040 / T-047 ordering hazard.** `MainActivity` attaches the UI engine in every flavour, so while the app's engine exists the worker never starts a headless engine; it notifies the UI and polls. `startForegroundIngestion` is wired in devSms only (L3). If T-040's production receiver ships in a non-devSms build before T-047 wires foreground ingestion, any SMS that arrives while the UI engine exists waits 60 s, then NO_RETRY, and stays in the spool until a later headless run. Merge T-047 before or with T-040 for non-devSms builds, or have T-040's brief check this.
- Deviations 1–5 are sound and documented in platform-channels §2 / ADR-005 (ADR wording affected by m-2).
- Suggested follow-ups: m-1 and m-3 → T-040 (it touches `CaptureRuntime`) or a small T-041 follow-up; m-2 → Lead/architect decision with the physical-device rows (L4); m-4 and m-5 → T-047.

## T-178 AttestationHostApi - APPROVED
Checked: the Android `requestHash` is the unpadded base64url of the exact 32 bytes (`AttestationHost.kt` `requestHashOf`). Wrong length and project number 0 fail closed without calling Google. `PROVIDER_INVALID` re-prepares once with no loop. The error map matches the task. Errors carry the code only. iOS makes a new key only on `forceNewKey`, `errSecItemNotFound` or `invalidKey`. Any other Keychain status is `ATTEST_UNAVAILABLE`. The stored keyId is replaced only after `attestKey` succeeds. `attestKey` and `generateAssertion` get the same `Data`. Calls are serialized, and there is no loop on a fresh key's `invalidKey`. Dart: the proof and the exception `toString` are redacted, and malformed proofs fail closed. Network config: system CAs only, cleartext off, user CAs only in `debug-overrides`, and the config is referenced from the main manifest. There are no logging calls, and the CI grep is extended.
- minor `AttestationHost.swift:107-110`: `replace` runs delete and then add. If the add fails after the delete worked, the old keyId is gone (the next call then makes another key). That is harmless because the old key was being replaced anyway, but `SecItemUpdate` with an add fallback would keep the old item on a failed write, as the design note says. Follow-up.
- minor: the device ACs (Play token decode, App Attest verify, user-CA proxy on release vs debug) are not run yet. They are deferred to `docs/05-reviews/T-178-device.md`, like T-172. Track them as a follow-up before Gold ships.
- nit `network_security_config.xml:7`: the comment says flatly that `dart:io` "never trusts user CAs". Design note 6 says this still has to be confirmed on a device. Word the comment the same way.

## T-179 SeatKeyHostApi - APPROVED
Checked: the Keychain items use `AfterFirstUnlockThisDeviceOnly`, are not synchronizable and sit in the app's own group. Accounts other than `own` / `earlier.<10 digits>` are never touched. Every Keychain read error is `SEAT_KEY_UNAVAILABLE` and deletes nothing. `own` is created only when it is positively absent (`errSecDuplicateItem` reads back the winner). Rotation is one atomic `SecItemUpdate` rename plus a FIFO trim to 4 earlier keys, so at most 5 keys exist. Dart rotates only when `seat_key_install` differs from the current install ID, and writes the marker only after a successful rotation, so element 0 is fixed for the install. The R5-6 flag is scoped to the install ID and dropped with `deleteIfEquals` on `InstallReregistered`. Android never opens the channel (no `kotlinOut`). Malformed native answers yield no keys. Errors are code-only and nothing logs.
- minor `SeatKeyStore.swift:329` / `:189`: "unusable" covers any CryptoKit error from `PrivateKey(dataRepresentation:)` or `signature(for:)` after 3 tries in about 400 ms, and the item is then deleted. The contract asks for that deletion, but a transient Secure Enclave error would destroy an earlier-install key and lose same-iPhone recognition for good. Consider deleting only on errors that prove the key is gone (for example the wrapped key not found / invalid key data) and otherwise dropping the key from the result for this call only. Follow-up. Record it in `T-179-device.md` if the device runs show any transient SE errors.
- minor `seat_keys.dart:144-157`: a `BackendStateStore` read or write failure inside `_prepare` propagates out of `publicKeys()` / `prove()`, unlike the documented "no keys" fallback. Callers (T-145/T-147) must handle it, or `_prepare` should map it to `null`. Follow-up.
- minor: the R-19 reinstall and "Delete everything" device ACs are not run. They are deferred to `docs/05-reviews/T-179-device.md`.

## T-044 Android permission host - APPROVED
Checked: `ActivityPermissions.requestSms` checks `smsFlavor` (read from the merged manifest's requested permissions) before any prompt. `*NoSms` answers `NOT_AVAILABLE` with no system call, and the headless host has no `UiPermissions`. Concurrent requests share one prompt. An empty or interrupted result counts as a denial. `checkPermissions()` records a baseline at attach and emits `onPermissionChanged` only when the capabilities differ. It runs on resume and after a prompt. Errors are code-only.
- minor `CaptureRuntime.kt:296-301`: revoking SMS in Settings kills the process, so the "Revoking SMS triggers onPermissionChanged" AC is met only by Dart's `getCapabilities` at the next start (the KDoc says so). Notification-access revocation does fire the event. Note it in the AC map, and in T-056's start-up read.
- minor `UiPermissions.kt:58`: `detach()` drops pending callbacks without answering them. That is fine when the engine dies, but it is worth a comment that the Dart future is abandoned on purpose.
- nit: `POST_NOTIFICATIONS` request is left open for the notifications owner, as the task file says; make sure it has a task.

## T-143 sync orchestrator - APPROVED
Checked against BR-SYNC-03: the request is built only from cursors (`catalogVersion`, `flagsVersion`, `pricesAsOf`, `entitlementIssuedAt`, `registryVersion`) and outbox rows. Contributions are read only while `contributionOptIn` is on (`sync_orchestrator.dart:360`). Each row is re-parsed against an exact key set into the generated DTOs, and bank requests are user-initiated. Nothing financial is read. The sync goes through `EntitlementService.anchored`, which uses a fresh nonce and hands the signed body (a throttle answer included) to T-144 first. A throttle answer applies nothing and keeps the outbox. Catalog ops, the outbox delete, prices and flags apply in one `db.transaction`. A failure rolls back and reloads the flags (the prices/flags repositories write through the same DB as nested savepoints). Snapshot version mismatch is refused. Release keys: `releaseResponseKeys` is empty and dev kids are refused in release, so every signed answer is dropped and nothing applies or grants Gold (fail closed). Nothing logs bodies; diag events are code-only.
- minor `sync_orchestrator.dart:425-429`: one contract-breaking row deletes **every** row gathered for this request, valid contributions and bank requests included. Drop only the offending row (validate each DTO's `toJson()` as it is built). Follow-up; it loses no financial data.
- minor `sync_orchestrator.dart:360`: contribution rows queued while the user was opted in and still in the outbox after an opt-out are sent if the user opts in again later. Confirm with the contribution owner whether opting out should purge them.
- minor `sync_providers.dart:75,118`: `allowDevKeys` / `allowInsecureLocalhost` use `!kReleaseMode`, so **profile** builds accept dev kids and plain-HTTP localhost. The current key lists contain no dev keys, so there is no exposure today. Prefer `kDebugMode`. Follow-up.
- minor: the "User rule never overridden" AC has no T-143 test. It relies on T-075's `Recategorizer` (which skips `user` sources). Add one orchestrator-level test with a real `Recategorizer`, or point the AC map at T-075's test.
- nit: the task file has no AC to test map section. The test names map cleanly (`sync_orchestrator_test.dart:207, 224, 239, 299, 492`).

## T-110 Ask engine - CHANGES_REQUESTED
Checked: the parser is pure, never echoes the question (redacted `toString`), and caps the input. Answers are one figure per currency and never summed across currencies, and the roast uses one currency. Unknown questions return a fallback with chips and no number. The engine has no logging. The 360-row utterance set passes.

- **major (money, wrong figure)** `ask_engine.dart:297-330`: a card name that matches several accounts (by design "ties are kept", e.g. CIB debit and CIB credit) makes the balance answer **add an asset balance and a credit-card balance into one figure**. Probe: `رصيد كارت CIB` with CIB Debit 10,000.00 and CIB Credit 300.00 returns one EGP figure of 10,300.00 with `liability: false`. Required change: never sum across asset and liability kinds. Either return per-account figures when the named set has more than one account, or split asset and liability sums with the liability flag per figure. Test to add: two accounts sharing a name (debit and credit), `رصيد كارت CIB`, assert no figure equals their sum and each account's balance is reported with its own kind.
- **major (money, wrong figure)** `ask_parser.dart:195-217` + `ask_engine.dart:302`: for `accountBalance` an account or card name without a cue word is not bound, and the `unknownTarget` guard only runs for spend / compare / biggest. So `balance of CIB` and `رصيد CIB كام` answer with the **total of all asset accounts** (probe: 10,000.05 including the cash wallet), shown as if it were the CIB balance. The same happens for a name that matches nothing (`رصيد NBE`). Required change: for balance (and any intent that takes an account), bind a matched account name with or without a cue. Extend the `unknownTarget` guard to `accountBalance`, so a named-but-unmatched target gets a fallback, never the overall total. Tests to add: parser rows `balance of CIB` / `رصيد CIB كام` → accountIds {CIB}, `رصيد NBE` → `!unknownTarget`; an engine test that `balance of CIB` returns only CIB's balance.
- minor `ask_engine.dart:72,120`: the engine catches `on Exception` only, so an `Error` (`StateError` from `.first` / `.single` at `:448`, `:505`, an `ArgumentError` from `Money` arithmetic) escapes, although the KDoc says "never throws". Today the chart layer returns `ChartNotEnoughData` for empty sets, so I found no live path. Use `on Object` to make the contract hold. Follow-up (trivial; can go in the fix pass).
- minor `ask_engine.dart:351-365`: "budget left" uses `categoryDonut(cycle).total` as the spend. Confirm it equals the Home / budget screen's cycle net-spend figure (same exclusions), or two screens show different "left" numbers. Follow-up.

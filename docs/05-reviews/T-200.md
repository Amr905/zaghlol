**Key loading once at start (deviation from self-check §5).** The justification holds. The guards check exactly the bytes that later sign, so a runtime file swap can't bypass them. Per-call reads give no memory benefit against the relevant attacker: code execution as the app uid can read the files anyway. Rotation already needs a restart. Handling is correct: symmetric keys sit in pinned arrays that `Dispose` zeroes; `ECDsa` lives in OpenSSL native memory, freed on dispose; a partial load is disposed on failure (`FileKms.cs:114-118`); file buffers are pinned and zeroed in `finally`. Each signing key has its own `Lock` covering `SignHash`/`ExportParameters`, while HMAC/AES-GCM objects are per call over a read-only array, which is thread-safe (`TwoActorsSignAtTheSameTime`). What is missing is memory locking and dump exclusion (S2). The `ObjectDisposed` check is not atomic with use during shutdown, which is harmless at process exit.

**Other areas checked, no finding:**
- **Guards G1–G13:** each fails closed with a constant message. `File.OpenHandle` exceptions (which carry the path) are replaced. The API and worker host-start tests confirm the same in the real `Program`.
- **Key tool:** `O_CREAT|O_EXCL` with 0400 means there's no moment when a key file is readable by anyone else. The directory is 0700 while writing, then 0500. Only public values are printed (test with sentinels). Refusals exit 2 without writing. The only gap is the symlink case (C1/S1).
- **Docs:** uid 1654 bind mount (Lead decision), Docker-secrets refusal, backup and the T-201 residual are accurate apart from C4–C7 and S2.

### Deviations (judged)
- **`canonical` 1–200 instead of 1–80:** accepted. A CHECK tighter than the server would make every later catalog apply fail on one long name, and FR-SYNC-03 applies all ops or none. The value is still non-empty. Documented in `database-schema.md` §2.4.
- **JSON CHECKs wrapped in `CASE WHEN json_valid(x) …`:** accepted and correct. A bare `json_type` raises "malformed JSON" instead of failing the CHECK, so the error would surface as `DB_WRITE_FAILED` instead of `DB_CONSTRAINT_CHECK`.
- **Date CHECKs as `date(x) IS x`:** accepted and correct. `date('junk')` is NULL, so `= x` would let junk through a CHECK. `IS` also rejects normalised overflow dates (`2026-02-30`).
- **`ux_budgets_overall`:** accepted. Without it, the spec's `UNIQUE (category_id, currency, period)` allows any number of NULL-category ("overall") budgets. The index is tested and listed in §3 invariants.
- **Frozen v3 step that drops and re-creates the offset triggers:** accepted. `v3DroppedTriggers` and `v3AddedObjects` are derived from the v2/v3 dumps by a test (`migration_v3_test.dart:70`), which also asserts that the only changed v2 objects are the two triggers. `DROP TRIGGER` without `IF EXISTS` makes a malformed v2 file fail, and a test shows that failure is restored byte-identical. Rule 2b in §5 records the pattern.
- **FTS secure-delete set after creation:** accepted. FTS5 options live in `_config` (data), so neither `createAll` nor the dumps carry them. They are set in `onCreate` (inside the create transaction) and in the frozen step, and `v3FtsOptions == ftsOptionStatements` is tested. The fresh, migrated (both executors) and FakeNext paths are all checked, and a positive control shows the token bytes stay when the option is off.
- **Contract notes:** accepted. Aliases are upserted with `ON CONFLICT (alias_norm, merchant_id) DO UPDATE SET match` (no REPLACE). The `match` update does not touch the FTS row, because the update trigger fires only on `id, alias_norm`. Merchant upserts use drift's `insertOnConflictUpdate`, which is `ON CONFLICT(id) DO UPDATE`, so aliases survive. The integer alias id gives a rowid that is stable under VACUUM. The SQLite ≥ 3.44 requirement is documented, and the device suite checks it on the shipped sqlite3mc.
- **`markFired` uses the changed-row count:** accepted. `fired_alerts` has no triggers, so `changes()` is exactly this statement's insert. `busy_timeout = 5000` (T-016) serialises two connections. Tests cover 10 concurrent callers on one connection, 6 callers across two connections (one per executor), and a positive control for the stale-insert-id bug.

### Focus checks
- **Money:** every amount column has `typeof = 'integer'`, a ±(2^53−1) bound and a currency `GLOB '[A-Z][A-Z][A-Z]'`. Limits and recurring amounts are ≥ 0; summary amounts are signed. `BudgetsDao` and `CycleSummariesDao` refuse a mixed currency before any SQL. `by_category` is decoded to `Money` in the row's currency. Totals are never summed across currencies. Gap: m-1.
- **Catalog key vs parsing-engine §5 / T-034:** the CHECK is `^[a-z0-9]+( [a-z0-9]+)*$` with length 1–64, which matches the cleaner's output and `merchantKeyMaxLength = 64`. Every non-empty golden key is accepted, and the Dart and SQL checks agree. The regex and the 64 limit are duplicated from `zaghlol_parsing`, which the app does not depend on yet; the golden-vector test is the guard against drift between the two.
- **Category code:** `length 2–32 ∧ GLOB '[a-z]*' ∧ NOT GLOB '*[^a-z0-9_]*'` is equivalent to the OpenAPI `^[a-z][a-z0-9_]{1,31}$`.
- **Cascades:** deleting a catalog merchant cascades to its aliases (and their FTS rows) only. `transactions.catalog_merchant_id` and `merchant_rules` (`catalog_merchant` kind) are soft references, so no user data is deleted. A rule that points at a removed merchant simply stops matching. `recurring_occurrences` cascade only from their own item. `txn_id` uses SET NULL, so purging a transaction keeps the occurrence. Categories referenced by rules or budgets can't be deleted (FK NO ACTION, tested); the DAO archives instead.

### Tests
The tests are strong. Both executors run on an encrypted temp file. Every CHECK has a passing control row. A sentinel test proves refused catalog writes carry no text. Migration coverage: populated v2 → v3 through the opener (copy made and deleted, data kept, live = fresh = dump, FK check clean, new tables, secure-delete, m-1/m-2), reopen without re-migration, two failure modes restored byte-identical, v1 → latest, and FakeNext running the real v3 step. All fixtures are synthetic. Missing: the n-2 case and a test for m-1.

## Security / privacy review

| # | Severity | Finding | Required change |
|---|----------|---------|-----------------|
| S-1 | Low (follow-up) | The v2 → v3 step turns secure-delete on but does not purge tokens of rows deleted **before** the step. Those stay in FTS segments until the next merge. No shipped v2 file exists (M0, pre-launch), so nothing is exposed today, and the step is frozen. | None for v3. If a later step ever turns on a privacy-relevant FTS option on shipped data, it should also run `'optimize'` (or `'rebuild'`). Note this beside rule 2b in §5. |
| S-2 | Info | Checked and OK. **Trigram query:** the key must be canonical (`[a-z0-9 ]`, ≤ 64) or the call throws `ArgumentError('not a canonical merchant key', 'key')`, whose message does not contain the value. Each trigram is wrapped in `"…"`, and the alphabet contains no `"`, so quoting is total. The query string and the limit are bound parameters (`?1`, `?2`), and the limit is capped at 50. No FTS5 or SQL injection path exists. **Errors:** writes go through `guardWrite`, and reads that take a key or rule value (`aliasesEqualTo`, `aliasCandidates`, `MerchantRulesDao.find`) go through `guardRead`. Thresholds and summaries refuse bad input with fixed codes (`BUDGET_THRESHOLDS_CORRUPT`, `CYCLE_SUMMARY_CORRUPT`, `ArgumentError` without the value), and `CurrencyMismatch` carries ISO codes only. **Data placement:** `merchant_rules` and the recurring tables are user data inside the encrypted DB and are never uploaded. `catalog_alias_fts` holds only catalog data, so leaving it without secure-delete is correct. The page-level `PRAGMA secure_delete = FAST` (T-016) still covers ordinary tables. **Migration:** it runs inside the T-016 copy/restore net, and restore on failure is proven byte-identical. **Surface:** no new network, SDK or log sink. | — |

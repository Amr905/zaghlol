## Verification notes
- Contract: parser matches the `prices` example in `backend-api.md` (asOf, stale, gold[{symbol,currency,price}] as decimal strings, fx{base,rates} as decimal strings, rates up to 9 decimals; JSON numbers rejected). Unchanged `null` block is handled by the caller (T-143), not by `apply`; fine.
- No `double`: rates are `rateE9` ints parsed by regex to BigInt; prices parsed via `Money.tryParse` after regex; extra non-zero fraction digits reject (no rounding); rate bounded to the `fx_rates` CHECK.
- Replay/older asOf rejected inside the transaction; equal accepted. Bad/partial block: parse is all-or-nothing before any write; empty gold or fx rejected, so nothing is wiped. Replace of quotes, rates and the stale flag is one drift transaction (nested savepoints in the DAO methods roll back together). Manual rows untouched by apply.
- Two-connection race test: not needed. The app has one DB connection (single writer); the read-then-write sits in one transaction, so a second connection would get SQLITE_BUSY rather than a lost update, and that path is the FU-094 busy handling, not T-112.
- Arithmetic re-derived by hand: USD 100.00 -> KWD at 0.3070 = 30.700 KWD (10000*307000000*1000/(1e9*100) = 30700); 1.000 KWD -> EGP = 48.95/0.307 = 159.4463 -> 159.45 (test); JPY 100 -> USD via rate; inverse = 1e9/r; cross via common base = rt/rf. Exponent scaling (`10^to / 10^from`) is correct for 0, 2 and 3 decimals. One half-even `roundDiv` on BigInt; ties tested (0.025 -> 0.02, 0.075 -> 0.08). Result is `Approx` (never `Money`), `MissingRate` when no direct/inverse/common-base path, same currency is an identity.
- Stale: strict > 24 h, backend `stale` flag cached in `secure_state`, far-future asOf reads stale (fail closed), any stale leg marks a conversion stale. Manual never labelled stale: consistent with FR-WLT-03.
- Docs match code (implementation notes, schema note in `database-schema.md` §2.6).

## Builder open question 1 (manual FX override)
FR-WLT-03 reads "...gold and FX rates ... from the backend; manual override; last-known price used offline". "Manual override" is most naturally the gold price (the backend's admin override in `backend-api.md` §Prices is also price-only, and `fx_rates` has no source column). It is not a blocker and not a defect of T-112. It is a genuine ambiguity, though: a user cannot correct a wrong FX rate for the ≈ view. Recommendation: the Lead files it in `docs/01-requirements/open-questions.md` for PO decision (price-only is acceptable for launch: ≈ is already labelled approximate and stale). If the answer is "yes, FX too", that needs a schema change (`fx_rates.source`, key change) and a new task; do not widen T-112.

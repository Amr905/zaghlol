## Break-glass script: proof (psql-only script, not automated)

Local PostgreSQL 16, roles from `deploy/db/bootstrap-roles.sql`, schema from `Zaghlol.Workers.dll --migrate`, script run with `psql` as `migrator`. Operators: `op-a` (support_lead, the requester), `op-b` (support_agent). The purchase UUID was passed in upper case every time.

| Case | Setup | Result |
|---|---|---|
| p1 | correction audit row 1 h old, freeze running | refused, "nothing was changed", freeze still set |
| p2 | correction audit row 25 h old | freeze cleared; audit row `support_unfreeze` with lower-case target, `break_glass: true` and `freeze_audit_id` = the correction row's id |
| p3 | no correction row, freeze started 1 h ago (`dispute_frozen_until` minus 30 days) | refused |
| p4 | no correction row, freeze started 25 days ago | cleared; `freeze_audit_id` null |
| no freeze | `dispute_frozen_until` NULL | refused |
| requester without `support_lead` (`op-b`) | 25-day-old freeze | refused |
| a second enabled `support_lead` | added `op-c` | refused; no extra audit row |
| bad input (`not-a-uuid`) | | input message, nothing changed |

When no correction row exists the API fails closed (break-glass is the only route), so the script falls back to the freeze's own start time: `dispute_frozen_until - 30 days` (the freeze length, `SupportRules.FreezeLength`). The existing refusals (lower-case target, support_lead, only enabled lead) are kept.

## riverpod_lint in app-ci

`app-ci` runs `flutter analyze` at the workspace root with `plugins: riverpod_lint: ^3.2.0` in `analysis_options.yaml`. Whether the plugin loads cannot be seen from the workflow. In this cloud workspace it does not report anything: with the `ignore` removed from `app/lib/main.dart`, both `flutter analyze app/lib/main.dart` and a full `flutter analyze` finish with "No issues found", and a probe file with a public notifier field and a bare `runApp` is clean too. So a green analyze says nothing about the plugin. The new step `riverpod_lint plugin is active (probe)` copies `.github/probes/riverpod_lint_probe.dart.txt` (a `runApp` without `ProviderScope`, the rule that BUG-007 reported) into `app/lib/`, analyzes it, and fails when `riverpod_lint/missing_provider_scope` is absent. Run here the script fails with that message (negative control: plugin silent). It has not been seen to pass: that needs the CI runner, where the plugin is known to report (BUG-007). If CI turns red on this step, either the plugin is not loading there (the point of the step) or the rule does not fire on the probe and the probe needs another rule.

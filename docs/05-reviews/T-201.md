**Transit API, checked against OpenBao source** (`openbao/openbao` main: `sdk/helper/keysutil/policy.go`, `internal/builtin/logical/transit/path_{decrypt,encrypt,hmac,sign_verify,keys,import}.go`) and the static-seal docs page:
- **Legacy File envelopes through an imported `aes256-gcm96` key: the claim is true.** `DecryptRaw` strips `vault:v<n>:`, std-base64 decodes, uses `keyEntry.Key` as is for a non-derived key, then `SymmetricDecryptRaw` takes `nonce = ct[:12]` and `aead.Open(nonce, ct[12:], AdditionalData)`. Here `AssocDataFactory` std-base64 decodes `associated_data`. This matches `FileKms.Wrap` exactly: nonce(12) ‖ ct(32) ‖ tag(16), with AAD `"zaghlol-file-wrap-v1"‖0‖keyRef`. An imported key is version 1, so `vault:v1:` is right. `ImportPublicOrPrivate` stores AES/HMAC material raw, sets `KeySize = len(key)` for `hmac`, and returns `keyEntry.Key` from `HMACKey()` for `hmac` keys (a random companion key for other types). The design note's pin rule therefore holds.
- **Sign:** `prehashed`, `hash_algorithm` from the URL, `marshaling_algorithm=jws` gives `RawURLEncoding(r‖s)` padded to 32 bytes each, and `key_version` is honoured. **HMAC:** std-base64 `vault:v<ver>:`, and `key_version` up to the latest is accepted. **Import:** RSA-OAEP(SHA-256, empty label) of a 32-byte ephemeral key (512 bytes), then Tink KWP (RFC 5649). This is the same as `RSA.Encrypt(OaepSHA256)` + `Aes.EncryptKeyWrapPadded`.
- **Decrypt-failure classification is sound.** A bad tag becomes `errutil.UserError{"cipher: message authentication failed"}`, which reaches the client as `logical.ErrorResponse` → `400 {"errors":["cipher: message authentication failed"]}`, exactly what `HasOnlyError` matches. These are other 400s and stay "unavailable": missing key (`encryption key not found`), `version is too new`, `too old`, soft-deleted, and bad base64. A future OpenBao that rewords the error fails safe: rows are retried and never deleted.
- **Stub fidelity is good enough for its tests to mean something.** It has the same prefixes, encodings, AES-GCM layout and AAD, BYOK unwrap, error strings and status codes, and it enforces the committed policies parsed from `setup.sh policy …`. It does not model `min_decryption_version`, soft delete, CIDR binding or real token semantics. The `openbao-live` job covers the real server.

## Flaky `HostStartupTests.TheApiRefusesToStartWithoutAKeyRing` (I-9): root cause found
- **Not reproduced as-is.** 30 consecutive runs of `HostStartup|OpenBao` produced 0 failures.
- **Reproduced with a probe.** A scratch-copy probe started the same factory 150 times in a row under CPU load (3× `yes`). **3/150 failed.** In every failure the exception was **`ObjectDisposedException: Cannot access a disposed object. Object name: 'IServiceProvider'`** from `Microsoft.AspNetCore.Mvc.Testing.DeferredHostBuilder.DeferredHost.StartAsync` → `WebApplicationFactory.CreateClient()`. It was not a `KmsConfigurationException`, and no other failure mode appeared.
- **Mechanism.** It's a race in `WebApplicationFactory` with minimal hosting, not in T-201 code. `Program` runs `await app.RunAsync()` on the entry-point thread. When a hosted service (here the KMS check) throws during start, `RunAsync`'s `finally` disposes the host. The factory's `DeferredHost.StartAsync` then calls `_host.Services.GetRequiredService<IHostApplicationLifetime>()` to subscribe to `ApplicationStarted`. If the app thread has already failed and disposed the host, that call throws `ObjectDisposedException`, which masks the real startup exception. The faster the refusal, the more often the app thread wins. This test fails in the first hosted service and has no network wait, so it is the most exposed. Every "refuses to start" test that uses `WebApplicationFactory` can hit the same race, including `OpenBaoHostStartupTests.TheApiRefusesToStartWhenOpenBaoIsSealed` and the `FileKmsHostStartupTests` refusals.
- **Suggested fix (test side).** Use one helper for all start-refusal tests. It builds a fresh factory and retries at most 3 times **only** when the exception chain is that specific `ObjectDisposedException` from `DeferredHost`, then asserts the expected `KmsConfigurationException`. A deterministic alternative: assert the refusal by starting the API in a child process, as `GracefulShutdownTests` does, and check the exit code and constant message. Don't widen the assertion to accept `ObjectDisposedException`: that would hide a real regression.

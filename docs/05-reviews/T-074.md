### Busy-timeout experiment (builder's claim)
Setup: encrypted DB opened twice on the same file (UI engine, plus a second connection in both background-isolate and foreground variants), using the repo's own `EncryptedDb` and `openEncryptedExecutor`. Connection A holds a write transaction (4 s). Connection B, 300 ms later:
- `PRAGMA busy_timeout` reads 5000 on both connections, so the setup line (`applyBusyTimeout`) is applied.
- B `BEGIN IMMEDIATE` fails after about 70 ms with SQLITE_BUSY (code 5). Same through drift's `transaction()`. **Builder's claim confirmed.**
- B lone `INSERT` also failed at once (about 66 ms, code 5), even after re-issuing `PRAGMA busy_timeout = 5000` on B. **This refutes the builder's second half** that "a lone write statement waits". In my setup it does not wait either. The apply tests pass because the statements are microsecond-short and rarely collide.
- Conclusion: the 5 s busy handler is not effective for cross-connection writers in the test environment, although the PRAGMA is set. I did not find the root cause. Candidates: the SQLite/SQLCipher build used by the test harness, or WAL write-lock handling. Whether a real device behaves the same is unverified.
- Impact: any UI-engine vs background-engine write collision can surface as a `DbWriteException` instead of waiting. T-074 is not made unsafe by this, because a failed apply changes nothing and nothing is half-applied. The "not in a transaction" choice is therefore fine, but its comment (dao:140-150) states "a lone write statement waits", which my experiment does not support. Correct the comment when convenient.
- Required follow-up (owner T-016, with T-017 for a retry helper): an investigation task with a regression test that holds a write transaction on A and asserts that B's write waits and succeeds. I left no experiment files in the tree.

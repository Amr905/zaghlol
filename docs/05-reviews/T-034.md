## Cross-task: is the key divergence a T-034 problem?
Both. The *rule* is a spec gap that must be fixed once in docs, but T-034 owns the code and chose a rule that contradicts the existing text (§5 "between single letters") and the only concrete backend example, so finding 1 is a T-034 **major**, not merely a follow-up. The backend side is not wrong: `CatalogText` only enforces structural shape (lowercase, collapsed single spaces, folded Arabic forms, ASCII, 1-64) and explicitly delegates the transliteration to `tools/catalog_build`. The app key output is a valid backend alias (it is a fixed point of `Normalize`), so nothing breaks at publish time; the risk is silent lookup misses.

## Recommendation: single canonical `merchant_norm` rule
1. `foldKey` (digits, tatweel, harakat, alef/ya/ta-marbuta, lowercase).
2. Transliterate Arabic with the Egyptian table.
3. Replace every character outside `a-z0-9` with a space; collapse and trim.
4. Strip **one leading article only**: first token `el`/`al` when another token follows, or attached `el`/`al` per the heuristic (or the Arabic `ال`, which at step 2 becomes `al`; so strip the Arabic article before transliteration, as today).
5. Join adjacent **single-character** tokens without spaces (`b t e c h` -> `btech`), per the existing §5 wording. Other spaces stay single.
6. Cap at 64, then trim a trailing space.

Result: `ELEZABY`, `EL EZABY`, `El-Ezaby` -> `ezaby`; `KOSHARY EL TAHRIR` -> `koshary el tahrir` (the backend example stays valid unchanged); token boundaries survive for step-3 matching and FTS trigram.

Changes needed elsewhere:
- **T-034** (this task): implement 1-6 and update tests (finding 1).
- **docs/03-technical/parsing-engine.md §5**: replace the `merchant_norm` sentence with the numbered rule above, and state that the key output is `[a-z0-9]` words separated by single spaces.

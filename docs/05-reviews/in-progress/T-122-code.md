## Verification notes
- **Doc parser circularity: none.** The parser reads the doc and the assertions read the migrated DB, so the two sources are independent. The branch's doc edits (logins sentence, `date_trunc` 3-arg) don't change any column the diff compares. CHECK *text* isn't compared with the doc; the negative tests cover what each CHECK means.
- **Triggers are correct.** Both are BEFORE DELETE, so the FK `SET NULL` later finds nothing to change and the pair CHECKs hold. The account trigger clears only `account_id` and `account_linked_by`; `attach_reclaim_used_at` is untouched. The install trigger clears exactly `install_id`, `proof` and `bound_at`. Both are `SECURITY DEFINER`, owned by `migrator`, with `search_path = zaghlol, pg_temp`, every name schema-qualified and `EXECUTE` revoked from PUBLIC (`TriggerFunctions…` tests this). A delete racing a sign-in that sets `account_id` is serialized by the FK's KEY SHARE lock and fails with 23503 rather than breaking the CHECK. TRUNCATE (which skips triggers) is owner-only.
- **Grants.** No role has UPDATE on `audit_log`. `ops_rw` alone has INSERT and `worker_rw` alone has DELETE; `ModelTests` and the DB-level denials both check this. No role has DDL, TRUNCATE, REFERENCES or TRIGGER, because `TablePrivileges` can't even express them. `ops_ro` and `ops_rw` read `installs`, `accounts` and `idempotency_records` through column grants that leave out `token_hash`, `apple_refresh_token_enc` and `response_body_enc`. `ops_rw` UPDATE on `purchases` / `purchase_seats` is limited to the support columns and excludes `recent_rebinds`. Fixture inserts run as the production writer role, which shows the grants are enough. Identity sequences need no grants. RI actions run as the owner.
- **Bootstrap.** It is idempotent: `IF NOT EXISTS` and attribute re-assertion, and the fixture runs it twice. It sets no passwords. The test fixture uses random passwords. `dev-passwords.sql` is mounted only by compose, and `.dockerignore` plus the multi-stage Dockerfile keep it out of the image. `public` is revoked and DB `CREATE`/`TEMP` are revoked from PUBLIC. `NothingIsCreatedInThePublicSchema` and the schema-ACL test pass. Only `plpgsql` is installed, so there is no `pgcrypto`.
- **Migration.** `EnsureSchema` uses Npgsql's existence-guarded DO block, so `migrator` needs no DB `CREATE`. The hand-added SQL runs after all tables and indexes, inside the migration transaction, and the history table lives in `zaghlol`. `Down()` drops the view, triggers and functions before the tables. `MigrationRoundTripTests` goes down to zero and back up; `MigratingAgainIsANoOp` covers re-runs. The `--migrate` job logs only the exception type and SQLSTATE and has a 10 min cap. EF's migration lock serializes concurrent runs.
- **Readiness (apart from #1).** It caches both true and false for 2 s and serializes probes through a single `SemaphoreSlim`. One caller's cancellation can't poison the cached result. 503 is problem+json with `code` and `no-store`, matching the OpenAPI `UpstreamUnavailable` response.
- **Workflow (apart from #3/#5).** The `commit` job runs no repo code: git runs with `core.hooksPath=/dev/null` and `core.fsmonitor=false`. Destinations are vetted against `.git`, symlinks and resolution escapes. The token appears only in the push step, as a masked extra header. `${{ }}` values reach the shell only through `env:`. The migration name is validated twice. Bot commits carry no tag, so there is no loop.
- **Layering.** `IDatabaseReadiness` lives in Application, the implementation in Infrastructure, and Api / Workers only wire DI. EF value converters do no crypto; hash and ciphertext columns are plain `byte[]`. "KMS key references" here only means that no key table or key material exists in the DB. The `Kms:*` / `KeyedHash:*` configuration is T-123's.

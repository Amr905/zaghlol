## Code

### Acceptance criteria
- **14 system categories, AR/EN exactly as in the spec:** met. I checked every row of `catalog_curated.csv` against spec section 4 (names, colours, buckets, order). The test `the committed catalog › 14 system categories` pins them.
- **Seed loads in < 1 s on the reference device:** measured on the host only (42 ms real seed; 164 ms for 600 merchants and 3000 aliases). A device run is still owed (FU-078 9). I accept this as a follow-up.
- **Tampered seed rejected:** met. Tests cover a flipped byte, a valid-looking semantic edit, a foreign or missing signature, an empty key set, corrupt or truncated gzip, and a gzip bomb, each followed by `_expectEmptyCatalog`.
- **DoD:** no UI, no money and no SMS are touched. Category names are catalog data, not ARB strings, which is accepted per the copy deck.

### M-1 major: the app/backend merchant-id and version agreement the pipeline relies on is false
`tools/catalog_build/lib/src/builder.dart:11-13`, `tools/catalog_build/README.md:16,19`, and FU-078 (9) all say: "the backend allocates ids in the same order when the normalized CSV is imported into an empty draft, so app and backend agree". The backend does not do this:
- `CatalogAdminStore.ImportSeedAsync` (backend `Catalog/CatalogAdminStore.cs:186-225`) writes the 14 categories first, then each merchant followed by its aliases. Every write goes through `ApplyPutAsync`, which adds a `catalog_drafts` row.
- A merchant's id is `catalog_drafts.Seq` (`AllocateMerchantAsync`, `:262-282`), and `Seq` is a single `IDENTITY ALWAYS` column shared by all entities (`CatalogConfigurations.cs:82`). Identity values are also used up by rolled-back transactions.
- On an empty database the first merchant therefore gets id 15, not 1. Every later merchant's id is shifted by its predecessors' alias counts. App id `n` ≠ backend id `n` for every merchant.
- Versions collide too. The seed says `version: 1`, and the backend's first publish is also version 1. Per backend-api §4 (sync composition), an app holding seed v1 sends `catalogVersion: 1` and gets `catalog: null` (it "is current"), or a delta `(1, n]` applied over a different id space. A full snapshot is sent only for 0 or for more than 20 versions behind.

**Failure path (T-059):** a delta `MerchantOp{id: 15, canonical: "Carrefour"}` overwrites the app's merchant 15 (some other brand). The app's aliases that pointed at 15 now resolve to Carrefour, and the app's merchant 1 ("Carrefour") collides on canonical, or both survive as duplicates. The result is silent miscategorization, or a sync apply that fails and rolls back on every launch (FR-SYNC-03). Nothing currently enforces "append only" either: no test pins `canonical → id` across builds.

**Required now (docs only, small):**
1. Correct the claim in `builder.dart`, the README and FU-078 (9). The bundled seed's ids and version are local and provisional. They are **not** the backend's.
2. Log a follow-up or open question (owner T-059 + T-125, due before the first backend catalog publish) recording the contract decision. Recommended pattern: **the release seed is the backend's published snapshot**. Fetch `GET /v1/catalog/{v}/full` plus `full.json.sig` (KMS-signed, ids and version allocated by the backend) and bundle those bytes unchanged. The loader already accepts that format, as the backend vector test shows. `catalog_build` then produces the T-125 import CSV, plus the dev seed for local builds only. Until then, T-059 must send `catalogVersion: 0` (force `mode: "full"`, replace the whole catalog) when the local catalog came from a seed that is not a backend snapshot. `catalog_meta.signature_kid` = dev kid is enough to detect this.
3. Optional: add a backend test asserting what `ImportSeedAsync` allocates, so the next person does not reintroduce the assumption.

### Minor (follow-ups, non-blocking)
- **m-1:** the `catalogSeedProvider` has no consumer yet (FU-078 7). Until the startup gate watches it, the seed never loads in the running app. The owner is already recorded.
- **m-2:** `retry: (_, _) => null` plus a code-only failure means a transient failure, such as a busy database, leaves the catalog empty until the next cold start. This is acceptable because the next launch retries. Note it for the gate's UX.
- **m-3:** `'two loaders at once'` asserts `loaded >= 1`. It could assert exactly one `loaded` and one `alreadyPresent`, which tightens the race check. Trivial.
- **m-4:** `name_en` stays NULL and `prefix` aliases need longest-first matching. Both are already in FU-078 (8) for T-075.

### Deviations (focus 6)
- **Subcategories not seeded:** accepted. `CategoryOp` has no `parent`, so this is a contract gap, not an implementation miss (FU-078 3).
- **Icon keys** are Material Symbols names: accepted, pending UX confirmation (FU-078 4).
- **`giving` bucket for category 12:** accepted. It is in the `categories.bucket` CHECK list (`database-schema.md:197`). The spec's "Wants / Giving" is a label, not two buckets.
- **Transliterated Arabic merchant names:** data only, accepted for now. An Egyptian reader must review them before release (FU-078 5).
- **First-launch-only load:** accepted. It never overwrites a synced catalog (tested), but only once M-1 (2) holds. Otherwise "never overwrite" freezes the user on mismatched ids.
- **Alias rule (focus 4):** correct. Every alias goes through `merchantKey`, all 41 vectors are tested through the builder, keys shorter than 2 characters fail the build, and cross-merchant key collisions fail the build. `AL MARAI` gets both `marai` and `almarai`, while `ELITE`/`ALBUM` are never split (tested). The backend accepts the normalized CSV under its own field and `IsNormalized` rules (`BundledSeedCsvTests`). Row order is the gap covered in M-1.

## Security

Egress: none. The loader reads only bundled assets, and nothing in the diff logs anything or makes a network call. Errors are code-only (`CatalogSeedException`, `DbWriteException` without catalog text, tested). The new dependency has no telemetry.

### S-1 Medium (before merge, small): the publicly known dev key is trusted by every build, with no release guard
`packages/zaghlol_catalog/lib/src/trusted_keys.dart:14-19` and `app/lib/core/catalog/catalog_providers.dart:214-217`. `s0000d`'s private scalar is committed (`tools/catalog_build/dev/dev_signing_key.json`) in a **public** repository, so anyone can sign a catalog that every build accepts, release builds included. No flavor or kid allow-list separates dev from release. The only safeguard is the FU-078 (1) note, and the test `the bundled trusted set is exactly the dev key until release` pins the dev key **in**.

- **Bundled-seed path today:** low real impact. An attacker who can replace the asset can also replace the key, because both are in the APK/IPA.
- **Why it is Medium:** FU-078 (2) tells T-141 to reuse `SeedTrustedKey`/`verifySeedSignature` for the network catalog. If the same trusted set, or a copy of it, reaches the sync verifier in a release build, the backend-signature defence against a compromised CDN or snapshot store (`full.json` is served anonymously from the CDN, backend-api §4) is void. Anyone can then push arbitrary merchant names, categories and aliases to every user. That means wholesale miscategorization and attacker-chosen strings shown in the UI.
- **Kid clash:** the backend's local dev ring also uses the kid `s0000d` (`backend/tools/dev-keys.sh`, `KeyRingTests.cs:190,214`), with different, per-developer key material. One kid then names two keys, which guarantees confusing verification failures against a local backend and makes "which `s0000d`?" ambiguous in audits.

Committing a dev private key is acceptable **only** with all four of these properties: (a) the kid is unmistakably dev (year `0000` already is, per backend-api §1 `s<yyyy><a-z>`); (b) release builds refuse it, fail-closed; (c) the backend never signs with it (true: the Local KMS provider refuses non-Development environments, `KmsServiceCollectionExtensions.cs:47`); (d) the build tool cannot be pointed at a production key file. (b) and (d) are missing.

**Required change (small):**
1. Fail-closed in release. Add `bool allowDevKeys` to `verifySeedSignature` (default `false`), and reject any kid matching `^[se]0000[a-z]$` unless it is `true`. The app passes `allowDevKeys: !kReleaseMode` (`catalogSeedKeysProvider`/loader). A release build that still carries the dev-signed seed then loads no catalog. That is visible in release QA, and it is the safe failure (keywords and manual categorization still work). Add tests for both settings. Keep the package pure Dart: the flag comes from the app, not from `dart.vm.product`.
2. Make `catalog_build --key` refuse any kid not matching `^s0000[a-z]$`. Production signing happens in the backend KMS, not from an exported JWK (see M-1 (2)); this stops anyone exporting the prod Sync key to a file "to rebuild the seed".
3. Give the committed catalog dev key a kid distinct from the backend local ring (for example `s0000a`), or have `dev-keys.sh` import the committed key. Re-sign; this is one CLI run.
4. Change the pinned-set test's wording to "dev key present only while `allowDevKeys`", and add a test that a release-mode loader rejects the committed seed.

### S-2 Low (follow-up): kid syntax looser than the contract
`seed_signature.dart:117,123` accepts `s[a-z0-9]{0,15}`, while the contract is `s\d{4}[a-z]`. This has no exploit, because the kid must also match a trusted key exactly (`:128`), but tightening it to the contract regex keeps the verifier aligned with the backend vectors. Follow-up.

### S-3 Info: trusted-key coordinates are not range-checked against p
`SeedTrustedKey` (`seed_signature.dart:30-40`) checks the curve equation but not `x, y < p`. Keys are compile-time constants, so there is no attack path. Optional hardening.

### Signature verification (focus 2): correct
- **Encoding:** raw P1363 `r‖s`, exactly 64 bytes / 86 base64url characters, unpadded. DER, padded, `ES384`, reordered and extra-space headers are rejected (all backend `response-signature-v1.json` vectors are run).
- **Range checks:** pointycastle 4.0.0 `ECDSASigner.verifySignature` rejects `r` or `s` outside `[1, n-1]` and rejects a point at infinity.
- **High-S** is accepted, matching the backend contract ("high-S accepted"). Malleability is irrelevant here because signatures are never used as identifiers.
- **Curve-point check:** done on key construction (tested). P-256 has cofactor 1, so no subgroup check is needed.
- **Constant time:** not needed for verification with public inputs.
- **`e`-key rule:** enforced (`:123`), and tested through the `entitlement-kid-on-header` vector.
- **Signed bytes:** the signature covers the inflated JSON bytes (`signature-over-gzip-bytes` vector rejected), and a backend-signed snapshot verifies and decodes byte-identically.
- **Error handling:** every failure becomes one `SEED_BAD_SIGNATURE` code with no input echoed.

### Loader safety (focus 3): correct
Order of work:
1. Meta check, then read the assets. Compressed size is capped at 8 MiB.
2. Streaming inflate with a hard 8 MiB output cap, checked per chunk, so a bomb stops early (tested with an 8 MiB + 1 KiB zero bomb).
3. Verify the signature.
4. Strict decode: `utf8` without `allowMalformed`, unknown members rejected, regexes, duplicates, dangling references, order checks, 200k-op cap.
5. Write everything in one transaction, with `catalog_meta` written last and re-checked inside the transaction (concurrent loaders tested, FTS integrity-check passes).

A failure part-way through rolls back fully (tested with a forced `UNIQUE` failure on the 14th category). The loader never overwrites a catalog that has a version (tested). The `.sig` asset is read in full before the 256-character cap. It is a bundled asset, so this is Info only.

### Supply chain (focus 5): acceptable
`pointycastle 4.0.0` (Bouncy Castle's Dart port, verified publisher) is pinned in `pubspec.lock` with sha256 `92aa3841…`. CI uses `--enforce-lockfile` throughout. Its runtime dependencies (`collection`, `convert`) were already in the lock. It is pure Dart, with no native code, I/O or network. It is used only for verification in the app, and for signing in the build tool.

The constraint `^4.0.0` is fine with the lockfile. The deviation from architecture §7 (`cryptography` for ES256) is real: `cryptography` has no pure-Dart ECDSA. The architect should amend §7, and T-141 should reuse this verifier (FU-078 2). That is Info only. Performance is a single verification at startup, so the "slow pure Dart" concern in §7 does not apply.

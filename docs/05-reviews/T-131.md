### Points the Lead asked me to check
| Item | Result |
|------|--------|
| State mapping | Matches the §3.5 table. `active`/`canceled_active` (by `autoRenewStatus` 1/0, anything else unknown), `in_grace` (uses `gracePeriodExpiresDate`), `on_hold` → Expired, `expired`, status 5 or `revocationDate` → `refunded` (with `revocationReason`) / `revoked`, which keeps the stored expiry on update. Lifetime: active/NULL or refunded. An unknown status, a missing expiry or grace date, or an unknown `autoRenewStatus` gives `Unknown`, which means 502 and no write. The latest product must be on the allow-list, else 502. `StatusOf` maps `in_grace`/`canceled_active` to Active and `revoked` to Refunded. Tested row by row. |
| New-payment rule under concurrency | Correct. `PaymentSql` runs in the upsert transaction after the row is locked (`FOR UPDATE`, or a blocked `ON CONFLICT DO NOTHING` followed by a re-lock). Under READ COMMITTED the second writer re-checks `last_payment_at < @pd` after the first commits, so exactly one gets 1 row. It runs regardless of the monotonic guard and only for `RequireCaller` with a `PURCHASE`-reason Get Transaction Info copy. Covered by Postgres tests. |
| `StorePurchaseRef` refactor / Play behaviour | Unchanged apart from the type rename, the case check (`ArgumentException`), the new `EnvironmentSeen` metric and `IsNewPayment = Inserted && Predecessor != null` (finding 9). `UpdateSql` for Google gained only `keep_expires` (always false for Play). `AGoogleRowNeverChangesItsProductOnUpdate` guards it. |
| Call budget per attempt, with the T-134 reserve | `AppleBudgetHandler` sits inside retry and circuit, so it costs one permit per attempt (`EveryHttpAttemptRetriesIncludedIsChargedToTheBudget`). Budget denial is not transient, so it is never retried and never counts toward the circuit; it maps to 503. The 20 % `Rtdn` reserve and restore-first denial are tested. Lifetime costs 1 call, a subscription 2. Finding 2 is about atomicity. |
| Order lookup semantics | Format check, then sandbox → fail with no call; `status` 0/1/other → continue/fail/unavailable; every entry is verified (`Api`, bundle, Production), and any failure there → unavailable plus the alert; then a constant-time `originalTransactionId` match without revocation → pass. Also a cap of 50 entries. See nit 7. |
| Config validation | Bundle/products (exactly 3, plan↔type), all-or-none key with PEM probe, issuer UUID, 10-char key ID, file-provider key refused in Production, base URLs locked outside Dev/Testing, test root only in Dev/Testing, `AllowSandbox` required in Production, `Resilience`/per-install overrides only in Dev/Testing, root fingerprint checked at startup. I checked the embedded resource: `CN=Apple Root CA - G3`, SHA-256 `63:34:3A:…:91:79`, which matches the constant. |
| Migration grants | `PurchaseLastPaymentAt` adds a nullable `timestamptz` and gives `app_rw` UPDATE (last_payment_at) only, through a frozen `GrantMatrix` list merged into `Current`. `worker_rw`/`ops_ro` get nothing, and `Down` drops the column (and with it the grant). The Apple update statement needs `product_id`/`plan`, which `app_rw` already has. |

### Deviations from the design note
| Deviation | Ruling | Reason |
|-----------|--------|--------|
| API JWT signed directly with `ECDsa` (not `Microsoft.IdentityModel.JsonWebTokens`) | Accepted | About 20 lines with a fixed header/payload, P1363 output, and no new dependency. Claims and caching are tested (`TheTokenHasApplesClaimsAndVerifiesWithTheKey`, `OneTokenIsReusedUntilFiveMinutesBeforeItExpires`) |
| Binding check before the status call | Accepted | The binding rests on the Get Transaction Info copy, as specified. Rejecting before the second call saves budget and writes nothing |
| Restore uses the `Restore` lane, with no per-install limiter | Accepted | This is what §6 intends ("restore is denied first"). T-185 owns restore throttling |
| Notifications reuse `StoreLane.Rtdn` | Accepted (nit 8) | The enum doc says it covers both stores |
| `AllowSandbox` required in Production (no default) | Accepted | Fails closed while PO question 4 is open. deployment.md documents it |
| Upper-case `appAccountToken` matches as a UUID and is stored lower-case | Accepted | §3.4 says "parse as a UUID". 16-byte constant-time compare; `AnUpperCaseAppAccountTokenIsTheSameUuidAndIsStoredCanonical` |
| Legacy `*.itunes.apple.com` hosts refused outside Dev/Testing | Accepted | FU-077 I-1 is a strict lock, and the defaults are Apple's recommended hosts |
| Writer updates `product_id`/`plan` for App Store rows | Accepted, with T-134 impact (finding 1) | Required by §3.5 (an upgrade re-plans the row). It is a separate statement, so the Google path needs no new rights |

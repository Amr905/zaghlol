## Callback safety (traced in sqlite3 3.9.1 `lib/src/ffi/bindings.dart:1163-1192`)
- Registration uses `NativeCallable.isolateLocal(..., exceptionalReturn: 0)` with `keepIsolateAlive = false` and `closeIn(_functions)`. SQLite calls the callback synchronously, on the thread of the blocked `sqlite3_step`, which is inside the isolate that owns the connection. So the isolate-local requirement always holds.
- Lifetime: `sqlite3_close_v2` (bindings.dart:905) closes the native connection first and then `_functions.closeAll()`, so the callable cannot be called after close. A connection that is never closed is released by the native finalizer when its isolate shuts down, and the Dart `Finalizer` closes the callable. No other thread holds that connection, so the callback is never called after its isolate is gone. Exactly one callable is created per open (`applyBusyTimeout` runs once per `setup`), so nothing leaks per open.
- Re-entrancy: none. The callback does not touch the database, and one connection runs one step at a time on one thread.
- Fail-closed: a throw inside the callback returns 0, so the statement fails with BUSY. After a 0, SQLite sets `nBusy = -1`, so the step stops waiting.
- Blocking `dart:io` `sleep`: the built-in handler blocked the same thread for the same length of time, so behaviour is unchanged. Dart's `TimerUtils::Sleep` loops on EINTR with the remaining time. The app's default executor is the background isolate, so the UI isolate blocks only in foreground mode, which tests use.
- Budget: the stopwatch restarts when `count == 0`. SQLite resets `nBusy` at the start of each VDBE step, so the budget is at most 5 s per statement step (plus at most one sub-ms tail), the same semantics as the built-in handler. An open runs several statements, so in the worst case it can wait 5 s for each of them, which was also true before.

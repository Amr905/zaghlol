## Summary

The format is sound. Each file gets its own chunk key, `K_chunk = HKDF(K_bk, fileId)`, with a random 128-bit `fileId`. Nonces are derived as a random 8-byte prefix followed by a u32 counter, and they are never stored. A nonce can only repeat under the same key if two files get the same `fileId`, which has probability about 2^-64 even after 2^32 files. The AAD of every chunk is the exact header bytes as read from the file, the chunk index and the `isLast` flag. This blocks truncation at a boundary or mid-chunk, dropping, reordering, duplicating, appending, splicing chunks across files and editing the header. The tests show each of these, and the negative proofs in the task file show the tests are wired correctly. The key wrap AAD binds the canonical KDF map and `kbkId`. After unwrapping, `kbkId` is compared in constant time, which also gives key commitment for the wrap, since plain GCM does not commit to its key. The header parser is a strict, canonical-only CBOR subset. The header is capped at 4096 bytes before it is read, no allocation depends on a length taken from the input, and KDF bounds are checked twice before Argon2id runs. A wrong passphrase stops at the unwrap step with zero chunks read. Plaintext stays untrusted until `done`, and both the code and the T-149 contract say so.

Key handling is also correct. The native changes give `backupKey` its own blob, AAD and Keystore alias on Android, and its own Keychain account on iOS. A blob copied from one slot to the other reads as `unusable` (Kotlin test). Every query on the iOS backup instance passes `account` explicitly. Passphrase change rotates `K_bk`. Secret and slot writes happen under one lease and in a crash-safe order. A store that reports `unavailable` never causes a re-key. Exceptions carry codes only. The no-logging grep covers the module, the normalizer adapter and the native text code. The four new packages (`cryptography`, `cryptography_flutter`, `hashlib`, and `convertlib` pulled in transitively) are pinned exactly and hash-locked. They are Apache-2.0 / BSD-3, have no network or telemetry code, and add no new native crypto. The findings are about defence in depth: residual key bytes inside the library, how generous the KDF bounds are, and requirements the UI, T-149 and T-150 tasks must carry.

## Store-policy and platform notes

- No new permissions, manifest entries, exported components, App Group data or Info.plist keys.
- `TextNormalizationHostApi` is registered only on the UI engine (Android `MainActivity`, iOS `AppDelegate`). It is stateless and returns no data beyond its input.
- The iOS backup Keychain item test lives in `TextNormalizationTests.swift`. That placement is odd but harmless, and the app-ci gate requires it.

## Verdict

**APPROVED.** No finding is marked "before merge". L-1 to L-4 and I-1 to I-7 become follow-ups for the owners above. L-3 and L-4 must be written into the acceptance criteria of the backup settings and restore UI tasks before those tasks start, and I-3, I-4 and I-7 into T-149 and T-150.

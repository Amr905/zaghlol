## Summary

The spike shows what it set out to show. On the host, the Android emulator (API 35 and minSdk 26) and the iOS simulator, the database is SQLCipher-4 AES-256 and is unreadable without the key. The key is a 256-bit CSPRNG value. It is never printed, never written to prefs, and never committed. The only place it is written is a 0600 file in a 0700 dir under the ephemeral `$RUNNER_TEMP`, and that file is not uploaded. The two negative proofs fail on every leg that ran, with the expected assertions. Each shipped native binary is hash-pinned through the locked `package:sqlite3`. The Linux host binary is also SLSA-attestation-verified. The CI workflow has a read-only token, actions pinned by SHA (all five pins checked against upstream tags), no secrets and no `persist-credentials`. No manifest, backup-rule, Gradle, Podfile or Xcode file is touched, so the T-165 guards stay intact. The findings below are defence-in-depth gaps in supply-chain verification and inputs for T-015.

## Findings

| L-1 | Low | `.github/workflows/db-platform.yml` L110–129 (attestation step) | Only the **Linux x64 host** binary is attestation-verified, because the host job downloads only that one. The binaries that actually ship (`libsqlite3mc.{arm,arm64,x64}.android.so`, `libsqlite3mc.arm64.ios.dylib`) are protected only by the hash inside `package:sqlite3`. That is strong integrity, but it means "whatever the package author's hash says". If the pub package or the maintainer's release pipeline were compromised, a matching hash and binary could be published without a valid build-provenance attestation, and CI would not notice for the shipped ABIs. | In the host job, also download the shipped assets for the locked release tag (filenames from `asset_hashes.dart`), check each against the hook's hash, and `gh attestation verify` each one. Alternatively, extract the `.so` files from the release APK in app-ci and verify them. | T-015 (or a CI follow-up before the first RC, T-171 checklist) |
| L-2 | Low | db-platform.yml L122 | `gh attestation verify … --repo simolus3/sqlite3.dart` accepts an attestation from **any** workflow or ref in that repo. The signer workflow and source ref are printed to the summary but not enforced. An attestation minted by a different workflow (for example a test workflow on a branch) would pass. | Add `--signer-workflow simolus3/sqlite3.dart/.github/workflows/<release workflow>` and `--source-ref refs/tags/sqlite3-<locked version>` (derived from `pubspec.lock`), plus `--deny-self-hosted-runners`. | same as L-1 |

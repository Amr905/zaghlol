## Safety checks

- Seat vacating and purchases: delete goes through the existing trigger and FK (`install_id` set NULL), and `device_key_hash` stays. The test asserts the seat holder is NULL, the device key is kept and the purchase survives. Raw SQL avoids the EF SetNull/CHECK problem (FU-015).
- audit_log: `worker_rw` RLS still guards it. `AClockAheadOfTheDatabase...` shows a clock 5 years ahead deletes nothing. A DELETE blocked by RLS silently skips, so no exception.
- SQL injection: only `@now` and `@batch` are parameters. The interpolated parts (table names, conditions, the four action literals) are compile-time constants from a fixed dictionary. The rule name is looked up, never concatenated. The CA2100 suppression is justified.
- ctid batching: the outer DELETE/UPDATE is `ctid IN (subselect LIMIT n)`. If a row is updated concurrently (for example a sync bumping `last_seen_at`), its old ctid is dead, so it is skipped. Under READ COMMITTED the re-check follows the update chain, and the new tuple has a different ctid, so it fails the qual. A skipped row is the safe result. Two purgers racing only lower the count, and a short batch ends the rule for that run. Correct.
- Install CTE: the data-modifying `idem` CTE runs even though the final SELECT does not read it. The count is of `gone` only. Correct.
- Logs: only `Operation` (a fixed rule name) and `Count`. The run-level failure logs the exception type name only. Metric tag `rule` takes only `RetentionRules.All` values, and the series are pre-seeded at 0.

## Deviations judged

- Accounts not purged: accepted. Schema §4 says there is no tombstone and T-135 hard-deletes.
- 1000-batch cap per run: accepted. The next run continues, so it only bounds the run time.
- "IP truncation" met by never logging IPs: accepted for this service. Request-log truncation belongs to the logging pipeline (T-138) per §4.
- Idempotency rows deleted with the install: accepted. They have no FK, and §4 says "deleted at once with its install".

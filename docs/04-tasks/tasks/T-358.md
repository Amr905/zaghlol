## Description
After categorisation ends in "needs classification", run eligibility (T-355) and queue eligible merchants (cap 100 distinct, oldest dropped; 60-day expiry). Sender: at app open and at most once per 10 min while open; back-off ≤ 1/h after failure; gate on flag, `cat.llm_consent`, quota snapshot (0 remaining before `resetsAt` → nothing sent; after reset sent automatically) and online; ≤ `cat.batch_max` per request, ordered by most transactions then most recent. Results: `ok` → `ai_merchant_suggestions` unconfirmed (+ recategorizer); `unknown`/`low_confidence`/`rejected` → `no_answer` (never re-sent); `quota` → stays queued. 409 clears consent; 503 pauses until next sync. Switching off empties the queue.

## Acceptance criteria
1. Fake-client tests: airplane mode → queued, back online → sent once; 101st merchant drops the oldest; 5 queued with 2 remaining → server answers 2 ok + 3 `quota`, the 3 stay queued; reset date passes → sent.
2. Scheduling: no more than one send per 10 min while open; back-off after failure.
3. **Negative proof 1:** captured request bodies over the synthetic fixture set contain only the closed fields and no amount, last-4, institution, date, SMS text or ineligible name.
4. **Negative proof 2:** flag off, no consent, quota 0 or switched off → zero requests.
5. Merchant names never logged (log capture).

## Design note (builder)
- `LlmCatSender` (`application/llm_cat_sender.dart`) only sends what `LlmCatQueueFiller.pickForSend` returns, through `LlmGatewayClient.categorise` (the only place the body is built). It reads no transaction field. The gateway client gained an optional `requestId` so a retry of the same batch inside the server's 2-minute window (110 s here) reuses the id and order.
- Gate layers: filler (flag, consent, pause, quota), client (same, plus proof only after the gate), sender (terms known; null terms = nothing sent, FU-425: no provider id is wired, so nothing is sent yet).
- Scheduling is in memory: one send per 10 min while open; failure back-off 1 h (server retry delay 1 min..1 h if given), also written to the queue rows' `next_attempt_at`; offline sends nothing and costs no interval. `run(now, lang)` is called at app foreground and after ingest/sync; it is NOT wired into `SyncLifecycle` (presentation, owned by T-359's lane): one line `ref.read(llmCatSenderProvider.future)` then `run`. No background permission.
- Replies are untrusted: only sent merchants, once each; `ok` needs a live system category (`sys:<code>`), confidence and a known source, else `no_answer`; `quota`/missing stay queued; a malformed body is a client failure (back-off). Applying goes only through `AiSuggestionApplier`. The local allowance is never counted by the sender (the client stores the backend's snapshot).
- `switchedOff()` empties the queue (the Settings switch is wired by T-359/T-362). `llmCatFeedback` not touched.

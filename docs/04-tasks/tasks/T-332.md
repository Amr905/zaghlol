## Description
- `ILlmProvider`, `LlmCall`, `LlmResult`, `LlmUsage`, `LlmOutcome`; `Sensitive<T>` whose `ToString`, JSON serialisation and logging destructuring all yield a fixed redaction.
- `LlmProviderRegistry` resolves the active provider id (from configuration now; T-334 switches it to remote config `llm.provider`); `ILlmApiKeyProvider` interface with a test implementation (real sources in T-333).
- `OpenAiResponsesProvider`: `POST /v1/responses`, `store:false`, `text.format` json_schema strict, `reasoning.effort:none`, `max_output_tokens`, static prompt first and user text last; no `user`/`metadata`/identifier fields; usage mapped incl. cached tokens.
- `FakeLlmProvider` replaying recorded fixtures; registered only in Development/Testing (startup guard elsewhere).
- Resilience: attempt 8 s, total 9 s, one retry only on connect failure before send, per-provider circuit breaker (≥ 50 % over 30 s with ≥ 10 calls, or 5 in a row → open 30 s, one probe); open → `Upstream` outcome. Provider HTTP spans record host and status only.

## Acceptance criteria
1. WireMock test asserts the OpenAI request body: `store:false`, strict schema, `reasoning.effort:none`, `max_output_tokens` from the call, no install id, account, IP, attestation or app version anywhere in body, headers or URL.
2. Outcome mapping tested: 200 valid JSON → `Ok`; refusal → `Refused`; malformed JSON → `Invalid`; timeout → `Timeout`; 5xx/open circuit → `Upstream`.
3. Circuit breaker opens and half-opens per the thresholds (time-controlled test).
4. `Sensitive<T>` never reveals its value through `ToString`, `System.Text.Json`, the structured logger or exception messages (tests).
5. Fake provider refuses to register outside Development/Testing (startup test).
6. Model ids, endpoints and prices come only from `Llm:Providers:<id>:*` configuration (decimals); no constants.

## Design note (builder, 2026-11-26)
- **Shapes.** `Zaghlol.Application/Llm`: `ILlmProvider`, `LlmCall`, `LlmResult`, `LlmUsage`, `LlmOutcome`, `LlmFeature`, `ILlmApiKeyProvider` (T-333 supplies real sources; a test implementation lives in the tests), `ILlmPromptCatalog` (system prompt text by `PromptId`; the real prompt files are T-339's). `Zaghlol.Infrastructure/Llm`: `LlmProviderOptions` (reads `Llm:Providers:<id>:*`, prices `decimal`), `OpenAiResponsesProvider`, `FakeLlmProvider`, `LlmProviderRegistry`, `LlmCallGuard` (timeouts, one connect-failure retry, circuit breaker), `AddZaghlolLlm` + startup check. Nothing is wired into the API host yet (T-333/T-339 call `AddZaghlolLlm`), so no shared file is touched.
- **`Sensitive<T>`.** `Zaghlol.Domain.Sensitive<T>` already exists (`ToString` = `***`, no public member, Serilog `{@}` shows nothing) and its JSON converter *reveals* on write because `InstallResponse` relies on it. I reuse it and do not change it. `LlmCall`/`LlmResult` put a redacting converter on their sensitive members, so serialising either record writes `"***"`. A bare `Sensitive<T>` serialised on its own still reveals (existing behaviour, documented; nothing in the gateway serialises one).
- **Registry.** `ILlmProviderRegistry.Active` resolves the id from `IActiveLlmProviderId` (config `Llm:ActiveProvider` now; T-334 replaces the implementation with remote config `llm.provider`); an unknown id fails closed.
- **Resilience.** Polly's breaker has no "5 in a row" rule, so the guard is a small own implementation on `TimeProvider` (time-controlled tests): ratio >= 50 % over 30 s with >= 10 calls, or 5 consecutive failures, open 30 s, then one probe. Attempt 8 s, total 9 s, one retry only for a connect failure (nothing was sent). Failures that count: timeout, 5xx/429, transport errors; `Invalid` and `Refused` are model answers and do not. Open circuit returns `Upstream` without a call. The caller's cancellation is rethrown and not counted.
- **OpenAI request.** `input` = [system prompt, user text last], `store:false`, `text.format` json_schema strict, `reasoning.effort:"none"`, `max_output_tokens`; no `user`, `metadata`, `prompt_cache_key` or any identifier. Response (checked against OpenAI's structured-outputs guide): `status:"incomplete"` -> `Invalid`; a `refusal` content part -> `Refused`; an `output_text` part must parse as a JSON object, else `Invalid`; usage from `usage.input_tokens`, `usage.input_tokens_details.cached_tokens`, `usage.output_tokens`. Any non-200 -> `Upstream`. Bodies and URLs are never put in an exception or log.

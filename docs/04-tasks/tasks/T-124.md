## Description
Anonymous installs with the accepted-fields boundary enforced, safe registration retries and install-scoped idempotency.

## Technical details
- `POST /v1/installs`, `DELETE /v1/installs/me` (202, tombstone, tokens stop at once); token SHA-256 storage; bearer auth handler (`401 INSTALL_TOKEN_INVALID`); `rotateInstallToken` support.
- **Registration retry (R3-6, §4.1):** no response holding an `installToken` is ever stored. Keep `registration_key_hash = SHA-256(Idempotency-Key)` and `registration_body_sha256`. A replay with the same key and body bytes within 24 h and before the install's first authenticated call gets `201` with a **freshly generated** token (hash replaced). The first authenticated call clears both columns. Otherwise `409 INSTALL_EXISTS`, or `409 IDEMPOTENCY_KEY_REUSED` for the same key with a different body.
- **Idempotency store (R2-8, R3-6)** for `verifyPurchase` and `signIn`: keyed by (installId from the token, operationId, key) plus SHA-256 of the body bytes; replay only when all four match and `expires_at > now()`; different body → `409 IDEMPOTENCY_KEY_REUSED`; a different install's same key is a new request; only final results stored (2xx, 409, 422), never 429/5xx; bodies KMS-envelope-encrypted; `DELETE /v1/installs/me` deletes that install's rows. (`DELETE /v1/accounts/me` purging by `account_id` is T-135.)
- Rate limiting per token and per /24 (token bucket, `429` + `Retry-After`). The restore buckets are T-185.
- Strict DTOs: unknown field → `400 UNKNOWN_FIELD` on every Zaghlol-defined body; the three third-party bodies are open (T-133/T-134/T-135). Global UTC-`Z` JSON converter and InstallId UUID v4 pattern (FU-013). Problem codes per §6.
- Live response-vs-spec test per endpoint, including `400 UNKNOWN_FIELD` (FU-011).

## Design note
### Design note (solution-architect, 2026-11-09)

**Scope and constraint.** Code goes in `Zaghlol.Api` (endpoints, auth handler, filters), `Zaghlol.Infrastructure` (stores) and one migration. No new NuGet package and no new crypto: SHA-256 and `RandomNumberGenerator` from the BCL, plus the existing `IKeyedHasher`, `IEnvelopeCipher` and `ISigner` ports. CLAUDE.md §2.1: the only data accepted is `installId`, `platform`, `appVersion`, the token, and the headers in backend-api §1.

**Endpoints.** `POST /v1/installs` (anonymous, 201) and `DELETE /v1/installs/me` (install auth, 202, empty body). Both use `StrictJson` (below). The 201 carries `{installToken: Sensitive<string>, serverTime}` and is signed by the existing response filter. Support code shared by every later endpoint: `IdempotencyFilter(operationId)` (used by T-130/T-135; T-124 tests it on a test-only route in the `Testing` environment) and `IInstallTokenRotator` (new token and hash in one UPDATE; `rotateInstallToken` is emitted by T-128+; no grace window, so a lost rotation response ends in `401 INSTALL_TOKEN_INVALID` and silent re-register per §6).

**Install credential.** Token = 32 bytes from `RandomNumberGenerator`, base64url (43 chars). Stored as `installs.token_hash = SHA-256(token)` and nothing else; a 256-bit random secret needs no pepper or slow KDF, and a deterministic hash lets auth be one indexed lookup with no KMS call per request (`InstallHashPepper` stays for log use only). **Migration:** add a unique index on `installs.token_hash` (none exists in `InstallConfigurations`; backend-schema must say so). Verification: reject anything that is not exactly 43 base64url chars with no DB hit; look up by hash where `deleted_at IS NULL`. Hash equality happens inside the index, and the registration body compare uses `CryptographicOperations.FixedTimeEquals`. The raw token appears only in the 201 body: never stored, logged, traced or in a metric tag (`Sensitive<T>`).

**Registration (`POST /v1/installs`), R3-6.** Requires `Idempotency-Key` (26-char Crockford ULID, else `400 VALIDATION_FAILED`). One transaction, no response stored:
1. `INSERT ... ON CONFLICT (id) DO NOTHING` with `token_hash`, `registration_key_hash = SHA-256(key)`, `registration_body_sha256 = SHA-256(body bytes)`, platform, appVersion. 1 row means `201`.
2. Else one atomic `UPDATE installs SET token_hash=@new, ... WHERE id=@id AND deleted_at IS NULL AND registration_key_hash=@k AND registration_body_sha256=@b AND created_at > @now-24h`. 1 row means `201` with the fresh token (the old hash is gone). Being a single statement, it races safely with the auth handler's clearing UPDATE: exactly one wins.
3. Else read the row: same `registration_key_hash`, different body, still in window means `409 IDEMPOTENCY_KEY_REUSED`; anything else (including a tombstoned install) means `409 INSTALL_EXISTS`. Neither response carries a token.
`@now` always comes from the injected `TimeProvider`, never the DB clock, so tests can freeze it.

**Auth handler** (`InstallTokenAuthHandler`, scheme `InstallToken`, applied to the `/v1` install group; account token is T-135). Steps: (1) `Authorization: Bearer` missing or malformed gives `401 INSTALL_TOKEN_INVALID` with `WWW-Authenticate: Bearer`; (2) hash lookup; none or tombstoned also gives 401 with the same body (no oracle); (3) the optional `Zaghlol-Install` header must parse with `InstallId.TryParse` (UUID v4, lowercase 8-4-4-4-12), else `400 VALIDATION_FAILED`; if valid but different from the token's install, 401; (4) if the row has `registration_key_hash` set, `UPDATE ... SET both = NULL` (the "first authenticated call", R3-6); (5) set the principal `installId` and `RequestLogItems.InstallHash` from `ILogPseudonymizer.InstallHashAsync(installId from the DB row)`. **F6:** the pseudonymizer only ever receives an `InstallId` struct, built by the same v4 pattern the DTO converter uses; free-form text cannot reach it (also for the unauthenticated register route, after body validation). **F7:** a pseudonymizer or KMS failure in step 5 is caught (not `OperationCanceledException`), counted on the diag metric, `installHash` is set to the constant `unavailable`, and the request still succeeds. A startup check (`IHostedService`) calls `InstallHashAsync` for a fixed GUID and fails the start outside Development/Testing; `Testing` hosts without KMS use the in-memory key.

**Delete (`DELETE /v1/installs/me`).** One transaction: `deleted_at = now`, clear `registration_*`, `DELETE FROM idempotency_records WHERE install_id = @id` (F13), then 202. The token is dead at once because auth filters on `deleted_at`; a second DELETE gets 401. Account link rows are left to T-135 (hard purge at 30 days, existing job).

**Rate limits.** Built-in `Microsoft.AspNetCore.RateLimiting` token buckets, which exist in the framework and add no package. State is **per process memory**, not Postgres: a DB write on every request would give the abuse path a DB-load lever, and the limits only need to be approximate. With N API instances the effective limit is up to N times higher; limits are sized for that (config `RateLimits:*`, defaults below). Two partitions: (a) per **/24** (IPv4) or /56 (IPv6) from the forwarded client address, run before auth, so failed-token floods count; (b) per **token hash** after auth. Defaults: /24 600 requests/min; `POST /v1/installs` additionally 60/h per /24 (mobile carriers put many users behind one /24, so this must stay generous); per token burst 30, refill 10/min. A rejection is `429 RATE_LIMITED`, `Retry-After` (whole seconds, at least 1) and `retryAfterSeconds`; it is never stored. The client address is taken only through `ForwardedHeaders` configured with the known proxy/network list; never read `X-Forwarded-For` raw. Restore buckets are T-185. Metric tag: the bucket name constant only.

**Idempotency store** (`IIdempotencyStore`, Infrastructure; table `idempotency_records` already exists). `IdempotencyFilter` runs after auth, reads the body bytes once (shared with `StrictJson`) and computes `SHA-256(body)`. Lookup: `WHERE install_id=@i AND operation_id=@op AND idempotency_key=@k AND expires_at > @now` (clock from `TimeProvider`). Hit with equal hash (fixed-time) means replay; hit with a different hash means `409 IDEMPOTENCY_KEY_REUSED`; miss means run the handler. Store only 2xx, 409 and 422 final results, after the handler: `status` plus `response_body_enc = IEnvelopeCipher.EncryptAsync(body, context: "idem/v1/"+installId+"/"+op)` (context binds the row to its install and operation). The stored bytes are the **unsigned** body (including the original `timeNonce`); the signing filter signs the replay with the current key (T-123 G2). Two concurrent requests with one key: `pg_try_advisory_xact_lock(hash(install,op,key))` around lookup, handler and insert; the loser gets `429 RATE_LIMITED` with `Retry-After: 1` (no new error code) and nothing is stored. Insert uses `ON CONFLICT DO NOTHING`. The purger (existing worker) deletes expired rows; correctness never depends on it.

**Strict DTO policy.** `StrictJson.ReadAsync<T>` reads at most 64 KB (`413 PAYLOAD_TOO_LARGE` beyond), requires `application/json` (`415`), and deserializes with a source-generated context: `UnmappedMemberHandling = Disallow`, `PropertyNameCaseInsensitive = false`, `AllowDuplicateProperties = false`, `required` members, enums as strings only, numbers not read from strings. On `JsonException`, a probe walks the parsed JSON against `JsonTypeInfo.Properties` (works with source generation, covers nested objects and arrays): an unmapped name gives `400 UNKNOWN_FIELD`, anything else `400 VALIDATION_FAILED`. Messages never echo the field name or value. Global converters: `UtcZDateTimeOffset` (write `yyyy-MM-ddTHH:mm:ssZ`, throw on non-zero offset; read only `Z`) and `InstallId` (UUID v4 pattern, FU-013). Patterns for `appVersion` and `platform` come from the OpenAPI file, not duplicated by hand. The open third-party bodies (T-133/134/135) use a separate `OpenJson` path, so the policy cannot leak there. **Sensitive members:** `installToken`, `rotateInstallToken` (added to the T-138 list), and the existing names (`purchaseToken`, `idToken`, `nonce`, `attestation`, `assertion`, `code`, `refreshToken`, `orderId`, `seatKeys`, `signedTransaction(s)`) must be `Sensitive<T>`; a reflection test over the Api assembly enforces it (T-138 code #3, test m7).

**DB role per group (FU-021).** The generic `IZaghlolDbContextFactory.CreateDbContext(DatabaseRole)` becomes `internal` to Infrastructure. Api code sees `IAppDbContextFactory` (role `App` fixed) for `/v1`; T-136 adds the admin one. Test: reflection over every type in `Zaghlol.Api.Endpoints.V1` and the install/idempotency stores shows no dependency on `DatabaseRole` or the generic factory; a Testcontainers test checks `SELECT current_user` is the app role and that Admin-only grants fail from it.

**Smaller routed items.** (1) `EnvelopeCipher.cs` (about lines 247, 352): map `CryptographicException` from `GenerateDataKeyAsync` (encrypt) and the decrypt data-key call to `KmsUnavailableException` with the constant message, as `Signer` and `KeyedHasher` do (T-123 code #2). (2) Ban `EnableSensitiveDataLogging`: an architecture test fails on that text in `backend/src/**/*.cs` and checks the built `DbContextOptions` extension reports it disabled (T-138 m7). (3) Test that `AddZaghlolLogPseudonymizer` uses the KMS key when present and throws outside Development/Testing without it (T-138 m6). (4) Review checklist: metric tag values and `SafeException` messages are constants (T-138 code #5). (5) Re-run the `Idempotency-Key` placement checks from T-138 m2 against the real endpoints.

**Error codes** (all `application/problem+json`, no request data echoed): 400 `VALIDATION_FAILED`, `UNKNOWN_FIELD`; 401 `INSTALL_TOKEN_INVALID`; 409 `INSTALL_EXISTS`, `IDEMPOTENCY_KEY_REUSED`; 413 `PAYLOAD_TOO_LARGE`; 415 `UNSUPPORTED_MEDIA_TYPE`; 429 `RATE_LIMITED`; 503 `UPSTREAM_UNAVAILABLE` (KMS or DB down; never `500` with KMS text); 500 `INTERNAL`.

**Test plan** (Testcontainers Postgres, frozen `TimeProvider`; negative cases marked N). Registration: new ID gives 201 and only `SHA-256(token)` is in the row; N missing or non-ULID key; N non-v4 or uppercase ID, bad platform or version; same key and body gives 201 with a different token, old token 401, new token 200; N after one authenticated call, same replay gives `INSTALL_EXISTS`; N only the install ID plus body with another key gives 409 and no token in the body; N same key, different body gives `IDEMPOTENCY_KEY_REUSED`; N replay at 24 h + 1 s gives `INSTALL_EXISTS`; race: replay vs first authenticated call, exactly one outcome. Auth: N missing, malformed (42/44 chars, wrong alphabet), unknown and tombstoned token give identical 401 bodies; N `Zaghlol-Install` mismatch 401, malformed 400; N pseudonymizer throws, request still 200 with `installHash=unavailable`; startup check fails without KMS outside Development. Delete: 202, token dead, `idempotency_records` rows gone, second DELETE 401. Idempotency: replay served; N other install, same key, is fresh and never sees the first body; N different body 409; N record past `expires_at` (purger not run) not served; N 429/5xx not stored and the retry re-runs; 409/422 stored; replay re-signed with the current kid; stored column is ciphertext and the wrong context fails to decrypt; concurrent same-key requests run the handler once. Rate limit: N 601st request in a minute gives 429 with `Retry-After`; /24 grouping (.1 and .200 share, .1.x vs .2.x do not); forged `X-Forwarded-For` from an untrusted peer is ignored; 429 has no stored record. DTOs: N unknown field at top level and nested gives `UNKNOWN_FIELD`; N duplicate key, wrong-case key, array-for-object, 65 KB body, wrong media type; offset timestamps are not accepted; reflection tests for `Sensitive<T>`, FU-021 and `EnableSensitiveDataLogging`; EnvelopeCipher KMS-crypto-exception mapping test; log capture test proving no token, key or install ID appears in logs, metrics or traces for 201/401/429 paths. FU-011: live response-vs-spec tests for both endpoints including `400 UNKNOWN_FIELD`.

**Rejected alternatives.** Storing the 201 body encrypted for replay (violates R3-6: a stored token). HMAC or Argon2 for token hashes (no benefit for 256-bit random input, adds a KMS call per request). Postgres-backed rate limits (DB write per request, gives attackers a lever). `JsonExtensionData` on every DTO (pollutes the OpenAPI-checked shape). Parsing `JsonException.Message` to detect unknown fields (brittle).

**Decisions for the PO / Lead.** (a) Rate-limit numbers and the /56 IPv6 prefix are proposals; the spec gives only the /24 rule. (b) In-memory buckets mean limits scale with instance count: accept, or pay for a shared store later (hosting ADR). (c) Concurrent same-key requests get `429 Retry-After: 1` instead of a new `IN_PROGRESS` code, so the closed error list stays unchanged. (d) The unique index on `token_hash` changes the T-122 model by a migration and needs a line in backend-schema.md.

## Acceptance criteria
- [ ] Unknown field → `400 UNKNOWN_FIELD`.
- [ ] Deleted install token stops working immediately, and its `idempotency_records` rows are gone (test).
- [ ] R3-6(a): replaying `POST /v1/installs` with the same key and body before any authenticated call returns 201 with a **different** token, and the first token no longer authenticates; after one authenticated call the same replay gets `409 INSTALL_EXISTS` (test).
- [ ] R3-6(a): knowing only the install ID (support code) and the body, with a different key, gets `409` and no token (test).
- [ ] R2-8: same install + op + key with a different body → `409 IDEMPOTENCY_KEY_REUSED`; the same key from another install is processed fresh and never sees the first install's body (test).
- [ ] R3-6(b): a record past `expires_at` that the purger has not yet removed is never served (test with a frozen clock).
- [ ] `429` and `5xx` results are not stored; a retry runs again (test).
- [ ] FU-011: live response-vs-spec test for `POST /v1/installs` and `DELETE /v1/installs/me`.
- [ ] DoD (CLAUDE.md §7): analyze clean, formatted, tests added, no hard-coded strings, RTL verified where UI, no `double` money, no raw SMS in logs.

## Description
Capture bank/wallet/online-bank app notifications.

## Technical details
NotificationListenerService filtering packages from config; read title/text/bigText; skip ongoing & group summaries; Guard; spool; enqueue worker. [doc change] 2026-11-11 (design note): packages = registry packages ∪ user `notification` senders, checked before extras are read; body = title + `\n` + (bigText or text); own intake thread.

## Design note
(solution-architect, Opus, 2026-11-11. C4: notification ingestion. Reviewers: challenge it. Carries FU-104 T-043 items (security L-1 with T-040, I-5). **[doc change]**s are made in this commit. Sister note: T-040, same branch. **Built after T-040** (it uses T-040's `CaptureRuntime`, `CaptureIntake`, `AndroidGuardChannel`, `recordMissed` and the SMS reserve; see T-040 §10).)

- From the T-038/T-039 notes (2026-11-11): same composition as T-040 (Guard kind → `AdmissionClass`, `recordRateLimited(notification, …)`; refused notifications count as `missedNotifications` and are not recoverable). ~~Run on the shared intake executor~~ **[doc change]** run on the listener's **own** intake thread (§3), not the listener's main thread.

**1. Placement and manifest.** Main source set (every flavour: in `*NoSms` it is the primary live channel). `capture/BankNotificationListener.kt` (thin glue), `capture/NotificationExtractor.kt` (pure), `capture/RecentNotifications.kt` (pure), `guard/GuardRuntime.kt` (+ `admitsNotificationPackage`), `capture/CaptureRuntime.kt` (+ notification dispatcher). `src/main/AndroidManifest.xml`:
```xml
<service android:name=".platform.capture.BankNotificationListener"
    android:exported="true" android:directBootAware="false"
    android:permission="android.permission.BIND_NOTIFICATION_LISTENER_SERVICE">
  <intent-filter><action android:name="android.service.notification.NotificationListenerService"/></intent-filter>
  <meta-data android:name="android.service.notification.default_filter_types" android:value="conversations|alerting|silent"/>
  <meta-data android:name="android.service.notification.disabled_filter_types" android:value="ongoing"/>
</service>
```
The two meta-data (API 31+) keep ongoing notifications from being delivered at all; verify the names and values against the `NotificationListenerService` reference while building; older APIs rely on the §2 flag check. No `android:label` (the system shows the app name; no new string). Requesting access is T-044. The placement check gains: every APK has this service with `BIND_NOTIFICATION_LISTENER_SERVICE`.

**2. `onNotificationPosted(sbn)` (main thread, no I/O, no extras read).** Return at once when: `sbn.packageName == context.packageName` (our own Android 8–11 capture notification); `notification.flags` has `FLAG_GROUP_SUMMARY` (its text aggregates children, which arrive on their own), `FLAG_ONGOING_EVENT` or `FLAG_FOREGROUND_SERVICE`. Otherwise submit `sbn` to the notification dispatcher. `onNotificationRemoved`, ranking updates: ignored. No `requestRebind` (access state and OEM kills are T-044's setup checker).

**3. Dispatcher.** One daemon thread `zaghlol-notif-intake` with a bounded queue of **64**; on overflow the new item is dropped and an `AtomicInteger` is incremented on the main thread; the intake thread moves it into `status.recordMissed("notification", wallMs)` before its next item (never from the main thread: that call may touch the Keystore). Separate from the SMS thread so a notification burst can't consume the SMS receiver's 5 s `goAsync` budget; the two meet only at the spool lock. No `goAsync` here: the bound service keeps the process alive while it runs; a kill mid-write leaves a whole entry or none.

**4. Package admission before any read (FR-ING-A-03: "Only notifications from apps in the institution registry are read").** On the intake thread: `snap = guard.current()`; `guard.admitsNotificationPackage(pkg)` = mode ≠ `INVALID` and `dartTrim(pkg)` ∈ base `packages` **or** (`notification`, key) ∈ user `userSenders` (PO Q2, provisional: include). A package that would only pass the Guard's generic sender-hint path (e.g. `com.x.bank` + amount) is **not** admitted: notifications never take the generic path, so every notification keep is `PRIORITY` [doc change platform-channels §2]. Not admitted → return; `sbn.notification.extras` is never touched for it (AC2 "not read into storage" is stronger: not read at all).

**5. Extraction (`NotificationExtractor`, seam `NotificationFields { title(): CharSequence?, text(), bigText(), textLines(): Array<CharSequence>? }`).** All reads inside one `try { } catch (Throwable)` (non-fatal): a `BadParcelableException`/`RuntimeException` from lazy extras unparcelling → skip silently. `title = EXTRA_TITLE`; `content = EXTRA_BIG_TEXT` if non-blank, else `EXTRA_TEXT`, else `EXTRA_TEXT_LINES` joined with `\n`. Length check on `CharSequence.length` **before** `toString()`: title > 256 or content > 4,000 UTF-16 units → skip (the Guard would say `too_long`). **Body [doc change platform-channels §2]:** `title + "\n" + content` when both are non-blank, else the non-blank one; both blank → skip without a Guard call. `toString()` drops spans; no other trimming (the Guard folds). `source = sbn.packageName`, channel `notification`, `simSlot = null`, `receivedAtMs = currentTimeMillis()` at the callback (same clock as SMS, for T-046's cross-channel window). Registry notification templates and fixtures (parsing-engine §fixtures, `package` + `body`) must use this exact shape.

**6. Repeats, updates, re-posts.** Apps re-post (`notify` with the same id: progress, re-alerts, reboot restore), and the DB's `body_hash` is the final dedupe. To save spool writes and worker runs, `RecentNotifications` keeps in **memory only** a map `SHA-256(pkg ‖ 0x00 ‖ body)` (first 16 bytes) → monotonic time, LRU **128**, TTL **15 min** (provisional constants): seen within TTL → skip; an **update** of the same `sbn.key` with a different body is a new message (spooled; T-046/T-089 merge pending → settled). The hash map is never persisted or printed; it resets with the process (then the DB dedupes). It never drops more than the DB would: the unique `body_hash` (source + body, BR-ING-02) already stores an identical body once. Recorded only after a `Written` result, so a refused or failed write is retried by the app's next re-post.

**7. Guard → spool.** `CaptureIntake.process(AndroidGuardChannel.NOTIFICATION, [msg], stamp)` from T-040: `Keep` → `store.write(record, PRIORITY)`; `Refused` (the store counts `missedNotifications`) → still enqueue + notify; `Drop(rate_limited)` → `recordRateLimited("notification", wallMs)` (counted missed); any other drop → nothing written. Notifications are exempt from the SMS reserve (T-040 §7, security L-1), so they keep the last 100 entries / ~0.8 MiB of the spool against an SMS flood.

**8. Not recovered (state it in the code KDoc and T-047's copy).** Refused, rate-limited, overflowed notifications and notifications posted while the listener is unbound (app update, force stop, OEM kill, access revoked, before first unlock) are lost; only the counts reach Dart (`missedNotifications`). No replay of `getActiveNotifications()` on reconnect (PO Q3).

**9. Never logging (I-5).** Same rules and CI grep as T-040 §9: no logging in `platform/capture`; `NotificationFields`, `CapturedMessage`, the dispatcher item and `RecentNotifications` have redacted `toString`; never interpolate `sbn`, `extras`, `Notification` or a `SpoolEntry` into a string (source scan); package names are treated as sensitive.

**10. Tests.** JVM (`src/test/.../capture`, PC runner):
- `NotificationExtractorTest`: title + bigText; text when no bigText; lines fallback; blank title; all blank → no Guard call; a counting `CharSequence` proves no `toString()` on an over-long field; throwing fields → skip, no output; spans → plain text.
- `NotificationAdmissionTest` (fake `NotificationFields` counting reads): unknown package → **zero** field reads; registry package; user `notification` sender; the same value as an `sms` user sender → not admitted; hint-only package (`com.example.bank` in `t1_base`) → not admitted; base `INVALID` → nothing read; own package, group summary, ongoing, foreground-service → nothing read (main-thread filter, tested through a `PostedNotification` seam over `sbn`).
- `RecentNotificationsTest`: same body twice → one write; after TTL (fake clock) → two; same key, new body → two; LRU eviction at 129; refused write not remembered.
- Intake: refused → `missedNotifications + 1`, enqueue once; `rate_limited` → `rateLimited + 1`, `missedNotifications + 1`; queue overflow of 65 → `missedNotifications ≥ 1`; written → enqueue + notify.
- Canary `ZG_CANARY_7731` in title and text, `ZG_CANARY_PKG` as a registry package through filter → extractor → intake → store with failing ciphers: no hit in stdout/stderr/exceptions/`toString`. Source scan as T-040.
- **Negative proofs** (patch, red, revert): extras read before the package check; group summary not skipped; generic-hint package admitted; own package admitted; dedupe off (two writes); dedupe recorded before the write result; missed not counted on refusal; body built as `text` only.
Instrumented (`src/androidTest/.../capture/NotificationListenerEmulatorTest.kt`, new `sms-spike-device.sh` phase, devSms debug + test APK):
1. Start the armed test in the background (as T-040 §11): it installs a runtime with `t1_base.json` from the test APK, spool `no_backup/spool-it-t043`, user part `userSenders: [{"value":"com.android.shell","ch":"notification"}]` through `hostFor(...).writeGuardConfig`, records the data-dir tree, sends `t043.ready=1`.
2. Script grants access after the process is up: `adb shell cmd notification allow_listener $PKG/app.zaghlol.platform.capture.BankNotificationListener` (verify per API level; fallback `settings put secure enabled_notification_listeners`).
3. Script posts from the shell package: `cmd notification post -S bigtext -t "<synthetic title>" t043a "<synthetic debit, EGP 150.00, card **4321>"`; the same again (repeat); the same tag with a new text (update); `-t "Bank" t043b "ZG_CANARY_7731 your OTP is 482913"` (OTP).
4. Test asserts within 30 s: exactly 2 entries (first + update; repeat deduped; OTP dropped); body == `title + "\n" + text`; source `com.android.shell`; channel `notification`.
5. Phase B (new armed run, user part **without** the shell package): post one more → no entry and the data-dir tree unchanged (AC2). App-uid logcat has no `ZG_CANARY`.
`cmd notification post` availability per API level must be checked when building; a level without it skips the post steps **by name** in the script's allow-list (as `bundledBaseLoads`), never silently. API 31+ also: an ongoing post (`cmd notification post` with an ongoing flag, if supported) is not delivered.

**Play policy.** Notification access is a user-granted special access, not a Play-declared permission like SMS; whether Play's User Data rules call for an in-app prominent disclosure before sending the user to the access screen is a T-044/T-176 check (For the Lead, below). The listener reads only admitted packages' text, on the device; nothing leaves the phone.

**For the Lead.** (a) Play prominent-disclosure check for notification access → T-044/T-176. (b) Registry notification templates (T-036 and later) must use the §5 body shape.

**Rejected.** One shared intake thread with SMS (a notification burst could time out the SMS receiver). Admitting Guard generic hints for packages (FR-ING-A-03 says registry apps; package names are trivially chosen by any app). Persisting the dedupe hashes (a body fingerprint on disk; the DB already dedupes). Replaying active notifications on reconnect (PO Q3; churn of expedited runs after each rebind). `EXTRA_TITLE_BIG`/`tickerText` (not used by the target apps; one shape keeps fixtures simple).

## Acceptance criteria
- [ ] Registered package notification → spool entry
- [ ] Other apps ignored and not read into storage (their extras are not read at all)
- [ ] Repeated identical notifications produce one spool entry; an update with new text produces a new one
- [ ] Refused, rate-limited and overflowed notifications are counted in `missedNotifications`
- [ ] DoD (CLAUDE.md §7): analyze clean, formatted, tests added, no hard-coded strings, RTL verified where UI, no `double` money, no raw SMS in logs.

- JVM tests with seams (PC runner + `kotlin-unit`, no Robolectric)

## Questions for the PO (provisional defaults behind one constant each)
- **Q1** See T-040 Q1 (80 % SMS share, 20 % kept for notifications).
- **Q2** FR-ING-A-03 says only notifications from apps in the institution registry are read. The user can also add their own senders (custom templates / "always capture"), and the Guard already supports such a sender for notifications. Should notifications from an app the **user** added be read too? Default: yes.
- **Q3** Notifications that arrive while the listener is not running (after an app update, force stop, a phone-maker battery kill, before the first unlock) are lost; the app only knows when it was refused or rate-limited. Accept, or should the app re-read the bank notifications still in the shade each time it reconnects (more background runs; duplicates are removed)? Default: accept.

## Lead decisions on the T-040/T-041/T-042/T-043/T-047 design notes (2026-11-11)

These settle the points where the two architects' notes differ; they take precedence over either note.

1. **Ownership of the composition point:** T-041 owns `CaptureRuntime.kt`, `AndroidCaptureDevice`, `MainActivity` wiring, the WorkManager line in `build.gradle.kts`, the WorkManager/spike lines of the placement script, and the Pigeon changes (`ingestion_api.dart`, `holdSpool`, `SpoolStatus.held`, `INVALID_ARGUMENT` — all accepted). 2. **Order:** T-041 and T-042 are built in parallel first. T-040 starts from main after T-041 merges; T-043 starts after T-040 merges (they share files). T-047 starts after T-041 merges.
3. **Spike removal:** the devSms spike receiver and `SpikeGuard` stay until **T-040** replaces them with the production receiver; T-041 replaces the spike's worker/engine/drain loop and `spike_metrics` channel. T-041's foreground "drained within 2 s" AC is proven on devSms until T-047 wires foreground draining for all builds.
4. **Accepted as written:** the worker in every flavour (WorkManager 2.12.0 in all builds, `DiagnosticsReceiver` removed, merged-manifest + no-`androidx.test` checks), held entries under `spool/held/` (FU-105), the 80 % SMS share of the spool, title + newline + content notification bodies (T-036 fixtures must follow), the T-047 capture-health model, `capture_senders` stays keyed by `sender` with the DAO refusing a channel conflict (FU-096 m-2).
5. **T-041 size:** not split; if the build runs long, the builder commits the spool/host follow-ups first and pushes often.
6. **Regex-only registry senders** missed by the first-run scan: T-036 exports concrete sender IDs where the registry knows them (follow-up for T-036).
7. **PO questions** in each note stay open; every default sits behind one constant and is marked provisional.

## Description
Implement `ILlmApiKeyProvider` for the three key sources: File KMS `<keydir>/llm_<id>.secret` (same file-mode checks), HostSecrets `ZAGHLOL_KEYS__llm_<id>` (same JSON wrapper with `secret`, same refusal of file sources), OpenBao KV `zaghlol/llm/<id>`. Vertex uses a service-account JSON as its secret. Keys are read once at start into a non-loggable holder; rotation is a new value + restart (runbook).

## Design note (builder, Opus, 2026-11-26)
- **Where:** `Zaghlol.Infrastructure/Llm/Keys/`. `LlmApiKeyStore` is the `ILlmApiKeyProvider` singleton; the hosted `LlmKeyStartup` (registered by `AddZaghlolLlm`, after the KMS checks) loads it once at start. A host that registers its own `ILlmApiKeyProvider` first (tests) keeps it; the configuration check still runs.
- **Source = `Kms:Provider`** (no new setting, no new storage): `File` → `<Kms:File:KeyDirectory>/llm_<id>.secret` read with `FileKms.ReadChecked` (same owner/mode/symlink/size checks; the T-200 directory checks already ran in `FileKms.Load`). `HostSecrets` → `ZAGHLOL_KEYS__llm_<id>` (a `-` in the id may be written `_`), the T-205 `host-key-v1` JSON wrapper with a `secret` member (`HostSecretsKms.ReadValue`, new `KeyKind.Secret`), same refusal of keys in configuration files and the same `Kms:AcceptSharedHostCustody` gate (re-checked here, not only by the KMS). `OpenBao` → KV v2 mount `zaghlol`, `GET /v1/zaghlol/data/llm/<id>`, `data.data` = exactly `{"secret": "<text>"}`, through the KMS's own AppRole client (`OpenBaoKms.ReadKvSecretAsync`, `KmsCall` policy). `Local` (Development/Testing only) → `<Kms:Local:KeyDirectory>/llm_<id>.secret`, no mode checks. No `Kms:Provider` → no source.
- **Which keys:** every provider under `Llm:Providers` (the active one is a remote-config value, so a switch needs no restart). Provider ids must match `^[a-z0-9][a-z0-9-]{0,39}$` (they form a file name and a KV path); another id refuses the start.
- **Refusal rules (AC1, AC3):** *absent* (no file, no setting, KV 404, or KV not readable: OpenBao answers 403 or is unreachable after the KMS check) → that provider has no key: a Warning names the source and the provider id, the rest of the backend starts, and the LLM call is refused (`HasKey` false; `GetKeyAsync` and the adapter throw `LlmServicePausedException`, which the endpoints map to `LLM_SERVICE_PAUSED`, before the circuit guard so it never counts as a provider failure). *Present but bad* (wrong file mode/owner/symlink, empty file or setting = "missing key" of AC1, too large, malformed wrapper, wrong `name`, extra KV members, a value with characters a header can't carry) → startup failure, `LlmKeyConfigurationException` (a `SafeException`) with a constant message naming the source and the provider id, never the value, a length or a prefix.
- **Format:** one trailing newline is removed. `OpenAiResponses` keys: 1..1024 visible ASCII characters (0x21..0x7E; no space, CR or LF, so no header injection). Service-account JSON (Vertex, T-338): ≤ 8 KiB, a JSON object with `"type":"service_account"`, `client_email` and `private_key` strings; `LlmKeyFormat.ServiceAccountJson` is implemented and tested now, T-338 maps its kind to it.
- **Configuration refusal (AC2):** at start, every configuration provider (JSON files, environment variables, command line, in-memory) is scanned for a key under `Llm` whose last segment is `ApiKey`, `Key`, `Secret`, `Token`, `AccessToken`, `Bearer`, `Credential(s)`, `Password` or starts with `ServiceAccount` (case-insensitive, `-`/`_` ignored) → startup failure, constant message, the path's provider id named, never the value.
- **Holder:** the loaded value is kept in a private dictionary of `LlmSensitive<string>` (`ToString` and JSON write `***`); `ILlmApiKeyProvider.GetKeyAsync` now returns `LlmSensitive<string>` (was `Domain.Sensitive<string>`, whose JSON writes the bare value). Intermediate byte buffers are pinned and zeroed. Residual: the header needs a .NET `string`, which can't be zeroed; it lives for the process lifetime (documented, accepted: the process is non-dumpable outside Development/Testing).
- **Logs:** only `{ProviderId}` and a fixed source word (`File`, `HostSecrets`, `OpenBao`, `Local`, `None`); no value, length, hash or prefix. HTTP client logging for `llm-*` clients is already removed (T-332).
- **Rotation:** new value in the store, restart, check the start-up log line "LLM key for provider … loaded from …" and one live call; runbook in `deployment.md` §3 "LLM provider keys".
- **Negative proofs (2):** (1) remove the configuration scan → the AC2 tests go red; (2) leak the key into the request URI (query) → the AC5 WireMock test goes red. A third, writing the value into the malformed-wrapper message, is covered by the AC4 sentinel test.

## Acceptance criteria
1. Each source loads a test key; wrong file mode, missing key, malformed wrapper → startup failure with a message that names the source, never the value.
2. Startup refuses any `Llm:Providers:*:ApiKey` (or similar) value in `appsettings*.json`, plain environment configuration or command line.
3. With the active provider's key missing, the LLM module is disabled (endpoints answer `LLM_SERVICE_PAUSED`), the rest of the backend starts.
4. **Negative proof 1:** a marker key value is absent from the log sink, OTel exporter, problem bodies and exception messages across load, provider 401 and provider 5xx paths.
5. **Negative proof 2:** the key never appears in the outbound request URL or query string (WireMock captures; header only).
6. Rotation runbook section written (steps, restart, verification without printing the key).

## Notes for the builder
- Reuse existing KMS provider plumbing; no new secret storage mechanism.

## Description
Buy and restore Gold safely on both stores, with install-bound attestation and same-iPhone recognition.

## Technical details
- **Purchase:** `in_app_purchase` 3.3+ (PBL 8, pending purchases enabled); `obfuscatedAccountId` / `appAccountToken` = HMAC(installId); `POST /v1/purchases/verify` (anchoring, via T-144's time anchor); outbox + WorkManager/BGTask retries until verified (BR-GOLD-06); complete purchases only after verify.
- **iOS verify `seatKeys`:** element 0 only, signed over `op = verify`, `challenge = SHA-256(signedTransaction)` (T-183 message builder, T-179 signer); omitted when T-179 reports the own key unusable or unavailable.
- **Verify outcomes** exposed as typed states for T-146: `seatHeldElsewhere` (+ `nextMoveAt`), `seatHeldElsewhere + accountRequired` (R4-4), pending, invalid.
- **Restore (`POST /v1/purchases/restore`):**
  1. Build the body (Android items `{productId, purchaseToken}` from `queryPurchasesAsync`; iOS signed transactions, 1–20).
  2. `bodyHash` via T-183 (RFC 8785 JCS, install ID = own current ID). If T-183's strict parser rejects the body, nothing is sent.
  3. **Android:** `AttestationHostApi.prepare()` only when the user starts a restore, then `attest(bodyHash)` (`requestHash = b64u(bodyHash)`).
  4. **iOS:** `SeatKeyHostApi.sign(message(op = restore, challenge = bodyHash))` first, then `clientDataHash = SHA-256("zaghlol-restore-attest-v1" ‖ 0x00 ‖ bodyHash ‖ SHA-256(pk₀ ‖ … ‖ pkₙ₋₁))` via T-183 (empty-string digest when no keys), then `attest(clientDataHash)`; the same hash is used for `attestKey` on a new key. `attestation.seatKeys` carries the signatures.
  5. Errors: platform transients retried 3× within 1 min, then "try again later" (offer Play services update when that's the cause); `422 DEVICE_ATTESTATION_FAILED` → iOS one retry with a forced new App Attest key (when no `attestationObject` was sent), Android one retry with a fresh token, then help message + offer sign-in; `409 MOVE_COOLDOWN` → store `nextMoveAt`, no automatic retry; `503 UPSTREAM_UNAVAILABLE` → back-off; never call restore without a proof.
  6. **`400 SEAT_KEY_MISMATCH` (R4-1(1), R5-6):** retry once without `seatKeys` (a fresh attestation over the new body hash); if that retry succeeds, tell T-179 to persist "own seat key unusable for this install" and stop sending `seatKeys` from this install.
- **StoreKit transaction check (R5-3(b))** for T-147: `hasStoreKitTransactionFor(purchase)` using `Transaction.currentEntitlements` / `Transaction.all`.
- **Android "Delete everything" warning data** for T-166: whether this install holds a seat and the token's `nextMoveAt` (D-55, EC-69).
- **Network config check:** the release Android build's `network_security_config` trusts system CAs only (set up in T-178; re-checked here on a release build).

## Design note
(Implementer note, Sonnet, 2026-11-13; PO cost rule 3.)
- **Layers.** `GoldStore` (port over `in_app_purchase` 3.3, StoreKit 2 on iOS, PBL 8 on Android) -> `PurchaseService` / `RestoreService` -> `GoldBackend` (BackendClient) and `EntitlementService.anchored`. Gold changes only inside `EntitlementService.handleBody` (signature, install binding, trusted time). The services never call `applyVerified`; after an answer they call `evaluate()` and treat anything but `active`/`grace` plus a returned entitlement as "not verified": no Gold, no acknowledgement, retry.
- **Outbox.** Unverified purchases live in `secure_state` key `purchase_outbox` (token or JWS, `Idempotency-Key`, seat proof once signed, back-off state). Retries resend the same key and the same bytes. Back-off 1 m, 5 m, 15 m, 1 h, 3 h, 6 h (then every 6 h), `Retry-After` wins when longer; a server `pending` is polled every 15 min; entries older than 14 days are dropped. Final answers (`PURCHASE_NOT_OWNED`, `PURCHASE_TOKEN_INVALID`, wrong app, expired, refunded, invalid) mark the entry `rejected` (kept, so a store replay is not verified in a loop) and are never acknowledged.
- **Completion** (Play acknowledge / StoreKit finish) only after `active` + a verified Gold token, or `active` + `seatHeldElsewhere` (the backend verified and acknowledged; BR-GOLD-06). If completion itself fails the entry becomes `verified` and the next store replay completes it without a second verify.
- **Restore** follows the task steps 1-6 exactly; see `restore.dart` header. Order on iOS: seat signatures over `bodyHash`, then `clientDataHash` over the keys in that order, then App Attest.
- **Triggers.** Store stream at app start (Play and StoreKit redeliver unfinished purchases), resume tick, an in-process timer at the earliest `nextAt`.
- **Contract change.** `BackendFailure.nextMoveAt` (from the `409 MOVE_COOLDOWN` problem body) added to T-141's failure type.

### Deviations / left open (report to Lead)
1. **No native wake-up for a closed app.** The outbox is retried when the app starts, resumes, or its timer fires, and Play/StoreKit redeliver the purchase at every start; a WorkManager/BGTask job that runs Dart while the app is closed needs a second headless engine (the existing one is the ingestion drain, `IngestionWorker`) and is not built here. `PurchaseRetryScheduler` is the seam. Within Google's 3-day window this works only if the user opens the app once after the backend returns. PO decision needed: build the native job as a follow-up (suggest FU: `purchase-retry-worker`), or accept.
2. **On-device checks not done** (no store accounts, no devices): the StoreKit-config test of `hasStoreKitTransactionFor` (adapter code is `SK2Transaction.currentEntitlements()` / `transactions()` by product ID; the logic above it is tested with a fake), the release-build user-CA check (T-178's `network_security_config` is unchanged here), and sandbox purchases.
3. `in_app_purchase_android` and `in_app_purchase_storekit` added as direct dependencies (the adapter imports their wrappers).

## Acceptance criteria
- [ ] Backend down at purchase → Gold after it returns, within Google's 3-day window.
- [ ] Pending (cash) purchase shows pending, no Gold.
- [ ] R2-1: the restore `bodyHash` uses this install's own current ID; a fake attestation host receives exactly that 32-byte value on Android and the `clientDataHash` on iOS (tests against `restore-binding-v1.json` `valid` vectors).
- [ ] R4-1(3): on iOS the seat-key signatures are produced before the attestation call, and the digest covers the public keys in request order (call-order test with fakes; vector test for `seatKeysDigestHex` / `clientDataHashHex`).
- [ ] R3-8: a body that T-183's strict parser rejects is never sent (test using every `invalid` vector).
- [ ] R4-1(1)/R5-6: on `SEAT_KEY_MISMATCH` the app retries once without `seatKeys`; after a successful retry the "own seat key unusable" flag is set and later restores, verifies and sign-ins send no `seatKeys` from this install (tests).
- [ ] `DEVICE_ATTESTATION_FAILED` → exactly one retry (iOS with a new key, Android with a fresh token), then the help state offering sign-in (test).
- [ ] `MOVE_COOLDOWN` → `nextMoveAt` stored, no automatic retry (test).
- [ ] R5-3(b): `hasStoreKitTransactionFor` returns false for a Play-bought or other-Apple-ID purchase and true for a StoreKit-config purchase (StoreKit test config).
- [ ] D-55: the Delete-everything warning provider returns "holds a seat" and `nextMoveAt` when the cached token covers a purchase (test).
- [ ] Release Android build: user-installed CA can't intercept a restore call (device check recorded; see T-178).
- [ ] DoD (CLAUDE.md §7): analyze clean, formatted, tests added, no hard-coded strings, RTL verified where UI, no `double` money, no raw SMS in logs.

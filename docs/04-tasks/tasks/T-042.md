## Description
Read only allowlisted senders' past SMS.

## Technical details
ContentResolver query with address IN (…) AND date > since, paged by _id, page ≤ 500; returns in-memory pages; never touches other senders.

## Design note
(solution-architect, Opus, 2026-11-11. C4: SMS ingestion. Reviewers: challenge it. Carries FU-085 (T-042 part), FU-088 (native `queryInbox`). **[doc change]**s are made in this commit. Sister note: T-041, same branch.)

**Goal.** Implement `AndroidCaptureHostApi.queryInbox(InboxQuery) → InboxPage` (contract exists, `serialBackgroundThread`) so T-048's first-run scan, per-open catch-up (PO Q7) and card re-scan (FR-CAP-07) read **only allowlisted senders' SMS**, in bounded pages, with the native Guard applied to every row. No state between calls; no spool; no new dependency.

**1. Files.** `app/android/app/src/main/kotlin/app/zaghlol/platform/capture/inbox/`: `InboxReader.kt` (logic), `InboxSource.kt` (seam: `query(selection, args, sortOrder): Cursor?`; production = `ContentResolver.query(Telephony.Sms.Inbox.CONTENT_URI, PROJECTION, …)`), `InboxCursor.kt` (opaque cursor codec), `SimSlot.kt` (or T-040's helper if it lands first: one mapping for live and inbox). `AndroidCaptureHost.queryInbox` delegates to an injected `inbox: InboxReader?` (null → `NOT_AVAILABLE`; the headless host always gets null, so the background never reads the inbox, FU-088). Guard: one new read-only method `CaptureGuard.senderKind(channel, source): GuardKeepKind?` (step 1 of §1.2 without the body: `registry` exact/regex, `user`, or `alwaysCapture` → `generic`; senderHints are **not** an allowlist). Lives in `src/main` (JVM tests run on the PC runner); the `*NoSms` builds can't hold `READ_SMS`, see §5.

**2. Sender filter (in SQL, then re-checked).** Input `senderAddresses` (≤ 1,000, else `INVALID_ARGUMENT`; empty → empty last page). Native keeps an address only if `senderKind("sms", a)` is `registry`, `user` or `alwaysCapture` (a Dart bug can't widen the read to a personal number). For each kept address it binds the distinct ASCII variants `{a, lower(a), upper(a)}` (the provider compares `address` with BINARY collation; the Guard compares `foldKey`). Selection, built from a constant template and `?` only (no `LIKE`, no functions, no `COLLATE`, nothing from input in the SQL text):
```
address IN (?,…,?) AND date > ? AND _id > ?        sortOrder: "_id ASC"
projection: _id, address, body, date, sub_id         uri: Telephony.Sms.Inbox.CONTENT_URI (type = inbox only)
```
Bound arguments per query ≤ 900 (SQLite before 3.32, i.e. API 26–29, allows 999): more variants → **chunks** of ≤ 898 variant arguments (an address never split across chunks), scanned one after another. Each row read is re-checked: `senderKind("sms", address) != null` and `address` ∈ the bound set; a row failing either (an OEM provider ignoring the selection) is skipped and counted, never returned. *Residual:* a sender id stored in mixed case not in the variants (e.g. `Nbe`) is not scanned (live capture still folds); T-036's registry lint should store sender ids as banks send them.
**Who passes which addresses (T-048, recorded here):** registry exact senders as written in the registry, user senders, and the distinct `raw_messages.source` values of channel `sms` already in the DB (covers senders matched by a registry **regex**, which SQL can't express). *Gap:* a regex-only sender never captured live is not found by the first-run scan (Lead question 1).

**3. Paging, cursor, limits.** `pageSize` clamped to 1..500 = rows **read** per call (kept + dropped), so a call's work and memory are bounded whatever the Guard drops. Read with `cursor.moveToNext()` until `pageSize` rows, then `close()` (`use {}` always). `LIMIT` is not put in `sortOrder` (strict-grammar providers may reject it); the cross-process `CursorWindow` (~2 MB) holds only rows that matched the selection, i.e. allowlisted ones. Cursor token `v1.<chunk>.<lastId>.<crc32>`: `crc32` over the sorted bound variant list + `since` (a different query with an old cursor → `INVALID_ARGUMENT`, never a silent skip). `nextCursor = null` when the last chunk returned fewer than `pageSize` rows. `scannedTotal` = rows read **in this call** (Dart sums for progress) [doc change §2 wording]. `providerId` = `_id` as decimal text (FU-085: Dart may keep the max seen; `_id` can be reused after deletes, so it is a hint, dedupe stays `body_hash`). Cancellation: Dart stops asking; each call is bounded by `pageSize`; no native state survives a call.
**Memory (AC2):** items ≤ 500 × body ≤ 4,000 chars (the Guard drops longer before returning) ≈ 4 MB of strings + one window; 10k messages = 20 calls, constant memory.

**4. Time bounds.** `date > sinceEpochMs` (`date` = receive time in ms; selection args are text and SQLite applies numeric affinity against the INTEGER column, verified by the emulator test). `since` below `now − 25 months` (A-11 max 24 + 1) is raised to it; `since > now` → empty last page. FU-085's other rules stay Dart-side (T-048): a null watermark never scans (first scan only through T-048's consented bounded path), catch-up `since = min(watermark, firstMissedSmsAtMs) − 10 min`, watermark clamped to `min(maxReceivedAt, now)`.

**5. Permission and flavour.** Manifest lacks `READ_SMS` (`*NoSms`) → `NOT_AVAILABLE` without touching the provider. Not granted → `PERMISSION_DENIED`. `SecurityException` from the provider → `PERMISSION_DENIED`; any other exception → `IO_ERROR`; argument problems → `INVALID_ARGUMENT` (new code, [doc change] §6). All code-only (`CaptureApiError(code, null, null)`).

**6. Multipart.** The inbox row is the whole message as the SMS app stored it (the telephony stack assembles parts; Android 4.4+ the default SMS app writes the row), so the reader does no joining. The live receiver joins PDUs itself (T-040); if an SMS app stores the text differently, `body_hash` differs and the DB's cross-channel dedupe (T-046 dedupe 2) is the backstop. A row over 4,000 chars is a Guard `too_long` drop, as live.

**7. Guard on every row.** `guard.current().guard.decide("sms", address, body)` — **without** the rate limiter (history is not a flood; `GuardRuntime.decide` would also consume the live window). `DROP` (OTP, per-institution promo, ignored institution/card, `config_invalid`) → not returned. `KEEP` → `RawInboxMessage(address, body, dateMs, simSlot, providerId)`. Dart runs its Guard again at ingest (T-046 drain-time re-check). `simSlot`: `SubscriptionManager.getSlotIndex(sub_id)` on API 29+, null below (no `READ_PHONE_STATE`); `sub_id` < 0 → null.

**8. Handoff.** Direct, in memory: the page goes to Dart, T-048 ingests it through `IngestRawMessages` with origin `inbox` and the same `bodyHashOf(source, body)` as live (`address` = live `originatingAddress`). **Not the spool**: 500-entry caps, a second encrypted copy and the ack protocol would add nothing for data that stays in the provider.

**9. Never logged.** No `Log`/`println` (the app-ci grep covers `platform/capture/**`); exceptions caught without message; `RawInboxMessage` is a generated `data class` whose `toString` has the body: never interpolated. Strings can't be zeroed; the page is dropped after the reply.

**10. Tests.** JVM (`src/test/.../capture/inbox`, fake `InboxSource` that evaluates the selection over in-memory rows and **counts every row it materialises**): selection text equals the template; args = variants + since + lastId, never > 900; a non-allowlisted address in `senderAddresses` is not bound; **non-allowlisted rows are never materialised** (FU-085); a provider that ignores the selection → its rows are skipped, not returned; OTP / ignored card / promo / too-long rows dropped; `alwaysCapture` sender kept; 1,234 rows / pageSize 500 → 3 pages, each row once, ascending; chunking with 1,000 addresses; cursor tamper and changed sender set → `INVALID_ARGUMENT`; `since` clamp and future `since`; pageSize clamp; `NOT_AVAILABLE` (no manifest permission, headless host), `PERMISSION_DENIED` (not granted, `SecurityException`); canary `ZG_CANARY_7731` in body and address never in exceptions, `toString` of host results, stdout/stderr. Instrumented (`src/androidTest/.../capture/inbox`, devSms, run by `sms-spike-device.sh`): **real provider**: script grants `READ_SMS` (`pm grant`), sends via `adb emu sms send` 30 messages from `5550100` (incl. a 3-part one, an OTP), 10 from `5550199`, then the test reads with pageSize 7: only `5550100` non-OTP rows, the 3-part message once, `date` filter works, `5550199` never returned; **AC2**: a lazy `AbstractCursor` source of 10,000 rows × 4,000-char bodies through 20 calls of 500: Java heap growth < 32 MB after GC and no `OutOfMemoryError`. **Negative proofs** (mutation, red, revert): `address IN` removed → "never materialised" red; per-row re-check removed → "provider ignores selection" red; Guard skipped → OTP test red; rate limiter used → "21 rows from one sender" red; variants removed → mixed-case test red; cursor crc ignored → tamper test red; pageSize not clamped → 10k test red.

**Emulator steps.** devSms debug + test APK; `adb shell pm grant app.zaghlol.dev android.permission.READ_SMS`; send the messages above; `am instrument -r -w -e class app.zaghlol.platform.capture.inbox.InboxReaderInstrumentedTest …` → OK; then `pm revoke` READ_SMS and rerun the denial test → `PERMISSION_DENIED`; `logcat | grep -c ZG_CANARY` = 0.

**Rejected.** Reading `DISTINCT address` first and matching regexes natively (reads every contact's number into memory). `LIKE`/`GLOB`/`lower(address)` in SQL (FU-085; strict-grammar risk). `content://sms` (includes sent and drafts). Returning dropped rows' counts per reason (diag only needs `scannedTotal − items`). Spool handoff (§8).

**Parallelism.** T-042 ∥ T-041: yes (§1 of T-041). T-042 ∥ T-040 / T-043: yes; T-042 touches none of their files. Shared spots: `AndroidCaptureHost.kt` (constructor param + `queryInbox` body; T-041 adds `holdSpool`), `CaptureGuard.kt` (new method only), `sms-spike-device.sh` (one new step): small textual merges, the second to merge rebases.

**[doc change]s made with this note:** platform-channels §2 (`InboxReader` as designed, `scannedTotal` = rows read in this call), §6 (`INVALID_ARGUMENT`). No Pigeon change.

**Questions.** *PO:* Q1 A user-added custom sender can be a mobile number (a cooperative, a merchant). The scan then reads **every** past SMS from that number, including personal ones, and the Guard keeps them all as `user` kind for review. Allow inbox scans for user-added numeric senders, or only live capture for them? Provisional: scanned (the user chose the sender). *Lead:* L1 Senders matched only by a registry **regex** and never captured live are missed by the first-run scan (SQL can't run the regex; reading every address is rejected). Accept the gap, or have T-036 add the known concrete sender ids per regex rule to the registry and Guard export? L2 accept `INVALID_ARGUMENT`.

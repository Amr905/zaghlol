**PO, 2026-11-28 19:21:** "when I click on the bird no change is happening now while the message changes" (latest main build; before batch 82 the tap animated with a stutter, T-276 smoothed it).

## Suspects (find the real cause; write it in the task file before fixing)
1. **T-292 (batch 82)** moved the Rive preload from `main()` to `RivePreloadOnFirstFrame` (after the first frame, skipped under reduce motion / platform disable-animations). If the Home bird is built before the preload completes, or the preload never runs, `RiveMascot` may stay on the still-image fallback for the whole session → taps only change the bubble.
2. **T-298 (batch 84)** `hapticsSyncProvider` / reduce-motion wiring: check nothing now feeds "reduce motion" true into the avatar on a normal phone.
3. `ZaghlolTapBubble` (`mascot_moments.dart`) → `ZaghlolAvatar` → `RiveMascot.apply(moment, talk, replay:)` (`rive_mascot.dart` ~243-330): the `tap` moment + `replay` counter may not reach the state machine (input name/value mismatch with `app/assets/rive/zaghlol.riv` regenerated in T-274, or the replay "leave for one frame" path never fires).
4. The batch 83 payday sheet / Saved toast changed the Home slot (`home_mascot_slot.dart`).
Use `git log -p` on these files since batch 78 (`git log --oneline 32b7add2..origin/main -- <files>`).

## Root cause (builder)
Not reproducible without a device (rive_native cannot load in tests); found by reading the history since batch 78 (`git log 7f6760d1c..HEAD`).
- Suspects 2 and 4 are cleared: nothing sets `reduceMotionProvider` true in the app (`hapticsSyncProvider` only reads it), and the payday/Saved-toast changes (T-294/T-295) do not touch the avatar path. The tap path (`ZaghlolTapBubble` -> `ZMascotBubble` -> `ZaghlolAvatar` -> `RiveMascot.apply(tap, replay)`) is unchanged since T-276 (7f6760d1c).
- The only change to the Rive loading path after T-276 is **307fb4099 (T-292, FU-391)**: `unawaited(preloadRiveMascot())` moved from `main()` (before `runApp`, runtime started on an idle engine) to `RivePreloadOnFirstFrame` (a post-frame callback), so `RiveNative.init()` + file decode now run concurrently with the first Home build and the mount's own load of the same shared future.
- Latent defect that turns any single failed load into the reported symptom: `_RiveMascotState._failed` was permanent. One failed first load (runtime busy during the start-up frames) left that Home bird on the still image for the whole session, while `ZaghlolTapBubble` kept changing the tip text and `apply()` was never reached (`_handle == null`). The shared-file failure is not cached, so later mounts recovered, which is why it looked like Home only.
- Confidence: the commit is the best candidate by elimination; the failure on device is not confirmed. The PO device check decides.

## Fix
`RiveMascot` retries a failed load: automatically after 2 s (up to 3 times) and on the next tap / moment / talk change. Preload timing is unchanged (it already starts at the first build under the root `ProviderScope`, also behind the DB gate, and the avatar switches to Rive as soon as the shared future completes).

## Builder assumptions
- Preload moved back to `main()` was not done: FU-391 needs the reduce-motion flags.
- Reduce motion stays still: the avatar never mounts `RiveMascot` then.

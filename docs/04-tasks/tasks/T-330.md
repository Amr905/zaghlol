## Description
`PlanValidator.Validate(planJson, sentText, lang) → Valid(plan, template?) | Fallback(reasonCode)`: (1) JSON Schema (JsonSchema.Net over the contract file); (2) every `ref` occurs verbatim in the sent text and no plain bundled-registry alias appears in any string; (3) `mention` is a substring of the normalised sent text; (4) amount rule; (5) cross-field rules; (6) template grammar (failure drops `t` only). Reason codes are a closed enum.

## Acceptance criteria
1. Every vector in `ask-plan-v1.json` gives its expected outcome and reason code.
2. Each §2.3 rejection class has a test: digit (Western and Arabic-Indic), `⟦`, stray `{`, `@`, `://`, `www.`, `label.tld`, markup characters, bidi override, two emoji, ar < 70 % Arabic letters, en with an Arabic letter, a blank not allowed for the plan, a blank used twice, > 200 chars.
3. Template failure keeps the plan (`Valid` with `t = null`); steps 1–5 failing → `Fallback`.
4. Validation never logs or throws with plan text; reason codes only (test with a log sink).

## Design note (builder)
- `PlanValidator` is a pure class in `Zaghlol.Application.Llm.Plans`: `Validate(JsonElement plan, string sent, string lang)` returns `Valid(plan, template?, templateReason?)` or `Fallback(reason)`. Steps 1-5 are a port of the reference in `Zaghlol.Contract.Tests/AskPlanReference.cs` (the vectors are the authority); step 6 lives in `TemplateGrammar` and only drops `t`. Reasons are a closed enum `PlanReason` with fixed code strings; the validator logs only a code through an optional `ILogger` and never the plan, text or question.
- The schema is embedded in the Application assembly from `backend/contracts/ask-plan-v1.schema.json` (one source of truth, no copy); `$id` is stripped before compiling, as in the contract tests. Shared edits: `Zaghlol.Application.csproj` (JsonSchema.Net reference + embedded resource) and `Dockerfile` (`COPY contracts/`).
- Normalisation (`foldKey`) is ported to `PlanText.Fold` (same table as `text_normalizer.dart`). Number words, registry aliases and currency exponents come from `PlanValidatorData` (defaults = the minimum lists of the vectors; the bundled institution registry is injected by T-349).
- NFC: under `InvariantGlobalization=true` `string.IsNormalized` accepts everything non-ASCII, so `Nfc.IsNfc` is own code: it rejects (conservatively) every character with NFC_QC=No from a pinned list (singletons, CJK compatibility, Indic nukta composites, Tibetan, Hangul jamo, U+0340/0341/0343/0344), any combining mark (Mn/Mc/Me) other than the Arabic marks U+064B-U+0652 and U+0670 (checked for canonical order) and U+0653-U+0655 (rejected only after a letter they compose with). A false "not NFC" only drops the template (plan kept), so conservative is safe; a false "NFC" is not possible for the listed classes. Residual: exotic scripts outside the list are not checked (documented in the code).

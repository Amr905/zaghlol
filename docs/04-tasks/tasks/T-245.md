## Design note (builder)
Safety property: a notice never marks anything paid on doubt, and an older notice never replaces a newer one.
- **No schema change.** The latest notice per card (institution + last-4) is one JSON value in `settings`, key `card_due.<inst>.<last4>` (<=64 chars, `[a-z0-9_.]`, well under 16 KB). It exists before the card does, so it doubles as the "pending until the card is created" store (scope 2). Reason: the table would only hold one row per card; a migration (frozen dump, v6 test schema, step tests) is not worth it. Backups already carry `settings`.
- **Pure domain** (`features/accounts/domain/card_due.dart`): `CardDue` (amount due, minimum due, due date, statement date, notice instant, paid minor, paid txn ids, applied flag) with `mergeNotice` (newer `receivedAtMs` wins; older or equal is rejected; a newer notice for the same due date keeps fields it lacks), `applyPayment` (counts a payment on or after the statement date, in the same currency, once per txn; paid only when paid >= minimum due, or the total due when no minimum is known; with neither known it is never paid) and the JSON codec (a bad value reads as no due).
- **Hook** (`CardNoticeHook` implementation, `DriftCardNoticeHook`): needs institution + last-4 + a currency and at least an amount or a due date, else the raw message is kept and nothing else happens. Stores the merged due; if it won, applies it to the matching credit account.
- **Apply to the reminders**: the existing active `card_due` recurring item of the account (created when missing) gets `next_due_date` = the notice due date and `amount_minor` = the amount due (remaining minimum after a partial payment). The user's typed `statement_due_day` changes only when it is empty or the notice is newer than the account's `updated_at`; otherwise only this cycle's date moves, the day stays. Reminders (FU-219 due days, `send_due_reminders`) then fire from the item as before; overdue reminders stay off for cards (OVERDUE-REMINDERS).
- **No matching card**: the stored due waits; `RecurringRepository.syncCardDues` (daily housekeeping and after every card save) applies any not-yet-applied due to accounts that now exist.
- **Payment**: `CardDuePaymentHook` (post-persist) feeds an inserted `transfer_in` on a credit account to `applyPayment`; paid inserts the occurrence and advances the item by the existing `progressAfterPayment`; partial lowers the item amount to the rest of the minimum.
- **Card detail** shows the latest due from the stored value (strings in ARB).

## Scope
1. Implement the dues hook from T-241: a parsed `cc_due` / `cc_statement` notice updates the matching card account (institution + last-4): statement amount due, minimum due, due date, statement date. Where the card already has dues fields (`account.dart`, card detail, bills/recurring dues) reuse them; add columns only if missing (migration with tests).
2. No matching card: keep the notice (raw message parsed, no transaction) and apply it when that card account is created later (same institution + last-4).
3. The existing due reminders (OVERDUE-REMINDERS, FU-219 due-days) fire from these dues; a card payment (`cc_payment`) on or after the statement date marks the due paid when it covers the minimum (partial payments: record, keep reminding for the rest of the minimum). Never change the user's typed due day without a notice newer than it.
4. Card detail shows "Due EGP x (min y) by <date>" from the latest notice; strings in `ar` (Egyptian colloquial) and `en`.
## Acceptance criteria
Ingest tests: case 7/8/12 synthetic fixtures update the card's due and create no transaction; a later notice replaces an older one, an older one never replaces a newer; payment marks paid; widget test of the card due line in `ar` and `en` (light/dark goldens if the screen has goldens); `flutter analyze` clean.

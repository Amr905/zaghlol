## Description
App updates fix past unrecognized messages automatically.

## Technical details
On start, compare registryVersion; re-parse review messages and messages parsed by changed templates in an isolate; never touch user-verified transactions. Also re-run `reparse_pending` raw messages (events without a handler in the build that stored them, e.g. `fx_conversion` before T-089; T-046 design note §6), through the `IngestRawMessages` re-parse entry (skips the Guard and dedupe 1; dedupe 2 still applies).

## Design note
Written by the builder (Sonnet), 2026-11-13. Code: `ingestion/application/reparse.dart` (`ReparseJob`), `IngestRawMessages.reparse(StoredRaw)`, three new `IngestStorePort` methods (`rawsToReparse`, `promoteRaw`, `txnOfRaw`). No schema change.
- **Selection:** background-channel raws that are `review` or `parsed` with `registry_version` older than the running registry, plus every `reparse_pending`. (The registry version is the highest template version, so a bump is a changed template.) Keyset pages of 50, at most 5000 rows per run; the run yields between rows. User-confirmed channels (share/paste/OCR/PDF/CSV) are never selected.
- **One write transaction per message**, parse outside it. Guard and dedupe 1 are skipped (new origin `MessageOrigin.reparse`, not background, not user-confirmed); dedupe 2 and pending/settled merge run through the normal `_persist`.
- **review / reparse_pending -> transaction:** the SAME raw row is promoted by a conditional update (`WHERE parse_status = <status read>`), which also resolves its open review items (`resolution = reparsed`). A lost condition (user dismissed or resolved it, another engine got there) throws inside the savepoint: nothing is written, outcome `skipped`. Promotion runs before any transaction write in every branch (as CR-6 does for inserts).
- **No new review items from a re-parse** (FU-109: personal-origin is not stored on the raw row, so the rule is applied by never creating review items): anything that would still end in review/undirected/deferred is only stamped with the new registry version (`review`, `parsed`) or left for the next run (`reparse_pending`). Generic results are not re-run (capture_senders / confirmed_count are not touched, A-66).
- **parsed rows with a changed template:** only NULL fields of the row's transaction are filled (the cross-channel attach rule), only when the transaction is live, not user-verified, not in a transfer pair or internal, and direction, status and amount equal the new parse. Amount, direction, status and category are never changed (a settled or merged amount must not be undone by an older message).
- **Nothing is deleted**, so `TransferPairing.onRemoved` has no caller; `onPersisted` runs after the commit for every transaction written (`ReparseJob(onPersisted:)`); its failures are counted, not thrown.
- **Concurrency:** one run at a time per job object; across engines the conditional promote plus `BEGIN IMMEDIATE` give one winner; live capture of the same text hits dedupe 1 on the existing `body_hash`.
- **Deviation:** no worker isolate. The DB lives on the app's DB isolate already and per-message parsing is cheap; the job yields between messages. Wiring `ReparseJob.run()` at app start is left to the app composition (not done here).

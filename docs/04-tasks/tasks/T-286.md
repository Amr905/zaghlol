## Scope
1. **FU-383** (`ingest_raw_messages.dart` ~1317-1361): after a cross-channel merge (T-281), mark the stored exchange as having its other-channel copy (or record the channel that produced each pair) so a **second real conversion** with the same amounts on the other channel is never merged into it; instead it is stored and flagged `possibleDuplicate` for the user. Same rule for the existing single-transaction cross-channel attach if it has the same exposure (check and write what you found). Prefer an existing column/table (source message links) over a schema change; if a schema change is unavoidable, stop and write why in this file.
2. **FU-384** (`transactions_list_screen.dart` ~291-325, bulk actions): selecting an exchange row selects both legs for every bulk action; Set category is not offered for exchanges (they have no spending category) and Set account is disabled when an exchange is selected (it would split the pair), with a short reason. Delete already uses `wholeExchanges`.

## Acceptance criteria
- Ingest test: SMS A stored, notification for a different real conversion B with equal amounts → two exchanges + a review item, not a merge. The T-281 merge test still merges a true copy.
- Bulk test: selection of an exchange row holds both legs; Set account/category cannot change one leg.
- ≤ 3 negative proofs.

## Design note (builder)

**FU-383, merge marker without a schema change.** No table links a raw message to the transaction it was merged into: a merged message's `raw_messages` row has no `transactions.raw_message_id` pointing at it. The existing raw↔transaction link table is `review_items` (`raw_message_id`, `txn_id`, JSON `payload`, `resolved_at`), and the code already keeps resolved items as durable marks (T-257 `oldDueNotice`). So every cross-channel merge now writes one **already-resolved** `low_confidence` item: `raw_message_id` = the merged message, `txn_id` = the stored transaction (the out leg for an exchange), payload `{"reason": "crossChannelCopy", "source": <txn source code of the merged message>}`, `resolution = 'cross_channel_copy'`. Being resolved, it never shows in the review queue, the open count, the SMS diagnostics or any kind-specific query (all filter `resolved_at IS NULL` or other kinds); `purgeResolvedBefore` has no caller; the FKs cascade with the raw or the transaction.
- Dedupe 2 (ordinary attach) and the T-281 exchange merge read the marks of their matches (`crossChannelCopySources`, one query). A match that already has a copy from the incoming message's source is **not mergeable**: the message is stored as its own transaction / exchange and gets the usual `possibleDuplicate` review item listing the matches. Nothing stored is changed and nothing is deleted; the user decides (T-250 rule).
- The mark is written in the same savepoint as the merged raw row, so a rollback removes both.
- Ordinary attach has the same exposure (checked: `_parsed` dedupe 2 merges on one match with no memory of earlier copies), so the same rule applies there.
- Rows merged before this change have no mark; they behave as before (only matters inside the 2-minute window right after the upgrade).

**FU-384, bulk actions.** Selection: tapping or long-pressing an exchange row toggles **both** leg ids; Select all adds the other leg of every exchange among the matching ids (lookup through `txnExchangeLookupProvider`). Action bar: when the selection holds an exchange leg, Category and Card are disabled and a one-line reason shows above the bar; Delete stays (it already takes whole exchanges). The tap handlers re-check through the lookup before opening a sheet (rows that are not loaded). In the use case, `SetCategory` now refuses a batch that holds an exchange leg (`BULK_EXCHANGE`, nothing changed), like `SetAccount` already refuses any paired leg (`BULK_PAIRED`), so no path can change one leg.

## Builder assumptions
- **What the marker can and cannot tell.** The marker only knows about copies that actually arrived. If A's other-channel copy never arrives, B's copy on that channel is, by content, indistinguishable from A's copy and is still merged into A (unchanged behaviour). B is not lost in that case as long as B's own message on A's channel arrives: same-source messages never match each other, so it is stored as its own transaction/exchange. The acceptance test therefore uses the case the marker can detect: SMS A, A's notification (merged), then B's notification with equal amounts.
- Dedupe 1 (`body_hash`) drops a byte-identical text forever, so a second real payment is only seen when its text differs (time, reference, balance). The test registry's notification templates gained an optional ` ref <digits>` suffix for this (test-only).
- The marker is per source: a copy from a **third** channel (for example a Shortcut message after SMS + notification) still merges.
- Set account was already refused for any paired leg (`BULK_PAIRED`, nothing changed); the list now keeps the button off with the reason instead of failing with the generic error. Set category is refused in the use case for exchange legs (`BULK_EXCHANGE`) and kept off in the list. Delete is unchanged (whole exchanges, T-281).

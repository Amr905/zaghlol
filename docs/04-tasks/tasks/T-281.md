## Today
An exchange (`transfer_pairs` kind `fx_conversion` / `cross_currency`) shows as two rows. Deleting one leg frees the other, which then counts as income or spending (`transfer_pairing.dart` onRemoved heal). A cross-channel duplicate of a conversion is stored as a second full pair (FU-364, `ingest_raw_messages.dart` ~1379).

## Scope
1. **List:** a complete exchange pair shows as **one row**: «غيّرت {from} ← {to}» (`←` mirrors to `→` in LTR; amounts and ISO codes are LTR runs) with «سعر البنك {rate} · مش مصروف» under it. With a currency filter the row still shows (it belongs to both currencies). Day-header per-currency totals do not count it as spending or income.
2. **Detail:** one exchange detail (both legs, accounts, rate, date, source message link if any).
3. **Delete / undo as one unit:** deleting the exchange removes both legs and the pair in one transaction, with the existing Undo restoring all of it. Nothing is deleted without the user's tap (T-250). Deleting a single leg from anywhere else (bulk actions, account delete) must either delete the pair as a unit or ask; never leave a freed leg silently counting as income or spending — pick the safer option and write it in this file.
4. **FU-364:** when a `possibleDuplicate` review item points at an exchange leg, resolving it keeps or deletes both legs together; when both legs of a new pair match an existing pair (same accounts, amounts, within the duplicate window), merge instead of storing a second pair.
5. Strings ar + en (plan §6 `txn.exchange.*`, with «غيّرت» not «حولت»).

## Acceptance criteria
- One row per exchange in the list (widget test), correct in ar/en and under a currency filter.
- Delete exchange → both legs and the pair gone; Undo → all back; cycle totals identical before/after delete+undo (test).
- Single-leg delete path: no freed leg counted as income/spending (test).
- FU-364 duplicate pair merged / resolved together (test).
- ≤ 3 negative proofs. Goldens via app-regen.

## Design note (builder)

**One unit, one transaction.** `BulkEditUseCase.apply(DeleteTransactions(wholeExchanges: true))` expands the selected ids with the live partner of every complete exchange pair (`fx_conversion` / `cross_currency`, both legs live), writes each such pair (id, legs, kind, created_at) into the Undo image (`pairs`), deletes the pair rows and soft-deletes every leg, all in the one existing transaction. `BulkActions.delete` (list row, selection, detail, review Remove) uses it. `undo` restores the legs as today and then re-inserts each recorded pair with the same id and kind, but only when both legs came back and neither has been paired since; otherwise the pair is skipped and the legs stay internal (counted nowhere). The Undo image stays `v: 1` (the `pairs` key is optional, older images have none).

**Every other single-leg delete path** (ignore rules, capture controls, housekeeping, voice Undo, dangling-link sweep) ends in `TransferPairingUseCase.onRemoved`. For an exchange pair it now dissolves the pair but **keeps the surviving leg internal** (one-sided, like EC-15), so it never turns into income or spending. Safer option chosen: nothing is deleted without the user's tap, and the survivor stays visible in the list as a transfer the user can delete or unlink by hand. The same rule applies to the heal inside `onPersisted` (a pair whose other leg is gone).

**List.** A read-only `ExchangeReader` (data layer) returns the complete live exchange pairs touching the loaded ids. The list keeps the first leg it meets and drops the other, and draws `TxnExchangeRow` («غيّرت {from} ← {to}» + «سعر البنك {rate} · مش مصروف»). Under a currency filter only one leg is loaded; the reader still finds the pair, so the row shows. Day totals already skip internal rows. The rate is the bank rate implied by the two amounts, shown as the side that is ≥ 1 (1 USD = 49.50, not 0.0202).

**Detail.** `TxnDetail` carries an `exchange` (both legs and kind). The detail screen shows one exchange view (both amounts, both accounts, rate, date, source, "How Zaghlol read this"); Edit is hidden for an exchange; Delete asks once with exchange copy and removes both legs; Undo restores both and the pair.

**FU-364.** Ingest of a conversion whose sent leg matches exactly one existing out leg that is in a complete exchange pair, and whose received leg matches that pair's in leg (same dedupe keys, same window and last-4 rules), merges: the raw message is stored as parsed, the balance is recorded, and no second pair is stored (`IngestMergedCrossChannel`). Otherwise the old behaviour stays (second pair + `possibleDuplicate` item); deleting either exchange from the list/detail then removes both of its legs together, and Keep only resolves the item.

No schema change.

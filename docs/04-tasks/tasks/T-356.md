## Description
Add `ai_merchant_suggestions(merchant_norm PK, category_id, confidence, source, state ∈ unconfirmed·confirmed·corrected·no_answer, created_at, decided_at)` and `llm_cat_queue(merchant_norm PK, txn_count, first_queued_at, last_seen_at, attempts, next_attempt_at)` with DAOs; outbox kinds `llmCatConfirmation` / `llmCatCorrection`; `CategorySource.ai('ai')`; export column `category_source` maps `ai` + unconfirmed → `ai_unconfirmed`. Both tables are cleared by "Delete everything" and included in the encrypted backup like other categorisation data.

## Acceptance criteria
1. Migration test from the current schema version on a populated synthetic DB; new tables empty and usable.
2. **Negative proof 1:** every existing transaction's category id and source, every rule and every outbox row are byte-identical after the migration.
3. **Negative proof 2:** a restore of a backup made before the migration upgrades cleanly and loses nothing (existing backup round-trip test extended).
4. Export test: an `ai` + unconfirmed row exports `ai_unconfirmed`; confirmed rows export as rules do today.
5. "Delete everything" empties both tables.

## Design note (builder)

**Schema v6 → v7, expand-only, one frozen step** (`core/db/migrations/v7_llm_categorise.dart`, dump `drift_schema_v7.json`, test `migration_v7_test.dart`). Policy: database-schema §4 2b/2c (frozen statements derived from the v6/v7 dumps by a test; CHECK changes by table rebuild; foreign keys off for the step, `foreign_key_check` before commit; any failure → the opener restores the byte-identical v6 file).

1. **Widen two CHECKs by rebuild** (SQLite can't alter a CHECK; the 2c rebuild is the established pattern, `writable_schema` is not used):
   - `transactions.category_source IN (…, 'ai')`. The rebuild copies every column **and the rowid** by name into `transactions__v7`, compares row counts before the drop, drops, renames, re-creates the six indexes and the four triggers on `transactions` (`trg_txn_offset_bu`, `trg_txn_fts_ai/au/ad`) from the v7 dump. Modern `ALTER TABLE … RENAME` refuses to run while a view or trigger names a missing table, so the view `transactions_fts_row` and the two `offset_links` triggers that read `transactions` are dropped by name first and re-created unchanged from the v7 dump afterwards. Child tables (`transfer_pairs`, `split_participants`, `offset_links`, `review_items`, `recurring_occurrences`) keep their FK text. FTS rows live in `transactions_fts_src` (keyed by `txn_id`), untouched; the copy fires no trigger (the new table has none yet).
   - `outbox.kind IN (…, 'llm_cat_confirmation', 'llm_cat_correction')`: same rebuild (+ `ix_outbox_kind`); nothing references `outbox`.
2. **Create** `ai_merchant_suggestions` and `llm_cat_queue` (new file `schema/financial_d.drift`):
   - `ai_merchant_suggestions(merchant_norm PK canonical key 2–64 [a-z0-9 ], category_id → categories NULL only for no_answer, confidence INTEGER 0–100, source ∈ llm·cache·catalog, state ∈ unconfirmed·confirmed·corrected·no_answer, created_at, decided_at set iff confirmed/corrected)`. `category_id` keeps the AI's category also when corrected (the correction payload needs it).
   - `llm_cat_queue(merchant_norm PK same key, txn_count ≥ 1, first_queued_at, last_seen_at, attempts ≥ 0, next_attempt_at NULL)`. Times are epoch ms (UTC) like every other table.
3. **DAOs** `AiMerchantSuggestionsDao`, `LlmCatQueueDao` (core/db/daos): typed rows, writes through `guardWrite`, multi-row writes in one transaction; no logging. Queue: upsert (count + last seen), due list in send order (most transactions, then most recent), cap trim (oldest `first_queued_at` first), expiry (60 d), attempt/back-off, remove, clear. Policies (cap 100, 60 days) are parameters; the sender (T-357/358) owns when to call them.
4. **Dart:** `CategorySource.ai('ai')` (app enum); `OutboxKind.llmCatConfirmation = 'llm_cat_confirmation'`, `llmCatCorrection = 'llm_cat_correction'`. The parsing package's `CategorySource` and the recategorizer precedence are T-357's (unchanged here).
5. **Export:** new last column `category_source` (appended, so existing column positions and the preview indices don't move). Value = the stored source code, except `ai` → `user_rule` once the merchant's suggestion is `confirmed` (Right made it a user rule), and `ai_unconfirmed` in every other case (unconfirmed, no row, `no_answer`, and `corrected` while the row still carries the AI category: an AI category is never exported as the user's choice without the user's Right). After T-285 (`pair`, `kind`) the export has 17 columns, `category_source` last. The CSV import (T-154 format) accepts the original 14-column header, T-285's 16-column one and the 17-column one; `category_source` is informational on import (capped, never stored). The service reads the states of the exported `ai` rows' merchants in one query through a small port (`AiSuggestionStates`).
6. **Backup / restore / delete everything:** both tables are FR-BAK-06 **backed-up** tables (`snapshot_tables.dart`): suggestions and the queue are the user's categorisation data, restored like `merchant_rules`. Rows round-trip as stored (the snapshot is the encrypted SQLite file), so an `ai` transaction and its `unconfirmed` suggestion come back unchanged; a v1–v6 backup is migrated on restore by the same step (no AI rows exist yet). The LLM outbox rows stay device-only like every outbox row. "Delete everything" crypto-shreds and deletes the whole database file, so both tables are gone; a test proves the reopened database has both tables empty.

**Collision note for the parallel lane:** v7 is taken from this branch (v6 → v7). The step rebuilds `transactions` and `outbox`; another v7 touching either table must be re-based onto this one as v8.

## Description
Biometric/passcode lock and hidden app switcher.

## Technical details
local_auth; timeout 60 s (A-10); FLAG_SECURE + setRecentsScreenshotEnabled(false) when on; iOS overlay on resign active; root/jailbreak heuristic warning (FR-SEC-07).

## Design note
(Builder note, T-103; the lead asked for a short note in the file first.)
- **Gate, not routes.** `AppLockGate` wraps the whole routed app through `MaterialApp.router(builder:)`. While locked (or while the app is inactive with the lock on) the content stays mounted but `Offstage`, so state and the current route survive and a deep link that arrives while locked (FU-125) lands after unlock. The lock screen (S-05) or a blank cover is drawn over it. This is the only shell hook (`app/lib/main.dart`).
- **State machine** (`AppLockController`): starts locked; the setting off unlocks; lifecycle `hidden`/`paused` records wall and monotonic time, `resumed` re-locks when the larger elapsed time reaches `app_lock.timeout_s` (A-10, default 60 s), when the wall clock moved back, or when the timeout is not readable. `inactive` alone never locks. Lifecycle changes while the OS prompt is up are ignored (the prompt itself pauses the app). One automatic prompt per lock event.
- **Fail closed:** an unreadable lock setting counts as on; an authenticator error is a failed check; no screen lock on the phone keeps the app locked with a message (no bypass); enabling the lock needs a device screen lock and one passed check.
- **Biometric then passcode:** `local_auth` with `biometricOnly: false`, so the OS prompt falls back to the device passcode (A-08).
- **Native (Pigeon `DeviceSecurityHostApi`, no contract widening):** `isDeviceRooted()`, `setSecureWindow(bool)`, `isDeviceSecure()`, all synchronous. Android: `FLAG_SECURE` plus `setRecentsScreenshotEnabled(false)` on API 33+; the last request is kept per process so a re-created activity is secured before its first frame. iOS: `SceneDelegate` puts a solid cover over every window of the scene in `sceneWillResignActive` and removes it in `sceneDidBecomeActive`, only when `setSecureWindow(true)`.
- **Root/jailbreak (FR-SEC-07):** heuristic on paths and build tags (Android) and paths plus a sandbox-write probe (iOS, never on the simulator). It only shows a one-time dialog per process; it never blocks.
- **Residuals:** the window becomes secure only after Dart has read the setting (first frames after the database opens); Android back while locked pops the hidden route stack (nothing is visible); the root/jailbreak checks are easy to bypass; the Face ID prompt text is English only (no localized `InfoPlist.strings` yet).

## Implementation notes

- Native: `DeviceSecurityHost.kt` (+ `MainActivity` now extends `FlutterFragmentActivity`, required by `local_auth`; `LaunchTheme`/`NormalTheme` now inherit `Theme.AppCompat.DayNight.NoActionBar` for Android 8 and below), `DeviceSecurityHost.swift`, `SceneDelegate.swift`, `AppDelegate.swift` registration, `Info.plist` `NSFaceIDUsageDescription`, Xcode project entries for `DeviceApi.g.swift`, the host and its test.
- Pigeon: `DeviceSecurityHostApi` gets its three methods (as already listed in platform-channels section 5); regenerated with the pinned pigeon.
- Dependency: `local_auth ^3.0.2` (adds `USE_BIOMETRIC` through the plugin manifest; no SMS or other restricted permission); dev: `local_auth_platform_interface`, `plugin_platform_interface` for the authenticator test.
- Public API for T-104: `appLockControllerProvider.notifier.enable(reason)` returns `EnableLockResult` (needs a phone screen lock and one passed check, then writes `Settings.appLockEnabled`); `deviceRootedProvider`.
- Tests: `app/test/features/security/` (`app_lock_controller_test.dart`, `app_lock_gate_test.dart`, `local_auth_authenticator_test.dart`, fakes in `security_fakes.dart`; the gate test drives the real Pigeon class through a fake platform on the default messenger), Kotlin `DeviceSecurityHostTest.kt`, Swift `DeviceSecurityTests.swift`.

### AC -> test map
- App switcher blank: gate tests "lock on: cold start hides content ... window secure", "inactive state shows a blank cover"; Kotlin `secureWindowIsAppliedAndRemembered`; Swift `testSecureWindowTogglesTheCover`; device steps below.
- Biometric fail falls back to passcode: `local_auth_authenticator_test` "device passcode is allowed as the fallback"; gate "retry button runs the check again".
- Timeout 60 s (A-10): controller tests "re-locks after the background timeout, not before", "timeout 0", "inactive alone never locks", wall/monotonic tests.
- Deep links pass the lock (FU-125): gate "a deep link while locked lands only after unlock".
- Root heuristic warns, never blocks: gate "rooted device: one warning dialog"; Kotlin and Swift heuristic tests.

### Manual device steps (not run here, no device in the cloud workspace)
1. Android 8, 13 and 15: turn the lock on (T-104 toggle or the test hook), open the recents screen: the Zaghlol card is blank; take a screenshot: blocked.
2. Cold start with lock on: prompt appears at once; fail the fingerprint three times: the OS offers PIN; PIN opens the app.
3. Background for 30 s: returns without prompt; background for 70 s: prompt.
4. Remove the phone screen lock while the app lock is on: the app stays locked with the "set a screen lock" message (no bypass).
5. iOS: lock on, press home, open the app switcher: blank card; Face ID denied: passcode fallback.
6. Rooted emulator image / jailbroken device: one dialog per launch, app keeps working.
7. Open a `zaghlol://review` link (adb / Notes) while locked: lock screen first, Review after unlock.

### Self-check (docs/workflow/self-check.md)
1. Never destroy data: N/A, nothing deletes or resets; a locked or failed state only hides content.
2. Concurrency: one OS check at a time (test "two unlock calls at once"); the UI engine is the only engine with the host registered.
3. Untrusted input: deep-link handling unchanged (T-024); no new external input; errors carry no platform text.
4. Fail closed: unreadable setting = locked; authenticator error = failed; clock moved back = lock; secure-window failure leaves the Dart cover. A real bug found by the tests: `setSecureWindow` failure was an unhandled async error, now caught.
5. Secrets and logs: nothing logged; no keys or credentials stored; Dart never sees the biometric result beyond success/failure.
6. Docs match the code: platform-channels section 5 updated; residuals listed in the design note.
7. Evidence: AC map above; C3, no negative proofs.

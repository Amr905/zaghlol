## Description
One small signed daily call.

## Technical details
- Compose blocks only when changed (`null` otherwise); server-side 24 h throttle; BR-SYNC-04 filters (person names, digits, phones, IPAs, custom categories); `install_hash` HMAC through `IKeyedHasher`; `daily_active_counts` upsert; ≤ 2 KB when up to date; ≤ 50 contributions and ≤ 10 bank requests per call.
- **Signed throttle with echo (R4-2):** a sync inside the window returns **200**, signed, with only `serverTime`, `nextSyncNotBefore` and `timeNonce` (T-123 filter).
- Every sync 200 carries `timeNonce`. The `entitlement`, `accountToken` and `supportNotice` blocks are filled by T-132 through an `ISyncEntitlementBlock` extension point defined here (returns `null` until T-132 lands).
- `entitlementIssuedAt` is accepted and passed to that extension point (T-132 uses it as the R5-7 delivery proof).

## Design note
Written 2026-11-10 by the solution architect (Opus). Sources: backend-api §1, §4.2, §4.8; backend-schema (`installs`, `merchant_contributions`, `bank_requests`, `daily_active_counts`); OpenAPI `sync`; FU-011, FU-048, FU-052 S-2, FU-056; T-127 review minor 1.

### 1. Contract and the BR-SYNC-03 boundary
- **Request** `SyncRequest` (OpenAPI is the truth): `catalogVersion`, `flagsVersion` (required), `pricesAsOf`, `entitlementIssuedAt`, `registryVersion`, `contributions[≤50]`, `bankRequests[≤10]`. Headers: `Zaghlol-App` (platform/appVersion), `Zaghlol-Install`, `Zaghlol-Time-Nonce`, Bearer install token. No `Idempotency-Key` on sync.
- **Closed shape.** The body is read with `StrictJson` into records with `[JsonUnmappedMemberHandling(Disallow)]` at every level (root, contribution, bank request), source-generated, case-sensitive: any extra member is `400 UNKNOWN_FIELD`, a wrong type or range `400 VALIDATION_FAILED`, over 64 KB `413`. Array sizes above 50 / 10 are `400 VALIDATION_FAILED` (the whole call, not truncation: the app never sends more). The DTOs carry no free-text member besides `merchantNorm` and `institutionName`, and nothing numeric besides the three version cursors and `registryVersion`. A contract test reflects over the request types and asserts the member allow-list equals the BR-SYNC-03 list, so adding a field breaks CI.
- **Platform and app version** come from the install row and `Zaghlol-App` (pattern `appVersion` of the schema CHECK; invalid is `400 VALIDATION_FAILED`). The header platform is ignored when it disagrees with the row (counted `zaghlol.sync.requests{outcome=rejected}` only if malformed).
- **Response types live in `Zaghlol.Api`** (T-123 code #10: `IAnchoredResponse` is internal): `SyncResponse` (full) and `SyncThrottledResponse` (`serverTime`, `nextSyncNotBefore`, `timeNonce` only), both implementing `IAnchoredResponse` with `timeNonce` written even when `null`. Two types make "only three members" structural, not a serializer option. In `SyncResponse` an unchanged block is an explicit `null`; `accepted` is always present (`{0,0}` when nothing sent). `UtcTimestamp` converter from FU-013 applies. `rotateInstallToken` is not emitted by sync in T-128 (FU-052 S-3: nothing stores it, and sync is not idempotency-stored; the field stays in the OpenAPI schema only if already there).
- **Block rules** (all pure functions in `Application/Sync`, `SyncComposer`):
  - `catalog`: `null` if `catalogVersion == latest` or nothing is published (latest 0). `mode: full` (with `fullUrl` from `catalog_versions`, `ops: []`) if `catalogVersion == 0`, `> latest` (client ahead of this server), `latest - catalogVersion > 20`, or the delta has more than `Sync:MaxDeltaOps` (default 2000; keeps the body bounded). Else `delta` from `ICatalogReader.DeltaAsync(cv, latest)`. `fromVersion` echoes the request.
  - `flags`: `FlagEvaluator.Snapshot(await IFlagReader.ListAsync, platform, appVersion, installId)`; sent iff `snapshot.Version != flagsVersion` **or** the `Zaghlol-App` version differs from `installs.app_version` before this call (an app update can flip `minAppVersion` without any flag version change; without this clause the update would never see the flag).
  - `prices`: `PriceReadService.GetBlockAsync`; sent iff the block is non-null and `block.asOf != pricesAsOf`. The app derives "stale" from `asOf` age too. T-127 minor 1 is resolved here: `PriceReadService.Build` sets `stale` when the newest **gold** feed time or the newest **FX** time is over 24 h (per kind), and backend-api §4.2 gets that sentence.
  - `entitlement`, `accountToken`, `supportNotice`: from `ISyncEntitlementBlock` (below), `null` until T-132.
- **Extension point** (internal, `Application/Sync`): `ISyncEntitlementBlock.ComposeAsync(SyncEntitlementContext{InstallId, EntitlementIssuedAt, Now}, ct) -> SyncEntitlementResult{Entitlement?, AccountToken?, SupportNotice?}`. T-128 ships `NullSyncEntitlementBlock` (all null). Called after the pre-check passes and **before** the write transaction, outside any transaction of ours: T-132 opens its own short transactions (R5-7 delivery-proof clear, `support_link_notice_iat`). Its side effects must be idempotent, because if the throttle claim then loses a race the response becomes the throttle answer (a repeated notice is harmless; delivery is never proven by it). An exception from it is `503` (nothing of ours written yet).

### 2. Throttle semantics
- State: new nullable `installs.last_sync_at timestamptz` (migration `AddInstallLastSyncAt`; no backfill: `NULL` = never synced). `last_seen_at` is not reused: it drives 12-month retention and other calls may touch it. The window is `Sync:ThrottleWindow`, default 24 h, read through `TimeProvider`.
- **Per install, server clock only.** The device clock is never consulted. Allowed iff `last_sync_at IS NULL OR now >= last_sync_at + window`.
- **Throttled answer** = `200` signed `SyncThrottledResponse{serverTime = now, nextSyncNotBefore = last_sync_at + window, timeNonce = echo}`. Nothing is written (no `last_seen_at`, no DAU, no intake: contributions and bank requests in a throttled call are ignored and stay in the app's outbox), nothing else is composed. The body shape is still validated first (a malformed or `UNKNOWN_FIELD` body is 400 even when throttled).
- Fast path: a cheap `SELECT last_sync_at, app_version, platform` decides throttle before any catalog/flag/price read, so a hammering client costs one indexed read. The **authoritative claim** is the conditional `UPDATE installs SET last_sync_at=@now, last_seen_at=@now, catalog_version=@cv, app_version=@appVersion WHERE id=@id AND deleted_at IS NULL AND (last_sync_at IS NULL OR last_sync_at <= @now - @window)`; zero rows means a concurrent call won (or the install was deleted: re-read; a tombstoned install is `401`), and the response is the throttle answer. Two simultaneous syncs therefore yield exactly one full answer and one DAU increment.
- `nextSyncNotBefore` in a full answer = `now + window`. The window is not shortened for jitter; the app schedules from `nextSyncNotBefore` (FR-SYNC-01 retries after failures are unaffected because failed calls claim nothing).
- Known trade-off (accepted, no PO input needed): if the full 200 is lost on the wire after commit, the retry gets the throttle answer and data arrives at the next window. The app keeps its cursors and outbox until it applies a full answer, so nothing is lost, only delayed ≤ 24 h; contributions re-sent later are deduped by key.

### 3. Composition order and transactions (FU-052 S-2)
**Decision: `/v1/sync` does not use `WithIdempotency`.** Reasons: the OpenAPI operation has no `Idempotency-Key`; the throttle already makes the call safe to repeat (a replay within the window is the throttle answer, a duplicate intake is deduped by unique key); and the idempotency session holds a DB connection and transaction open while the handler opens more (S-2), which for a handler that reads three sources would take 2+ pooled connections per request. Not using it removes S-2 for sync; T-130 must still solve it for purchases.
Pipeline (filters order: `RequireInstallToken` → `WithTimeNonce` → `RequireResponseSignature`; no idempotency filter):
1. Strict-parse body, validate `Zaghlol-App` (no DB).
2. Read the install row + pre-check throttle (1 short query, connection released). Throttled -> signed throttle answer.
3. **Read phase, no transaction, no connection held across awaits other than each query's own**: category-code set, catalog (latest, delta/full), flag list, price block, `ISyncEntitlementBlock`. Each is an independent short query on the pooled connection; no external HTTP is made on this path at all (price provider calls are the worker's, T-127). Per-request peak is 1 connection. Reads are not mutually snapshot-consistent; they need not be (the app applies catalog by version, and flags/prices carry their own versions).
4. **Intake preparation (CPU + KMS, no DB)**: validate/normalize contributions and bank requests (section 4), compute `install_hash` once with `IKeyedHasher` (KMS HMAC; one call per sync).
5. **One short write transaction** (READ COMMITTED): the conditional claim `UPDATE` (above); if it affects a row: `INSERT ... ON CONFLICT DO NOTHING` for contributions and bank requests (multi-row, returning inserted count), and `INSERT ... ON CONFLICT (day, platform, app_version) DO UPDATE SET installs = installs + 1` for `daily_active_counts` (day = UTC date of `now`). Claim, intake and DAU commit together or not at all: no claim without its DAU row, no intake from a call that was throttled. At most one DAU increment per install per UTC day follows from the 24 h window.
6. Build `SyncResponse` (counts in `accepted` = rows actually inserted, i.e. valid and not already present), emit metrics, return. The signing middleware signs the exact bytes (T-123); `ZaghlolMetrics.SyncResponse(bytes, upToDate)` is fed from the serialized length.
Nothing is written before step 5, so every failure in steps 3-4 leaves the throttle unconsumed and the app retries under BR-SYNC-02.

### 4. Intake validation (contributions, bank requests)
- **Order per item**: shape (already strict) → normalize → privacy filter → code checks → dedupe/insert. Violations drop the item silently (counted, never echoed, never logged with content).
- **Normalize**: Unicode NFKC, trim, collapse internal whitespace, invariant lower-case (Latin only; Arabic unchanged), then reject if empty or under 2 chars. Digits are *not* folded in the stored value (the DB CHECK sees the same text the API filtered); the filter folds them itself.
- **Privacy filter**: `ContributionPrivacy.IsAcceptable(normalized)` runs **before any insert** (T-127 note; the CHECK is only a backstop and a CHECK violation would leak row detail into server logs). Covers: > 64 chars, `@` (e-mail / InstaPay address), 6-digit runs in any script with up to 3 separators (phone, card, account). Applied to `merchantNorm` and `institutionName`. Phone numbers, IPAs and card/account digits are thereby dropped (acceptance test). A person name cannot be detected reliably server-side: the residual is covered by the app's own filter, the A-48 threshold (≥ 5 distinct installs) and mandatory operator review (T-129). Say this in `security-model.md` §6, do not claim name detection.
- **Codes**: `institutionCode` must match `^[a-z0-9_]{1,64}$`; `categoryCode` must be in the live catalog's category set (so custom categories are dropped, BR-SYNC-04). A new read-only `ICatalogReader.CategoryCodesAsync` (tiny table) provides it. Bank request: `country` `^[A-Z]{2}$`, `channel` in {sms, notification} (enum), `institutionName` normalized and filtered as above, stored as `institution_name_norm`.
- **Dedupe**: key `(merchant_norm, institution_code, install_hash)` and `(institution_name_norm, country, channel, install_hash)`. Duplicates inside one request are removed first; against stored rows `ON CONFLICT DO NOTHING` (a re-sent or changed category for the same key is ignored; one install gets one vote per merchant/institution). `install_hash = HMAC-SHA256(K_hash, installId)` via `IKeyedHasher` (key distinct from `K_audit` and `K_seat`). If the hasher is unavailable: the intake is dropped, the sync still succeeds, `zaghlol.diag.install_hash_unavailable` increments (existing metric); the app resends next window. Raw install id is never written to these tables.
- **Caps**: 50 / 10 per call (request limit, section 1); plus a per-install lifetime-in-30-days guard is *not* added (the 24 h throttle and unique keys already bound it to 50 rows/day/install); `merchant_contributions` growth is bounded by the 180-day purge.
- Contribution counts/aggregation into `contribution_aggregates` are T-129 (worker); T-128 only inserts raw rows.

### 5. Failure modes
| Source | Failure | Result |
|--|--|--|
| Install row / DB write | down, timeout | `503 UPSTREAM_UNAVAILABLE`, nothing consumed |
| Catalog (reader, version row) | exception, missing `catalog_versions` row for latest | `503` whole call (a `null` catalog would read as "up to date" and then burn the window) |
| Flags | read error | `503`. A flag whose stored rules fail strict parse is **OFF** for everyone (fail closed), not a failure (FU-056 below) |
| Prices | read error | **degrade**: `prices: null`, metric `block_failure{block=prices}`; prices are advisory and the app tolerates stale; empty cache is `null` too |
| Entitlement extension | exception | `503` |
| KMS signing | down | existing T-123 behaviour (`503`, unsigned body never sent) |
| KMS hasher | down | intake dropped, sync succeeds (above) |
No partial answer ever hides a failed catalog/flags/entitlement read as `null`. `Retry-After: 30` on `503`.

### 7. Observability and logging
- Metrics (fixed tag sets, no install id, no merchant/institution text): `zaghlol.sync.requests{outcome=ok|throttled|rejected}` (counter), `zaghlol.sync.response.size` (existing; `upToDate` = all of catalog/flags/prices/entitlement null), `zaghlol.sync.catalog{mode=none|delta|full}`, `zaghlol.sync.intake{kind=contribution|bank_request, result=accepted|filtered|invalid_code|duplicate|dropped_hasher}`, `zaghlol.sync.block_failure{block=catalog|flags|prices|entitlement}`, `zaghlol.sync.flag_rules_invalid{flag}`. `SeedSeries()` is extended so all series exist at 0 (dashboard alerts on absent series).
- Logging: structured, fixed event codes only (`SYNC_THROTTLED` at Debug, `SYNC_BLOCK_FAILED{block}`, `SYNC_FLAG_RULES_INVALID{flag}`). Never log: request body, contributions, bank request text, `Zaghlol-Time-Nonce`, install token, install hash, `entitlementIssuedAt`. The installId appears only as the existing pseudonymized log key. Exception logging for the intake path uses the exception type only. A test asserts a captured log of a sync with a phone-number contribution contains neither the number nor the merchant text.

### 8. Threats
| Threat | Control |
|--|--|
| Client smuggles financial data in extra fields | closed DTOs, `UNKNOWN_FIELD`, member allow-list contract test |
| Phone / card / e-mail / IPA in free text | filter before insert (not the CHECK), NFKC + digit folding; CHECK as backstop |
| Poisoning a merchant's category by one install | unique key per install, ≥ 5 distinct installs, operator review (T-129) |
| Hammering with a wrong clock | server-side window, cheap fast path, per-token/network rate limits already in the pipeline |
| Throttle answer replayed to another install to re-anchor trusted time | echo of the caller's own nonce inside the signed body; test with install B's nonce |
| Joining contributions to an install | HMAC with KMS pepper; raw id never stored; no timestamps finer than the row's `received_at` |
| Race giving two full answers / two DAU | conditional UPDATE claim in the same transaction as DAU |
| Large delta or full URL as amplification | `MaxDeltaOps`, full = URL only (CDN), 64 KB request cap |
| Log/trace leakage | section 7 rules |

### 10. Rejected alternatives
- *Use `WithIdempotency` for sync*: reintroduces S-2 and a stored encrypted body per daily call for no gain; the throttle is the idempotency mechanism.
- *Claim the throttle first, then compose*: a transient catalog/flag failure would burn 24 h. Claiming last with a conditional UPDATE costs only wasted reads on a lost race.
- *One transaction around reads and writes*: holds a connection across upstream-style reads and widens lock time; reads are independent.
- *Reuse `last_seen_at` for the throttle*: couples retention to throttle semantics.
- *Reject (400) a whole call for one bad contribution*: contradicts "silently drops"; and would let a single odd merchant string block a catalog update.
- *Always send `flags` and `prices`*: breaks the 2 KB up-to-date budget.

## Description
Accept up to 50 closed `llmCatFeedback` items only while the install's `llm_categorise` flag is on; re-check each with `ContributionPrivacy` and the category codes (`userCategory` may be `custom`); store `right` as confirmations and `wrong` as corrections with `install_hash` = the existing KMS-peppered contribution HMAC; duplicates per (merchant, install_hash) keep the first; `accepted.llmCatFeedback` = stored rows. ≥ 3 distinct-install corrections whose `ai_category` equals the cache row delete that cache row. Retention: confirmations 365 days or when resolved; corrections 90 days after `resolved_at` or 180 days after creation.

## Acceptance criteria
1. Right on «zawya coffee / dining» → one confirmation row with install hash; Wrong groceries → education → one open correction; `custom` stored as `custom` with no custom name anywhere.
2. Flag off → items ignored, `accepted.llmCatFeedback = 0`; invalid items dropped individually.
3. Three corrections from different installs delete the matching cache row; two do not.
4. **Negative proof 1:** after intake, a dump of both tables contains no install id, account id, IP or app version bytes (data check with marker ids).
5. **Negative proof 2:** a marker merchant in feedback is absent from logs, traces and metrics.
6. Purger tests for each retention rule.

## Design note (builder, C4)
- **Identity (llm-categorise §4 exactly):** a feedback row carries `install_hash` only: the existing KMS-peppered HMAC of the install id, the same value `merchant_contributions` already holds. No install id, account id, IP, app version or token. `created_at` is cut to the UTC day (less than the spec's `timestamptz`, no time that can be matched to one sync).
- **Independence:** distinct `install_hash` values; the unique key `(merchant_norm, install_hash)` makes it one row per install per merchant and verdict, so one install reaches 1 of the 3 however often it resends. T-354 counts rows per `(merchant_norm, category)`.
- **Where:** pure rules in `Application/Llm/Categorise/Feedback/CategoriseFeedbackIntake` (name filter reused from T-352, closed system codes + `custom`, verdict agreement, dedupe, cap 50), the flag gate in `SyncService` (the install's own evaluated `llm_categorise`), inserts and the contradiction delete inside the sync's claim transaction (`SyncStore`), so a lost claim or failure writes nothing and a retry adds nothing.
- **Cache contradiction:** after the insert, delete cache rows of the call's corrected merchants whose `category_code` equals the `ai_category` of at least 3 non-`rejected` corrections; merchants are advisory-locked in sorted order first so two simultaneous third corrections both see each other.
- **Confirmations:** stay `collecting`; the 3-confirmation operator review is a count in T-354 (never automatic). Nothing to do at intake.
- **Never logged:** telemetry kinds `llm_cat_confirmation` / `llm_cat_correction` with the existing fixed result tags; no name anywhere else.

### What is stored per feedback row (for the PO, FU-412)
- Confirmation: random id, `merchant_norm`, `category_code` (the AI's, which the user kept), `source` (`llm|cache|catalog`), `install_hash`, `created_at` (UTC day), `status = collecting`.
- Correction: random id, `merchant_norm`, `ai_category`, `user_category` (a system code or the literal `custom`; no custom name), `source`, `install_hash`, `created_at` (UTC day), `status = open`, `operator_id`/`resolved_at` empty until T-354.
- Residual: the same hash links one install's contributions, confirmations and corrections to each other (not to the install); the merchant name travels in the same request as the install token (FU-412 wording still open).

## Fix round (batch 97, B97-M1 / FU-439)
- **Attestation evidence:** a sync's feedback block (both tables and the contradiction delete) is stored only when the install has an `llm_quota_counters` row (`cat`, `install`, `used > 0`) for the current or previous Cairo month. Others are dropped silently (accepted 0). Residual: install-level, not per merchant (follow-up FU-446).
- **Repeat protection:** the delete counts only corrections created after the cache row's `created_at`.
- **FU-439:** cache writes only from a one-name prompt; a row is served only at `cat.cache_min_confidence`; the catalog is checked first.

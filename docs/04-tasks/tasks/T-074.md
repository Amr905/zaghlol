## Implementation notes

Files: `app/lib/features/categorization/domain/merchant_rule.dart` (entities, `RulesRepository`, `RulesException`), `.../data/rules_repository.dart` (`DriftRulesRepository`), `.../data/rules_providers.dart`, new methods on `MerchantRulesDao` (`byId`, `setCategory`, `countPastMatches`, `pastMatchIds`, `applyToPast`); test `app/test/features/categorization/data/rules_repository_test.dart` (16 tests x 2 executors = 32, all green). No schema or migration change.

Behaviour:
- `save` validates the value per kind (same rules as the table CHECKs), refuses unknown or archived categories, upserts in place. It never changes past rows (A-13).
- `countPastMatches` / `pastMatchIds` give the count and the list the user picks from; `applyToPast(id, transactionIds:)` changes only the chosen ids that still qualify. Null = every qualifying match; an empty set = nothing. Cap 1000 ids.
- A row qualifies only if live, not internal, not user-verified, `category_source` in none/catalog/heuristic, matching the rule key and not already in the rule's category. `user` and `user_rule` rows are never touched.
- `match()` is the lookup T-075 calls first: any rule beats the catalog; among rules counterparty, then `merchant_norm`, then catalog merchant.
- Delete leaves already-applied categories in place.

Deviations / decisions:
- apply-to-past is one conditional UPDATE that re-checks every guard in SQL (rule, category archive flag, eligibility), not select-then-update, so an edit committed by another connection in between is never overwritten. It is not wrapped in a drift transaction: in the two-connection test `BEGIN IMMEDIATE` from the second connection failed at once with SQLITE_BUSY (busy_timeout not applied), whereas a lone write statement waits. The `last_applied_at` stamp is a second statement; a crash between them loses only the stamp. FU candidate: any future multi-statement transaction across two engines hits the same BUSY (owner: T-017 DAO layer / whoever adds a retry helper).
- `user_rule` rows are left alone even when the rule is re-pointed (they may come from another rule; doubt means no change). So editing a rule's category affects future transactions and rows still uncategorized/catalog/heuristic, not rows the rule itself categorized earlier.
- The domain enum `RuleMatchKind` shares its name with the DAO's string constants class; imports use `show`.

Open questions: (1) precedence among rule kinds (counterparty > merchant_norm > catalog) is my choice, not in the spec. (2) Should re-pointing a rule re-categorize rows it applied earlier? Needs a per-row rule id to be safe; not in the schema.

## Description
The single path from raw message to stored transaction.

## Technical details
Guard re-check; parse; body-hash dedupe; cross-channel ±2 min dedupe; pending/settled merge (A-63); account resolve; categorize hook (interface, rule/none until categorizer lands); persist txn + raw message in one transaction; return ids to ack; review items for low confidence/unrecognized; emit events. Idempotent.

**1. Shape.** `app/lib/features/ingestion/{domain,application,data}`. `IngestRawMessages.call(List<IncomingMessage> batch) → Future<IngestBatchResult>`; it throws `IngestBatchFailed(code)` (a `SafeException`) when the batch transaction did not commit. `IncomingMessage{deliveryId, channel (raw_messages wire), source, body, receivedAtMs, simSlot?, origin}` with `origin ∈ {spool, inboxScan}` (background) and `userConfirmed` (share/paste/OCR after the user's confirmation; §11). `IngestBatchResult{outcomes: Map<deliveryId, IngestOutcome>, ackable: List<deliveryId>, changedTxnIds, changedAccountIds, createdAccountIds}`. `IngestOutcome` is sealed: `inserted(txnId)`, `mergedCrossChannel(txnId)`, `mergedPending(txnId)`, `duplicate`, `dropped(reason)`, `review(rawId, kind)`, `balanceOnly(rawId)`, `deferred(rawId)` (event without a handler, §6). No outcome or exception carries a body, sender, last-4, merchant or amount. The domain part (keys, mapping table, merge decisions, §4-§7) is pure Dart with no Flutter or drift import. Injected ports: `Clock`, `IdGenerator` (T-050), `LocalZone.offsetAt(wallClock)` (EC-10; tests pin it), `GuardConfigSource` (base bytes from the bundled asset, T-036; a test base before then), `Categorizer` (§8), `CycleKeyOf` (§10), `PostPersistHook`s (empty in T-046; T-089 pairing/FX/card settlement, refund matching and suggestions plug in here), `DiagSink` (codes and counts only). The spike `IngestStore.commit` + `raw_message_mapper` are replaced by this use case inside the existing `IngestionCycle`; the drain → parse → commit → ack order stays.

**2. Pipeline order.** *Before the transaction* (pure, may run on a worker isolate; never on the DB): (a) parse with `ParsingPipeline.parse` (never throws; a thrown `Object` is `ParseUnrecognized(internalError)`); (b) compute `body_hash` (§3), the dedupe key, `merchant_norm` and the candidate fields. *Inside one write transaction per batch* (drift `transaction` = `BEGIN IMMEDIATE`, FU-094): (0) once per batch, read `ignore_rules`, `capture_senders` (always-capture) and build the Dart Guard (§9); then per message, inside its own nested transaction (a SAVEPOINT; drift ≥ 2.0 reverts a failed inner transaction and lets the outer one continue): (1) Guard re-check (background origins only) → `dropped`; (2) `ParseDropped` → `dropped`; (3) dedupe 1: `hashExists` → `duplicate`; (4) disposition by result (§6); (5) build the candidate transaction (§6 table); (6) dedupe 2 cross-channel (§4); (7) pending/settled merge (§5); (8) account resolve (T-045 `resolve`, kind from `inferAccountKind(eventWire, isAvailableLimit, hasLast4)`, label = registry institution name in the app language, currency = amount currency); (9) categorize (§8); (10) insert the raw row (`insertIfNew`; `false` here is a race loser → roll back the savepoint, `duplicate`) and the transaction (FTS by triggers); (11) balance: T-045 `recordBalance(balance, available, asOf: occurred_at, sourceTxnId)` (newest wins, never summed or converted); (12) review items (§7); (13) post-persist hooks. Commit, **then** emit events (§10), **then** return; the caller acks `ackable`.

**3. Idempotency keys.** *`body_hash`* = lowercase hex `SHA-256("zg.raw.v1" ‖ 0x00 ‖ senderKey ‖ 0x00 ‖ hashNorm(body))`; `senderKey` = `guardSourceKey(channel, source)` (folded SMS id, trimmed package); `hashNorm` is a **frozen** function in `features/ingestion/domain/` (Arabic-Indic and extended digits → ASCII, `٫`/`٬` → `.`/`,`, the platform-channels §1.2 invisible marks removed, every whitespace run → one space, trim; no case or letter folding) with golden vectors; it never calls the evolving parser normalizers, so a parser change can't make an inbox re-scan (FR-CAP-07, T-048) miss old rows. Changing it needs a migration that re-hashes `raw_messages` **[doc change: database-schema §2.2]**. The receive time is **not** in the hash (re-delivery and inbox copies must collide; EC-02 identical bodies: PO Q2). *`dedupe_key`* = `d1|<institution>|<direction>|<currency>|<amount_minor>` built from `Money.toStorage()` (T-012 F5), never from the message text; no last-4 (compared in code, §4) and no time bucket (the window is a range query on `ix_txn_dedupe(dedupe_key, occurred_at)`) **[doc change: database-schema §2.2]**. NULL for transactions without an institution (manual, voice, generic).

**4. Dedupe 2 (cross-channel, BR-ING-02 rule 2, A-30, EC-01).** Candidates: same `dedupe_key`, `occurred_at` within ±24 h (fetch bound), different `source` from the new message's mapped source, same status class (`declined` matches only `declined`; `pending`/`posted` match each other), **soft-deleted included** (a deleted payment is not resurrected by its second copy; it stays deleted), then filtered in code by time: `|Δ minute(occurred_at)| ≤ 2` **or** `|Δ raw received_at| ≤ 2 min` (both raws on the phone clock, so a wrong phone clock or a bank time stamp can't split a pair, EC-10); and by last-4: equal, or one side NULL (PO Q1, provisional). Exactly one candidate → attach (§5 merge), outcome `mergedCrossChannel`; the new raw row is stored `parsed` (its hash absorbs re-delivery; T-076 re-parse of it re-runs dedupe 2). More than one → insert the new transaction and a `low_confidence` review item with `payload {reason: "possibleDuplicate", candidateTxnIds}` (the schema has no `possible_duplicate` kind; Lead question L1) **[doc change: domain-algorithms §3]**. Same source with a different body → never merged (EC-02).

**5. Merge rules.** *Cross-channel attach* into the existing T0: amount and currency equal by construction; fill only NULL fields of T0 (`original_*`, `merchant_raw`/`merchant_norm`, `counterparty_*`, `reference_no`, `balance_after_minor`), never overwrite a value; T0's `occurred_at`, `source`, `template_id` and category stay; if T0's account has no last-4 and the new message has one, move T0 to the card account (T-045 resolve); if T0 had `category_source = 'none'` and gained a merchant, re-run §8. `parse_confidence` = max. A user-verified T0 (`is_user_verified = 1`) is never modified (attach only). The new message's balance goes through `recordBalance` either way. *Pending/settled (A-63, EC-54)*: P = a `pending` transaction of the same institution, last-4 rule of §4, same currency, `merchant_norm` equal when both have one (a `settled` event without merchant matches on the rest), `|a − p| × 100 ≤ 5 × p` (integers), occurred within 7 days before. Several → smallest `|a − p|`, then oldest. Merge: P gets the settled amount, `original_*` if given, status `posted`, NULL fields filled; the settled raw row is stored `parsed`. A user-verified P only changes status, and a differing amount adds a `low_confidence` item (`settledAmountDiffers`). **Symmetric**: a `pending_auth` arriving after a matching posted/settled transaction (7 days after it at most) is attached to it, no new row, so arrival order does not matter **[doc change: domain-algorithms §3]**.

**6. Dispositions and the event mapping.** `ParseUnrecognized` → raw `review` + `unrecognized` item. `ParseGeneric` → every one goes through `genericDisposition(confirmedCount, alwaysCapture)` from the `capture_senders` row keyed by `senderKey` (FU-080); `review` → raw `review` + `new_sender` item with the suggested fields; `autoSaveLowConfidence` (and only with a direction) → transaction + `low_confidence` item (`generic: true`), account per PO Q3. T-046 **never** changes `confirmed_count` (A-66: only the user's confirmation, T-049). `ParseParsed` → the table below (template `direction` decides `transfer_out`/`transfer_in` for transfer-like events) **[doc change: parsing-engine §6]**:

| Event | Direction | Status |
|---|---|---|
| `card_purchase`, `card_purchase_fx`, `atm_withdrawal`, `bnpl_installment` | expense | posted |
| `pending_auth` / `settled` | expense | pending / posted (§5) |
| `declined` | expense | declined (BR-TXN-03) |
| `transfer_out/in`, `instapay_out/in`, `cc_payment`, `wallet_topup` | transfer_out / transfer_in | posted |
| `salary` · `refund`, `reversal` · `fee` | income · refund · fee | posted |
| `balance_only` | no transaction; raw `parsed` + balance | — |
| `fx_conversion` (handler: T-089) | none yet: raw `reparse_pending`, outcome `deferred` | — |

Any event without a registered handler is `deferred` the same way; T-076 re-runs `reparse_pending` rows **[doc change: T-076]**. FU-078 is taken here: the number parser accepts one leading `-` or `−` in `balance`/`available` captures only (never `amount`), giving a negative `Money` with an informational reason (factor 1000); the implementer updates parsing-engine "Not handled yet" as built.

**7. Review items.** Payload JSON never holds the body, sender or a raw-message excerpt (ids, reason codes, confidence, suggested typed fields only). `low_confidence` for `needsReview` (raw + txn ids, `confidencePermille`, `reasons`), generic auto-save, possible duplicate, settled-amount difference; `unrecognized`, `new_sender` as §6. No `needs_category` items: "needs classification" is `category_source = 'none'` (T-075/T-078).

**8. Categorize hook.** `Categorizer.categorize(CategorizeInput{merchantNorm, counterparty, institution, direction}) → {categoryId?, source, catalogMerchantId?}`, called inside the transaction (so a rule committed by the UI before our `BEGIN` is applied). T-046 ships `RulesOnlyCategorizer` over the T-074 rules (counterparty → merchant_norm → catalog merchant), else `none`. T-075 replaces it and must keep its in-transaction part ≤ 5 ms per message (catalog/fuzzy work can be computed before the transaction).

**9. Guard re-check (BR-CAP-01; T-035 Q1 fallback relies on it).** `CaptureGuard` built from the base asset plus a user part made by `buildGuardUserConfig` from the DB rows read in step 0, so it never depends on the native encrypted user file (a corrupt one, Q1 `baseOnly`, is covered). No rate limiter at drain. If the user part fails to build (caps), use base-only and check `CaptureControlsDao.isIgnored(inst, last4, ignoreChannel)` for each registry keep. An invalid **base** at drain is not "drop everything": the batch stops before the transaction with `IngestBatchFailed(CONFIG_INVALID)`, nothing acked (a build defect must not delete captured messages) **[doc change: platform-channels §1.2]**. `userConfirmed` inputs skip the Guard (user intent; platform-channels §2.1).

**10. Transactions, ack and crash safety.** One write transaction per batch (≤ `kDrainBatchSize` 20); per message a savepoint. A `DbWriteException` with a constraint/trigger code, `AccountsException` or a money error inside a message → roll back its savepoint, store the raw row alone as `review` + `unrecognized` (`payload.reason = "ingestFailed"`, code only); if that fails too, or on any `DB_WRITE_FAILED` (busy, I/O, full), the whole batch rolls back → `IngestBatchFailed`, nothing acked, cycle `retry`. `ackable` = every message of a committed batch (stored, merged, duplicate, dropped, deferred). Crash or kill before commit → SQLite rolls back → re-delivery is processed fresh → one transaction; crash after commit, before ack → re-delivery hits `body_hash` → `duplicate` → acked. Two engines (UI + headless, FU-094): all dedupe and merge reads are inside the `BEGIN IMMEDIATE` transaction, so writers serialize; `ux_raw_body_hash` and `ux_accounts_inst_last4` stay the backstops. *Stuck entry*: the cycle keeps the delivery ids it has seen; when a drain returns only seen ids (an entry that failed in every batch), it ends with `ok` and a `stuck` count, and T-041 does not re-enqueue for stuck-only **[doc change: platform-channels §2]**. *Events*: after commit only, one `TransactionsChanged(accountIds, cycleKeys)` per batch when anything changed (sets unmodifiable, names per FU-037; cycle key from `CycleKeyOf`, default `cycleFor` with the stored payday, A-43). Nothing on failure. Budget alerts and mascot triggers are produced by their engines reacting to it (§6 Events row **[doc change: parsing-engine §6]**). The UI engine sees headless writes only by re-querying on attach/resume (T-047).

**11. Other origins.** `inboxScan` (T-048) = `spool` minus the ack. `userConfirmed` stores the transaction `is_user_verified = 1` and never auto-merges: if dedupe 2 finds candidates, the call returns `possibleDuplicate(candidateIds)` without writing, so the confirming screen asks. T-076 re-parse uses a `reparse(rawId)` entry that skips the Guard and dedupe 1 and never modifies user-verified transactions (its own note).

**12. Privacy.** Nothing logs or prints; `DiagSink` gets codes and counts only (`ING_DROP_<REASON>`, `ING_DUP_HASH`, `ING_MERGE_XCH`, `ING_MERGE_PENDING`, `ING_MSG_FAILED`), never ids (ULIDs encode receive times, FU-086 I-2). OTPs: the Guard and stage 0 drop them before any write (no raw row, review item, FTS row or diag field); kept-OTP shapes are the ADR-005 residuals. Bodies live only in `raw_messages.body` (encrypted DB).

**13. Performance (headless 50 s cycle, FR-ING-A-01).** Parse ≤ 10 ms per message, outside the transaction. Write transaction ≤ 250 ms p95 per 20-message batch on the reference device (dedupe 2 by `ix_txn_dedupe`; pending by `ix_txn_account_time` over pending rows), so a UI write waits well under the 5 s busy budget. No batch starts with less than 5 s of `kCycleBudget` left (the native 55 s drain bound is never hit mid-transaction, FU-093 N4). Host benchmark (tag `benchmark`): 500 messages into an encrypted DB with 20k transactions in ≤ 10 s; device numbers go to T-173.

**14. Tests** (encrypted DB as T-045/T-050, fakes for ports). ACs: same SMS twice (one batch and two batches) → one transaction; SMS + notification of one payment, both orders, notification without last-4, phone clock 3 h off → one; crash: throw at each step before commit, then re-deliver → one; commit then ack failure → re-delivery `duplicate`. Rules: every row of the §6 table; pending→settled and settled→pending; ±5 % boundaries (5 % merges, 5.01 % does not); several candidates; declined vs posted never merged; soft-deleted target stays deleted; user-verified never modified; generic `review` vs auto-save, `confirmed_count` unchanged; ignore rule added after spooling → nothing stored (FR-CAP-02 inspection over `raw_messages`, `review_items`, `transactions`, FTS, diag); native user part corrupt → re-check still drops; base invalid → nothing acked; negative balance stored. **Property test**: 200 fixed seeds; synthetic scenarios (1-3 messages per payment: SMS, notification, pending/settled, exact duplicates) shuffled, randomly duplicated, split into random batches with random pre-commit failures → the projection (account, direction, status, amount, currency, count) equals the expected set. **Two connections** (separate isolates, as `busy_wait_test`): SMS on A and notification on B, 50 rounds with random delays → one transaction each; the same body via spool (A) and inbox scan (B) → one raw row; B holds the lock 6 s → A's batch `IngestBatchFailed`, nothing acked, next cycle succeeds; isolate killed inside a held transaction → reopen, re-deliver, one transaction. **Privacy**: canary body `ZG_CANARY_7731` through every outcome under a print-capturing zone → no hit in output, exceptions, results, review payloads, diag. **Negative proofs** (patch, see red, revert): dedupe 1 skipped; dedupe 2 read moved before `BEGIN` (two-connection test with a test barrier); ack before commit; Guard re-check removed; last-4 wildcard off (notification test); symmetric pending rule off (property test); `confirmed_count` incremented.

**Rejected.** One transaction per message (20× commits and fsyncs; lock churn against the UI) and one transaction for the whole drain (lock held for seconds, one failure loses all progress). Dedupe in the spool (fingerprint leak; T-008). Dedupe reads outside the write transaction (cross-connection race). Receive time in `body_hash` (re-delivery and inbox copies would no longer collide). Applying the Guard rate limiter at drain (would drop a legitimate backlog). Auto-merging user-confirmed input. A new `possible_duplicate` kind via a v5 migration inside this task (Lead L1).

Deviations / decisions beyond the note:
- A soft-deleted cross-channel target is attach-only like a user-verified one (no field filled, no account move, no event), so a deleted payment stays exactly as the user left it; its balance is still recorded.
- A transfer-like template without a direction (`neutral`) goes to review (`unrecognized`, `reason: directionUnknown`) rather than guessing.
- A non-transient batch failure (`CONFIG_INVALID`, `INGEST_MSG_UNSTORABLE`, `INGEST_INTERNAL`) lets the cycle keep draining; those entries come back as stuck and the cycle ends `OK` with the code. Transient (`DB_WRITE_FAILED`/`DB_READ_FAILED`) ends the cycle `RETRY` at once.
- The categorizer is a port (`Categorizer`); `RulesOnlyCategorizer` (T-074 rules) ships here. T-075's branch was **not** merged; T-075 wires its categorizer into `buildIngestRawMessages(categorizer:)`.
- The Guard base comes from `RegistryGuardBase` (export of the loaded registry) until T-036's asset.

Residuals / follow-up proposals:
- FU (owner suggestion T-089): pending SMS merged with a settled **notification**, then the settled SMS arrives → two transactions (the SMS shares the pending row's source, so dedupe 2 skips it, and no pending row is left).
- An inbox copy whose receive time differs from the original by more than the window, arriving first, is stored as its own transaction.
- Generic eligibility in the parser does not read `capture_senders`: an always-capture sender outside `generic.alwaysCapture`/hints stays `unknownSource` (review) until the registry or T-049 adds it.
- Negative proof for "dedupe 1 skipped" shows red only in the one-batch test (diag count): the `ux_raw_body_hash` backstop still turns the copy into `duplicate` (by design, two layers).

## Self-check (docs/workflow/self-check.md)
1. Never destroy data on doubt: applies. Nothing in the use case deletes; an invalid Guard base fails the batch before the transaction (`CONFIG_INVALID`, nothing acked, entries stay in the spool); non-transient failures leave entries in the spool as stuck, never dropped; merges only fill NULL fields, never overwrite; user-verified and soft-deleted targets are attach-only. Tests: "an invalid Guard base…", "a user-verified target is never modified", "a soft-deleted target…", cycle "stuck" tests.
2. Concurrency: applies. All dedupe/merge reads inside `BEGIN IMMEDIATE`; per-message savepoints; `ux_raw_body_hash` backstop (`ING_DUP_RACE`). Two-connection tests: 50 rounds, barrier race, spool vs inbox scan, lock holder past busy timeout, killed isolate.
3. Untrusted input: applies. Batch cap 100 (`INGEST_BATCH_TOO_LARGE`); spool bodies are capped at 4,000 chars by the strict spool decode (platform-channels §1.3), and the parser does not parse longer text (`maxParseBodyLength`, → review); the use case itself does not cap `userConfirmed` bodies, so T-049/T-076 callers must (residual); Arabic-Indic/extended digits and invisible marks normalized in `hashNorm` (golden vectors); errors are codes only.
4. Fail closed: applies. Invalid Guard base → nothing stored, nothing acked; user part unbuildable → base Guard plus per-message DB ignore check; unknown channel → dropped; unknown error → whole batch rolls back (`INGEST_INTERNAL`).
5. Secrets and logs: applies. Nothing logs; outcomes/exceptions/`toString`s carry kinds/codes; diag gets fixed codes and counts only; review payloads hold ids, reason codes, confidence and typed amounts only. Canary test `ZG_CANARY_7731` under a print-capturing zone; app-ci grep extended.

## Review follow-ups (added by Lead)
- From the T-012 security review F5: build dedup and fingerprint keys from `Money.toStorage()` (minor + currency code), never from the source amount text. The parser normalises `01.50`, `1.5` and `-0`.

## Description
Native device attestation for restore, bound to the exact 32-byte hash Dart computes, and a release network configuration that keeps user-installed CAs out of the restore path on Android.

## Technical details
- Pigeon contract exactly as platform-channels §4a: `prepare()`, `attest(Uint8List hash32, bool forceNewKey) → AttestationProof {type, token?, keyId?, assertion?, attestationObject?}`.
- **Android:** `com.google.android.play:integrity` **standard request**; `StandardIntegrityManager.prepareIntegrityToken` with the cloud project number from build config, provider cached; `request(requestHash = base64url(hash32))`. Error mapping: `NETWORK_ERROR`, `TOO_MANY_REQUESTS`, `GOOGLE_SERVER_UNAVAILABLE` → `ATTEST_TRANSIENT`; `INTEGRITY_TOKEN_PROVIDER_INVALID` → re-prepare once, then `ATTEST_TRANSIENT`; outdated Play services → `ATTEST_PLAY_SERVICES_OUTDATED`; others → `ATTEST_UNAVAILABLE`.
- **iOS:** `DCAppAttestService`; `isSupported == false` → `ATTEST_UNAVAILABLE`. **One install-bound key:** generated lazily on first use; `keyId` in the Keychain with `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`, not synchronizable. `generateAssertion(keyId, clientDataHash = hash32)`. On `forceNewKey` or an `invalidKey` error: delete the stored `keyId`, generate a new key, `attestKey(keyId, clientDataHash: hash32)` with the **same** hash as the assertion, and return `attestationObject` too. `serverUnavailable` → `ATTEST_TRANSIENT`.
- **Install binding (R2-1, R4-1(3)):** native code never builds or alters the hash and never sees the install ID; on iOS the 32 bytes Dart passes are the restore `clientDataHash` that already covers the seat public keys (computed in T-183/T-145).
- **Release network config (ADR-012 (d)):** `network_security_config.xml` with `<base-config cleartextTrafficPermitted="false">` trusting `<certificates src="system"/>` only; user CAs only under `<debug-overrides>`; referenced from the main manifest.
- No device identifiers collected; no verdict on the device; proofs never written to the diag log.

## Acceptance criteria
- [ ] Pigeon contract matches platform-channels §4a; the stale-generation check (T-004) passes.
- [ ] R2-1: unit tests (Android Robolectric / iOS XCTest with a mocked service) show the hash passed to `request` / `generateAssertion` / `attestKey` is byte-identical to the Dart input; on iOS `attestKey` and `generateAssertion` receive the same hash.
- [ ] iOS: `forceNewKey = true` and an `invalidKey` error both replace the stored `keyId` and return an `attestationObject`; the Keychain item has `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly` and `kSecAttrSynchronizable = false` (XCTest reads the item attributes).
- [ ] Error mapping table above covered by tests on both platforms.
- [ ] Device test (real hardware, recorded in `docs/05-reviews/T-178-device.md`): an Android token for a test hash decodes server-side (T-181 fake or Google decode) with `requestHash` equal to the input; an iOS assertion for a test hash verifies with T-181's verifier.
- [ ] Release network config: on a release build with a user-installed CA, an HTTPS call to the staging API through that CA's proxy fails; on a debug build it succeeds (device test, recorded).
- [ ] No proof, token or key ID is written to logs (log-capture test).
- [ ] DoD (CLAUDE.md §7): analyze clean, formatted, tests added, no hard-coded strings, RTL verified where UI, no `double` money, no raw SMS in logs.

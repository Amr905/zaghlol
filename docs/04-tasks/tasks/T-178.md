## Description
Native device attestation for restore, bound to the exact 32-byte hash Dart computes, and a release network configuration that keeps user-installed CAs out of the restore path on Android.

## Technical details
- Pigeon contract exactly as platform-channels §4a: `prepare()`, `attest(Uint8List hash32, bool forceNewKey) → AttestationProof {type, token?, keyId?, assertion?, attestationObject?}`.
- **Android:** `com.google.android.play:integrity` **standard request**; `StandardIntegrityManager.prepareIntegrityToken` with the cloud project number from build config, provider cached; `request(requestHash = base64url(hash32))`. Error mapping: `NETWORK_ERROR`, `TOO_MANY_REQUESTS`, `GOOGLE_SERVER_UNAVAILABLE` → `ATTEST_TRANSIENT`; `INTEGRITY_TOKEN_PROVIDER_INVALID` → re-prepare once, then `ATTEST_TRANSIENT`; outdated Play services → `ATTEST_PLAY_SERVICES_OUTDATED`; others → `ATTEST_UNAVAILABLE`.
- **iOS:** `DCAppAttestService`; `isSupported == false` → `ATTEST_UNAVAILABLE`. **One install-bound key:** generated lazily on first use; `keyId` in the Keychain with `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`, not synchronizable. `generateAssertion(keyId, clientDataHash = hash32)`. On `forceNewKey` or an `invalidKey` error: delete the stored `keyId`, generate a new key, `attestKey(keyId, clientDataHash: hash32)` with the **same** hash as the assertion, and return `attestationObject` too. `serverUnavailable` → `ATTEST_TRANSIENT`.
- **Install binding (R2-1, R4-1(3)):** native code never builds or alters the hash and never sees the install ID; on iOS the 32 bytes Dart passes are the restore `clientDataHash` that already covers the seat public keys (computed in T-183/T-145).
- **Release network config (ADR-012 (d)):** `network_security_config.xml` with `<base-config cleartextTrafficPermitted="false">` trusting `<certificates src="system"/>` only; user CAs only under `<debug-overrides>`; referenced from the main manifest.
- No device identifiers collected; no verdict on the device; proofs never written to the diag log.

## Design note
(Opus, 2026-11-13, written by the implementer as the C4 keys note.)

1. **Seams.** Each platform splits a thin SDK adapter from a testable core. Android: `IntegrityGateway` (`prepare(cloudProjectNumber)`, `request(requestHash)`; failures carry the `StandardIntegrityErrorCode` int or null) with `PlayIntegrityGateway` as the only file that touches the Play SDK; `AttestationHost` holds the logic. iOS: `AppAttestService` (wraps `DCAppAttestService.shared`) and `AttestKeyIdStore` (Keychain, through the existing `KeychainClient` seam of `DbKeyKeychain.swift`); `AttestationHost` holds the logic.
2. **Hash.** Native code receives 32 bytes and passes them on unchanged: Android `requestHash = Base64.getUrlEncoder().withoutPadding()` of the bytes (43 chars, matches `requestHashB64u` in `restore-binding-v1.json`); iOS `clientDataHash` = the same `Data` for `attestKey` and `generateAssertion`. Any other length → `ATTEST_UNAVAILABLE` without calling the SDK (Dart validates first). No install ID, no hashing in native code.
3. **Android provider.** Cached for the process, main-thread confined (Pigeon calls and `Task` listeners both run on the main thread). Concurrent prepares coalesce into one SDK call. `INTEGRITY_TOKEN_PROVIDER_INVALID` → drop the provider, prepare once more, request once more; a second `PROVIDER_INVALID` → `ATTEST_TRANSIENT`. Cloud project number from `BuildConfig.PLAY_INTEGRITY_CLOUD_PROJECT_NUMBER` (Gradle property `zaghlol.playIntegrityCloudProjectNumber`, default 0); 0 → `ATTEST_UNAVAILABLE` without calling Google (fail closed). Error map: `NETWORK_ERROR`, `TOO_MANY_REQUESTS`, `GOOGLE_SERVER_UNAVAILABLE`, `CLIENT_TRANSIENT_ERROR` → `ATTEST_TRANSIENT`; `PLAY_SERVICES_VERSION_OUTDATED`, `PLAY_STORE_VERSION_OUTDATED` → `ATTEST_PLAY_SERVICES_OUTDATED`; everything else, including non-Play exceptions → `ATTEST_UNAVAILABLE`. (`CLIENT_TRANSIENT_ERROR` is Google's "retry" code; mapping it to transient uses an existing code, it does not widen the contract.)
4. **iOS key lifecycle (self-check §1).** One install-bound key, its `keyId` in a generic-password item (service `app.zaghlol.attest`, account `app_attest_key_id_v1`, `AfterFirstUnlockThisDeviceOnly`, not synchronizable, Runner's own access group). A new key is made only on **positive** evidence: `errSecItemNotFound`, `forceNewKey` (server said the key is unknown), or `DCError.invalidKey` from `generateAssertion`. Any other Keychain status → `ATTEST_UNAVAILABLE` (never a new key on doubt). Order: `generateKey` → `attestKey(newId, hash)` → replace the stored `keyId` → `generateAssertion(newId, hash)`. A failure before the replace leaves the old item untouched; a failed Keychain write → `ATTEST_UNAVAILABLE` (no proof for a key we can't keep). A second `invalidKey` on a fresh key → `ATTEST_UNAVAILABLE` (no loop). `serverUnavailable` → `ATTEST_TRANSIENT`; `isSupported == false` and every other error → `ATTEST_UNAVAILABLE`. Calls are serialized (one at a time), so two concurrent restores can't create two keys. Completions hop to the main thread.
5. **No logs, code-only errors.** No logging calls in either directory (added to the app-ci no-logging grep); errors carry the code only (`message`/`details` null), so a token, key ID or hash can't leak through an error.
6. **Release network config.** `res/xml/network_security_config.xml`: `base-config cleartextTrafficPermitted="false"` with system CAs only; user CAs only in `<debug-overrides>`; referenced from `src/main/AndroidManifest.xml`. Residual (stated in platform-channels §4a): Flutter's `dart:io` `HttpClient` (our `BackendClient` transport) reads Android's system CA store itself and does not honour `network_security_config`, so it already ignores user CAs in every build type, debug included. The config covers platform-stack HTTP in our process and any future switch to a platform HTTP client; the debug half of the device test below therefore only succeeds for a platform-stack client.
7. **Device tests.** Android: an internal-test-track build (Play-installed, so `appRecognitionVerdict = PLAY_RECOGNIZED`, with a real cloud project number) calls `attest(bodyHash of the `android-lifetime` vector)`; the token is decoded with Google's `decodeIntegrityToken` (or T-181's decoder) and `requestDetails.requestHash` must equal `requestHashB64u`. iOS: a development-signed build on hardware (App Attest sandbox, `aaguid = appattestsandbox`) calls `attest(clientDataHash of the `ios-member-order` vector, forceNewKey: true)`; the proof is fed to T-181's verifier locally with the development environment and must verify both the attestation and the assertion. Results go to `docs/05-reviews/T-178-device.md` (needs real hardware and store accounts: deferred like T-172).

## Acceptance criteria
- [ ] Pigeon contract matches platform-channels §4a; the stale-generation check (T-004) passes.
- [ ] R2-1: unit tests (Android Robolectric / iOS XCTest with a mocked service) show the hash passed to `request` / `generateAssertion` / `attestKey` is byte-identical to the Dart input; on iOS `attestKey` and `generateAssertion` receive the same hash.
- [ ] iOS: `forceNewKey = true` and an `invalidKey` error both replace the stored `keyId` and return an `attestationObject`; the Keychain item has `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly` and `kSecAttrSynchronizable = false` (XCTest reads the item attributes).
- [ ] Error mapping table above covered by tests on both platforms.
- [ ] Device test (real hardware, recorded in `docs/05-reviews/T-178-device.md`): an Android token for a test hash decodes server-side (T-181 fake or Google decode) with `requestHash` equal to the input; an iOS assertion for a test hash verifies with T-181's verifier.
- [ ] Release network config: on a release build with a user-installed CA, an HTTPS call to the staging API through that CA's proxy fails; on a debug build it succeeds (device test, recorded).
- [ ] No proof, token or key ID is written to logs (log-capture test).
- [ ] DoD (CLAUDE.md §7): analyze clean, formatted, tests added, no hard-coded strings, RTL verified where UI, no `double` money, no raw SMS in logs.

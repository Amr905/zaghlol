## Design / spec pointers
- `docs/03-technical/ask-llm.md` §4.3 (ledger after every provider call, UTC, 60 s cache, 80 %/100 %, overshoot), §4.5 (`llm_spend_daily`), §9 FR-LLM-62 metric list in `docs/01-requirements/ask-llm.md`.

## Description
After **every** provider call (counted or not) upsert `llm_spend_daily` (UTC day, feature, provider, model) with tokens and `cost_usd` from configured decimal prices (input, cached, output per 1M). `SpendGuard.IsPaused()` uses the UTC-month total cached 60 s per process against `llm.spend_cap_usd` (default 10.00): ≥ 80 % → one alert per month per feature through the existing ops notifier; ≥ 100 % → both features paused until the next UTC month or a cap raise. Counters-only metrics per day (requests, plans by name, fallbacks, refusals by reason, validation failures, 429s, attestation failures, quota hits, latency p50/p95, cost). Ledger rows older than 13 months purged.

## Acceptance criteria
1. Cost math in `decimal` with cached tokens priced separately; a table test for each candidate's price shape.
2. 80 % alert sent once per month per feature (second crossing in the same month → no alert); next month re-arms.
3. At 100 % `IsPaused()` is true for ask and cat; raising `llm.spend_cap_usd` resumes within 60 s.
4. Metrics carry no tags with text, install or account ids (test enumerates tag keys).
5. Purge keeps 13 months.

## Notes for the builder
- Overshoot ≤ 60 s × global rate × worst call cost is accepted; document it next to the guard.

## Design note (builder, Sonnet)
- **Clock:** ledger day and month are UTC (ask-llm §4.3, provider billing). The quota month (T-335) is Africa/Cairo; deliberately different.
- **Concurrency: reserve-then-settle.** `SpendGuard.ReserveAsync` adds the call's worst-case cost (max input tokens at the dearer input price + max output tokens) to an in-process in-flight sum and refuses when `settled total + in-flight + worst case > cap`. Settle replaces the reservation by the real cost. Settled total = ledger sum cached 60 s + this process's settles since the refresh (added before the write, so a racing refresh can only double count = safe side). This is stricter than the spec's "overshoot <= 60 s x rate x worst cost": within one process the cap is never passed by more than the unused part of a worst case. Residual (accepted, documented on `ISpendGuard`): other processes' spend is seen after <= 60 s; production runs one API process.
- **Fail closed:** cap/ledger read failure -> `IsPausedAsync` true and `ReserveAsync` throws `LlmServicePausedException`; a failed ledger write keeps the entry queued (still counted) and pauses every call until it is written; unknown provider id (no price) -> paused; an abandoned reservation is charged at its worst case.
- **Alert:** `IOpsAlertSink` (new, next to `IOpsNotifier`; `WebhookOpsNotifier` implements both, same `OpsChannel:WebhookUrl`). Once per (UTC month, feature), claimed atomically by a zero-cost marker row in `llm_spend_daily` (provider `~alert80`, model `-`) so it survives restarts and several processes; no migration and no new table. Residual: claim-then-send, so a failed post is not retried (logged only).
- **Metrics:** `LlmMetrics` on the shared Zaghlol meter; tag keys limited to `LlmMetricTags.AllowedKeys`; values from fixed sets or patterns, else `other`. Attestation failures stay on T-336's `zaghlol.llm.attestation` counter. Cost is a `Counter<decimal>`. The endpoint (T-349) calls the plan/fallback/refusal/validation/429/quota methods; the guard records the provider call itself.
- **Purge:** rule `llm_spend_daily`: `day < UTC date(now) - 13 months`.
- **Not wired:** `AddZaghlolLlmSpend` is not called by the API host (T-349 does, with `AddZaghlolFlagAdmin`/another `IOpsAlertSink`, `AddZaghlolRemoteConfig`). FU-413's duplicate key catalogue is in the quota files (T-335), not touched here.

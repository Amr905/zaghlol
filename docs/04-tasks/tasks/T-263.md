## Scope
1. Reproduce from code: find every path where a shared image (single, multiple, from Gallery, WhatsApp, Files; `image/*`, `content://`) ends in a "not implemented/coming soon/unsupported" message (Android `ShareActivity`/`ShareIntake`, Dart share inbox, `ScanService`, flavours `devSms`/`devNoSms`/`prod*`, the OCR-available check). Batch 41 built Android share → OCR: find why the PO's build doesn't reach it (flavour, feature flag, OCR model missing, type refused after batch 72's MIME rules).
2. Fix so one shared image opens the scan confirmation; several images → the first, with a note; no OCR on the phone → the clear "not available on this phone" screen, never "not implemented".

## Acceptance criteria

## Design note (builder)

Root cause (found by reading the code; no device available):

1. **Warm start (app already open, the common case when sharing from Gallery/WhatsApp).** `MainActivity.onResume` announces pending shares to Dart with `store.list()` directly. The Pigeon host (`ShareIntakeHost`) adds `ocrPath = id` to image descriptors, but this second path did not, so Dart received an image with `ocrPath == null`, `SharedItemsLifecycle` built `ScanImagePath(null)` and S-32 showed "Reading images isn't ready on this phone yet" (the PO's "not implemented"). Dart then de-duplicated the id, so the later poll (which had the path) was ignored. Cold starts worked because only `pollPending` ran. Flavours, feature flags and the MIME rules were not involved; the OCR model asset (`assets/tessdata/ara.traineddata`) is present.
2. **Several images.** The manifest declared only `ACTION_SEND`, so Gallery's multi-select share never offered Zaghlol.
3. PDF/CSV shares also land on the "not ready" screen: out of scope (statement import, T-269).

Fix: `ShareDescriptor.withOcrPath()` is the single place that sets the OCR handle, used by the Pigeon host and by `onResume`; Dart falls back to the share id for an image without `ocrPath`. `ACTION_SEND_MULTIPLE` (`image/*`) is accepted: the first item is read, a localized Toast (string resource en/ar) says so. No Pigeon contract change (the note is native, so no new reject reason is needed).

## Builder assumptions

- The "note" for several images is an Android Toast from string resources (`native_android_shareMultipleFirstOnly`, to be added to the copy deck), not a Dart snackbar, to avoid widening the Pigeon contract. Propose a contract change if the PO wants it in Flutter.
- iOS: `ShareExtension/Info.plist` allows `NSExtensionActivationSupportsImageWithMaxCount = 1`, so sharing several photos does not offer Zaghlol on iOS; a single image goes extension -> App Group -> `ocrPath` -> OCR -> S-32 (no "not implemented" text on that path). Raising the count (the extension already takes the first image provider) is untested without Xcode, so it is left as a follow-up.

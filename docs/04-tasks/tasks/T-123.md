## Description
Every security-relevant response is signed, and anchoring responses carry the caller's time-nonce echo inside the signed body.

## Technical details
- `ISigner` with a KMS provider and a local dev key; kid rotation (next/active/retired); `Zaghlol-Signature: kid=…; alg=ES256; sig=…` over the exact response body bytes; JWS compact builder for entitlement and account tokens; public JWK export for app embedding.
- `IKeyedHasher` (HMAC-SHA256 through the KMS abstraction) used by `K_seat`, `K_audit` and the `install_hash` pepper. The key never leaves the KMS in production; a fake for tests.
- **Time-nonce filter (R4-2):** an endpoint filter for the six anchoring operations (`POST /v1/sync`, `GET /v1/entitlement`, `POST /v1/purchases/verify`, `POST /v1/purchases/restore`, `POST /v1/accounts/signin`, `POST /v1/accounts/signout`). It validates `Zaghlol-Time-Nonce` (22 base64url chars, else `400 VALIDATION_FAILED`), exposes it to the handler, which copies it unchanged into the 200 body as `timeNonce` (`null` when absent). The value is never stored, logged or traced (the header is on the logging deny-list, T-138). Endpoint tasks (T-128, T-132, T-135, T-185) apply it and test their own operations.
- Every 200 of the six anchoring operations is signed, the sync throttle answer and sign-out included.

## Design note
### Design note (solution-architect, 2026-11-06)

**Approach.** Everything lives in `Zaghlol.Infrastructure/Kms` behind three narrow ports, plus one middleware and one endpoint filter in `Zaghlol.Api`. No new NuGet dependency: ECDSA, HMAC and AES-GCM come from `System.Security.Cryptography`, and the JWS is built in-house, about 40 lines.

**Ports (KMS abstraction).** No method returns private, HMAC or data-key material. A reflection test asserts that no public member of any `Kms` type returns an `ECParameters`, an `ECDsa`, a `byte[]` named `*Key*`, or exposes a key export.
```csharp
public enum SigningPurpose { Sync, Entitlement }    // Sync: every Zaghlol-Signature header + catalog .sig; Entitlement: JWS tokens
public sealed record SigningKey(string Kid, SigningPurpose Purpose, SigningKeyStatus Status, string KeyRef, JsonWebKey PublicJwk);
public interface ISigningKeyProvider {               // adapter per KMS
  ValueTask<byte[]> SignDigestAsync(string keyRef, ReadOnlyMemory<byte> sha256, CancellationToken ct); // returns P1363 r||s, 64 bytes
  ValueTask<byte[]> GetPublicKeyAsync(string keyRef, CancellationToken ct);   // X9.63 point, startup check only
}
public interface ISigner {                           // what callers use
  ValueTask<ResponseSignature> SignAsync(SigningPurpose p, ReadOnlyMemory<byte> data, CancellationToken ct); // (kid, sig)
  ValueTask<string> CreateJwsAsync<T>(SigningPurpose p, T payload, CancellationToken ct); // compact, header {"alg":"ES256","kid":..,"typ":"JWT"}
  IReadOnlyList<SigningKey> PublishedKeys(SigningPurpose p);                  // next + active + retired; JWKS export
}
public enum KeyedHashKey { Seat, Audit, InstallHashPepper }
public interface IKeyedHasher { ValueTask<byte[]> HmacSha256Async(KeyedHashKey k, ReadOnlyMemory<byte> data, CancellationToken ct); }
public interface IEnvelopeCipher {                   // idempotency bodies, Apple refresh tokens (T-122 columns)
  ValueTask<byte[]> EncryptAsync(ReadOnlyMemory<byte> plain, string context, CancellationToken ct);
  ValueTask<byte[]> DecryptAsync(ReadOnlyMemory<byte> blob, string context, CancellationToken ct);
}
```
- **Domain separation of keyed-hash inputs** (`"install" ‖ 0x00 ‖ …`, `purchase_id ‖ pk`) belongs to the callers: T-182, T-136 and T-124/T-128. `IKeyedHasher` is a raw HMAC.
- **Envelope format v1:** `0x01 ‖ len(keyRef) ‖ keyRef ‖ len(wrappedDek) ‖ wrappedDek ‖ nonce(12) ‖ ciphertext ‖ tag(16)`. The cipher is AES-256-GCM with a fresh data key per record (KMS GenerateDataKey / Encrypt). The AAD is `"zaghlol-env-v1" ‖ 0x00 ‖ context`, where context is for example `idempotency_records:<installId>:<operationId>:<key>`, so a ciphertext copied to another row doesn't decrypt.
- **Key ring = configuration**, not a DB table; `signing_keys` was removed from `backend-schema.md` in the T-122 commit. `Signing:Keys[]` holds `{kid, purpose, status, keyRef, publicJwk}` and is written by T-140 IaC next to the KMS keys. Startup validation fails fast unless:
  - exactly one `active` per purpose;
  - kids are unique and match `^[se][0-9]{4}[a-z]$` (`s` = sync, `e` = entitlement, for example `s2026a`);
  - every JWK is P-256;
  - each JWK equals `GetPublicKeyAsync(keyRef)` (this catches a wrong key reference);
  - a sign-then-verify probe of each active key passes.
- **Rotation:** `next` keys are published (embedded in the app ≥ 1 release earlier) and never sign. Exactly one `active` key signs. `retired` keys never sign; they stay in `PublishedKeys` so tests and the JWKS export can still verify them, until they are deleted from config after the app release that drops them. Moving next → active is a config deploy.
- **Providers:** `Kms:Provider = Local | <cloud>`.
  - **Local:** `Kms:Local:KeyDirectory` holds PEM P-256 keys and 32-byte HMAC/AES keys, named by `keyRef` (`local:s2026a`). `backend/tools/dev-keys.sh` (openssl) creates them in the git-ignored `backend/.dev-keys/`, and compose mounts that read-only.
  - **Fail closed:** `Local` is allowed only when the environment is `Development` or `Testing`; startup throws in `Staging`/`Production`.
  - **Tests** use an in-memory `FakeKms` with keys generated per run.
  - **Cloud adapter:** written once the PO picks the provider (T-140; see the open question). It must provide asymmetric P-256 sign, an HMAC-SHA256 sign, and data-key wrap. All three hyperscalers do, but **on Azure only Managed HSM** offers HMAC (HS256); standard Key Vault does not. The adapter converts DER signatures to P1363.
  - **KMS calls:** 2 s timeout, one retry; no caching of results.

**What the signature covers.**
- `Zaghlol-Signature: kid=<kid>; alg=ES256; sig=<86 base64url chars>`, exactly that order, separators `"; "`, no padding.
- The signed message is ECDSA P-256 / SHA-256 over **the exact response body bytes as they leave our middleware, before any content-encoding**. Headers, status and request are not covered; the time nonce supplies the request binding (backend-api §1).
- `sig` is IEEE P1363 `r‖s` (64 bytes). High-S signatures are valid; verifiers must not require low-S.
- Only status **200** responses of endpoints carrying `RequireResponseSignature()` metadata are signed: the six anchoring operations and `GET /v1/catalog/{version}/full`. The catalog `.sig` file (T-125) holds the same header-value string.
- Tighten the OpenAPI `ZaghlolSignature` pattern to `^kid=[se][0-9]{4}[a-z]; alg=ES256; sig=[A-Za-z0-9_-]{86}$` in this task.
- **JWS (entitlement and account tokens):**
  - The signing input is `b64u(header).b64u(payload)`, with UTF-8 JSON from System.Text.Json (no indentation) and the same P1363 signature.
  - Tokens use the `e…` keys and response headers use the `s…` keys. The app accepts only `s` kids for headers and only `e` kids for JWS (T-141), which rules out cross-use.

**Middleware buffering (`ResponseSigningMiddleware`).**
- **Order:** `UseExceptionHandler` → (response compression, if ever enabled) → `UseRouting()` (now explicit) → auth → **signing** → endpoints. Compression stays outside signing, so signing sees uncompressed bytes.
- **Buffering:** if the endpoint lacks the metadata, the middleware passes the request through untouched. Otherwise it swaps `IHttpResponseBodyFeature` for a `StreamResponseBodyFeature` over a `MemoryStream`, so both `Body` and `BodyWriter` land in the buffer, runs `next`, then restores the original feature in `finally`.
- **Response:** if the status is 200, it signs the buffer, sets the header and `Content-Length`, and copies the buffer out. Any other status copies out unsigned.
- **Cap:** a 1 MiB buffer limit. If a handler exceeds it, the middleware throws `ResponseTooLargeToSign`, which becomes 500 `INTERNAL` plus a metric. Nothing unsigned is ever streamed for a signed endpoint.
- **Writes and exceptions:** an early `StartAsync`/flush by a handler only writes to the buffer, so headers can't be committed before signing. A downstream exception discards the buffer and rethrows to the outer handler (unsigned problem+json).
- **Idempotent replays** (T-124) write the stored body bytes through the same middleware. They are re-signed with the current active key, and the bytes are identical.

**Time-nonce filter (`TimeNonceFilter`, `.WithTimeNonce()`).**
- Applied to the six operations by their owning tasks (T-128, T-132, T-135, T-185). It is registered **first** among endpoint filters, ahead of the idempotency filter, so a malformed nonce is always 400 and never a replay.
- **Validation:**
  - Absent header → `null`.
  - Exactly one header value matching `^[A-Za-z0-9_-]{21}[AQgw]$`, the canonical 16-byte encoding and the same pattern as the OpenAPI `TimeNonce`. Anything else, including an empty value, two values, padding, `+` or `/`, gives `400 VALIDATION_FAILED` with a fixed `detail`-less body.
- **Exposure:** the value is placed only in an `ITimeNonceFeature` on `HttpContext.Features`. It is not added to Activity tags, baggage, `LogContext`, ProblemDetails extensions or exception data.
- **Copy into the body:** handlers copy it into response DTOs implementing `IAnchoredResponse { string? TimeNonce }`, serialized with `JsonIgnoreCondition.Never` so `null` is written explicitly.
- **Fail-closed check:** after the handler, if the result is a typed `Ok<T>` with `T : IAnchoredResponse` and `TimeNonce` differs from the feature value, the filter throws, giving 500 and a metric. Raw replay results are exempt, because by spec they echo the original nonce.
- **Storage:** the echo is never stored separately. It exists at rest only inside the encrypted idempotency body (accepted by backend-api §1).

**Shared test vectors (app ↔ backend).**
- `backend/tests/Zaghlol.Contract.Tests/vectors/response-signature-v1.json`: a synthetic test key's **public** JWK only (kid `s0000t`); valid cases `{bodyB64u, header}` including a high-S signature and an empty-object body; invalid cases for a flipped body byte, an unknown kid, an `e` kid on a header, DER encoding, `alg=ES384`, padding, reordered or extra-spaced params, and a signature over the gzip bytes.
- `jws-es256-v1.json`: valid entitlement and account tokens, plus `alg:none`, `HS256` with the public key as the secret, an unknown kid, an `s` kid, padding and a modified payload.
- `keyed-hash-v1.json`: RFC 4231 cases 1–4 through `IKeyedHasher`, backend only.
- **Generation:** ECDSA is randomized, so vectors are generated **once** by an opt-in test (`ZAGHLOL_GEN_VECTORS=1`), committed, and the private key is discarded.
- **Consumers:** .NET contract tests verify every vector. Fresh signatures from `FakeKms` also round-trip against `PublishedKeys`. The Dart verifier (T-141, T-144) reads the same files by repository path, as T-183 does.

**Failure modes.**
- **KMS unreachable or timeout on sign:** `503 UPSTREAM_UNAVAILABLE`, `Retry-After: 5`, plus a metric and an alert (T-138). The verify / sign-in transaction has already committed by then; a client retry with the same `Idempotency-Key` replays the stored body, so no double effect.
- **Misconfigured key ring** (no active key, JWK mismatch, `Local` in production): the process refuses to start, so the readiness probe never goes green.
- **Retired kid still referenced:** cannot sign by construction.
- **Clock:** none involved; `serverTime` is set by handlers.
- **Large body:** 500, as above.
- **Exception text** never includes the key reference, data or nonce (`SafeException` messages are constants).

**Tests.**
- Signature round-trip against the exported JWK.
- Rotation: sign with A, rotate config A → retired / B → active; A's old signature still verifies via `PublishedKeys`, and new ones use B.
- The middleware signs 200 and leaves 4xx/5xx unsigned; `BodyWriter` and `Body` writes are covered; the over-cap response gives 500; an exception gives an unsigned problem.
- The nonce acceptance cases on a test-only endpoint (21 and 23 chars, `=`, `+`, valid byte-for-byte echo, absent → `null`).
- A log/span capture with a sentinel nonce that also throws inside the handler: the sentinel appears in no log, span or exception output (reuse T-138's harness if it is merged, else `CapturingSink` plus an in-memory `ActivityListener`).
- Keyed-hash RFC vectors, envelope round-trip, and AAD mismatch failure.

**Rejected alternatives.**
- **Signing in an endpoint filter:** the `IResult` serializes after the filter returns, so the filter can't see the bytes.
- **Holding the private key in memory:** violates security-model §6 (sign-only KMS access).
- **A `signing_keys` table:** a DB write could change the signer, and it adds a DB dependency in the hot path.
- **Detached JWS (RFC 7515 Appendix F) for responses:** the header format is already fixed by contract and the app; no gain.

## Acceptance criteria
- [ ] Signature verifies with the exported public key.
- [ ] Rotation keeps the old kid verifiable until retired.
- [ ] R4-2: a malformed `Zaghlol-Time-Nonce` (21 chars, 23 chars, `=` padding, `+`) gives `400 VALIDATION_FAILED`; a valid one is echoed byte-for-byte inside the signed body; an absent one gives `timeNonce: null` (filter test on a test endpoint).
- [ ] R4-2: a log/trace capture test shows the nonce value appears nowhere (logs, spans, exception output).
- [ ] `IKeyedHasher` output for a fixed key and input matches a test vector; the production provider exposes no API that returns key material.
- [ ] DoD (CLAUDE.md §7): analyze clean, formatted, tests added, no hard-coded strings, RTL verified where UI, no `double` money, no raw SMS in logs.

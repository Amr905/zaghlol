## Description
Loss-free, encrypted hand-off from native to Dart.

## Technical details
Keystore AES-256-GCM key `SpoolKey` (TEE-backed, **never StrongBox**, no user auth; Lead decision 2026-11-10) — [doc change] 2026-11-11, was "StrongBox if available"; versioned binary record v1 (T-008, Lead Q8; was CBOR) in noBackupFilesDir/spool, atomic write; drain returns decrypted entries; ack deletes; KEY_INVALIDATED handling (reported through status, not thrown); delete-on-proof after the 100/300/900 ms retry ladder (was "quarantine after 3 decrypt failures"); generic-keep budget and SPOOL_FULL status (T-035 security L-3).

**2. Key (`SpoolKey`, FU-068, FU-086 I-3).** Alias, spec and TEE-only rule unchanged (`SpoolKeySpecTest` keeps `REQUEST_STRONGBOX = false`). Changes, behind a `KeystoreOps` seam (load, create, delete, creationDateMs) so the logic is JVM-tested:
- **Unusable key.** `load()` throwing is classified with T-015's `KeyErrorClassifier`; only when the first attempt and the 100/300/900 ms retries are all `UNUSABLE` does `SpoolKey` delete the alias and create a new one, under the existing `GetOrCreate` lock. Any `UNAVAILABLE` → throw (callers map to `IO_ERROR`, nothing deleted). Today an unusable key would fail every write forever.
- **Lost key evidence, not a marker.** `creationDateMs()` = `KeyStore.getCreationDate(ALIAS)`. On drain, an entry whose first decrypt fails the GCM tag **and** whose ULID time is before the key's creation is written under a previous key: deleted at once without the retry ladder (I-3: 100 entries no longer cost ~130 s), counted `decryptDeleted`, and `keyInvalidatedAtMs` set in the status (§5). Entries at or after the creation time, or when the creation date can't be read, take the normal ladder. Deletion still needs a tag failure (proof); the clock only chooses ladder vs no ladder, so a clock change can't cause a deletion. A key replaced while nothing was pending raises no alert (nothing was lost; T-047 rewrites the Guard user part on every start anyway).
- **`KEY_INVALIDATED` is reported, not thrown** [doc change §6]: `drainSpool` keeps returning the readable entries; Dart reads `getSpoolStatus().keyInvalidatedAtMs`, rewrites the Guard config, runs the catch-up (T-048) and shows the Settings "re-scan" hint (T-047/T-078).

**3. Entry.** Format unchanged (platform-channels §1.3: `<ulid>.bin` = `nonce(12) ‖ AES-GCM(record v1) ‖ tag`, AAD `zaghlol.spool.v1|entry|<ulid>`). The two former spike timing fields stay in the record (`rxElapsedNs`, `bootCount`; T-041 may stamp the commit natively, FU-081) — they are inside the ciphertext. File names are ULIDs and reveal receive times (FU-086 I-2): accepted, recorded in §1.3 [doc change] (no_backup, deleted on ack and by "Delete everything").

**4. Write path and admission (L-3, FU-084).** `SpoolStore.write(record, cls: AdmissionClass)` with `PRIORITY` (Guard kind `registry`/`user`) or `GENERIC` (Guard kind `generic`); the caller (T-040/T-043) maps the Guard's kind. Under the store lock: list the directory once → `n` entries + tmp, `bytes`.
1. `n ≥ 500` or `bytes + estimate > 4 MiB` → `Refused(FULL)`.
2. `GENERIC` and (`n ≥ 250` or `bytes + estimate > 2 MiB`) → `Refused(GENERIC_BUDGET)` — generic keeps can use at most half the spool, so a flood from unknown senders can't block bank messages; a **hard, persistent** bound with no kind on disk.
3. `GENERIC` and more than 10 generic writes in the last 60 s (process-wide, in memory, monotonic clock) → `Refused(GENERIC_RATE)` (best effort; resets with the process).
4. Else encrypt and write: `<ulid>.bin.tmp`, write, `fd.sync()`, `ATOMIC_MOVE` rename, best-effort directory fsync (`Os.fsync` on the dir fd; ignored if it fails).
On any `Refused` the store records it in the status (§5) and returns; the caller still enqueues the worker and notifies an attached UI engine so the spool drains (FU-084b: "SPOOL_FULL → catch-up"). Old entries are never evicted. The per-sender Guard rate limit is **best-effort per process**; the spool caps are the hard bound [doc change ADR-005 *Threats*]. Numbers 250/2 MiB/10 are provisional (PO Q1).

**5. Capture status** (`CaptureStatusStore`, new). `noBackupFilesDir/capture/status.bin`, AES-GCM with `SpoolKey`, AAD `zaghlol.capture.v1|status`, fixed binary record v1: `seq u32 | refusedFull u32 | refusedGeneric u32 | rateLimited u32 | missedNotifications u32 | firstMissedSmsAtMs i64 (-1) | lastRefusedAtMs i64 | decryptDeleted u32 | keyInvalidatedAtMs i64 (-1)`; counts saturate at `u32` max. Written only on an **alert** (refusal, rate-limit drop of a kept message, delete-on-proof, key loss), never for a normal keep and never for a non-financial drop (T-040 AC "personal SMS leaves no file"). `recordRateLimited(channel, wallMs)` is for T-040/T-043 (Guard `rate_limited` on SMS is recovered by catch-up from `firstMissedSmsAtMs`). Read failure: tag/format proof → start from zero with `keyInvalidatedAtMs = now`; I/O/Keystore → keep the delta in memory, merge on the next successful read, never overwrite the unread file. `clear(seq)`: zeroes the counters only if `seq` matches (alerts that arrived meanwhile survive), then `seq + 1`.

**6. Host API** (`AndroidCaptureHost`, one per engine; replaces the spike's `SpoolHost` when T-041 wires engines). Constructor: `engineId, store, claim, status, scheduler: IngestScheduler?, guardWriter: ((ByteArray) -> Unit)?, guardState: (() -> GuardConfigState)?, device: CaptureDevice?`; an unwired dependency answers `NOT_AVAILABLE`. **T-040 wires `guardWriter`/`guardState` to T-038's `GuardRuntime`**, T-041 registers the host on both engines.
- `drainSpool(max)`: sweep tmp, `claim.acquire(engine)` else `[]`, oldest first, clamp 1..100, skip `Unavailable`, count `Deleted`; remembers the returned ids in a per-host `drained` set; `claim.hold`.
- `ackSpool(ids)`: > 100 ids → `IO_ERROR`; deletes only ids that are **listed, valid ULIDs and in this host's `drained` set** (AC3; a stray or late ack from another engine can't delete an entry it never received; at-least-once is kept by the DB's `body_hash`); idempotent; `claim.acked`. Dart acks committed entries **and** entries its drain-time Guard re-check dropped (T-046).
- `writeGuardConfig(userConfigJson)` → `guardWriter`; `GuardConfigWriteException(code)` → `CaptureApiError(code)` (`CONFIG_INVALID` / `IO_ERROR`).
- New `getSpoolStatus(): SpoolStatus` and `clearSpoolAlerts(int seq)` (§5) [doc change §2].
- Every method: `catch` everything → `CaptureApiError(code, null, null)` (FU-034).
**Pigeon** [doc change §2; FU-097 L-2, moved here from T-038]: `void writeGuardConfig(Uint8List userConfigJson)` with `@TaskQueue(serialBackgroundThread)` (Keystore + fsync must not run on the main thread); new
```dart

class SpoolStatus { int pending; int seq; int refusedFull; int refusedGeneric; int rateLimited;
  int missedNotifications; int? firstMissedSmsAtMs; int decryptDeleted; int? keyInvalidatedAtMs; GuardConfigState guardState; }
@TaskQueue(type: TaskQueueType.serialBackgroundThread) SpoolStatus getSpoolStatus();

```
**7. Crash safety.** Kill before rename → only a `.tmp` (invisible to drain, counted in caps). `sweepTmp` runs **under the store lock**, where no write is in flight (single process, writes hold the lock), so it deletes every `.tmp` regardless of age: no wall-clock dependency (the spike's 60 s age rule fails when the clock moves back) [doc change §1.3]. Kill after rename → durable entry. Kill between commit and ack, or mid-ack → re-drained, deduped by `body_hash`. Status: same tmp + fsync + rename. Disk full → `IOException` → tmp deleted, caller gets the error (T-040 counts it in memory).

**8. Concurrency.** Writers: SMS receiver and notification listener (both on one intake executor, T-040/T-043); readers: one Pigeon serial task queue per engine (UI, headless). Locks and order: `GuardRuntime` → `SpoolKey`; store → status → `SpoolKey`; never the reverse. Drain and ack take no store lock (rename and delete are atomic per file) except the tmp sweep. The drain claim (spike `SpoolClaim`, unchanged) keeps two engines from processing the same entry; the per-host `drained` set scopes acks. All in the default process (same assumption as `SpoolKey`).

**9. Never logging.** No `Log`/`println`/`System.out` in `platform/spool`, `platform/capture` (except `.g.kt`), `platform/guard`: extend the `app-ci` grep to those directories. `SpoolRecord`, `SpoolEntry` mapping, results and status `toString()` redacted; errors code-only. Production native code has no diag log; diagnostics reach Dart only as status counts (T-021 records them as `DiagEvent`s).

**10. File ownership (T-038 ∥ T-039).** T-039 only: `platform/spool/**`, `platform/capture/**` (non-generated + generated), `app/pigeons/capture_api.dart` and its generated Dart/Kotlin/Swift, `src/devSms`/`src/testDevSms` import fixes, `app-ci.yml` (grep, threshold), `sms-spike.yml` + `.github/scripts/sms-spike-device.sh` (instrumented step below). T-038 only: `platform/guard/**`, `src/sharedTest/**`, `build.gradle.kts`, `packages/zaghlol_parsing/test/fixtures/guard/golden.json`. Neither edits the other's set.

**11. Tests.** JVM (`src/test/.../spool`, PC runner + `kotlin-unit`), software AES-GCM fake + temp dir + `FileOps` fault seam:
- AC1 (simulated): a new `SpoolStore` over the same dir reads every entry; fault at tmp open / write / fsync / rename → either a complete decryptable entry or none, never a partial `.bin`; sweep removes tmp, not entries or foreign files.
- AC2: entry bytes contain no canary (UTF-8/UTF-16LE/BE); another key → tag failure; renamed entry (AAD swap) → deleted on proof after the ladder.
- AC3: ack deletes only listed ∩ drained-by-this-host; invalid ULID ignored; > 100 → `IO_ERROR`; idempotent; other engine's entries untouched.
- Admission: 500th written, 501st `FULL`; byte cap; generic at 250 / 2 MiB / 11th per minute refused while `PRIORITY` still written; never evicts.
- Status: persists across instances; no write on a normal keep (directory listing unchanged except the entry); `clear` with stale `seq` is a no-op; tag-failed status → reset + `keyInvalidatedAtMs`.
- Key: `UNUSABLE`×4 → one delete + create; mixed → no delete; stale-key entry deleted with zero `sleep` calls and `keyInvalidatedAtMs` set; entry newer than the key or unknown creation date → ladder (3 sleeps).
- Canary through write/read/drain/ack/status with a failing cipher: no canary in exceptions, `toString`, stdout/stderr.
Instrumented (`src/androidTest/.../spool`, real Keystore): key spec (`key.encoded == null`; API 31+ `KeyInfo.securityLevel != STRONGBOX`; no user auth); AC2 with a test-only alias delete → stale-key path; **AC1 for real**: two `am instrument` phases run by `sms-spike-device.sh` — phase `write` writes 20 entries and halts the process (`Runtime.halt`) between fsync and rename of a 21st; phase `read` (new process) finds exactly 20 decryptable entries and no 21st, and the tmp is swept.
**CI split** [doc change testing-strategy]: the JVM list runs (PC runner + GitHub `kotlin-unit`); the instrumented suites of T-038, T-039 and T-060 run only in `sms-spike` (opt-in by pushing to `ci/<task-id>`): add a `connectedDevSmsDebugAndroidTest` step (or `assembleAndroidTest` + `am instrument`) per API level and path filters for `src/main/kotlin/app/zaghlol/platform/{spool,guard,capture}/**`, `src/androidTest/**`, `src/sharedTest/**`, `packages/zaghlol_parsing/test/fixtures/guard/**`. T-060's `ShareIntakeInstrumentedTest` has never run in CI; if it fails there, report it to the Lead instead of fixing it here. **No Robolectric** [doc change Testing requirements]: it would add a large dependency, it has no real AndroidKeyStore (tests need a fake provider either way) and its regex is the JVM's; plain JVM tests with seams plus emulator runs cover both sides.

**Rejected.** CBOR (dependency; the v1 binary record is reviewed and fuzzed). Evicting old entries when full (an old bank SMS is worth more than a new flood). A plaintext key-epoch marker file (evidence from tag failure + key creation date is enough and writes nothing). Throwing `KEY_INVALIDATED` from `drainSpool` (it would hide the readable entries). Ack of any listed id (T-008 spike behaviour; a stray ack could delete an uncommitted entry). StrongBox (Lead decision 2026-11-10). Kind in file names for a per-kind count (leaks content class).

## Acceptance criteria
- [ ] Entries survive process kill (instrumented two-phase test with a hard halt; JVM fault injection at every write step)
- [ ] Files unreadable without key (no canary in entry bytes; another key or a swapped name fails authentication)
- [ ] Ack deletes only listed ids that this engine drained
- [ ] A full spool refuses the new message, never evicts, records it in `getSpoolStatus` and still schedules a drain; generic keeps never use more than half the spool (L-3)
- [ ] Lost or unusable spool key: readable entries still drained, old-key entries deleted only on a tag failure, `keyInvalidatedAtMs` reported; nothing deleted on a transient Keystore error
- [ ] Pigeon `writeGuardConfig(Uint8List userConfigJson)` on a background task queue; `getSpoolStatus` / `clearSpoolAlerts` added; generated files fresh
- [ ] DoD (CLAUDE.md §7): analyze clean, formatted, tests added, no hard-coded strings, RTL verified where UI, no `double` money, no raw SMS in logs.

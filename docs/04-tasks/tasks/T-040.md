## Description
Live SMS capture with personal SMS never stored.

## Technical details
SMS_RECEIVED receiver; assemble multipart PDUs (EC-09); sim slot (EC-11); Guard; spool; goAsync ≤ 5 s; enqueue expedited IngestionWorker; notify engine if attached; nothing logged. [doc change] 2026-11-11 (design note §1): the receiver is in every `*Sms` variant (`src/sms`), not only prodSms; the enqueue goes through the injected `IngestScheduler` (WorkManager in staging/prod comes with T-041).

**1. Flavour placement [doc change: title said "prodSms"].** The receiver exists in **every `*Sms` variant** (`src/sms/`: dev, staging, prod) and in no `*NoSms` variant. Glue class `src/sms/kotlin/app/zaghlol/platform/capture/SmsReceiver.kt` (so the NoSms dex has no receiver class at all); everything testable lives in `src/main/.../platform/capture/` (shared with T-043, runs in `testDevNoSmsDebugUnitTest` on the PC runner). Manifest `src/sms/AndroidManifest.xml`: `<receiver android:name="app.zaghlol.platform.capture.SmsReceiver" android:exported="true" android:permission="android.permission.BROADCAST_SMS" android:directBootAware="false">` with action `android.provider.Telephony.SMS_RECEIVED`, no priority. `src/noSms/AndroidManifest.xml` gains a `tools:node="remove"` entry for that receiver (defense in depth, like the permissions). Never `abortBroadcast`, `setResultCode`, `SEND_SMS` or default-SMS-app roles. devSms keeps the spike receiver until T-041 removes it: the spike Guard keeps only `5550100`/`+15550100` and the production Guard only config senders, so they never both keep one message (a test asserts no test config lists those senders); both write the same `noBackupFilesDir/spool/` (one lock per path, T-039 fix #1), so the spike worker drains production entries end to end.

**2. Files.** `capture/CaptureRuntime.kt` (process-wide, `get(context)`; holds `GuardRuntime.get`, one `SpoolStore` and one `CaptureStatusStore` over the T-039 paths with `SpoolKey::creationDateMs` and `SystemClock::elapsedRealtime`, a `scheduler: IngestScheduler?` slot, a spool-changed listener list, the SMS dispatcher; `hostFor(engineId, claim, device)` builds an `AndroidCaptureHost` with the two adapters of section 6, for T-041 to register; construction does no file or Keystore I/O; `@VisibleForTesting internal fun installForTest(...)`: restore handle for the instrumented test). `capture/CaptureIntake.kt` (channel-agnostic Guard → spool → status → enqueue/notify; reused by T-043). `capture/SmsAssembler.kt`. `capture/BoundedDispatch.kt` (ported from the spike, same tests). `capture/GuardAdapters.kt`. Edits: `guard/GuardRuntime.kt`, `guard/GuardTypes.kt` (section 5), `spool/SpoolStore.kt` (section 7), `spool/CaptureStatusStore.kt` (section 8), `capture/IngestScheduler.kt` (KDoc contract, section 4), the spike initializer (registers its scheduler and UI notifier in `CaptureRuntime`) and the spike `WorkManagerScheduler` (waits for the operation, section 4).

**3. Receiver lifecycle.** `onReceive` (main thread, no I/O): check the action; stamp `wallMs = currentTimeMillis()`, `rxElapsedNs`; read PDUs with `Telephony.Sms.Intents.getMessagesFromIntent` inside `try` (malformed → empty list); read the slot (`android.telephony.extra.SLOT_INDEX`, else legacy `slot`; `-1` → null; never `READ_PHONE_STATE`); `goAsync()`; hand the parts to `CaptureRuntime.smsDispatch` (one daemon thread `zaghlol-sms-intake`, **SMS only**; T-043 gets its own thread so a notification burst can't eat the SMS budget) with a **5 s** budget: `finish()` exactly once, when the work ends, throws, or the budget passes (the work is then abandoned, not interrupted; the atomic write leaves a whole entry or none). Past `finish()` the process may be killed: a message lost there is recovered by the inbox catch-up (watermark − 10 min, FU-088), so no in-memory "timed out" hint is kept (it would die with the process). Pre-unlock SMS are not delivered to this receiver (not direct-boot aware; credential storage is locked anyway) → catch-up.
- **Multipart (EC-09).** The telephony stack reassembles a concatenated SMS and delivers all its PDUs in one broadcast, in sequence order. `SmsAssembler.assemble(parts)`: group by address in first-seen order, append bodies **in array order** (never re-sort by timestamp: all parts share the service-centre time), a null part body contributes `""`, a part with a null/empty address is dropped. Normally one broadcast = one message; several addresses become several messages.
- **Sender and body accessors.** Use the accessors that reproduce the system inbox row byte for byte, so the catch-up's `bodyHashOf(address, body)` equals the live one (FU-085/FU-088 dedupe). Candidates `displayOriginatingAddress` / `displayMessageBody` (they differ from `originatingAddress`/`messageBody` only for email-gateway SMS); the emulator test (section 11) compares the spooled `(source, body)` with the inbox row and decides. The source is stored raw (no `+20`/`0` rewriting); the Guard folds it.

**4. Guard → spool → enqueue (`CaptureIntake.process(channel, messages, stamp)`).** Per message: `guard.decide(AndroidGuardChannel.SMS, source, body)`.
- `Drop(rate_limited)` → `status.recordRateLimited("sms", wallMs)` (sets `firstMissedSmsAtMs`; T-038 L-3). Any other `Drop` → **nothing**: no file, no directory, no status write, no enqueue.
- `Keep(kind)` → `SpoolRecord(channel "sms", source, body, wallMs, simSlot, inst, last4, rxElapsedNs, bootCount)`, `store.write(record, kind → PRIORITY | GENERIC)`. `Written` → remember; `Refused` → nothing more here (the store records it); `IOException`/Keystore failure → swallowed (code only), nothing enqueued for it.
- After the batch: if anything was **written or refused**, `scheduler?.enqueue()` once (refused: the drain must still run, FU-084b) and post `onSpoolChanged(pendingCount)` to the main thread for registered listeners (`pendingCount` computed on the intake thread). Enqueue failures are swallowed (the entry stays; next enqueue or app start drains).
- **Scheduler contract [KDoc]:** `enqueue()` returns only after WorkManager has **persisted** the request (`enqueueUniqueWork(...).result.get(≤ 2 s)`) or throws, because the process may die right after `finish()`. Request (T-008, unchanged; owner T-041): unique `zaghlol.ingest`, `APPEND_OR_REPLACE`, `setExpedited(RUN_AS_NON_EXPEDITED_WORK_REQUEST)`, no constraints, exponential 10 s, never `setForeground`. One enqueue per broadcast, not per message; a burst of 5 SMS still appends up to 5 runs, each of which finds an empty spool fast: whether to coalesce (expedited quota on Android 12+) is T-041's call. Until T-041, `*Sms` staging/prod builds have no scheduler (slot null): entries are drained by the UI engine at start (T-047); devSms uses the spike's.

**5. Typed channel (FU-101 L-1, before merge).** New `enum class AndroidGuardChannel(val wire) { SMS("sms"), NOTIFICATION("notification") }` in `guard/GuardTypes.kt`; `GuardRuntime.decide(channel: AndroidGuardChannel, source, body)` replaces the `String` overload, so `share`/`apple_pay`/`shortcut_message` (fail-open generic keeps) cannot reach the native Guard. `CaptureGuard.decide(String, ...)` stays the shared port (golden parity unchanged). **T-038 L-2:** `GuardRuntime` caches the compiled base-only `GuardConfig` once the base parsed; a `Transient` user read reuses it (no re-parse per message). Rate limiter: the one per-process instance inside `GuardRuntime`, unchanged.

**6. Adapters (FU-104 code #3).** `guardWriterFor(rt)`: calls `rt.writeUser(bytes)`; `GuardConfigWriteException(CONFIG_INVALID)` → `CaptureApiError("CONFIG_INVALID", null, null)`, `(IO_ERROR)` → `"IO_ERROR"`, anything else → `"IO_ERROR"`; never forwards a message or cause. `guardStateOf(snapshot)`: mode `INVALID` → `BASE_INVALID` (whatever the user state); `FULL`+`OK` → `FULL`; `BASE_ONLY`+`ABSENT` → `BASE_ONLY`; `BASE_ONLY`+`UNREADABLE` → `USER_UNREADABLE` (T-047 rewrites at once); `BASE_ONLY`+`RETRY` → `UNKNOWN` (transient, nothing to rewrite); any other pair → `UNKNOWN`. `guardState` calls `rt.state()` on the Pigeon background queue (it may do the first load).

**7. Notification reserve (T-039 security L-1, with T-043; PO Q1 below) [doc change platform-channels §1.3, ADR-005].** In `SpoolStore.write`, after the `FULL` check: `record.channel == "sms"` and (`n ≥ 400` or `bytes + estimate > 3.2 MiB`) → `Refused(SMS_RESERVE)`. Notifications keep the full 500 / 4 MiB, so a spoofed-SMS flood (recoverable by the catch-up) can't crowd out notifications (not recoverable). Constants `SpoolPolicy.SMS_MAX_ENTRIES = 400`, `SMS_MAX_BYTES = 3_355_443` (provisional — PO). Status: `SMS_RESERVE` counts as `refusedFull` and sets `firstMissedSmsAtMs` (no record or Pigeon change). The generic budget is unchanged and checked after it.

**8. Status write coalescing (T-039 security L-2).** `CaptureStatusStore.record` persists **at once** when it is the first change since the last successful persist or `≥ 10 s` (monotonic, injected) have passed; otherwise the change stays in the shared in-memory delta, merged by the next `read()`/`clear()` or the next `record` after the window. A process kill loses at most the counts of one window, never the fact. New `recordMissed(channel, wallMs)` (no refusal counter; T-043 uses it for queue overflow). `clear(seq)` semantics unchanged.

**9. Never logging (I-5).** No `Log`/`println`/`System.out`/`printStackTrace` in `platform/capture`, `src/sms/kotlin` (extend the `app-ci` grep to that dir). `SmsPart`, `AssembledSms`, `CapturedMessage`, `IntakeResult` have redacted `toString`; never interpolate a `SpoolEntry`/`SpoolRecord` into a string or exception (generated `SpoolEntry.toString()` contains the body): a JVM source scan fails on `"$entry"`/`${entry`/`entry.toString()` in capture code. Errors are codes. Package names and sender ids count as sensitive (never logged either).

**10. Parallelism with T-043.** Not in parallel: T-043 consumes `CaptureRuntime`/`CaptureIntake`/`recordMissed`/the reserve built here and edits the same `CaptureRuntime.kt`, `GuardRuntime.kt`, `sms-spike-device.sh` and the placement check. T-043 starts from T-040's approved branch (or after merge).

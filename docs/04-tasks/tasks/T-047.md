## Description
Dart side of capture on Android (iOS hooks added in M2).

## Technical details
Build the Guard user part (plaintext JSON, `buildGuardUserConfig`) and pass it to `writeGuardConfig(Uint8List userConfigJson)` on changes to ignore rules / capture senders / custom templates and on every app start; native validates, encrypts and writes it (T-035 security L-2, [doc change] 2026-11-11; `CONFIG_INVALID` → the old file stays, surface a build error); drain spool on foreground event, app start and from ingestionMain; capability/degraded state provider; setup progress state (FR-ONB-11).

## Design note
(solution-architect, Opus, 2026-11-11. C3. Inputs: T-035/T-039/T-046 notes and reviews, platform-channels §1.1-§2, parsing-engine, FR-ING-A-05/A-08, FR-ONB-11, EC-13, FU-067/076/096/104/105, copy-deck §1.4/§1.7/§1.21. **[doc change]** marks edits made in the same commit. No copy is invented: keys that do not exist are written "TBD" and listed under PO questions.)

**Layout** (`app/lib/features/capture/`). `domain/` (pure): `capture_health.dart`, `alert_absorb.dart`, `guard_write_policy.dart`. `application/`: `GuardConfigWriter`, `SpoolOrchestrator`, `CaptureHealthController` (Riverpod notifier). `data/`: `CaptureHostPort` (Dart interface over `AndroidCaptureHostApi`; fakes in tests), `GuardInputsReader` (rows to `buildGuardUserConfig` inputs). Only the **UI engine** runs this module. The headless engine keeps `IngestionCycle` only: it never writes the Guard config and never reads or clears the spool status, so there is one reader and one clearer.

**1. Guard user part: when it is built and written**
- Built **on demand** inside `write()` and nowhere else (security L-2): read `ignore_rules`, `capture_senders` (always-capture), `custom_templates` senders in one transaction, call `buildGuardUserConfig(baseRegistryVersion: bundled base, goldActive: EntitlementPort, default false until billing)`, pass the bytes to `writeGuardConfig`, then `fill(0)` the buffer in `finally`. No provider, field, setting or log keeps the bytes or a hash of them (ignore rules are inst + last-4, a 10^4 space: a stored hash is a fingerprint). Providers expose only `GuardWriteState` (enum + error code). Dedupe of identical writes is not needed: bytes are deterministic and a write is one AES-GCM + fsync of at most 64 KB.
- Triggers: (a) **every UI-engine start**, after the DB gate opens, unconditionally (also with zero rows, so native reports `full`); (b) a Drift `watch` on the three tables, **300 ms trailing** (bulk edits), plus `flush()` called by the writer of a rule (T-078, T-049, the picker) right after its DB commit with **no debounce**: AC "rewrites before next capture" is `await flush()` returning, not a timer; (c) resume, only if dirty or `guardState != full` or `keyInvalidatedAtMs != null`; (d) `guardState == userUnreadable` or `keyInvalidatedAtMs != null` in a status read: write at once, then **re-read** and expect `full`; still not `full` = `GuardWriteState.notEffective` (one retry, then surface); (e) `onPermissionChanged` does not write. Remove-rule (un-ignore) takes the same path; its catch-up offer is T-078.
- **Single flight with a generation counter.** `flush()` completes with the result of a write whose *build started after the call*; a change during an in-flight write schedules exactly one more. Test: change during write, `flush` awaits the second write.
- Failures (old file always stays in force; the Dart drain-time re-check in T-046 still enforces BR-CAP-01 on the database side, so a failed write is delayed filtering, not a leak):
  | Cause | State | Retry |
  |---|---|---|
  | `GuardConfigError` from the builder (code + path: bad row, cap) | `buildFailed(code, path)`; no native call | none until a row changes |
  | `CONFIG_INVALID` from native (Dart and native readers disagree: a defect) | `rejected` | none (deterministic) |
  | `IO_ERROR`, `PLATFORM_*`, timeout | `transient` | 2 s, 10 s, 60 s, then parked until the next trigger |
  | `NOT_AVAILABLE` (no native writer wired / flavour) | `unavailable` | none |
  State carries codes only, never a value. A rule that is saved but not yet written is reported to the caller of `flush()` as a failure result so the rule UI can say so (copy TBD, PO Q5); the rule is **not** rolled back (the DB is the truth).
- **Senders (FU-096 m-2, FU-104/T-035 I-6).** Decision: keep `capture_senders` PK `sender`; no migration. **[doc change]** `CaptureControlsDao.setAlwaysCapture` / `recordConfirmation` use `ON CONFLICT (sender) DO UPDATE ... WHERE channel = excluded.channel`; no row changed = `ChannelConflict` (typed result, not an exception), so the other channel is never silently counted. The Guard key is `(channel, sender)` and a package name contains a dot while most SMS ids do not; a real collision is rare, and a `(sender, channel)` PK means a v5 migration (C4) for no observed case. Rejected: composite PK now. **Notification user senders** (a package name; the whole notification stream of that app is then captured): a domain `validateUserSender(channel, value)` accepts only a package-name shape, refuses a bundled deny list (messaging, mail, social, browser, dialer/SMS apps), caps notification user senders at 10 (`kMaxNotificationUserSenders`, provisional, PO Q3) and requires a confirm step naming the app (picker UI: T-056/S-61 owners). Everything else is refused before the DB write.

**2. App-level capture health** (pure function `deriveCaptureHealth(caps, toggles, absorbedAlerts, guardWrite, lastCycle) -> CaptureHealth`; the notifier only feeds it).
- `channels`: sms-live (`active` if `smsFlavor && smsGranted && capture.sms`; `unavailable` if `!smsFlavor`; `off(permission)` if flavor but not granted; `off(user)` if the toggle is false), notifications (`notificationAccess && capture.notifications`; same off reasons), share/paste and manual (always `active`). Voice is added by the voice module's own provider when it exists. iOS channels: T-066 adds enum values; the derive function is exhaustive-switch so the compiler finds them.
- `mode`: `degraded` iff SMS live is `unavailable` or `off(permission)` (FR-ING-A-05, EC-13); `fault` iff `guardState == baseInvalid` (every message is dropped: a build defect, no user action; copy TBD); else `full`. A deliberate toggle-off is neither.
- `issues` (independent, each with its action):
  | Input | Issue and what the UI shows |
  |---|---|
  | SMS `off(permission)` | `home_banner_smsOff` + `common_action_fix`; onboarding variant `onboarding_androidSetup_degraded*` (exist) |
  | notifications `off(permission)` | `home_banner_notifOff` + `common_action_fix` (exists) |
  | persisted `unreadableAt` (from `decryptDeleted > 0`) | `capture_settings_unreadable` + re-scan (exists) |
  | persisted `missedNotifications > 0` | "some notifications were missed" with count, dismissible (T-039 PO Q2): key TBD |
  | `guardWrite` is `buildFailed`/`rejected`/`notEffective`/`transient` parked | settings-level warning: key TBD (PO Q5) |
  | `lastCycle.stuck > 0` | diagnostic row only in S-61, no banner: key TBD |
  | `guardState` `unknown` | nothing shown (never claim a fault we cannot see) |
  `refusedFull`, `refusedGeneric`, `rateLimited`, `firstMissedSmsAtMs` have **no user copy**: SMS are recovered by the catch-up (PO Q2 default); they feed the S-61 diagnostic row at most. Banner priority and stacking (one C-20 at a time?): TBD with UX.
- `keyInvalidatedAtMs` alone raises **no notice** (T-039 code #5: `status.bin` exists after the first alert, so a later key replacement sets it with nothing lost; an unreadable status file also reports it with a random `seq`). It triggers the rewrite and a silent catch-up request only. The notice needs `decryptDeleted > 0`.
- **Absorb-then-clear** (`alert_absorb.dart`, pure): the app owns durable state, native is a mailbox. On each read `s`: if `s.seq == absorbedSeq` (setting `capture.alert.absorbed_seq`), a previous clear failed: only retry the clear. Else, in **one** DB/settings transaction: `missedNotifications += s.missedNotifications` (saturating), `catchUpFromMs = min(existing, s.firstMissedSmsAtMs)` (also set, with reason `keyInvalidated`, when `keyInvalidatedAtMs != null`; value from T-048's default window when none), `unreadableAt` if `decryptDeleted > 0`, `absorbedSeq = s.seq`. Then `clearSpoolAlerts(s.seq)`. Counters never feed the UI directly. The only imprecision: an alert racing the clear leaves `old + new` and the next read adds `old` again to the *informational* missed-notification count (over-count by at most one snapshot; the catch-up request is a `min` and the flags are idempotent, so no recovery is lost or repeated). New setting keys (T-020 style, in the encrypted DB): `capture.alert.absorbed_seq`, `capture.alert.missed_notifications`, `capture.alert.unreadable_at`, `capture.catchup.from_ms`, `capture.catchup.reason`. Dismissing the missed-notification notice zeroes the count only. Consumption of `capture.catchup.*` is T-048 (T-047 ships a `CatchUpScheduler` port with a recording implementation, and calls it after each drain when SMS live is `active`).
- Status is read at app start (before and after the first config write), **after every drain cycle** of the orchestrator, and on resume.

**3. Draining: UI engine vs worker**
- The worker (T-041) is the only drainer when no UI engine is attached. When the UI engine is attached the worker calls `onSpoolChanged` and waits (platform-channels §2), so the orchestrator **must** drain on that event or the worker times out at 60 s and retries.
- `SpoolOrchestrator` (UI engine): one `IngestionCycle(mayCreateDatabase: true)` at a time, serialised with an `again` flag (the pattern of `SpikeIngestion`, which T-047 replaces for production; the spike stays for `devSms`). Triggers: start (after the DB gate and the first config write), `AppLifecycleState.resumed`, `onSpoolChanged` (250 ms coalesce, any lifecycle state while the engine lives), after a rule change (applies the T-046 re-check to waiting entries), and the retry timers below. Order at start: capabilities, status read, config write, drain, status read/absorb/clear.
- Drain returns empty while `getSpoolStatus().pending > 0`: the headless engine holds the claim (60 s). Re-poll at 5 s, 15 s, 45 s, then stop and leave it to the worker (`scheduleIngestionNow()`); never a tight loop. `CycleOutcome.retry`: 5 s, 30 s, 2 min, then parked until the next trigger. `deferred` in the UI engine = the startup gate is not finished: wait for it. `ok` with `stuck > 0` is not retried (T-046 §10).
- After a cycle, and on every resume, the orchestrator calls `markTablesUpdated` for the ingestion tables, because headless writes are invisible to the UI engine's Drift streams (T-046 §10).
- Startup/resume hooks owned here (FU-067, FU-076): construct `ShareIntakeService`, `attach()` + `pollPending()` at start and on every resume; call `purgeExpired()` once per start after the first drain.
- **Idempotency with native.** `writeGuardConfig`: atomic whole-file replace, last writer wins, deterministic bytes, safe to repeat. `drainSpool`: at-least-once; re-delivery ends in `duplicate` by `body_hash`; ack only after commit and only ids this engine drained. `clearSpoolAlerts(seq)`: compare-and-clear. `scheduleIngestionNow`: unique work. A UI-engine crash between commit and ack, or between absorb and clear, repeats work and nothing else.

**Test plan** (unit tests with a fake `CaptureHostPort`, fake clock, in-memory DB; plus the emulator test). Negative proofs mean the test fails if the guarded behaviour is removed.
1. Rule add then `await flush()`: fake host received the new bytes before `flush` completed; a rule change during an in-flight write leads to a second write and `flush` waits for it.
2. L-2: after `write()` the buffer the fake kept is all zero; the settings table and every provider value contain no sender, institution or last-4 (scan of dumped state); `GuardWriteState.toString()` carries code only. Negative: a variant that caches the bytes is caught.
3. Failure table, one case per row, each asserting "no native call" or "retry schedule" and that the previous bytes in the fake are unchanged; `CONFIG_INVALID` is never retried.
4. Parity: bytes equal `buildGuardUserConfig` fed from the T-046 `BatchContext` mapping for the same DB state; Gold off with `kCaptureCustomTemplateSendersWithoutGold` both values.
5. Health table: each `GuardConfigState` x capabilities x toggles gives the expected `mode`/`issues`; `unknown` shows nothing; `keyInvalidatedAtMs` without `decryptDeleted` shows no notice (negative proof for T-039 code #5); a deliberate toggle-off is not `degraded`; Play flavour lists share/paste + manual (+ notifications if granted).
6. Absorb: same `seq` twice absorbs once; clear failing then succeeding does not double count; the race case over-counts by at most one snapshot and never reduces the catch-up request; unreadable status file (random `seq`) gives a silent catch-up and no notice.
7. Orchestrator: `onSpoolChanged` while a cycle runs gives exactly one extra cycle; empty drain with `pending > 0` re-polls on the 5/15/45 s schedule and stops; the headless engine's fake never calls `getSpoolStatus`/`clearSpoolAlerts` (grep test on `ingestion_main.dart` imports).
8. Senders: channel conflict returns `ChannelConflict` and leaves the row; deny-listed package, bad shape and the 11th notification sender are refused with no DB write.
9. Emulator: change a rule in the UI, send a matching SMS, assert it is dropped natively (no spool entry) and a registry SMS for another card is kept.

**Rejected.** Persisting the user part or a fingerprint (L-2); a fixed 5 s debounce for rule changes (breaks "before next capture"); letting the headless engine write config or clear alerts (two clearers, stale `seq` races); clearing alerts only when the user dismisses (blocks recovery bookkeeping); showing raw counters in the UI; a `(sender, channel)` primary key now.

## Acceptance criteria
- [ ] Changing an ignore rule rewrites config before next capture
- [ ] Degraded mode lists active channels (sms-live, notifications, share/paste, manual) with the off reason; a deliberate toggle-off is not degraded
- [ ] The user part is built on demand, passed as plaintext to `writeGuardConfig`, zeroed after the call and never kept in settings, a provider or a log (T-035 L-2)
- [ ] `keyInvalidatedAtMs`/`userUnreadable` rewrite the config at once and verify `guardState == full`; alerts are absorbed into app state before `clearSpoolAlerts(seq)`
- [ ] `capture_senders` channel conflict is refused (FU-096 m-2); notification user senders are validated and capped
- [ ] The UI engine drains on start, resume and `onSpoolChanged`; the headless engine never reads or clears the status
- [ ] DoD (CLAUDE.md §7): analyze clean, formatted, tests added, no hard-coded strings, RTL verified where UI, no `double` money, no raw SMS in logs.

## Lead decisions on the T-040/T-041/T-042/T-043/T-047 design notes (2026-11-11)

These settle the points where the two architects' notes differ; they take precedence over either note.

1. **Ownership of the composition point:** T-041 owns `CaptureRuntime.kt`, `AndroidCaptureDevice`, `MainActivity` wiring, the WorkManager line in `build.gradle.kts`, the WorkManager/spike lines of the placement script, and the Pigeon changes (`ingestion_api.dart`, `holdSpool`, `SpoolStatus.held`, `INVALID_ARGUMENT` — all accepted). T-040 and T-043 call `CaptureRuntime.afterSpoolWrite()` (or the equivalent T-041 exposes) and own only their receiver/listener code, the typed Guard channel (FU-101 L-1), the write-error/Guard-state adapters (FU-104 #3), status-write coalescing, the notification reserve and their manifest entries.
2. **Order:** T-041 and T-042 are built in parallel first. T-040 starts from main after T-041 merges; T-043 starts after T-040 merges (they share files). T-047 starts after T-041 merges.
3. **Spike removal:** the devSms spike receiver and `SpikeGuard` stay until **T-040** replaces them with the production receiver; T-041 replaces the spike's worker/engine/drain loop and `spike_metrics` channel. T-041's foreground "drained within 2 s" AC is proven on devSms until T-047 wires foreground draining for all builds.
4. **Accepted as written:** the worker in every flavour (WorkManager 2.12.0 in all builds, `DiagnosticsReceiver` removed, merged-manifest + no-`androidx.test` checks), held entries under `spool/held/` (FU-105), the 80 % SMS share of the spool, title + newline + content notification bodies (T-036 fixtures must follow), the T-047 capture-health model, `capture_senders` stays keyed by `sender` with the DAO refusing a channel conflict (FU-096 m-2).
5. **T-041 size:** not split; if the build runs long, the builder commits the spool/host follow-ups first and pushes often.
6. **Regex-only registry senders** missed by the first-run scan: T-036 exports concrete sender IDs where the registry knows them (follow-up for T-036).
7. **PO questions** in each note stay open; every default sits behind one constant and is marked provisional.

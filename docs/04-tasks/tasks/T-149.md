## Description
Everything in FR-BAK-06, nothing in FR-BAK-07.

## Technical details
SQLite backup API into temp DB keyed with K_snap; settings manifest; restore: verify, decrypt, open, copy into new DB under fresh K_db, atomic swap; refuse newer schema (EC-26); migrate older; re-grant capture prompt; catalog re-sync.

## Design note
*flutter-core-engineer (Opus), 2026-11-13, written before the code (C4, no crypto/keys design here: every key and primitive is T-148's). Inputs: security-model §5 (restore order), database-schema §2/§4, FR-BAK-03/06/07, EC-26, T-148 note §6–§7, T-016 opener and file set, self-check §1.*

**0. Scope.** `app/lib/features/backup/application/` (+ `data/` for the key-slot adapter, FU-099 item 2). Snapshot → plaintext container → `BackupCipher.encrypt`; and restore: `BackupCipher.open` → container → staged DB → atomic swap. No upload/listing (T-150/T-151), no UI.

**1. Contents v1 (plaintext inside the encrypted stream).** Exactly three entries, in this order, then end of stream: `entry = nameLen u8 ‖ name ASCII ‖ size u64 BE ‖ bytes`.
- `db.snapshot`: an SQLCipher file keyed with `K_snap` (never plaintext pages; a body starting with the plaintext SQLite magic is refused before a byte is written). Size 4 KiB..16 GiB.
- `settings.json` (≤ 1 MiB): `{"v":1,"settings":{key:value}}`, the snapshot's `settings` table (the settings manifest; restore checks it equals the restored table).
- `manifest.json` (≤ 64 KiB): `{"v":1,"contentsVersion":1,"schemaVersion":n,"snapshotBytes":n,"settingsBytes":n,"tables":{name:rowCount}}`. Strict decode (exact key set, integer types, caps).
Unknown names, other order, oversize, trailing bytes → `corruptContents`.

**2. What is in and out (FR-BAK-06/07).** The snapshot is the whole DB (all FR-BAK-06 tables, incl. raw messages, settings, rules, templates, review queue, ignore rules, voice usage) **minus device tables**, emptied in the snapshot: `db_meta`, `secure_state` (keys/tokens/entitlement/flags/backup slot), `outbox`, `diag_log`, and the downloaded catalog (`catalog_merchants`, `catalog_aliases` (+ its FTS through the triggers), `catalog_keywords`, `catalog_meta`). A test classifies every table of the schema, so a new table fails until it is put in one list.

**3. Snapshot (backup side).** In a work dir `<temp>/zaghlol_backup_work/` (cleared by the orphan wipe; every file there is SQLCipher-encrypted). A raw connection on the live file with `K_db` → SQLite backup API (one step, one read transaction: consistent) into `snap.db` keyed with `K_snap` (journal DELETE, `temp_store` memory) → `secure_delete=ON`, empty the device tables → `VACUUM` (no freed page keeps old content) → `integrity_check`, counts, settings. Then the container streams `snap.db` from disk into `encrypt`. `fileId` is chosen first (new optional `fileId` on `BackupCipher.encrypt`) so `K_snap` can be derived before the header is written. Work files are deleted when the stream ends, errors or is cancelled.

**4. Restore order** (security-model §5; each step only if the previous passed; **nothing touches the live DB before step 7**):
1. `cipher.open(maxSchemaVersion: appSchemaVersion)`: newer schema refused before the KDF (EC-26), wrong passphrase at unwrap.
2. Container → `snap.db` in the work dir (encrypted bytes only), small entries in memory with caps. Untrusted until `done`.
3. `done` (authenticated) → manifest ↔ header (contents/schema version, sizes).
4. Open `snap.db` with `K_snap`: `user_version` must equal the header's (0 or mismatch → corrupt; > app → `newerSchema`), `integrity_check` (incl. CHECKs) ok, `foreign_key_check` empty, device tables empty, row counts = manifest, settings = `settings.json`.
5. Stage: backup API `snap.db` → `stage.db` under **this device's `K_db`**; migrate an older schema with the normal `AppDatabase` steps (no migration guard: its copy files belong to the live directory), `validateSchema` on (shape = current schema, so no foreign trigger/view survives), `integrity_check` + `foreign_key_check` again.
6. Carry device state: read the live device tables in one read transaction, write them into `stage.db` in one transaction; set `secure_state backup.key_slot.v1` to the restored file's slot; `db_meta restore_regrant_due = 1` (FR-BAK-07 re-grant prompt) and `restore_catalog_resync_due = 1`. Page sizes and `user_version` of stage and live must match.
7. **Swap:** SQLite backup API `stage.db` → the live `zaghlol.db`, through a raw connection with `K_db`. It is **one write transaction on the live file** (WAL): a crash, kill, `SQLITE_FULL`, timeout or cancel before the commit frame leaves the old database exactly as it was; after it, the new one. SQLite recovers it on next open; no file is renamed, so the sandbox root and its backup-exclusion flag are never touched (T-165 F4), and other connections (drift, headless engine) simply see the new content. Bounded by a timeout (cancel = rollback).
8. After the commit: store the restored `K_bk` in the secret store (new `BackupCipher.storeRestoredKey`, under the lease, read back). A crash here leaves slot ≠ secret → `keyMismatch` → the next backup asks for the passphrase (`recoverWithPassphrase`), the T-148 path.
9. Delete the work dir; the caller re-opens the DB (`ref.invalidate(appDatabaseProvider)`) and triggers the catalog sync.

**5. Never destroy data on doubt.** The only write to live data is step 7, a single SQLite transaction. Every earlier failure (including a process death) leaves only work-dir files, which hold encrypted derived copies and are swept at the start of the next backup/restore. The work dir is never inside `db/`, so the T-016 opener never mistakes a staged file for a migration copy. One in-process lock serialises backup and restore (the headless engine never runs either).

**6. Deviations / choices.** (a) "copy into a new DB under fresh K_db, swap atomically" is done as a copy under **this device's existing `K_db`** plus a page-level transactional replace, not a key + file rename: two stores (Keystore and file) can't be swapped atomically, and a rename under open connections would corrupt the WAL. On a new phone `K_db` is fresh anyway, and the source's key never travels (FR-BAK-07). (b) Reserved name `zaghlol.db.restore.tmp` stays unused. (c) Residual: device-table writes landing between step 6's read and the step-7 commit (seconds) are lost; restore is a foreground, modal flow. (d) No money is decoded during restore (pages are copied, then checked by SQL), so the T-012 F6 rule has nothing to apply to; CHECK constraints are verified by `integrity_check`. (e) The live DB must exist (the app opened it); the service never creates it.

**7. Errors.** `BackupSnapshotException(code)` codes `busy, newerSchema, corruptContents, liveUnavailable, swapFailed, io` (code-only, `SafeException`); crypto errors pass through as `BackupCryptoException`.

**8. Tests.** Checklist (every FR-BAK-06 table identical, device A → device B with different `K_db`), device tables kept from B, older-schema (v3) snapshot migrated, newer refused before the KDF with live untouched, tampered/plaintext/oversize contents refused, fault at every step leaves live intact and is swept, crash snapshot of the files mid-swap opens the old DB, crash after swap → `keyMismatch` → passphrase recovery, privacy scan of the work dir and DB dir at every step, no secure-state bytes in the decrypted snapshot, concurrent calls → `busy`.

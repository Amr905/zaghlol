## Root cause (Lead, reproduced off-device)
The PO's original photo (1932×2576, English restaurant receipt with one Arabic word) was run through Tesseract with the app's own `ara.traineddata` (LSTM, PSM auto), as `TesseractArabicEngine` does. Every Latin line comes back as Arabic-letter noise with wrong digits, e.g. `Amount Due 436.00` → `44600 ونا 11نا 481710`, `Net Sales 382.46` → `321146 535 أول١ا`, hotline/phone lines → long digit runs. `OcrMerger` (ADR-009) **keeps every Tesseract line that contains an Arabic letter** and **drops the overlapping ML Kit Latin line**, appending only its digit tokens. So on a Latin receipt the correct ML Kit text is replaced by noise, and the receipt reader sees junk numbers (1,558). A smaller image changes the boxes/noise, which is why the compressed copy read correctly. The merger's own comment says its thresholds are unvalidated.

## Scope
1. `OcrMerger`: an Arabic (Tesseract) line replaces an overlapping Latin (ML Kit) line only when it is credibly Arabic: Tesseract line confidence ≥ a threshold (start 0.60; `RawLine` already carries confidence) **and** Arabic letters are the majority of its letters **and** the overlapping ML Kit line is not a strong Latin read (≥ 3 Latin letters in words of ≥ 2 letters, or it is digits/amount-only). Otherwise keep the ML Kit line and drop the Tesseract one. Mixed lines (`Name: عميل نقدى`): keep the ML Kit line and append the credible Arabic words (confidence per word if available; else the Arabic-letter tokens) — never append digits from the Arabic line.
2. Never append to a kept Arabic line a digit token longer than the ML Kit token it came from, and never let the Arabic line's own digits stand where an overlapping ML Kit line has digits: ML Kit's digits win (the existing "ML Kit reads digits better" rule, applied fully).
3. Tesseract lines with no overlapping ML Kit line: keep only when confidence ≥ threshold and Arabic-majority (today any Arabic letter is enough).
4. Large images: confirm the decode sample size path (`OcrLimits.DECODE_MAX_PIXELS`) is the same for camera, gallery and share; add an upper bound on the long side for the Tesseract pass only if it measurably reduces noise in the fixtures (don't change ML Kit input).
5. Pure-Kotlin unit tests (`OcrMergerTest`) with fixtures built from the Lead's reproduction (synthetic copies of the noise lines and the matching Latin lines with boxes): the Latin receipt keeps `Amount Due 436.00`, `Net Sales 382.46`, `VAT 53.54`, `Visa 436.00`; a real Arabic pharmacy receipt (Arabic lines with confidence ≥ threshold, digits from ML Kit) is unchanged; a mixed line keeps both parts. Update ADR-009 with the validated rule.
6. iOS (Vision) is not affected; say so in the task file after checking the Swift merger path, if any.

## Acceptance criteria
`OcrMergerTest` cases above pass and the Latin-receipt case fails on the old merger; existing OCR host tests green; no raw OCR text logged. Kotlin compiles in CI (not locally).

## Description

## Implementation notes
Files: `app/lib/core/flags/{feature_flags,flags_service,flags_providers}.dart`, `app/test/core/flags/flags_service_test.dart`. No schema change (uses `secure_state`, key `flags.snapshot`, JSON `{v:1, version, at, values}`, <= 4 KiB).
- `FeatureFlag` enum is the closed set (`zakah`, `smart_roi`, `roi_named_products`). `FeatureFlagsState.isOn` is true only for a `fresh` snapshot that says ON.
- Fail closed: never synced, unknown/missing key, malformed or oversized stored bytes, read error, stale (older than 14 days by app clock, `FlagsService.maxAge`) and a clock more than 5 min before the snapshot time all read OFF. Stored bytes are never deleted on doubt; the next good sync replaces them.
- Apply (`FlagsService.apply`, called by sync T-143 or `refresh()` via the `RemoteFlagsSource` port, implemented later by BackendClient T-141): strict validation (int version >= 0, bool values; unknown keys ignored; any non-bool known value rejects the whole answer), a lower version than stored is rejected (replay), equal accepted (the backend resends on app-version change). Writes are serialized; the state changes only after the write succeeded.
- UI follows without restart: `featureFlagsProvider` (stream, current value then changes, no gap) and `featureFlagProvider(flag)` (false while loading or on error). A timer publishes the stale transition by itself.
- EC-49: the service has no delete path; turning a flag off hides features only.
- Shared files: none touched (no edit to the settings/T-020 files or any shared provider file).

Deviations / assumptions: the 14-day `maxAge` and 5-minute tolerance are my choice (the docs give no number); the app clock is not the trusted clock (T-144), so a user who sets the clock back can keep their own snapshot fresh (stated residual). Providers `remoteFlagsSourceProvider` (null until T-141) and `flagsClockProvider` are the injection points.

### Self-check (docs/workflow/self-check.md)
1. Never destroy data on doubt: applies; no delete/overwrite on read or parse error (test "unverifiable stored bytes ... not deleted").
2. Concurrency: applies; two simultaneous applies are serialized, higher version wins (test "two syncs at once"). The DB write is a single upsert.
3. Untrusted input: applies; size cap on stored bytes, strict types, unknown keys ignored, errors carry no input (tests for each malformed case).
4. Fail closed: applies; see above.
5. Secrets and logs: no logging; snapshot holds flag data only (test).
6. Docs match code: notes above state residuals; no contract change in docs/03-technical.
7. Evidence: AC1 "never-synced app has every flag OFF"; AC2 "providers: featureFlagProvider follows a sync, no restart" and "AC2: a later change updates the state"; unit tests only (C2).

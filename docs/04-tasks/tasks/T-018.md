**2. Catalog (§2.4).** Server data, integer ids as on the backend; constraints mirror the OpenAPI shapes so a bad op fails the whole apply transaction (FR-SYNC-03) instead of storing junk:
- `catalog_merchants`: `id ≥ 1`; `canonical` 1–80 chars (a display name, e.g. "Koshary El Tahrir", not the key); `category_code` = OpenAPI `CategoryCode` (`^[a-z][a-z0-9_]{1,31}$`, as GLOBs); `version ≥ 0`. `category_code` stays a soft reference (no FK to `categories.system_code`), as in the spec: the catalog sends merchants and categories as independent ops.
- `catalog_aliases`: `alias_norm` must be the **canonical merchant key** of parsing-engine §5 (T-034): 1–64 chars of `[a-z0-9 ]`, no leading, trailing or double space (exactly `^[a-z0-9]+( [a-z0-9]+)*$`, as in backend-schema `catalog_drafts`); a test feeds every non-empty output of `packages/zaghlol_parsing/test/fixtures/merchant_key_vectors.json` through it. `match IN ('exact','prefix','token')`. Identity stays `(alias_norm, merchant_id)` (UNIQUE), but the table gets an `id INTEGER PRIMARY KEY`: the external-content FTS needs a rowid that survives `VACUUM`, which a composite-key table's implicit rowid does not (same reason as `transactions_fts_src`, accepted in T-017). `ix_alias_merchant` for the FK cascade.
- `catalog_alias_fts`: `fts5(alias_norm, content='catalog_aliases', content_rowid='id', tokenize='trigram')`, kept in sync by after insert / update / delete triggers on `catalog_aliases` (external-content `'delete'`). The DAO upserts with `ON CONFLICT … DO UPDATE` (never `INSERT OR REPLACE`, whose implicit delete fires no trigger without `recursive_triggers`).
- `catalog_keywords`: `(keyword_norm, lang)` key; `keyword_norm` 1–64 chars, no leading/trailing/double space and no control characters (Arabic keywords are folded Arabic, not `[a-z0-9]`, backend-schema); `lang GLOB '[a-z][a-z]'`; `category_code` as above; `weight` integer 0–100 (OpenAPI).
- `catalog_meta`: single row `id = 1`, `version ≥ 0`, non-empty `signature_kid`.

**3. Rules (§2.4).** `merchant_rules` as specified, plus per-kind value CHECKs: `merchant_norm` → the canonical key form; `catalog_merchant` → a positive decimal integer without leading zero; `counterparty` → 1–128 chars, no control characters. `ix_rules_category` (FK child index; category deletes/merges).

**4. Budgets, alerts, summaries, recurring (§2.5).** Money CHECKs exactly as T-017 §4 (`typeof = 'integer'`, ±(2^53−1), currency `GLOB '[A-Z][A-Z][A-Z]'`):
- `budgets.limit_minor` ≥ 0; `rollover` 0/1; `thresholds` `json_valid` and a JSON array; **`ux_budgets_overall`** (partial unique on `(currency, period) WHERE category_id IS NULL`), because the spec's `UNIQUE (category_id, currency, period)` treats NULLs as distinct and would allow two "overall" budgets for the same currency and period (A-16).
- `fired_alerts`: `kind` a slug (`[a-z0-9_]`, 1–64), non-empty `subject_id`/`period_key`, `threshold` integer ≥ 0. "Fire once" is the primary key: `FiredAlertsDao.markFired` is `INSERT … ON CONFLICT DO NOTHING` and returns whether this caller won (two actors: exactly one `true`).
- `cycle_summaries`: `cycle_start` a real ISO date (`date(x) = x`), `income_minor`/`spend_minor` signed money (a read-model cache must not refuse a computed value), `by_category` a JSON object.
- `recurring_items`: `amount_minor` ≥ 0 with currency; `cadence_days` set iff `cadence = 'custom_days'` (1–3660); `due_day` NULL or 1–31; `next_due_date` NULL or a real ISO date; `total_count` NULL or ≥ 1; `0 ≤ paid_count ≤ total_count`; `reminder_days` 0–60; `name` 1–60 chars; `merchant_norm` NULL or canonical key. `ix_recurring_due` (`next_due_date WHERE status = 'active'`), `ix_recurring_account` (FK).
- `recurring_occurrences`: `due_date` a real ISO date; `ix_recurring_occ_txn` (FK `ON DELETE SET NULL` lookup).

**5. DAOs (`app/lib/core/db/daos/`).** Plain classes as in T-017, writes through `guardWrite`, reads that take user/external text through `guardRead`; nothing logs. `CategoriesDao` (insert, by id/system code, active list ordered by `sort`, archive), `CatalogDao` (apply-op primitives: upsert/delete merchant, alias, keyword; meta get/set; exact alias lookup; `aliasCandidates(key, limit)` = trigram candidates, see below), `MerchantRulesDao` (upsert by `(match_kind, match_value)`, lookup, delete), `BudgetsDao` (insert/update with `Money`; a `Money` whose currency differs from the row is refused before SQL), `FiredAlertsDao`, `CycleSummariesDao` (upsert/get), `RecurringDao` (items + occurrences). Repositories (T-030, T-051, T-074, T-075) build on them. Seeds (14 system categories) are T-030's; this task ships none.
**Trigram candidates (AC2).** The input must already be a canonical key (else `ArgumentError`, nothing queried). Keys shorter than 3 characters have no trigram and return no candidates (exact/prefix lookups cover them). Otherwise the query is the OR of the key's distinct trigrams, each a quoted FTS5 string (only `[a-z0-9 ]`, so quoting is total), bound as a parameter, ranked by `bm25`, `LIMIT` capped at 50 (default 10); a misspelt key (`ezabi` for `ezaby`) still finds its alias. Results are `(merchant_id, alias_norm, match)`.

**As built (implementer, 2026-11-11): differences from the note above.**
- §2: `catalog_merchants.canonical` is 1–**200** characters, not 1–80: the backend has no length limit on `canonical`, and a CHECK tighter than the server would fail every later catalog apply on one long name. Still non-empty.
- §2/§4: `financial_b.drift` starts with `import 'financial.drift';` (drift needs it to resolve `split_participants`/`offset_links` in a trigger of another file). JSON CHECKs are `CASE WHEN json_valid(x) THEN json_type(x) = '…' ELSE 0 END`, because `json_type` raises on malformed JSON instead of returning false. Date CHECKs use `date(x) IS x` (NULL-safe: `date('junk')` is NULL, which a plain `=` would let through a CHECK). `ix_recurring_account` is partial (`WHERE account_id IS NOT NULL`).
- §5: `FiredAlertsDao.markFired` answers from the changed-row count: drift's insert id is SQLite's last insert rowid, which after an ignored insert still names the previous insert (a test shows the stale-id version goes red). Tests cover 10 concurrent callers and two connections on the same file.
- §6/§7: the FTS probes are in `test/core/db/fts_probe.dart` (shared with the device suite); the device suite gains a populated v2 → v3 test (secure-delete set and effective on the shipped sqlite3mc, trigram candidates, m-1/m-2), so this task opts into `ci/T-018` for db-platform.
- §5: `CategoriesDao.upsertSystem` keeps `is_archived` on update; no seeds (T-030).

## Description
The one place that decides who holds a purchase's single Gold seat. Every channel (verify, restore, sign-in, support) calls it inside its own transaction.

## Technical details
- All operations run under `SELECT … FOR UPDATE` on the `purchase_seats` row, in the caller's transaction, and write `purchase_events` with the documented `cause`.
- **Window:** `ceil_hour(t)` to the next whole UTC hour (R3-4). A move sets `last_moved_at = now`, `next_move_at = ceil_hour(now + 30 d)`; allowed only if `next_move_at` is null or `now ≥ next_move_at`. The stored value is the only one checked and returned.
- **Bind** (verify, seatless purchase): holder = buying install, `proof = binding`, not a move. **Same holder:** no change.
- **Plan change** (D-59, D-61(a), R3-7, R4-4): account rule first (account-linked purchase and no valid account token for it → stay, claimant `channel = verify`, `accountRequired`); else move if no cooldown (`seat_move:verify`) or stay and add claimant. Never refuses (caller still acknowledges). Google successors inherit the predecessor's seat, `account_id`, `attach_reclaim_used_at`, `next_move_at`.
- **Account-attach reclaim** (D-58, R3-3): once per purchase while `attach_reclaim_used_at IS NULL`; counts as the move; sets it; never cleared.
- **Claimants** (R3-4): up to 3 per purchase, 7 days; a fourth replaces the oldest; a repeat refreshes; stores the caller's per-purchase seat-key hash if registered; channel `restore | signin | verify`.
- **Seat-key registration and trust (R4-1(1), R5-2):** `RegisterElementZero(install, pk, trusted)` stores `installs.seat_key_hash` once (never replaced); **`trusted = true` is accepted only from an App Attest-covered call** — the API requires an `AppAttestVerified` capability token that only T-185 (restore after a passed assertion) can obtain; verify and sign-in register untrusted; the flag only goes false → true.
- **Holder key:** whenever an iOS install becomes or stays holder, `device_key_hash = SeatKeyHash(registered key)` and `device_key_trusted = installs.seat_key_trusted`; a holder without a registered key sets NULL/false; kept when the seat goes vacant.
- **Rebind** (D-55, D-63): non-holder; element 0 = caller's registered key; a valid element at **position ≥ 1** hashes to `device_key_hash` (position 0 never rebinds); attestation/ID token and account rule already passed; fewer than 2 entries in `recent_rebinds` after pruning entries older than 30 days → pass without cooldown, `device_key_hash` = caller's registered key, append time, `seat_rebind:<channel>`.
- **Over the cap** (D-65(a)): restore match → over-cap rebind, never refused, window restarts, `recent_rebinds` unchanged, `seat_rebind_over_cap:restore`; sign-in match → same **only if `device_key_trusted`**, otherwise an ordinary move under the cooldown with `restoreSuggested = true` and `seat_rebind_over_cap:signin` recorded; every over-cap case emits the `seat_rebind` alert metric (purchase UUID only).
- **Support-move primitive** (D-56, R5-4) for T-186: move to the target, restart the window, remove the target's claimant entry, `movedBy = support` for the loser; `device_key_hash` from the target's claimant entry (NULL if none, **always NULL on a move back**); `device_key_trusted` from the **target install's** `seat_key_trusted` at that moment, false whenever the hash is NULL, never kept from the previous holder.
- **Vacant seats** (install deleted/purged): taking one is a move unless it is a same-iPhone rebind.
- Returns a typed outcome (`Bound | Unchanged | Moved | Rebound | ReboundOverCap | Refused(nextMoveAt) | AccountRequired | ClaimantAdded`) with `movedBy` for the previous holder.

## Design note
*Opus (implementer acting as architect, per the Lead's brief), 2026-11-11. Inputs: backend-api §4.3 (Seat at verify, Restore step 5, Same-iPhone recognition), §4.6 steps 4–6, §5.3; backend-schema `purchase_seats`, `seat_claimants`, `purchase_events`; T-182 consumer API and security review L-1.*

**1. Shape.** `Zaghlol.Application/Seats`:
- `SeatService` (stateless; `SeatKeyHasher`, `ISeatTelemetry`). Every method takes an `ISeatStore`, which is **the caller's open transaction** (the service never begins or commits). Methods: `RegisterElementZeroAsync`, `VerifyAsync`, `RestoreAsync`, `SignInAsync`, `SupportMoveAsync`. Each returns a `SeatResult {Outcome, CallerHolds, NextMoveAt, PreviousHolder, MovedBy, RestoreSuggested, Cause}`.
- `SeatRules.Decide(...)`: the pure decision (state table below), unit-tested cell by cell; the service only loads, hashes, decides and writes.
- `SeatClock.CeilHour(t)`: the next whole UTC hour, `t` itself when it already is one. `next_move_at = CeilHour(now + 30 d)`. The cooldown runs while `now < next_move_at` (the stored value, nothing recomputed).
- Infrastructure: `NpgsqlSeatStore` over a caller's `NpgsqlConnection` + `NpgsqlTransaction` (callers in Infrastructure, e.g. T-132's writer, pass theirs), and `ISeatTransactionFactory.BeginAsync(SeatLogin.App | Support)` for Application callers (T-185, T-135, T-186): one READ COMMITTED transaction on the App or Admin login, rolled back on dispose unless committed.

**2. Locks (one order everywhere).** `installs` row (registration only) → `purchases` row `FOR UPDATE` → `purchase_seats` row `FOR UPDATE`. The purchase lock comes first because verify's upsert (T-130) already locks it, and it serialises the *creation* of a seat row too (no insert race, no empty row left behind). A Google predecessor is read `FOR SHARE` after the successor (chains only point backwards, so no cycle). KMS calls for the rebind match run under the lock (at most 4, parallel; T-182); element-0 hashing runs before any lock.

**3. Seat keys (R4-1(1), R5-2, T-182 L-1).**
- `RegisterElementZeroAsync(store, VerifiedSeatKeys keys, AppAttestVerified? attested)` → `Registered | AlreadyRegistered | Mismatch` and, unless mismatch, a `RegisteredSeatKey` (element 0 + the install's current `seat_key_trusted`). Registration is `UPDATE … SET seat_key_hash = @h WHERE seat_key_hash IS NULL` under the install lock (set once; the SEC F9 trigger is the backstop). Mismatch writes nothing.
- `trusted = true` only with an `AppAttestVerified` whose install equals `keys.InstallId`, whose covered `seatKeysDigest` equals `keys.Digest()` and with `keys.Op = restore` (else `ArgumentException`); the flag only goes false → true (`UPDATE … SET seat_key_trusted = true WHERE seat_key_hash = @h`). `AppAttestVerified` is a sealed class (not a struct, so `default` can't forge it) with an **internal** constructor and no public factory; an IL-scanning test fails if any method outside namespace `Zaghlol.Application.Purchases.Restore` (T-185) constructs it.
- Seat operations accept only a `RegisteredSeatKey` (internal constructor, issued by registration), so rebind condition 1 holds by type. The holder hash is `SeatKeyHasher.SeatKeyHashForHolderAsync(purchaseId, keys)`, which hashes **element 0 only**; the public `SeatKeyHashAsync` now refuses `Position ≠ 0` (L-1), and `MatchSeatAsync` uses a private path.
- **Holder key:** caller becomes or stays holder **with** a `RegisteredSeatKey` → `device_key_hash` = its element-0 seat hash, `device_key_trusted` = its install flag. Becomes holder **without** one → `NULL` / false (never kept from the previous holder). Stays holder without one → unchanged. Vacated by the delete trigger → kept.

**4. State table** (`h` = holder: none = no seat row, self, other, vacant; `cd` = `now < next_move_at`; `m` = an element at position ≥ 1 matches `device_key_hash`; `cap` = `recent_rebinds` pruned to the last 30 days has 2 entries; `tr` = `device_key_trusted`; `acct` = the purchase's `account_id` is set and the request's valid account token is not for it). One event row = one `purchase_events` row with `from_state = to_state` = the purchase's state.

A "move" sets `last_moved_at = now`, `next_move_at = CeilHour(now + 30 d)`, `bound_at = now`. A vacant seat taken is a move (R5/S8/V6) unless it is a rebind. Whenever the caller becomes holder, its own claimant row (if any) is deleted. `recent_rebinds` is pruned (entries ≤ now − 30 d dropped) and written back on every App-login seat write.

**5. Claimants (R3-4).** Under the seat lock: a repeat by the same install updates `claimed_at`, `channel` and `device_key_hash = COALESCE(new, old)` (the install's registered key never changes, so the old hash is the same key's); otherwise, if 3 unexpired rows exist, the oldest unexpired one is deleted, then the row is inserted. Rows older than 7 days are ignored by the count and by the support eligibility check.

**6. Events and telemetry.** Exactly one event row for each outcome that changes the holder or the window (V1, V6, R3–R5, S3–S8, P3) and for S7 (the over-cap sign-in record the spec asks for); none for the no-op outcomes. The cause CHECK has no sign-in no-op cause, and "nothing that affects Gold is written" for refusals (§4.3), so "every outcome writes exactly one row" is read as "per this table" (tests assert one row or zero for every cell). `zaghlol.seat.change{channel, kind}` for each change; `IAlertSignal.Raise(SeatRebindOverCap, purchaseId)` for R4, S5–S7. Callers count `MOVE_COOLDOWN` refusals (the 409 is theirs).

**7. Decisions for review.** (a) V4 on a *vacant* seat leaves it vacant: verify changes a holder only for a new payment (§4.3), and the owner's path back is restore. (b) Rebind proof `device` (the only otherwise unused proof value), but a `basic` restore stays `basic` so the 2-day token limit can't be shed by a rebind. (c) The account rule for support targets (target linked to the account) stays with T-186; the primitive enforces target eligibility (claimant / move-back) only. (d) Successor inheritance copies the whole seat row (holder, proof, times, key, `recent_rebinds`), not only `next_move_at`, so the D-63 budget can't be reset by an upgrade.

**8. Tests.** Application: `SeatRulesTests` (every cell above, plus the boundary at `next_move_at − 1 s` / `next_move_at`), `SeatClockTests`, `AppAttestVerifiedTests` (IL scan). Infrastructure (Testcontainers): `SeatServiceTests` per cell with the event-row assertion, the R5-4 support trio, the 20-way concurrency test, the D-58 reclaim-after-relink test, the claimant cap/expiry tests, the R4-1(1) hash test and the accepted-residual-1 sign-in chain scenario.

## Acceptance criteria
- [ ] FR-GOLD-08 invariant: at most one holder per purchase under 20 concurrent move attempts (concurrency test).
- [ ] R3-4: `next_move_at` is always a whole UTC hour and the cooldown check uses it exactly (boundary test at `next_move_at − 1 s` and `next_move_at`).
- [ ] D-58/R3-3: a second reclaim on the same purchase, after account deletion and re-link, is an ordinary move under the cooldown (test).
- [ ] R3-4: a fourth claimant replaces the oldest; claimants older than 7 days are ignored (tests).
- [ ] R4-4/D-59/D-61(a): the plan-change table (account-linked with/without token × cooldown/no cooldown) produces the documented outcome in all four cells (test).
- [ ] D-55/D-63: rebind from position 1 passes without cooldown; a match on element 0 is never a rebind; a third rebind within 30 days is over-cap (tests).
- [ ] D-65(a): over-cap restore match passes and restarts the window; over-cap sign-in match passes only with `device_key_trusted = true`, otherwise ordinary move with `restoreSuggested` (tests).
- [ ] **R5-2:** registration via verify or sign-in leaves `seat_key_trusted = false`; only the restore path (with the `AppAttestVerified` capability) can set it true; a test proves the capability can't be constructed outside the restore assembly.
- [ ] **R5-4 (shared with T-186):** support move from a holder with `device_key_trusted = true` to a claimant with an untrusted registered key → `device_key_trusted = false`; a move back → `device_key_hash = NULL`, `device_key_trusted = false`; a move to a claimant whose install key is trusted → `true` (three tests).
- [ ] The seat's hash after a rebind is the caller's registered key, not the matched earlier key (R4-1(1) test).
- [ ] Every outcome writes exactly one `purchase_events` row with the documented `cause` (test).
- [ ] Accepted residual 1 of the security review (sign-in rebind budget on stock iOS) is bounded as specified: a chain of sign-ins yields at most 2 cooldown-free rebinds plus one over-cap hop in 30 days (scenario test).
- [ ] DoD (CLAUDE.md §7): analyze clean, formatted, tests added, no hard-coded strings, RTL verified where UI, no `double` money, no raw SMS in logs.

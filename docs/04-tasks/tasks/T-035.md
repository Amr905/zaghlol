## Description
One definition of what may be stored, reused by Kotlin and Swift.

## Technical details
Guard algorithm per platform-channels §1.2; config JSON generator from registry + DB state (ignore rules, capture senders, custom templates); shared golden case file (≥ 60 cases: non-financial drop, OTP drop, institution ignore, card ignore, generic keep) consumed by Dart/Kotlin/Swift tests.

## Design note
(solution-architect, Opus, 2026-11-11. C4: SMS/notification ingestion. Reviewers: challenge it. Deviations from `docs/03-technical` are marked **[doc change]**; they need Lead sign-off, and this task updates platform-channels §1.1–1.2 to match. Carries FU-082 and the Guard part of FU-084.)

**Goal.** One pure-Dart definition of "may this message be written anywhere", plus the data (config + golden cases) that makes the Kotlin (T-038) and Swift (T-061) Guards provably identical. Code in `packages/zaghlol_parsing/lib/guard/`; no I/O, no logging, no Flutter. The Dart Guard is also the drain-time re-check for T-046 (ignore rules set after a message was spooled, or a broken native config, are caught there before the DB).

**1. Config: two parts [doc change].** The registry ships with the app (D-17), so its part needs no runtime write. Split §1.1's single file into:
- **Base** `guard_base.json`: generated at build time from the registry by `exportGuardConfig` (bump `v` to 4), plaintext (public registry data, protected by the app signature), bundled as a Flutter asset `app/assets/guard/guard_base.json` that native code reads without an engine (Android `AssetManager` `flutter_assets/...`; iOS T-061 also copies it into the App Group for extensions). Fields: `v`, `registryVersion`, `senders[{match,value,inst}]`, `packages[{value,inst}]`, `wallet[{name,inst}]` (new: `walletCardNames`, for `apple_pay`), `drop{global[],byInst{}}`, `last4{inst:[],"*":[]}`, `generic{senderHints,bodyHints,alwaysCapture}`, `shortcutKeywords`, `rate{perSenderPerMin}`. Deterministic bytes (sorted, fixed key order); `registry_lint --check-guard-config` fails CI when stale. Size ≤ 200 KB.
- **User** part: built by `buildGuardUserConfig(ignoreRules, userSenders)` from DB state (T-047 reads the DB and calls it): `{v:1, baseRegistryVersion, ignore[{inst,last4|null,ch}], userSenders[{value,ch}]}` (`userSenders` = `capture_senders.always_capture` ∪ Gold custom-template senders). Sorted, deduped, ≤ 64 KB, ≤ 1,000 ignore rules, ≤ 200 senders; over a cap → error, never truncation. Dart can't use the non-exportable spool key, so **Pigeon `writeGuardConfig(Uint8List userConfigJson)` takes plaintext** [doc change; today "encryptedConfig"]: native parses it with its own reader (invalid → `CONFIG_INVALID`, old file kept), encrypts with `SpoolKey` (AAD `zaghlol.guard.v1|user`), writes `files/guard/guard.user.enc` via tmp + fsync + rename, zeroes the buffer.
- **Modes** (`GuardConfig.parse(baseJson, userJson?)` → `full | baseOnly | invalid`): user absent → `baseOnly` (fresh install; normal). User undecryptable, malformed or unknown `v` → `baseOnly` + diag `CONFIG_INVALID` (keeps registry senders, T-038 AC2; see PO Q1). Base unreadable or invalid → `invalid` → every message dropped with `config_invalid` (build defect; the Android catch-up scan recovers SMS). An older `baseRegistryVersion` is fine: ignore rules are keyed by institution code, so an app update never loses them and never waits for an app open.

**2. Normalisation (FU-082).** All matching runs on `foldKey(body)` and `foldKey(source.trim())` (T-013: digits incl. Arabic-Indic → ASCII, `٫٬`, invisible marks incl. ZWJ/ZWNJ/RLM/BOM removed, tatweel and harakat removed, `أإآٱ→ا ى→ي ة→ه`, whitespace runs incl. newlines → one space, **ASCII-only** lowercase). Natives port it code unit by code unit: no `Normalizer`/NFKC, no locale or Unicode `lowercase()` (Turkish İ, Kelvin sign), no confusable folding (a Greek-Epsilon "NBΕ" must stay unknown: folding would widen the allowlist). Body length is checked on the **raw** body in UTF-16 code units (Swift `utf16.count`, not `count`).

**3. Portable regex subset (new lint, every Guard-bound pattern: sender regex, drop, last4, hints).** Kotlin/Android and Swift use ICU, Dart uses ECMAScript; they disagree on `\b \w \d \s`, case folding and inline flags. The exporter strips a leading `(?i)`, applies `foldArabicVariants`, then the lint rejects: any uppercase ASCII letter (the body is lowercased; patterns compile case-sensitive everywhere), `\b \B \w \W \d \D \s \S \p \u \x`, inline flags, lookaround, backrefs, named groups, possessive/atomic, POSIX classes, escapes other than of metacharacters, more than one capture group in `last4` (group 1 = 4 digits), plus the existing backtracking heuristic and runtime probe (extended to sender regexes). Write `[0-9]`, a space, `(?:^|[^a-z])otp(?:$|[^a-z])` instead. Compile: Dart `RegExp(p, unicode: true)`, Kotlin `Regex(p)`, Swift `NSRegularExpression(pattern: p, options: [])`. The Dart Guard compiles the **exported** text, never the registry's `CompiledPattern`, so it tests exactly what natives run.

**4. Algorithm (replaces platform-channels §1.2 [doc change]).** Input `channel, source, body`; output `Keep(inst?, last4?, kind: registry|user|generic)` or `Drop(reason)`.
0. Channel not in {`sms`,`notification`,`shortcut_message`,`apple_pay`,`share`} → `unknown_channel`; empty folded body → `empty_body`; raw length > 4,000 → `too_long` (before any regex).
1. Resolve: `notification` → package exact on the trimmed source; `sms`/`shortcut_message` → sender exact on folded key, then sender regex on folded key; `apple_pay` → longest `wallet.name` (folded) contained in the folded source, tie → none. Hit → `inst`, kind `registry`. Else source ∈ `userSenders` (same channel) → kind `user`; else ∈ `generic.alwaysCapture`, or channel ∈ {`apple_pay`,`shortcut_message`,`share`}, or (`senderHints` match source **and** `bodyHints` match body) → kind `generic`; else **Drop `not_financial`**. (§1.2's "guess institution by body" is removed: ambiguous and drift-prone.)
2. `drop.byInst[inst]` match → `otp_or_promo_inst`; else `drop.global` match → `otp_or_promo_global` (same order and reason split as pipeline stage 0).
3. If `inst` ≠ null: ignore channel = `sms` for `sms` and `shortcut_message` (iOS SMS arrive via Shortcuts; FR-CAP-01 toggle), else the channel itself; `share` has no ignore. Rule `(inst, null, ch)` → `ignored_institution`.
4. `last4` = group 1 of the first hit in `last4[inst]` then `last4["*"]`, accepted only if exactly 4 ASCII digits. Rule `(inst, last4, ch)` → `ignored_card`. Never last4 alone (EC-59): rules without `inst` cannot exist (schema `NOT NULL`) and the parser rejects them; no last4 found → only step 3 applies (BR-CAP-02). With several cards in a body, the first hit decides.
5. Keep.
`decide` is pure. **Rate limit (FU-084b)** is a separate `SenderRateLimiter(nowMonotonicMs)`, applied only to Keep: > `perSenderPerMin` keeps from one `(channel, sourceKey)` in a sliding 60 s → `rate_limited` (diag count only). In-memory, ≤ 64 keys LRU, resets with the process (persisting would write sender IDs). Android recovers rate-limited SMS via the Q7 catch-up; notifications are lost (PO Q3).

**5. What is dropped (FU-082 corpus, data in `shared.json` / institution files).** Global drop = OTP/verification only, shaped as *keyword within a short non-digit gap of a 4–8 digit code, either order*, so footers like "never share your OTP" on a real transaction do **not** drop it. Keywords (folded): otp, one time password/passcode, verification/verify/security/activation/login code, passcode; رمز/كود التحقق، التفعيل، الدخول، الامان؛ كلمه السر لمره واحده؛ الرقم السري المؤقت؛ كلمه المرور المؤقته. The code must not be an amount (`[0-9]{4,8}` not followed by `[.,][0-9]`). Promo patterns are **per institution only** (generic promo words collide with transaction words: `خصم` = debit); unmatched promos from a bank reach review as `unrecognized` (PO Q6). Align the spike's Kotlin list and the Dart registry (`كود التفعيل`) by generating, not copying.

**6. Spoofing stance (FU-084).** The Guard is a privacy filter, not an authenticity check: alphanumeric sender IDs can be spoofed and the Guard keeps on sender match. Mitigations elsewhere: generic/user-sender messages are always review (T-073); template-matched spoofs are auto-saved — a residual this task records in ADR-005 *Threats* (FU-084c) with the rate limit and spool caps as the DoS bound.

**7. Shared golden cases (single file, never copied).** `packages/zaghlol_parsing/test/fixtures/guard/golden.json`, with configs beside it (`configs/t1_base.json` generated from a synthetic test registry in `test/fixtures/guard/registry/`; `configs/t1_user.json`, `configs/bad_user.json`, ...). Kotlin adds the directory as a Gradle test-resources `srcDir`; Swift adds it as a folder reference in the test bundle. Format:
```json
{ "format": 1, "synthetic": true, "count": 74,
  "fold":  [ { "in": "رمز‍التحـقق ١٢٣٤", "out": "رمزالتحقق 1234" } ],
  "cases": [ { "id": "otp.ar.indic_digits", "tags": ["otp_drop"], "config": "t1",
               "channel": "sms", "source": "NBE", "body": "...",
               "expect": { "decision": "drop", "reason": "otp_or_promo_global" } },
             { "id": "card.ec59.other_inst", "tags": ["card_ignore","negative"], "config": "t1", "channel": "sms",
               "source": "CIB", "body": "...", "expect": { "decision": "keep", "kind": "registry", "inst": "cib", "last4": "9910" } } ],
  "rate":  [ { "id": "rate.burst", "config": "t1", "events": [ { "tMs": 0, "channel": "sms", "source": "NBE", "n": 21 } ],
               "expect": { "kept": 20, "rateLimited": 1 } } ],
  "modes": [ { "id": "user.malformed", "base": "configs/t1_base.json", "user": "configs/bad_user.json", "expect": "baseOnly" } ] }
```
Every harness asserts `count` = cases read, so a partial reader fails. Minimum per tag (≥ 60 cases): fold ≥ 15 (Indic/extended digits, ZWJ/ZWNJ/RLM, tatweel, harakat, alef/ya/ta variants, newline, NBSP, Turkish İ stays, emoji); `non_financial` ≥ 10 (personal number, unknown alpha ID, confusable ID, hints on sender only, unknown package, empty, 4,001 chars, unknown channel); `otp_drop` ≥ 15 (EN/AR, `OTP123`, code-first, Indic digits, ZWJ/tatweel inside keyword, uppercase, institution promo); `negative` keeps ≥ 8 (OTP-footer on a purchase, merchant "HOTPOT", `خصم` debit, 4-digit amount `1500.00` near "OTP"); `inst_ignore` ≥ 6 (channel mismatch keeps; `shortcut_message` hits an `sms` rule; notification by package); `card_ignore` ≥ 10 (EC-59 same last4 other bank keeps, other last4 keeps, no last4 keeps, Indic last4, `xx4567`, two cards); `generic_keep` ≥ 8 (alwaysCapture, user sender, hints, `apple_pay` wallet name and unknown card, `share`); `registry_keep` ≥ 6; modes ≥ 4; rate ≥ 3. All bodies, numbers and cards synthetic (CLAUDE.md §2.6), never edited real SMS; phone senders use obviously fake numbers.

**8. Never logging.** `lib/guard/` has no `print`, `log`, `dart:developer` or `dart:io`; `GuardKeep.toString()` and `GuardDrop.toString()` print the reason/kind only (no last4); config errors carry a code and JSON path only, never a value (the user part holds institution + last4 = financial data).

**9. Performance.** Config parse + compile ≤ 20 ms; `decide` ≤ 1 ms typical and ≤ 5 ms for a 4,000-char adversarial body on the reference device (cold Android process per SMS, 5 s receiver budget). Dart CI test uses loose bounds (1,000 adversarial decisions < 2 s) to avoid flakes; natives measure in T-038/T-061.

**10. Tests (→ ACs).** Golden runner (AC1). Generator: deterministic bytes, sorted/deduped user part, caps error, checked-in `t1_base.json` equals regeneration. Lint: one rejection test per forbidden construct, uppercase rejected, `(?i)` stripped, Arabic variants folded. **Parity:** every golden case through `ParsingPipeline` — Guard OTP drop ⇔ `ParseDropped`; **last4 parity lint** — for every registry fixture whose template captures `last4`, the Guard's last4 on that body is equal (else a card-ignore could miss natively). EC-59 (AC2): property test over random rule sets — a rule never drops a message of another institution. Negative proofs: canary body `ZG_CANARY_7731` + last4 run through every API in a zone capturing `print` → no output, absent from every `toString` and error; source scan of `lib/guard/` for `print(`/`dart:io`/`developer`; malformed user part never yields `invalid`.

**Rejected.** One encrypted file holding registry + user state (stale after an app update until the next open; a base read failure loses bank SMS). Exporting patterns as written for native raw-body matching (FU-082: no normalisation, three regex dialects). Matching OTP keywords alone (drops real transactions with security footers). Global promo list. Persisted rate counters. Confusable folding of sender IDs.

The `app-ci` base-config staleness step lands with T-036 (first real `app/assets/registry`). platform-channels §3 line "Text goes through Guard → spool with channel `share`" (iOS) contradicts §2.1 (Android share bypasses the Guard); the Guard defines `share` either way, but the two platforms should agree.

**Questions for the PO.**
- **Q1** If the encrypted user part can't be read (corrupt file, lost key), should the Guard keep bank messages using only the bundled rules (recommended; an ignored card's message may then sit encrypted in the spool until the app drops it at drain), or drop everything until the app rewrites the config (no trace, but notifications and iOS messages in that window are lost)?
- **Q2** A message that carries both a one-time code and a transaction ("OTP 123456 to confirm EGP 500 at X") is dropped; the completed-transaction SMS normally follows. Confirm.
- **Q3** Rate limit: more than **20** kept messages per sender per minute are dropped. Confirm the number, and that notifications dropped this way are not recoverable (SMS are, via the catch-up scan).
- **Q4** After Gold lapses, are senders of the user's custom templates still captured (as generic review items, recommended) or dropped?
- **Q5** On iOS, the per-card "SMS" capture toggle also governs messages arriving through the Shortcuts Message automation. Confirm.
- **Q6** Promotional messages from a bank are dropped only where that bank has explicit promo patterns; others land in the review queue as unrecognised rather than risk dropping real transactions. Acceptable?

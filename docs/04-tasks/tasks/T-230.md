## Scope
On Android, alarms are cleared on reboot, so the Friday "your week is ready" nudge (T-228) and any scheduled bill reminders are lost until the app next runs. Check how scheduled notifications are stored today (`NotificationPresenter`, `NotificationsHost`, any AlarmManager / WorkManager use). Make them survive a reboot: either re-arm from a small native store of pending schedules on `BOOT_COMPLETED` / `LOCKED_BOOT_COMPLETED` (receiver not exported beyond the system broadcast; only ids, times and the already-redacted text that was scheduled; nothing financial beyond what the notification itself would show; stored in no-backup storage), or move them to WorkManager if the repo already uses it and timing allows. Adding `RECEIVE_BOOT_COMPLETED` is allowed (normal permission); say so in the store-policy notes if the repo keeps a permissions list. iOS: confirm scheduled `UNNotificationRequest`s survive restarts (they do by OS design) and note it.
## Acceptance criteria
1. After a simulated reboot (Robolectric/unit test of the receiver re-arming from the store), the same notifications are scheduled with the same ids/times; past-due ones are not fired in a burst (drop or show once, say which).
2. Hide-amounts: re-armed text is the redacted text that was scheduled; when hiding turns on later, FU-267's re-derive still cancels/replaces them.
3. Store updated on schedule/cancel; cleared by delete-all.
4. Kotlin tests in CI (`ci/T-230`, report the app-ci result); `dart analyze`, `dart format`, notification tests green; permissions doc updated if one exists.

## Design note (builder)
- Repo uses AlarmManager (inexact) for scheduled alerts, no WorkManager for them; kept. New `ScheduleBook` + `FileScheduleStore` (`noBackupFilesDir/notif/schedules.txt`): id, time and the already-redacted fields only. Written by `schedule`, removed on fire/`show`/`cancel`/`cancelScheduled`/`cancelAll` (so delete-all and FU-267's re-derive clear it).
- `NotificationBootReceiver` (not exported, BOOT_COMPLETED only, `RECEIVE_BOOT_COMPLETED` added) calls `rearmAfterBoot`. LOCKED_BOOT_COMPLETED not used: the store is credential-protected, and moving redacted text to device-protected storage is not worth it; alerts re-arm after first unlock.
- Past-due after reboot: DROPPED (no burst); Dart re-derives at next app start.
- iOS: pending `UNNotificationRequest`s persist across restarts by OS design; no change. Docs: `platform-channels.md` 4c updated (permission list).

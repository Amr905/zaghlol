## Description
Automatic categorization at ≥ 80% (SM-04).

## Technical details
Precedence rule > catalog exact > prefix/token > fuzzy (FTS5 trigram top-10 + Jaro-Winkler ≥ 0.92 / 0.88 contributed) > keywords (score ≥ 60, margin 20) > needs classification; P2P straight to rules/needs (BR-CAT-03); hooks into ingest.

## Design note
Author: solution-architect (Opus), 2026-11-11. Parsing-engine §5 carries the summary (marked [doc change] below).

**Shape.** Pure Dart in `packages/zaghlol_parsing/lib/categorize/`: `categorize(CategorizeInput, CategorizerPorts) -> Future<CategoryDecision>` plus pure `jaroWinkler`, `matchAliases`, `scoreKeywords`. Ports (interfaces, no Flutter, no drift): `RulePort.match`, `CatalogPort` (`aliasesEqualTo`, `aliasesByKeys(keys, kinds)`, `aliasCandidates`, `merchantCategory`), `KeywordPort` (all keywords, loaded once per run), `CategoryPort` (system_code to live category id). The app adapter (`app/lib/features/categorization/data/`) implements them with `CatalogDao`, `RulesRepository.match`, `CategoriesDao.bySystemCode`; no schema change. Input: `merchantNorm` (canonical key or empty), `merchantText` = `foldKey(cleanMerchant(merchant_raw).cleaned)` (for keywords; `merchant_norm` is transliterated so Arabic is lost there), `counterpartyKind/Value`. Output: `{categoryId?, catalogMerchantId?, source, ruleId?, tier}`; `tier` is for the accuracy report only, never stored or logged with text.

**Tier order and stop conditions** (first hit stops; a tier that returns "ambiguous" or an unusable category falls through):
0. Empty key and no counterparty: keywords only on `merchantText`, else none. A non-empty key is checked with `isCanonicalMerchantKey` first (the DAO throws otherwise).
1. Rules, call A: `match(counterparty, merchantNorm)` (counterparty beats `merchant_norm`, A-68). Hit and category live: `user_rule`, stop. A rule whose category is archived or missing is ignored (fail closed, continue).
2. **P2P** (kind `ipa|phone|person`, BR-CAT-03): after call A, stop with `none`. `own_account`: `none`, stop (internal; queue filters `is_internal`). `person` is added to the spec's ipa/phone (conservative; PO-2).
3. Catalog exact: `alias_norm = key`, any `match` kind.
4. Prefix/token: look up only the key's token-boundary prefixes (kind `prefix`) and all contiguous token runs of up to 6 tokens (kind `token`) with one `alias_norm IN (...)` query (PK index), never `LIKE`. Longest alias (characters, then token count) wins, `prefix` over `token`. FU-090 item 8: `talabat` also matches `talabat mart` and loses to a longer alias.
5. Fuzzy (below).
   After 3, 4 or 5 yields a merchant: rules, call B: `match(catalogMerchantId)`; a rule wins (`user_rule`, `catalog_merchant_id` kept), else the merchant's `category_code` via `CategoryPort` gives `catalog`. Merchant found but its category archived or missing: keep `catalog_merchant_id`, source `none`.
6. Keywords: per category the sum of weights of distinct matched keywords; top >= 60 and top - runner-up >= 20 (runner-up 0 if none): `heuristic`. Tokens of `merchantText` are compared whole, also with a leading `ال` removed; Latin and Arabic keywords, both languages loaded. No substring matching.
7. Else `none` (needs classification).
Ambiguity at tiers 3 to 5: best-level aliases that span more than one `category_code` skip the tier (never guess); same category, several merchants: order by `canonical` ASCII then id (seed ids are provisional, FU-091, so this order is deterministic per catalog, not across catalogs).

**Candidates (tier 5).** Reuse `CatalogDao.aliasCandidates(key, limit: 10)` as built in T-018 (OR of the key's distinct quoted trigrams over `catalog_alias_fts`, `ORDER BY rank, id`, cap 50). Run only when the key without spaces is at least 6 characters (below that no fuzzy: short keys give false hits; `metro`/`metra` scores exactly 0.92). Known limit: ten aliases of one merchant can crowd out another; accept, the catalog is curated, and the accuracy report counts such misses.

**Scoring.** Standard Jaro-Winkler (window floor(max/2)-1, transposition t/2, p 0.1, prefix cap 4, boost only if Jaro > 0.7) on `alias_norm` vs key, and on both with spaces removed; score = the larger. Both are already canonical keys (`merchantKey` transliterates Arabic and drops the article, so `ELEZABY`, `EL EZABY`, `El-Ezaby` all give `ezaby`, and an Arabic alias gives the same Latin form); no second normalization inside the categorizer, and `foldKey` is used only for keyword text. Accept at >= 0.92 compared as `score >= threshold - 1e-9` (real examples sit exactly on the line: `ezaby`/`ezabi` and `metro`/`metra` are 0.92, `metro`/`mitro` 0.88; floating point alone would flip them). Extra guards: the digit characters of key and alias, in order, must be equal; a runner-up merchant of another category within 0.02 makes the tier ambiguous. Order candidates by (score desc, Jaro desc, `canonical`, id); input order never matters. [doc change: parsing-engine §5, min length, digit rule and 0.02 margin are new; confirm in PO-3]
The 0.88 contributed-alias threshold has no data to hang on: `catalog_aliases` has no institution or contributed flag and the sync carries none. Ship 0.92 only; keep `contributedThreshold` as a parameter with an empty `contributedAliasIds` so adding the data later changes no logic (PO-1).

**Arabic acceptance criterion.** `صيدليات العزبي` keys to `sydlyat alazby`, which no fuzzy score ties to `ezaby`. The seed has no Arabic alias, so the implementer adds `صيدليات العزبي` and `العزبي` as aliases (kind `prefix`) of El Ezaby in `tools/catalog_build/data/catalog_curated.csv` (an Arabic reader reviews them with T-059) and regenerates the seed. `ELEZABY` and `EL EZABY` hit the seeded `ezaby` prefix alias at tier 4, not fuzzy. [doc change: seed data, owner T-075; T-059 keeps them]

**Sources written.** `user_rule`, `catalog` (tiers 3 to 5, all merchant matches), `heuristic`, `none`. Never `user`; `is_user_verified` never set.

**Never overwrite.** New rows: set by the ingest insert. Existing rows (catalog update FR-SYNC-05, re-parse, backfill, T-077): one conditional `UPDATE` (same pattern as `applyToPast`, T-074) with `deleted_at IS NULL AND is_internal = 0 AND is_user_verified = 0 AND category_source IN ('none','catalog','heuristic')` and the id and old `category_id`/`catalog_merchant_id` in the WHERE, so a user edit committed in between wins. `user` and `user_rule` rows are never touched. A re-run never downgrades: a `none` result leaves an existing catalog/heuristic category alone (doubt means no change); an unchanged result writes nothing. Archived target category: skip the row.

**Performance budget** (proposed; the device number is measured in the db-platform suite, host asserts are generous): per message at most 7 DB round trips (A, exact, prefix/token, FTS, B; keywords in memory) and p95 <= 25 ms on the reference mid device with 600 merchants / 3000 aliases / 100 rules (host p95 <= 5 ms). Backfill (apply-to-past, catalog update, reparse): group by distinct `merchant_norm` (and counterparty for rules) and categorize each key once, memoized for the run; chunks of 200 keys per transaction in the background isolate, UI thread untouched; budget 1000 distinct keys <= 3 s host, <= 10 s device, 50k transactions < 30 s. No in-memory duplicate of the matcher (two implementations would diverge from the FTS top-10).

**Determinism.** Same input, catalog and rules give the same decision: no clock, no random, no map-order dependence, every choice ends in a total order (…, `canonical`, id). A test shuffles port results (candidates, aliases, keywords) 20 times and expects the identical decision. bm25 rank depends only on the index content.

**Edge cases.** Empty/emoji-only key; key over 64 (cleaner already caps); alias with digits (`19011`); `el`-prefixed English words; two merchants sharing an alias; rule pointing to an archived category; catalog merchant with unknown category code; Arabic keyword with article; counterparty-only message; `person` counterparty with a merchant-like name.

**Tests.** (1) JW golden vectors from a fixture table (`ezaby/ezabi` 0.92, `metro/mitro` 0.88, `carrefour/carrefoure` 0.98, `talabat/talbat` 0.9278, `zara/zaha` 0.8667, `ezaby/ezaby pharmacy` 0.8714); symmetric; 1.0 on equal; empty strings. (2) Threshold edges with a fake scorer: 0.9199999999, 0.92, 0.9200000001; 0.02 margin 0.0199 / 0.02; keyword 59 / 60, margin 19 / 20; length 5 vs 6; digit mismatch. (3) Tier order: rule beats catalog; counterparty rule beats `merchant_norm` rule beats catalog-merchant rule; exact beats longer-looking prefix; longest prefix wins; `talabat mart` over `talabat`; token mid-key; call B fires only after a merchant is found. (4) Acceptance: the three El Ezaby spellings to El Ezaby (real seed); IPA/phone transfer with no rule to `none`; with a rule to `user_rule`. (5) Negative proofs: `metro` does not fuzzy to `metra` (length gate); `ezaby 2` does not match `ezaby` fuzzy (digits); a person named like a merchant stays `none`; two same-score merchants in different categories give `none`, in the same category the lower `canonical`; user/user_rule/verified rows survive recategorize, also under a concurrent user edit (FU-095: build one real interleaving harness for both this UPDATE and `applyToPast`; if SQLite offers no deterministic hook, assert guards are in the single statement via `EXPLAIN`/SQL text and run a two-connection stress loop, and record that in the review); no downgrade to `none`; archived category not written; no raw merchant text in any exception or log (sentinel). (6) Accuracy report: fixture file of synthetic merchants with expected category, per-tier counts and an overall rate printed by the test (target >= 80%, SM-04; fixture must include 20% hard cases so the number means something); perf test on the seed and a 3000-alias synthetic catalog; determinism shuffle test.

**Rejected.** In-memory full-scan fuzzy for backfill (diverges from top-10); a SQL `LIKE 'alias%'` prefix scan (no index use, wrong boundary); Levenshtein (JW is in the spec and favors shared prefixes); matching on `catalog_merchants.canonical`/`name_ar` (not keyed; aliases are the contract); one rule call with a null `catalogMerchantId` (rule kind `catalog_merchant` would never fire); substring keyword matching (false hits on short Arabic roots).

## Description
Each iOS install owns one Secure Enclave P-256 seat key that survives app deletion and "Delete everything" on the same iPhone, so a reinstall can be recognised without spending the monthly move.

## Technical details
- Pigeon contract exactly as platform-channels §4b: `publicKeys() → List<Uint8List>` (X9.63, 65 bytes; own key first, then up to 4 earlier keys, newest first; empty when the Secure Enclave is unavailable), `sign(message) → List<SeatSignature>` (IEEE P1363 `r‖s`, 64 bytes, same order; an unusable key is dropped from the Keychain and the result), `rotateForNewInstall()`. Android: no implementation.
- **Storage:** `SecureEnclave.P256.Signing.PrivateKey`; its `dataRepresentation` in a generic-password Keychain item, service `app.zaghlol.seatkey`, `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`, `kSecAttrSynchronizable = false`, no shared access group; FIFO cap of 5 keys.
- **Element 0 fixed per install (R4-1(1)):** `publicKeys()` returns the same own key for the whole life of an install; a new own key only when the old one is unusable, or after `rotateForNewInstall()`.
- **Dart `SeatKeyService`:** wraps the host API; returns nothing on Android or when `SEAT_KEY_UNAVAILABLE`; holds the **"own seat key unusable for this install" flag (R5-6)** in `secure_state`, set by T-145/T-147 after a confirmed `SEAT_KEY_MISMATCH`; while set, `seatKeys` are not sent from this install; the flag is **dropped on T-141's `InstallReregistered`** (it lives with the install ID). Keys and signatures never reach the diag log.
- Messages are built in Dart by T-183 (`"zaghlol-seat-v1" ‖ 0 ‖ op ‖ 0 ‖ installId ‖ 0 ‖ challenge`); native signs exactly what it gets.

## Design note
Required — solution-architect (Opus) writes it before implementation (C4). Must name the oldest and newest supported iOS versions (ADR-019) and the physical devices for the R-19 test.

**Design note (Opus, 2026-11-13, written by the implementer as the Opus note).**

1. **Contract.** `app/pigeons/seat_key.dart` holds `SeatKeyHostApi` and `SeatSignature` exactly as platform-channels §4b, with `dartOut` and `swiftOut` only: no `kotlinOut`, so an Android build has no generated seat-key code at all (the empty stub leaves `clock_api.dart`). Errors are code-only: `SEAT_KEY_UNAVAILABLE` when the Keychain state can't be read or written (before first unlock, any status other than success / not found). This code is written into §4b (it was named only in this task).
2. **Keychain layout** (service `app.zaghlol.seatkey`, generic password, `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`, `kSecAttrSynchronizable = false`, the app's own application-identifier group as `DbKeyKeychain` uses, never a shared group). Account `own` holds this install's key; accounts `earlier.<10-digit sequence>` hold earlier keys (higher = newer). Value: the `dataRepresentation` of a `SecureEnclave.P256.Signing.PrivateKey` created with access control `AfterFirstUnlockThisDeviceOnly` + `.privateKeyUsage`. Items under the service with any other account are ignored (never returned, never deleted).
3. **Operations** (one `NSLock`, one shared host for every engine in the process). `publicKeys()` and `sign()` first load `own` (creating it with `SecItemAdd` only when the item is positively absent; `errSecDuplicateItem` reads the winner back), then up to 4 `earlier` keys, newest first. `rotateForNewInstall()` renames `own` to `earlier.<max+1>` with one `SecItemUpdate` (atomic; idempotent: no `own` → nothing to do), then deletes the oldest `earlier` items beyond 4 (FIFO cap 5). No Secure Enclave (Simulator) → `[]` / no-op without touching the Keychain.
4. **"Unusable" is proven, never guessed** (self-check §1). A key is unusable only when its item was read successfully and either its bytes are empty or over 8 KiB, or loading it / signing with it / verifying its own signature fails on all three attempts (0, 100, 300 ms). Only then is that one item deleted (query names service + account). Any Keychain read error is `SEAT_KEY_UNAVAILABLE` and deletes nothing. An unusable own key is replaced by a new own key in the same call (so element 0 is always this install's key; the server then answers `SEAT_KEY_MISMATCH` and T-145/T-147 set the R5-6 flag).
5. **Dart `SeatKeyService`** (`app/lib/features/gold/application/seat_keys.dart`). Android, no install ID, `SEAT_KEY_UNAVAILABLE`, any other platform error or a malformed native answer (key ≠ 65 bytes / `0x04`, signature ≠ 64 bytes, > 5 entries, duplicates) → no keys. **Install binding:** `secure_state` key `seat_key_install` holds the install ID the native own key belongs to. When it differs from the current install ID (first run, a reinstall, "Delete everything", an R5-1 re-registration), the service calls `rotateForNewInstall()` first and writes the marker only after it succeeded (a crash in between rotates again, which is a no-op). So element 0 never changes during an install, and a reinstall's earlier key sits at position 1. **R5-6 flag:** `seat_key_unusable` holds the install ID it was set for (`markOwnKeyUnusable()`, called by T-145/T-147); it suppresses keys only while it equals the current install ID, and `InstallReregistered` deletes it (`deleteIfEquals`, so a flag set for the new install survives). Calls are serialized in the service; nothing logs.
6. **Crash windows / residuals.** A crash between creating the key item and returning wastes nothing (the item is `own`). A crash after a rename and before the trim leaves 6 items until the next rotation (only 4 earlier are ever returned). A second Dart isolate using the service at the same time as the UI isolate is not serialized (seat keys are only used by the foreground verify / restore / sign-in flows). Keychain survival after app deletion is current iOS behaviour, not a documented guarantee (ADR-012 (g)).
7. **Versions and devices (ADR-019).** Oldest supported: **iOS 17.0** (deployment target 17.0); newest: **iOS 26.x** (current release). R-19 devices: an **iPhone XS or XR kept on iOS 17.x** (A12, Secure Enclave; the last line that can stay on 17 without a newer phone) and an **iPhone 15 or 16 on the newest iOS 26.x**. Simulator has no Secure Enclave and only exercises the Keychain / software-key paths. The real-device runs are recorded in `docs/05-reviews/T-179-device.md` (deferred with T-008/T-011/T-120/T-165: real-device runs, SPRINT.md).

**Manual device steps (R-19; iPhone XS/XR on iOS 17.x and iPhone 15/16 on iOS 26.x; debug build with a temporary debug screen or `flutter run` console that shows only SHA-256 prefixes of the public keys, never the keys):**
1. Fresh install, register, trigger `publicKeys()`: note the SHA-256 prefix of element 0 (K1). Trigger `prove(restore, …)` and verify the signature with CryptoKit (or the backend verifier) against K1.
2. Kill and relaunch: element 0 is still K1.
3. Delete the app; reinstall; register (new install ID). `publicKeys()` → element 0 is a new K2, element 1 is K1. `prove()` returns two signatures; both verify (K1's proves the Secure Enclave key survived, not only the item).
4. "Delete everything": element 0 becomes a new K3, element 1 is K2, element 2 is K1.
5. Repeat on the second device / iOS version.

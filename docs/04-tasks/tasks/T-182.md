## Description
Verify `seatKeys` proofs (ECDSA P-256 over the shared message format) and compute the keyed hashes the seat service stores, so no raw public key is ever persisted or logged.

## Technical details
- **Parse:** `seatKeys` = array of `{publicKey, signature}`; `publicKey` X9.63 uncompressed P-256 point, 65 bytes, base64url without padding; `signature` IEEE P1363 `r‖s`, 64 bytes, base64url. Max keys per op: `verify` 1, `restore` 5, `signin` 5. Public keys must be **distinct** (repeat → validation failure). Point must be on the curve.
- **Message:** `"zaghlol-seat-v1" ‖ 0x00 ‖ op ‖ 0x00 ‖ installId ‖ 0x00 ‖ challenge` with `installId` the lower-case UUID text from the **install token**; `challenge` 32 bytes (`verify`: SHA-256 of `signedTransaction`; `restore`: install-bound `bodyHash`; `signin`: SHA-256 of the raw nonce).
- **Result:** the whole set is valid (a `VerifiedSeatKeys` value) or rejected with an internal reason; the caller decides the HTTP outcome (restore/sign-in: rejected → `400 VALIDATION_FAILED`; verify: ignore). *(Design note §3: every element must be valid, since no caller can use a partly valid set.)*
- **Keyed hashes** through `IKeyedHasher` (T-123) with `K_seat`: `InstallKeyHash = HMAC-SHA256(K_seat, "install" ‖ 0x00 ‖ installId ‖ publicKey)`; `SeatKeyHash = HMAC-SHA256(K_seat, purchase_id ‖ publicKey)`; `digestOfPublicKeys = SHA-256(pk₀ ‖ … ‖ pkₙ₋₁)` (SHA-256 of the empty string when absent) for T-185's `clientDataHash`.
- **Element-0 helper:** `CheckElementZero(install, seatKeys) → NoneRegistered | MatchesRegistered | Mismatch` against `installs.seat_key_hash` (registration itself is done by the seat service, T-184, inside its transaction).
- **Test support** for downstream tests: a software-key `SeatKeyTestSigner` that makes real proofs (and each negative form), used with the **real** verifier, plus a fixed-`K_seat` `FakeKms` setup (design note §8). The redacting logger drops `seatKeys`; raw keys never leave this module except as hashes.
- **`K_seat` startup check** (`Kms:HmacKeys:SeatCheck`, design note §6).

## Design note
*solution-architect (Opus), 2026-11-11. Inputs: backend-api §4.3 *Same-iPhone recognition*; ADR-012 Part B (g); backend-schema §2–§3; security-model §1, §6; deployment §3 KMS; T-123 (`IKeyedHasher`, `FakeKms`); T-124 (`InstallId`, strict DTOs); T-131 (`StoreBindingRef`, verify DTO pass-through); T-132/T-135/T-184/T-185 (consumers); T-179/T-183 (app side). R5-3 is closed by D-66 (option (b)): no sign-in attestation, so nothing here changes for it.*

**0. Scope.** Pure, synchronous proof parsing and verification plus the `K_seat` keyed hashes, in `Zaghlol.Application/Seats/SeatKeys`. No DB access, no HTTP mapping, no registration (T-184 does that inside its transaction). New dependencies: none (`System.Security.Cryptography`, `System.Numerics.BigInteger`, `System.Buffers.Text.Base64Url`).

**1. Types (Application).** No public member returns raw key or signature bytes, and every `ToString()` returns `***`.
- `SeatOp { Verify, Restore, SignIn }` → wire literals `verify|restore|signin` (ASCII).
- `SeatChallenge`: pairs an op with its 32 bytes. Factories: `ForVerify(string signedTransaction)` = SHA-256(UTF-8 of the decoded JSON string), `ForRestore(ReadOnlySpan<byte> bodyHash)` (must be 32 bytes, else `ArgumentException`), `ForSignIn(string rawNonce)` = SHA-256(ASCII nonce). This removes op/challenge mix-ups at the call sites.
- `SeatKeyProofInput(string PublicKey, string Signature)`: the Api maps `Sensitive<IReadOnlyList<VerifySeatKeyInput>>` to this only at the point of use.
- `ParsedSeatKeys`: structurally valid, request order. Exposes `Count` and `Digest()` = SHA-256(pk₀ ‖ … ‖ pkₙ₋₁) over the raw 65-byte points. `SeatKeysDigest.Empty` = SHA-256("") for an absent field (T-185 `clientDataHash`).
- `VerifiedSeatKeys`: only `SeatKeyProofVerifier` can construct it. It exposes `ElementZero` and `Others` (positions ≥ 1) as `VerifiedSeatKey` handles. The bytes are `internal` and reach only `SeatKeyHasher` in the same module.
- `InstallKeyHash`, `SeatKeyHash`: two distinct 32-byte wrappers, so the two kinds can't be compared with each other. `FromStored(byte[])` throws `InvalidOperationException` (no data in the message) for a length other than 32, which the DB CHECK makes impossible. `ToStorage()` returns a copy. `Matches(other)` uses `CryptographicOperations.FixedTimeEquals`.

**2. Proof format (unchanged wire contract; pinned here byte for byte).**
- `message = ASCII("zaghlol-seat-v1") ‖ 0x00 ‖ ASCII(op) ‖ 0x00 ‖ ASCII(installId) ‖ 0x00 ‖ challenge(32)`.
- `installId` comes **only** from the authenticated install token (`InstallId.ToString()`, lower-case "D", 36 characters), never from the body.
- Key: P-256, X9.63 uncompressed (`0x04 ‖ X ‖ Y`, 65 bytes). Signature: ECDSA-SHA-256, IEEE P1363 `r ‖ s` (64 bytes). Both are base64url without padding.
- **No timestamp in the proof.** Freshness and replay protection come from the challenge:
  - restore: `bodyHash` is bound to the install and the body, and the App Attest assertion is single-use by its counter;
  - sign-in: the nonce is single-use (`replay_guard`, committed before the seat transaction);
  - verify: SHA-256(`signedTransaction`) is **not** single-use, and needs no further protection. The proof is bound to this install ID, so another install can't reuse it. Verify only ever registers a key, untrusted and set-once, and never rebinds. A replay by the same install is therefore a no-op.
- **High-S signatures are accepted; never enforce low-S.** The existing valid vector `restore` already has s > n/2, and CryptoKit does not normalise s. Malleability doesn't matter here: signatures are never stored, hashed or used as identifiers.

**3. Verification order** (`SeatKeyParser.Parse(op, inputs)` then `SeatKeyProofVerifier.Verify(parsed, challenge, installId)`). Both are total functions: they never throw on input.
1. Count: 1 ≤ n ≤ max(op), with verify 1 and restore/sign-in 5. Otherwise `Empty` or `TooMany`. The count check runs before any decoding.
2. Encoding, per element:
   - `publicKey` is exactly 87 characters and `signature` exactly 86, all in `[A-Za-z0-9_-]`;
   - decode, then re-encode, and the result must equal the input ordinally (`Encoding`).
   This rejects padding, whitespace and non-canonical trailing bits, all of which `Base64Url.DecodeFromChars` would accept. A 64-byte key (86 characters) and a 33-byte compressed key fail here.
3. Prefix: `pk[0] == 0x04`, otherwise `BadPoint`. This rejects the hybrid prefixes 0x06 and 0x07, which are also 65 bytes.
4. Distinct: decoded keys are compared pairwise and ordinally (public data); a repeat is `Duplicate`. → **`ParsedSeatKeys`.** T-185 calls `Parse` in step 1 (structural garbage never costs an App Attest verification), takes `Digest()` in step 2 and calls `Verify` in step 2b.
5. Point check, per element, in managed code with `BigInteger` (public data, so no constant-time concern):
   - x < p and y < p;
   - y² ≡ x³ − 3x + b (mod p).
   This also rejects the all-zero point. Otherwise `BadPoint`. Constants come from FIPS 186-5 / SEC 2. A test checks them against `ECDsa.ExportExplicitParameters` for `nistP256`.
6. Signature, per element:
   - 1 ≤ r, s ≤ n − 1, otherwise `BadSignature`;
   - `ECDsa.Create(new ECParameters{Curve = nistP256, Q})` (dispose it) and `VerifyData(message, sig, SHA256, IeeeP1363FixedFieldConcatenation)`;
   - a `CryptographicException` on import or verify counts as `BadSignature` (or `BadPoint` for import).
7. Steps 5–6 run for **every** element, with no early exit. The set is valid only if every element passes, and the result is `VerifiedSeatKeys` or `Rejected(reason)`. Reasons: `empty|too_many|encoding|bad_point|duplicate|bad_signature`; the first failing element's reason is used. The reason feeds only the metric (§7), never the response.

**4. Keyed-hash construction and domain separation** (`SeatKeyHasher`, over the Application port `ISeatKeyMac.MacAsync(ReadOnlyMemory<byte> input, ct)`; the Infrastructure `KmsSeatKeyMac` calls `IKeyedHasher.HmacSha256Async(KeyedHashKey.Seat, …)`). Every UUID is the lower-case hyphenated text, 36 ASCII bytes; `pk` is the raw 65-byte point.
- `InstallKeyHash = HMAC(K_seat, ASCII("install") ‖ 0x00 ‖ installId ‖ pk)`: 109 bytes.
- `SeatKeyHash = HMAC(K_seat, purchaseId ‖ pk)`: 101 bytes. *(Pinned: text, not the 16-byte binary UUID.)*
- `SeatCheck = HMAC(K_seat, ASCII("zaghlol-kseat-check-v1"))`: 22 bytes (§6).
- `K_seat` is used for nothing else. The three inputs have fixed and pairwise different lengths, and they start with different bytes (`i`, a hex digit, `z`), so no input of one construction can equal an input of another. Each construction has fixed-width fields, so it is injective in its own fields.
- The keyed hashes are computed only from a `VerifiedSeatKey`. An unverified key is never hashed.
- **Element 0:** `CheckElementZeroAsync(InstallId, InstallKeyHash? registered, VerifiedSeatKeys, ct)` → `(ElementZeroStatus {NoneRegistered | MatchesRegistered | Mismatch}, InstallKeyHash computed)`. It returns the computed hash so that T-184 registers it without a second KMS call.
- **Seat match (for T-184):** `MatchSeatAsync(purchaseId, SeatKeyHash stored, VerifiedSeatKeys, ct)` → the index (≥ 1) or none.
  - It hashes every element at position ≥ 1 and compares each one in constant time, with no early exit. Element 0 is never a match candidate (backend-api §4.3, condition 2).
  - `SeatKeyHashAsync(purchaseId, keys.ElementZero)` gives the value written to `device_key_hash`.
  - KMS cost: at most 4 MAC calls per candidate seat (T-184 asks only for seats with a non-NULL `device_key_hash` that the caller doesn't hold), run with at most 4 calls in parallel.

**5. Failure behaviour (fail closed).**
- Bad input is always a rejection result and never an exception. Callers send the uniform `400 VALIDATION_FAILED` on restore and sign-in, with no detail about which element failed or why; verify ignores it.
- KMS failure: `KmsUnavailableException` propagates, giving the existing `503 UPSTREAM_UNAVAILABLE`.
  - The hasher never returns a placeholder, and callers must never treat a failure as "no match", "none registered" or `NULL device_key_hash`.
  - On verify, T-132 skips the seat-key step on that exception. Entitlement signing needs the KMS anyway.
- No exception message, log line or span attribute contains input, key, signature or hash bytes.

**6. `K_seat` lifecycle.**
- **Storage:** a dedicated KMS HMAC-SHA256 key that never leaves the KMS. It isn't in the secrets manager, the config or the DB. The API identity has MAC permission only. `Kms:HmacKeys:Seat` names an **immutable key version** (the versioned kid):
  - GCP: a `CryptoKeyVersion`, which `MacSign` requires anyway;
  - Azure Managed HSM: a versioned key URI;
  - AWS: the key ARN (HMAC KMS keys have no automatic rotation).
  Auto-rotation stays off, and IaC sets deletion protection or `prevent_destroy` (T-140).
- **Startup check:** `Kms:HmacKeys:SeatCheck` holds the 64-hex `SeatCheck` value, which IaC computes once when the key is created.
  - At startup the API recomputes it and compares in constant time. In Staging and Production a missing value, a mismatch or an unreachable KMS stops the start (`KmsConfigurationException`, readiness never goes green).
  - In Development and Testing it is checked when set.
  - This catches a wrong key reference and a recreated or rotated key. Otherwise every iOS install would silently get `SEAT_KEY_MISMATCH` and lose same-iPhone recognition.
- **No scheduled rotation** (decision).
  - Why: stored hashes can't be recomputed, because raw keys are by design never stored. `K_seat` is a pseudonymisation key over random 65-byte points that can't be guessed, so its leak alone links nothing. It confirms a link only for someone who also holds the raw keys (in transit only, D-62).
  - **Emergency rotation on suspected compromise:** create a new key version and `SeatCheck`, then run one migrator transaction that bypasses the SEC F9 triggers and sets these to NULL/false: `installs.seat_key_hash` and `seat_key_trusted`, `purchase_seats.device_key_hash` and `device_key_trusted`, and `seat_claimants.device_key_hash`.
  - Effect: installs register again on their next valid proof (no mismatch storm). Same-iPhone recognition of existing seats is lost once, and trust returns only with the next attested restore. → PO question 1. Runbook in deployment §3.

**7. Metrics without PII** (`ISeatKeyMetrics`, implemented by `ZaghlolMetrics`; tags are fixed words only):
- `zaghlol.seat.proof{op, result}`, where `result` is `valid` or a rejection reason (§3);
- `zaghlol.seat.element_zero{op, status=none_registered|matches|mismatch}`;
- KMS errors stay on the existing `kms_unavailable{op=hmac}`.
No IDs, hashes or key prefixes appear anywhere, and there is no new alert.

**8. Test support and keeping it out of Production.**
- `backend/tests/Shared/SeatKeyTestSigner.cs` (namespace `Zaghlol.Testing`, linked by `<Compile Include>` like `FakeKms`):
  - makes software P-256 keys and real proofs over the real message for any op, install and challenge;
  - offers mutators for every negative form in §3 (and DER, other op, other install, other challenge, key B with key A's signature).
- Consumers (T-132/T-135/T-184/T-185) use the **real** verifier with this signer. There is no always-valid fake verifier, because it would hide a wrong challenge or op in a consumer.
- `FakeKms` gets a fixed `K_seat` through `AddSecret(HmacKeyRef(Seat), 000102…1f)` for vectors, and keeps the random default otherwise. `FakeKms.Fault` covers KMS failure.
- Exclusion from Production:
  - nothing in `src/` references `tests/Shared`;
  - an architecture test asserts that no type in the Domain, Application, Infrastructure, Api, Workers or Ops assemblies is in namespace `Zaghlol.Testing` or named `Fake*`/`*TestSigner`;
  - `Local` and fake KMS are already refused outside Development and Testing (T-123), and the §6 startup check refuses an unknown `K_seat`.
- Software keys are accepted by the production verifier on purpose: the server can't tell Secure Enclave keys apart, and trust comes only from App Attest (R5-2).

**Rejected alternatives.**
- **A dual-key `K_seat` transition with lazy re-hash:** it needs the raw key while the old hash is still accepted. The SEC F9 trigger forbids replacing `seat_key_hash`, and it adds a key-version column for an event that should never happen.
- **A version byte in the stored hash:** it breaks the `octet_length = 32` CHECK, and there is nothing to version.
- **A per-purchase subkey derived through the KMS (HKDF) to save MAC calls:** it changes the documented construction and puts subkeys in process memory, for at most 4 calls per seat.
- **Relying on .NET import to check the curve:** the behaviour depends on the platform (OpenSSL vs CNG), and an explicit check costs microseconds.
- **Enforcing low-S:** it would reject genuine Secure Enclave signatures, including the current vector.
- **Per-element results:** no caller uses a partly valid set, and returning them invites partial acceptance.

**Deviations / decisions (for the reviewers).**
1. **`FakePriceProvider` is allowlisted** in the §8 architecture rule. It is T-127's deliberate production stand-in while D-41 is open: selected only by `Prices:Providers = fake` and refused in Production. Renaming it is out of scope. The allowlist is one explicit entry, and `TheRuleRecognisesTestSupport` proves that the rule matches `FakeKms` and `SeatKeyTestSigner`.
2. **The parser is internal, and the public entry is the `SeatKeyProofVerifier` instance** (`Parse` / `Verify` / `ParseAndVerify`). This lets the metric be recorded in one place. The note's static `SeatKeyParser.Parse` would have needed every caller to count.
3. **`VerifiedSeatKeys` and `VerifiedSeatKey` carry the `InstallId` they were verified for.** `InstallKeyHashAsync` and `CheckElementZeroAsync` throw `ArgumentException` (constant message) for a key verified for another install, so a caller can't register a key under the wrong install.
4. **Design note §3 step 2 wording:** .NET 10's `Base64Url.DecodeFromChars` already returns `InvalidData` for non-zero trailing bits. It still accepts padding and whitespace (probed), and those are caught by the length and alphabet checks. The re-encode comparison is kept as defence in depth (code comment), so the rule doesn't depend on the runtime decoder. Likewise, the explicit 1 ≤ r, s ≤ n − 1 check overlaps the platform verifier, and the explicit curve check overlaps OpenSSL's import (see the negative proofs).
5. **Startup check in Development/Testing:** an unset value is skipped (a warning is logged). A malformed or mismatching value refuses the start there too, because "checked when set" was read as "fails when wrong". Any environment other than Development/Testing (e.g. `Ci`) is strict.
6. **Seat-match concurrency** is bounded by construction: `MaxKeys` = 5, so at most 4 candidates run under `Task.WhenAll`, and there is no semaphore. A test asserts at most 4 calls in flight and exactly 4 calls.
7. **Extra vectors** beyond the note's list, all derived from public data by a throwaway script with no private keys:
   - `malformed`: `hybrid-prefix-0x07`, `padded-signature`, `second-element-signature-of-first` (`bad_signature`) and `second-element-off-curve` (`bad_point`);
   - `valid` `restore-low-s` and `invalid` `other-challenge`, as the note specifies.
8. **Wycheproof:** fetched by sparse `git clone` of C2SP/wycheproof at commit `dab4ea2ed021eb633874959ca601004f3457d911`. The file is vendored unmodified with `LICENSE` and `NOTICE.txt`, and the test pins its SHA-256. It has 262 cases (173 valid, 89 invalid, 0 acceptable). All of them pass through `P256.VerifyP1363`, including high-S `valid` cases.

**Config / secrets the operator must set.** `Kms:HmacKeys:SeatCheck` = 64 lower-case hex of `HMAC-SHA256(K_seat, "zaghlol-kseat-check-v1")`. IaC computes it once when `K_seat` is created (T-140). It is **required outside Development/Testing**, and it is not a secret. `Kms:HmacKeys:Seat` must name an immutable key version, with auto-rotation off and deletion protection on (`deployment.md` §3). No new secrets, no endpoints and no migrations.

## Description
The only way the app talks to the backend, with the data boundary built in.

## Technical details
- DTOs generated from OpenAPI (no free-form maps; pinned generator version, FU-013); embedded public keys (current + next); verify `Zaghlol-Signature` over the exact body bytes; drop unsigned or invalid bodies of signed operations; error mapping to Failures, unknown problem codes by HTTP status class.
- Tokens in `secure_state`; `rotateInstallToken` honoured.
- **Lazy `POST /v1/installs`** (first sync or first purchase): install ID UUID v4 from a CSPRNG; on `409 INSTALL_EXISTS` regenerate the ID; a retry after a lost response reuses the same `Idempotency-Key` and body bytes (gets a fresh token, R3-6).
- **`Idempotency-Key`** for verify, installs and sign-in: ULID whose 80 random bits come from `Random.secure()`; never reused for a different request; never logged (R3-6).
- **Re-registration (R5-1, §6):** on `401 INSTALL_TOKEN_INVALID`, delete the cached entitlement token and the account token **before** registering a new install ID; emit an `InstallReregistered` event (consumed by T-144 trusted state and the T-179 "own seat key unusable" flag). Local data is kept.
- **Anchoring hook (R4-2):** the six anchoring operations take a `timeNonce` argument supplied by T-144's time-anchor service and send it as `Zaghlol-Time-Nonce`; the client never invents one.
- `seatKeys` members exist only on the iOS request types; the Android build cannot serialize them (compile-time or test).
- Recording client hook for privacy tests (debug only).

### Design note (implementer, Opus, 2026-11-13; no architect note existed when the task started)

**Layout (`app/lib/core/backend/`).** `generated/api_models.g.dart` (DTOs + operation table), `backend_client.dart` (the only HTTP client), `response_signature.dart` (ES256 header verifier and the pinned key set), `transport.dart` (`BackendTransport` port + `dart:io` adapter), `ids.dart` (UUID v4, ULID, `TimeNonce` wrapper), `backend_state.dart` (`secure_state` keys and store port), `backend_failure.dart`, `debug/recording_transport.dart` (privacy-test hook).

**DTO generation (FU-013).** `openapi-generator-cli` `dart-dio`/`built_value` would add `built_value` + `build_runner` (a lockfile change; `build_runner` does not resolve in this workspace, see T-016) and a `packages/` member outside this lane. Instead an in-repo generator, `app/tool/api_codegen/` (pure Dart over `package:yaml`, already in the lock), reads `backend/openapi/zaghlol-v1.yaml` and emits models for every schema reachable from the ten app operations, plus a generated operation table (method, path, success status, signed, anchoring, idempotency, auth). The generator *is* the pin: its version constant is written into the output header, and `api_models_drift_test.dart` regenerates in memory and fails on any byte difference, so a contract change or a generator change can't land without regenerating. Request classes have `toJson()` only (declared properties only, nulls omitted, pattern/length/count checks before anything is sent); response classes have `fromJson()` only (unknown fields ignored, unknown enum values → `unknown`, strict types, never echoing input). JSON Schema `if/then` conditional requirements (catalog ops) are not generated; T-143 checks them.

**Signature.** Exactly T-123's form: header `^kid=(s[0-9]{4}[a-z]); alg=ES256; sig=([A-Za-z0-9_-]{86})$`, no trimming, one header value; P1363 `r‖s`, `1 ≤ r,s < n`, high-S accepted; ECDSA P-256/SHA-256 (pointycastle, as `zaghlol_catalog`) over the body bytes after `dart:io` decompression. `e` kids, unknown kids and dev kids (`?0000?`, outside debug) are refused. The pinned set (current + next) is injected through `BackendConfig`; **no production `s` key exists yet** (T-140 KMS), so the release set is empty and every signed operation fails closed until the PO supplies the public JWKs.

**Install registration (R3-6).** `ensureInstalled()` is single-flight per isolate. A pending registration `{installId, idempotencyKey, bodyBytes}` is persisted in `secure_state` before the first send; any retry (lost 201, timeout, 5xx, app restart) resends the same key and bytes. `201` stores the token and clears the pending record. `409 INSTALL_EXISTS` / `IDEMPOTENCY_KEY_REUSED` drops the pending record and starts over with a new UUID v4 and a new ULID (at most 3 rounds per call). Accepted residual: two engines registering at once can each send the same pending record; the server's replay rotates the token, so the loser's stored token may be dead and self-heals through the R5-1 path.

**Re-registration (R5-1).** Only on a strictly parsed `401` problem whose code is `INSTALL_TOKEN_INVALID`: write a `reregistration_pending` marker, delete the entitlement token, the account token, then the install token and ID, and register; `InstallReregistered` is emitted once the new token is stored (the marker survives a crash in between). The failed call is reported as `BackendFailureKind.installReset`; the caller retries. Local data is kept. `401 ACCOUNT_TOKEN_EXPIRED` deletes only the account token.

**Anchoring.** The six anchoring operations take `TimeNonce? timeNonce`; `null` is an `assert` in debug and a `clientBug` failure in release. `TimeNonce` only validates the 22-char shape; the value comes from T-144.

**Platform boundary.** The client is built for one `ClientPlatform`; sending an iOS request variant (or a `SignInRequest` with `seatKeys`) from Android, or an Android variant from iOS, throws before serialization.

## Acceptance criteria
- [ ] Unsigned or tampered response rejected.
- [ ] Only allow-listed fields can be serialized.
- [ ] R3-6: `Idempotency-Key` values come from `Random.secure()` (test with an injected RNG) and never appear in the diag log (test).
- [ ] R5-1: on `INSTALL_TOKEN_INVALID` the entitlement and account tokens are deleted before the new `POST /v1/installs` is sent (ordered fake-server test), and `InstallReregistered` fires.
- [ ] `409 INSTALL_EXISTS` → new install ID; lost 201 → retry with the same key and body (tests).
- [ ] An anchoring call without a `timeNonce` from the time-anchor service fails fast in debug (assert) (test).
- [ ] FU-013: generator version pinned.
- [ ] DoD (CLAUDE.md §7): analyze clean, formatted, tests added, no hard-coded strings, RTL verified where UI, no `double` money, no raw SMS in logs.

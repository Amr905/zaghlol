## Description
Server-side verify iOS purchases, plus the live App Store order-ID lookup used by support.

## Technical details
- Decide library (Enjna.AppStoreServerLibrary review vs in-house x5c → Apple Root CA G3 + ES256); `bundleId` / `environment` / `appAccountToken == HMAC(installId)` checks; App Store Server API `Get Transaction Info` + `Get All Subscription Statuses`; upsert by `originalTransactionId`.
- Classify a transaction as a **new payment** (new `transactionId` for its `originalTransactionId` with `transactionReason = PURCHASE`: upgrade, downgrade, crossgrade, re-subscription) and expose it in the `IStoreVerification` result; T-132 applies the D-59/D-61(a) seat rule.
- Verification for restore (T-185) skips only the `appAccountToken` check, which names the old install after a phone change.
- **Ownership lookup for support (D-57, §5.3):** `IAppStoreOrderLookup.CheckAsync(orderId, purchase)` via **Look Up Order ID** (`GET /inApps/v1/lookup/{orderId}`): `status = 0`, and one signed transaction, verified like any other, carries the purchase's `originalTransactionId`. Outcomes `pass | fail | unavailable`. The order ID is `[Sensitive]`: never stored, logged, traced or put in an exception message.
- **App Attest validation is not here:** it moved to T-181 (architecture.md previously said "reviewed under T-131").

**1. Library decision: in-house verifier.**
- **Candidate reviewed:** `Enjna.AppStoreServerLibrary` 2.3.0 (NuGet, MIT, published 2026-09-13, `net8.0`, depends on `Microsoft.IdentityModel.JsonWebTokens` and `System.Text.Json`). It is community-maintained and not affiliated with Apple.
- **Rejected, for these reasons:**
  - it deserializes every response field into its own models, which breaks the rule "DTOs declare only the fields we read" (§4.5, T-130 §1.3);
  - we can't control its URL or exception redaction, and that control is needed for the D-57 order ID and for transaction IDs;
  - its revocation checking (`enableOnlineChecks`) depends on the network;
  - it adds a single-maintainer supply-chain dependency on the billing path.
- **In-house cost:** about 250 lines on `System.Security.Cryptography` (`X509Chain` with `CustomRootTrust`, `ECDsa`). The ES256 API-auth JWT is signed with `Microsoft.IdentityModel.JsonWebTokens` 8.23.0, which is already referenced. **No new package.**
- **Doc fix (§11 a):** architecture.md l.285 and INT-20 should say "in-house" and drop the alternative.

**2. `AppleJwsVerifier` (pure, synchronous, no I/O).** Input: a JWS string, a `JwsSource` (`App` or `Api`) and the time `now`. Every failure gives `AppleJwsException(reason)`, a `SafeException` with a constant message. `reason` is one of `malformed | alg | chain | oid | signature | payload`.
1. **Shape:**
   - at most 16 384 chars (OpenAPI `Jws`), checked before any decode;
   - exactly 3 segments, strict base64url with no padding;
   - header and payload parsed with `AllowDuplicateProperties = false` (a duplicate is `malformed`).
2. **Header:**
   - `alg` must be exactly `"ES256"`;
   - `x5c` must be an array of **exactly 3** standard-base64 DER certificates, each 4 KiB or less;
   - `jku`, `jwk`, `x5u`, `kid` or `crit` present is `alg`;
   - other members are ignored;
   - the verification key comes **only** from `x5c[0]`. There is no JWKS and no key lookup.
3. **Chain (no network):**
   - `X509ChainPolicy { TrustMode = CustomRootTrust, CustomTrustStore = {pinned root}, ExtraStore = {x5c[1]}, RevocationMode = NoCheck, DisableCertificateDownloads = true, VerificationTime = t }`;
   - the chain must build with exactly 3 elements, element 1 must be byte-equal to `x5c[1]`, and element 2's SHA-256 thumbprint must equal the pinned root's;
   - `x5c[2]` must be byte-equal to the pinned root.
   - **Pinned root:** Apple Root CA - G3, embedded as a resource, with its SHA-256 fingerprint asserted at startup against a constant copied from apple.com/certificateauthority by the implementer. A wrong or missing resource stops startup.
   - In Development and Testing only, `Purchases:Apple:TestRootCertificate` replaces the pin. Production refuses it.
4. **OIDs:**
   - the leaf must carry extension `1.2.840.113635.100.6.11.1`;
   - the intermediate must carry `1.2.840.113635.100.6.2.1`. These are the checks Apple's own library makes;
   - the leaf key must be EC P-256.
5. **Signature:** `ECDsa.VerifyData(ASCII(header.payload), sig, SHA256, IeeeP1363FixedFieldConcatenation)`, and the signature must be exactly 64 bytes, so the DER form is rejected.
6. **Validation time `t`:**
   - `Api` source: `now`. These JWSs were freshly signed by Apple for this call.
   - `App` source: the payload's `signedDate`, read before trust. This is needed because StoreKit hands out JWSs signed under intermediates that have since expired (the September 2023 incident); Apple's library does the same when online checks are off. It is bounded by `signedDate ≤ now + 5 min`.
   - This is safe because the **grant never rests on the app's JWS alone**: state, revocation and the binding are taken from the `Api` copies (§3), which are validated at `now`.
   - **Rejected:** OCSP (network, latency, a new failure mode on the payment path; Apple's API over TLS is our freshness source).

**3. Verify procedure (iOS).** Each step runs only if the previous one passed, and nothing is written before step 6. `readAt` is taken before step 3.
1. **App JWS:** `AppleJwsVerifier(App)`. Any failure is **`422 PURCHASE_TOKEN_INVALID`**, with no Apple call.
2. **Claims of the app JWS** (source-generated DTO; read fields only: `bundleId, environment, productId, type, transactionId, originalTransactionId, appAccountToken, inAppOwnershipType, transactionReason, purchaseDate, expiresDate, revocationDate, revocationReason, signedDate`):
   - `bundleId == Purchases:Apple:BundleId`, else `422 PURCHASE_WRONG_APP`;
   - `productId` must be in `Purchases:Apple:Products` (`productId → {type: auto_renewable|non_consumable, plan}`, exactly 3 entries, validated at startup), and the payload `type` must match (`Auto-Renewable Subscription` / `Non-Consumable`), else `PURCHASE_WRONG_APP`;
   - `environment ∈ {Production, Sandbox}`. `Xcode` / `LocalTesting` can't chain to the pinned root, and are refused here anyway. `Sandbox` while `Purchases:Apple:AllowSandbox = false` is `PURCHASE_TOKEN_INVALID`;
   - `transactionId` and `originalTransactionId` must match `^[0-9]{1,32}$`, else `PURCHASE_TOKEN_INVALID`.
3. **Apple reads, routed by the signed `environment` only.** Production uses `https://api.storekit.apple.com`; Sandbox uses `https://api.storekit-sandbox.apple.com` (Apple's recommended domains since 2026-05-05; the old `*.itunes.apple.com` domains still work).
   - **No production → sandbox fallback.** Apple's documented "try sandbox on `4040010`" applies only when the environment is unknown, and ours is always signed.
   - **`Get Transaction Info`** `GET /inApps/v1/transactions/{transactionId}` gives `signedTransactionInfo`, verified with `AppleJwsVerifier(Api)`. It must have the same `transactionId`, `originalTransactionId`, `bundleId` and `environment` as step 2; otherwise 502 plus an alert (Apple contradicting itself is doubt, not user fault).
   - **Subscriptions only:** `Get All Subscription Statuses` `GET /inApps/v1/subscriptions/{transactionId}` (no `status` filter). Pick the `lastTransactions[]` item whose `originalTransactionId` is ours, and verify its `signedTransactionInfo` and `signedRenewalInfo` (both `Api`). If it is absent, the answer is 502.
4. **Binding (`RequireCaller` only),** on the **`Get Transaction Info` copy:**
   - parse `appAccountToken` as a UUID and compare its 16 bytes in constant time with `StoreBindingRef(callerInstallId)`;
   - absent, unparsable or different is **`422 PURCHASE_NOT_OWNED`**, with nothing written;
   - `inAppOwnershipType ≠ PURCHASED` (`FAMILY_SHARED`, `ASSIGNED`) is also `PURCHASE_NOT_OWNED` (PO question 5);
   - with `Skip` (restore), both checks are skipped.
5. **State mapping.** It comes from the `Api` copies only, and any value outside the table means no write and **502, never a grant**.

   | Apple (status / latest transaction / renewal info) | `purchases.state` | Verify | `expires_at` |
   |---|---|---|---|
   | `1` Active, `autoRenewStatus = 1` | `active` | Active | latest `expiresDate` |
   | `1` Active, `autoRenewStatus = 0` | `canceled_active` | Active | latest `expiresDate` |
   | `4` Billing Grace Period | `in_grace` | Active | renewal `gracePeriodExpiresDate` |
   | `3` Billing Retry (no grace) | `on_hold` | Expired | latest `expiresDate` |
   | `2` Expired | `expired` | Expired | latest `expiresDate` |
   | `5` Revoked, or latest `revocationDate` set | `refunded` (`revocationReason` present) / `revoked` (otherwise) | Refunded | unchanged |
   | Lifetime: `revocationDate` null | `active` | Active | NULL |
   | Lifetime: `revocationDate` set | `refunded` | Refunded | NULL |

   - **L-1 lesson:** a subscription in an entitling row (`1` or `4`) with a missing `expiresDate` or `gracePeriodExpiresDate` is 502.
   - The row's `product_id` and `plan` come from the **latest** transaction, so an upgrade from monthly to yearly re-plans the row. The latest `productId` must also be on the allow-list, else 502 (our config is behind Apple).
   - There is no `pending` on iOS: Ask to Buy never reaches the server.
6. **Upsert** through `PurchaseWriter`:
   - `store = app_store`, `store_key = originalTransactionId`, `linked_purchase_token = NULL`;
   - `obfuscated_install_ref` = the canonical `appAccountToken`;
   - `acknowledged = true`, because Apple has no server acknowledgement. The app finishes the transaction; the 2026-04 `Finish Transaction` API is not used;
   - `environment`, the state, `expires_at`, and `install_id` on insert only (as in T-130), with the same `last_verified_at < @readAt` guard;
   - in the same transaction, the new-payment update (§4).
7. **Result:** `StoreVerificationResult` with `IsNewPayment`. Then the T-130 endpoint's grant gate applies.

**Apple answers** (an L-4 lesson: only explicit codes are final):

| Answer | Result |
|---|---|
| `400` with `4000006` (invalid transaction ID) | `422 PURCHASE_TOKEN_INVALID` |
| `404` `4040010` | 502 with `Retry-After` within 10 min of the JWS `signedDate` (Apple's eventual consistency right after purchase); after that, `422 PURCHASE_TOKEN_INVALID` |
| `401` | 502, `outcome=auth_error`, alerted |
| `429` | 502, honouring `Retry-After` |
| `5xx`, timeout, open circuit | 502 |
| Any other 4xx | 502 with `client_error` and an alert on the rate |
| Our own budget denied | 503 `UPSTREAM_UNAVAILABLE` |

**4. New-payment classification** (D-59/D-61(a): a new `transactionId` for its `originalTransactionId` with `transactionReason = PURCHASE`).
- **Schema:** migration `PurchaseLastPaymentAt` adds `purchases.last_payment_at timestamptz NULL` (Apple only: the `purchaseDate` of the newest `PURCHASE`-reason transaction seen by **verify**), with `app_rw` UPDATE on it. `worker_rw` gets nothing, because T-134 must not advance it. No transaction ID is stored.
- **Rule** (inside the upsert transaction, independent of the `last_verified_at` guard):
  ```sql
  UPDATE purchases SET last_payment_at=@pd WHERE id=@id AND (last_payment_at IS NULL OR last_payment_at < @pd)
  ```
  - It runs only when `BindingCheck = RequireCaller` and the `Get Transaction Info` copy has `transactionReason = PURCHASE`. `@pd` is that copy's `purchaseDate`.
  - `IsNewPayment` is true iff 1 row was updated.
- **What this gives:**
  - a re-verify of the same or an older transaction is false;
  - `RENEWAL` is false;
  - an upgrade, crossgrade or re-subscription (same `originalTransactionId`, later `purchaseDate`) is true **once**, even under concurrent verifies;
  - a first purchase is true, which T-184 treats as a bind because there is no seat yet;
  - restore and T-134 never set it, so a notification that arrives before the app's verify can't swallow the move.

**5. API auth (`AppStoreApiTokenProvider`).**
- **Key:** an App Store Connect **In-App Purchase** key (PO question 1) from the secrets manager: `Purchases__Apple__IssuerId`, `__KeyId`, `__PrivateKey` (PKCS#8 PEM).
  - It is loaded into `ECDsa` once.
  - It is never logged, echoed or written to a file.
  - A value from a file-based configuration provider stops Production startup (FU-077 I-4 applied here).
- **JWT:**
  - header `{alg: ES256, kid, typ: JWT}`;
  - payload `{iss: issuerId, iat, exp: iat + 20 min, aud: "appstoreconnect-v1", bid: bundleId}`. Apple caps the lifetime at 60 min;
  - cached and re-minted 5 min before `exp`, so one token per process per 15 min.
- **Errors:** minting failures are `auth_error`; an `OperationCanceledException` is `timeout` (FU-077 I-2).

**6. Client, resilience and budget.**
- **Client:** a typed `HttpClient` per environment, using T-130's Polly settings (5 s attempt, 3 jittered retries on 408/429/5xx/timeout, circuit 0.5/10/30 s, 20 s total). Request logging is off, and spans use route templates only (`/inApps/v1/transactions/{id}`, `/inApps/v1/subscriptions/{id}`, `/inApps/v1/lookup/{orderId}`).
- **Base-URL lock:** the Apple URLs are required in every environment except Development and Testing (FU-077 I-1).
- **Budget:** `AppleCallBudget`, a **separate** token bucket from Play's (a different quota), with lanes `verify`, `notification` (T-134), `support` and `restore`. Restore is denied first and is capped at 30 %. FU-077 M-2 is applied from the start:
  - the permit is taken **per HTTP attempt** in a `DelegatingHandler` inside the retry;
  - the bucket is sized per replica (`total / Purchases:Apple:Replicas`);
  - 20 % is reserved for `notification`;
  - verify gets a per-install limit of 10 per hour;
  - Apple publishes no fixed numbers; it answers 429 per endpoint, so the bucket is config with a conservative default, sized from observed 429s before go-live.
- **Call cost:** lifetime 1 call, subscription 2.

**7. `IAppStoreOrderLookup.CheckAsync(Sensitive<string> orderId, purchase)` (D-57).**
- **Format:** `^[A-Z0-9]{6,20}$` after upper-casing; anything else is `fail` with no call.
- **Sandbox:** a `sandbox` purchase is `fail`, because Look Up Order ID doesn't exist in sandbox.
- **Call:** `GET /inApps/v1/lookup/{orderId}` (production), then `status ≠ 0` is `fail`.
- **Pass:** each `signedTransactions[]` entry is verified (`Api`, bundle, `Production`). The result is `pass` iff any entry has `originalTransactionId == purchase.store_key` (constant time) and `revocationDate` null. A refunded entry is `fail`.
- **`unavailable`:** a JWS failure in the response (with an alert), 5xx, 429, timeout, open circuit, the `support` budget, an unknown `status` value (the T-130 nit 11 lesson) and 401 (with `auth_error`).
- **The order ID** is never stored, logged, traced, put in an exception or made a metric tag.

**8. Logging and metrics.**
- **Never logged:** JWS strings, transaction and original transaction IDs, `appAccountToken`, the order ID, the bearer JWT, the private key, Apple response bodies. Logs carry only `purchaseId` (after the write) and reason enums.
- **Instruments, each tag from a constant set:**
  - `zaghlol.store.call{store=app_store, env=production|sandbox, api=tx_get|sub_status|order_lookup, outcome=…T-130 set…}`;
  - `zaghlol.purchase.jws{source=app|api, outcome=ok|malformed|alg|chain|oid|signature|payload}` (an alert on any `api` failure);
  - `zaghlol.purchase.verify{store=app_store, …}` (existing);
  - `zaghlol.purchase.environment{store, env}` (watches for sandbox use in production);
  - `zaghlol.purchase.ownership_check{path=apple, …}`, which adds the `apple` value to `PurchaseTags.OwnershipPaths`.

**9. Threats.**
- **Forged or tampered JWS:** the pinned root, an exactly-3 chain built offline, both OIDs, `alg` fixed to ES256 with the key only from `x5c[0]` (no `alg: none`/HS256 confusion, no `jku`/`jwk`), and the P1363-only signature. Even a JWS that passes is re-read from Apple.
- **Replay across installs:** the `appAccountToken` binding, checked on Apple's copy, gives `PURCHASE_NOT_OWNED` with nothing written.
- **Replay on the same install:** harmless. Idempotency applies, and the payment is not new (§4).
- **Downgrade to sandbox:** the environment comes only from the signed payload; there is no cross-environment fallback; `AllowSandbox` gates it; the env metric shows it. Sandbox purchases are free for TestFlight testers (PO question 4).
- **Stale JWS** (an app JWS from before a refund): the state comes from fresh API reads.
- **Refund or revocation:** status `5` / `revocationDate` gives `refunded`/`revoked`. T-134 handles `REFUND`/`REVOKE` notifications. Offline Gold is bounded by the entitlement `exp ≤ iat + 3 d` (T-132). Whether `revoked` is sticky against verify is the T-130 review question for T-133/T-134; T-131 doesn't decide it.
- **Out-of-app purchases** (offer codes, promoted IAP) carry no `appAccountToken`: `PURCHASE_NOT_OWNED`, and the app falls back to restore (attested, T-185). Apple's `Set App Account Token` API (2025-06) could stamp them later; it is not used now.
- **API key theft:** an In-App Purchase key only, held in the secrets manager, rotated yearly (deployment.md), with an alert on 401.
- **MITM on outbound calls:** system TLS, and every Apple response is itself JWS-verified.
- **DoS:** the size cap before decode; a fixed 3-certificate chain (bounded cost); the budget; rate limits.

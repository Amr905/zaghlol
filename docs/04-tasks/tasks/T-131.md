## Description
Server-side verify iOS purchases, plus the live App Store order-ID lookup used by support.

## Technical details
- Decide library (Enjna.AppStoreServerLibrary review vs in-house x5c → Apple Root CA G3 + ES256); `bundleId` / `environment` / `appAccountToken == HMAC(installId)` checks; App Store Server API `Get Transaction Info` + `Get All Subscription Statuses`; upsert by `originalTransactionId`.
- Classify a transaction as a **new payment** (new `transactionId` for its `originalTransactionId` with `transactionReason = PURCHASE`: upgrade, downgrade, crossgrade, re-subscription) and expose it in the `IStoreVerification` result; T-132 applies the D-59/D-61(a) seat rule.
- Verification for restore (T-185) skips only the `appAccountToken` check, which names the old install after a phone change.
- **Ownership lookup for support (D-57, §5.3):** `IAppStoreOrderLookup.CheckAsync(orderId, purchase)` via **Look Up Order ID** (`GET /inApps/v1/lookup/{orderId}`): `status = 0`, and one signed transaction, verified like any other, carries the purchase's `originalTransactionId`. Outcomes `pass | fail | unavailable`. The order ID is `[Sensitive]`: never stored, logged, traced or put in an exception message.
- **App Attest validation is not here:** it moved to T-181 (architecture.md previously said "reviewed under T-131").

## Acceptance criteria
- [ ] Tampered JWS rejected.
- [ ] Sandbox and production handled.
- [ ] `appAccountToken` of another install → `422 PURCHASE_NOT_OWNED` on verify (test).
- [ ] An upgrade transaction (`transactionReason = PURCHASE`, new `transactionId`) is flagged as a new payment; a re-verify of an existing transaction is not (test).
- [ ] Look Up Order ID: `status ≠ 0` → `fail`; order whose transactions carry a different `originalTransactionId` → `fail`; Apple 5xx → `unavailable` (WireMock tests).
- [ ] D-57: a log/trace capture test shows the order ID appears nowhere.
- [ ] FU-011: live response-vs-spec test for verify (iOS).
- [ ] DoD (CLAUDE.md §7): analyze clean, formatted, tests added, no hard-coded strings, RTL verified where UI, no `double` money, no raw SMS in logs.

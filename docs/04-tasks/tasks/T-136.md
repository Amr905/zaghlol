## Description
Secure operator access, the audit log, and a support lookup that returns entitlement and seat status only.

## Technical details
- **OIDC** JWT validation (company IdP); short-lived tokens (≤ 1 h); MFA signal required.
- **Roles:** `catalog_editor`, `flags_admin`, `prices_admin`, `support_viewer`, `support_agent`, `support_lead` (R5-5(b)); `x-required-roles` enforced per operation; a contract test checks the roles in code against the OpenAPI (`AdminOperationRolesMatchTheSpecRequiredRoles`, live form).
- **FIDO2 for `support_agent` and `support_lead` (R3-9, R4-6):** the IdP's conditional-access policy scoped to the `zaghlol-ops` and admin-app clients is the enforcement point. **Confirm on the chosen IdP** which claim proves phishing-resistant MFA: Entra `acrs` containing the configured authentication-context ID (Entra `amr` has no FIDO2 value); Google Workspace generally none. If a proving claim exists, the API requires it for both support roles; if none, the API check is **advisory** (requires the MFA signal, increments a diag counter) and T-137's runbook records the IdP policy as the control. Device-code grant disabled for the CLI client.
- **Audit log:** exactly one row per admin write naming the operator; support rows never hold an e-mail, an order ID or free text; support lookup / seat move / detach / unfreeze rows kept exactly 1 year (purge in T-139).
- **Support lookup** `POST /admin/v1/support/entitlement:lookup` (`support_viewer`): `{installId}` or `{email}` (exactly one) in the body, never a query string. Returns `SupportEntitlement` with per purchase `{purchaseId, plan, state, store, seat, accountLinked, linkedBy, lastMovedAt, nextMoveAt, pendingClaimants, buyingInstallSilent, isBuyingInstall, disputeFrozenUntil, rebindsLast30Days}`; no tokens, transaction IDs or other installs' IDs. Audit row stores the install ID or `email:` + `hex(HMAC-SHA256(K_audit, NFC(trim(lower(email)))))` plus the matched `account_id`.
- No endpoint returns installs in bulk.
- **The support write endpoints** (`seat:move`, `purchase:detach`, `purchase:unfreeze`) are in **T-186**; this task supplies the role policies, the audit writer and the alert counters they use.

## Design note
Author: solution-architect (Opus), 2026-11-10. Replaces the "required" stub. Scope: operator auth, roles, audit writer, lookup. The three support write endpoints are T-186.

**1. IdP and abstraction.** The IdP is not chosen (open PO question Q1). Code targets *generic OIDC* behind a profile, so the choice is configuration plus one claim rule: `OperatorAuth:Profile = Entra | Google | Generic`. Only the proving-claim rule differs: Entra requires `acrs` to contain `OperatorAuth:RequiredAcrs` (authentication-context ID); Google and Generic have no proving claim, so `PhishingResistantMode = Advisory`. R4-6 evidence (IdP, claim present or not, conditional-access policy name, CLI device-code off) is recorded in this file by the implementer once Q1 is answered; until then the default is `Advisory` and a startup warning log says so.

**2. Token validation** (`OidcOperatorTokenValidator : IOperatorTokenValidator`, registered by `AddOperatorAuthentication` when `OperatorAuth:Enabled=true`; otherwise `RejectAll` stays). Use `Microsoft.IdentityModel.JsonWebTokens` + `Microsoft.IdentityModel.Protocols.OpenIdConnect` (`ConfigurationManager<OpenIdConnectConfiguration>`; implementer confirms the current maintained version and pins it in `Directory.Packages.props`, one-line justification in architecture.md). No `JwtBearer` handler: our scheme already exists and must keep its single-body 401. Rules, all fail closed to `null`:
- Issuer exact match to `OperatorAuth:Issuer`; discovery at `{Issuer}/.well-known/openid-configuration` over HTTPS only, and the discovered `issuer` must equal the configured one (mix-up defence). Audience exact match to `OperatorAuth:Audiences` (list: `zaghlol-ops`, admin app).
- Algorithm allow-list `RS256`, `ES256` (configurable subset); `none`, HS*, and `jku/x5u/jwk` header keys ignored; `kid` required; keys only from the pinned JWKS. `typ`/`at+jwt` not required (IdPs differ).
- JWKS cached 24 h (`AutomaticRefreshInterval`), forced refresh at most once per 5 min on unknown `kid` (stops a key-flood DoS); on refresh failure keep last good keys up to 7 d, then fail closed.
- `exp`, `iat`, `nbf` required; clock skew 60 s; lifetime `exp - iat <= 3600 s` (reject longer, even if signed); `iat` not more than 60 s in the future. Token length already capped (8192) by `TryReadBearer`.
- MFA: `amr` must contain `mfa` (also accept `hwk`, `fido`, `swk+pin`-style values listed in `OperatorAuth:AcceptedAmr`, default `["mfa"]`); missing `amr` is refusal. For `support_agent` or `support_lead` in `Enforced` mode additionally `acrs` contains the context ID; a mismatch authenticates but the role is **dropped**, so the policy returns 403 (acceptance: 403 for both roles). In `Advisory` mode the roles stay and `operator_phishing_resistant_unproven_total{role}` increments (fixed tag values, per FU-049).
- `sub` is the only identity key (never e-mail or `preferred_username`, which are mutable).

**3. Operator row and roles.** After signature checks, `SELECT id, roles, disabled_at FROM operators WHERE oidc_subject=@sub` on the `ops_ro` login (read-only; validator never writes). No row or `disabled_at` set: `null`. Effective roles = row roles (token groups are ignored, so the DB is the single authority and revocation is immediate: cache is a 30 s per-`sub` positive/negative memory cache, max 1000 entries, so a disable takes effect within 30 s). Known roles only: `catalog_editor, flags_admin, prices_admin, support_viewer, support_agent, support_lead`; unknown strings are dropped and counted. `OperatorRoles` and `AddOperatorAuthentication` gain the four new roles (policy per role exists today for two). `support_agent`/`support_lead` imply nothing: each operation declares its role set in `x-required-roles`; `support_viewer` is never implied by write roles unless the spec lists it. Contract test `AdminOperationRolesMatchTheSpecRequiredRoles` compares code to OpenAPI. Provisioning of `operators` rows (FU-024): a `migrator`-run seed command `zaghlol-ops operators` is out of scope; this task adds a migration-time grant and an idempotent SQL/CLI seeder entry point `backend/deploy/db/seed-operator.sql` documented in the runbook (T-137); no runtime role writes `operators`.

**4. Replacing the default.** `AddOperatorAuthentication` keeps `TryAddSingleton<RejectAll>`; a new `AddOidcOperatorValidator(config)` replaces it with `Replace` only when enabled and valid. Startup check (`OperatorAuthStartupCheck : IHostedService`, same pattern as `ForwardedHeadersStartupCheck`): in any environment other than Development/Testing, if `Enabled=false`, or Issuer is not `https`, or Audiences empty, or Algorithms contain anything outside the allow-list, or discovery/JWKS cannot be fetched at boot, or `TestIssuer:Enabled=true`, the host **fails to start** (not silently reject-all). Prove `/v1` can't get Admin (FU-021): endpoint groups bind the DB role (`/admin/v1` group → Admin context via `RequireOperatorRole`; `/v1` DI resolves an `IDbContextFactory` that refuses `DatabaseRole.Admin`); test enumerates all endpoints.

**5. Audit writer.** `IAuditWriter.Write(AuditEntry, NpgsqlTransaction)`: shared by flags/catalog/prices/lookup/T-186, inserted **in the same transaction as the write** (so exactly one row per call; roll back = no row), `at` left to the DB clock (RLS), operator id from `OperatorIdOf`. `AuditEntry` is a closed record per action (no free-form `Dictionary`), serialised to `details`; fields for support actions are enums or IDs only, so e-mail, order ID and free text cannot be expressed. The DB CHECKs are the backstop. A failing audit insert fails the write (503), never skipped. Existing flags/catalog stores migrate to the shared writer. Reads (catalog GETs) are not audited; the lookup is, as `support_lookup`.

**6. Support lookup** (`POST /admin/v1/support/entitlement:lookup`, role `support_viewer` or higher support role; body `{installId}` xor `{email}`, unknown fields `400 UNKNOWN_FIELD`, both or neither `400`). Resolution: installId direct; e-mail normalised `NFC(trim(lower))`, matched via the existing account e-mail lookup (hash/column per backend-schema; the e-mail is never a query parameter, log field, span tag or exception message; route template only). Returns exactly the `SupportEntitlement` fields in backend-api §5.2. **Must not return:** purchase tokens, transaction/order IDs, any other install's ID, the e-mail, `oidc_subject`, device data, any ledger or transaction data (BR-SYNC-03: the backend has none). Not found by e-mail returns an empty purchases list with the same latency class as found (no account-existence oracle beyond the operator's legitimate need; audited either way). Audit: `support_lookup`, `target` = install ID or `email:`+hex(HMAC-SHA256(K_audit, NFC(trim(lower(email))))) via KMS `K_audit` (separate key from the `install_hash` pepper), `details.account_id` when matched. `isBuyingInstall` null for e-mail; `rebindsLast30Days` clamped 0..2. Per-operator rate bucket exists; add a stricter `support_lookup` bucket (e.g. 20/min/operator) and counter `support_lookup_total{role}` as the enumeration alert; no bulk endpoint.

**7. Local dev and tests without an IdP.** `FakeOidcIssuer` test helper (in `Zaghlol.Tests`): in-process Kestrel/`TestServer` host serving discovery + JWKS, RSA/EC keys generated per run, `Mint(sub, amr, acrs, roles?, iat, exp, aud, alg)`. Dev: `OperatorAuth:TestIssuer:Enabled=true` (honoured only in Development/Testing; startup check rejects it elsewhere) starts the same fake issuer and logs a dev token command; real validator code path is used in both, so no "test-only bypass" validator exists. No token is ever logged.

**8. Config keys.** `OperatorAuth:{Enabled, Profile, Issuer, Audiences[], Algorithms[], AcceptedAmr[], PhishingResistantMode (Enforced|Advisory), RequiredAcrs, ClockSkewSeconds=60, MaxLifetimeSeconds=3600, JwksRefreshHours=24, OperatorCacheSeconds=30}`; `Kms:AuditKeyId` (K_audit). No secrets in config (public keys only).

**9. Threats.** Forged/alg-confusion token (allow-list, pinned JWKS); issuer mix-up (discovered issuer check); stolen long-lived token (<=1 h, re-check row every 30 s); revoked operator (row `disabled_at`); role escalation via token claims (DB roles only); JWKS poisoning/flood (HTTPS, throttled refresh, cap); MFA downgrade (`amr` required; Entra `acrs` enforced); dev bypass shipped (startup check, no bypass validator); audit evasion (same-txn insert, failure fails write, no UPDATE/backdating via RLS); PII leakage (typed audit entries, DB CHECKs, log-capture test); lookup enumeration (rate bucket, no bulk, alerts); operator-identity oracle (single 401 body); `/v1` reaching Admin (FU-021).

**10. Test plan -> acceptance.** (Integration with `FakeOidcIssuer` + Postgres.)
- Token without `amr` mfa, wrong iss/aud/alg (`none`, HS256 with public key as secret), unknown `kid`, expired, `exp-iat>1h`, skew edge, disabled operator, unknown `sub`, unknown role: all 401 [AC1].
- Every admin write operation (enumerated from the route table) leaves exactly one `audit_log` row naming the operator; failed insert fails the write [AC2].
- Enforced: `support_agent`/`support_lead` token without `acrs` ID -> 403; with -> 200. Advisory: 200 and counter +1 [AC3]. CLI device-code evidence recorded in this file [AC4] (manual, IdP console screenshot/export).
- `support_lead` distinct from `support_agent`; `support_viewer` gets 403 on every write operation (enumerated) [AC5].
- E-mail lookup: audit target is `email:`+64 hex, `details.account_id` set, DB scan for the e-mail finds nothing; log-capture sink and span exporter contain no e-mail [AC6].
- Lookup response: `isBuyingInstall` null on e-mail, `disputeFrozenUntil`, `rebindsLast30Days` in 0..2, JSON contains no other install ID [AC7]; live response-vs-spec test incl. `400 UNKNOWN_FIELD` [AC8, FU-011].
- Startup check matrix (each bad config outside Dev/Testing throws; Dev/Testing allowed); `/v1` cannot create an Admin context [FU-021]; role contract test against OpenAPI; JWKS rotation and throttled refresh; 30 s cache revocation (fake clock); rate-limit bucket keyed by operator.

**11. Rejected.** ASP.NET `JwtBearer` handler (loses single-body 401 and our per-request operator lookup); trusting token group claims for roles (slow revocation, IdP-coupled); API-issued operator sessions (new credential store, more attack surface); a bypass validator for tests (could ship); hashing e-mail with plain SHA-256 (dictionary-reversible).

**Open PO questions.** Q1: which IdP (Entra ID vs Google Workspace)? It decides whether `acrs` Enforced mode is possible and the conditional-access policy name to record. Q2: confirm the staff-count/IdP tenant that will own the `zaghlol-ops` and admin-app client registrations (needed for Audiences and R3-9 evidence).

## R4-6 / R3-9 evidence (implementer, 2026-11-10)
- **IdP chosen:** not yet (open PO question Q1). The code ships the generic OIDC path with profiles `Entra | Google | Generic`.
- **Proving claim:** Entra only (`acrs` containing the configured authentication-context ID, `OperatorAuth:RequiredAcrs`); Google Workspace and Generic have none. Until Q1 is answered the deployed mode is **`PhishingResistantMode=Advisory`**: the API requires the MFA signal (`amr`), keeps `support_agent`/`support_lead`, counts `zaghlol.diag.operator_phishing_resistant_unproven{role}` (alert `ZaghlolOperatorPhishingResistantMfaUnproven`) and logs a startup warning. Both modes are covered by tests (`PhishingResistantRoleTests`, `OidcOperatorTokenValidatorTests`).
- **Conditional-access policy name:** TBD once the IdP is chosen (to be recorded here and in T-137's runbook).
- **CLI client device-code grant disabled (R3-9):** TBD (IdP console export to be attached once the `zaghlol-ops` client is registered, Q2).
- **Google profile caveat:** Google ID tokens carry neither `amr` nor `nbf`, both of which the design note requires, so `Profile=Google` refuses every token as specified. If Q1 picks Google Workspace, the note's MFA-signal rule needs a decision first.

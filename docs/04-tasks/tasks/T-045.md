## Description
Cards and accounts appear automatically and track balances.

## Technical details
Find-or-create by (institution, last4); kind inference from template event/hints; exactly one default cash; balances upsert when message newer than as_of; merge (re-link transactions) and hide.

## Design note
Status: written by the implementer (Sonnet, flutter-core-engineer) before implementation, 2026-11-11 (CLAUDE.md §6: C3 note). Inputs: this file; FR-ACC-01…06 and D-69; database-schema §2.1 and §3; parsing-engine §6 (account resolve, balance update); T-017 "As built" and review (n-1 closed here: `upsertBalance` is already `async`); the T-050 repository pattern.

**1. Layout.** `app/lib/features/accounts/{domain,data}`: pure-Dart `account.dart` (entity, `AccountKind`, hints, `inferAccountKind`, `AccountsException`) and `accounts_repository.dart` (port); `data/drift_accounts_repository.dart` and `accounts_providers.dart`. `Clock`, `IdGenerator` and their providers are reused from the transactions feature (no second copy). New DAO methods go in `AccountsDao`; no schema change, so no migration.

**2. Resolve (FR-ACC-01).** `resolve(AccountHint)` -> `ResolvedAccount(account, created)`. Input: institution code (required, trimmed, <= 32 runes), `last4` (optional; Arabic-Indic digits normalised to ASCII, then 2-4 digits, else `ACC_INVALID`), currency, label (trimmed, cut to 30 runes), kind (explicit or inferred). Lookup is by (institution, last4) over **all** rows, live first; a merged row is followed to its target, so a card the user merged is not re-created by its next message. Insert if absent. The unique index `ux_accounts_inst_last4` is the arbiter: a loser gets `DbWriteException` unique/primary-key, re-reads, and returns `created = false`. Exactly one caller sees `created = true`. A hint without last4 resolves to the institution-only account (`last4 IS NULL`); the schema has no unique index for that case (NULLs are distinct), so its auto-created id is deterministic (`inst:<code>`) and the primary key is the arbiter. `created` accounts store `default_currency` from the hint; a different currency on a later message does not change the account (transactions carry their own currency; multi-currency accounts hold several).

**3. Kind inference.** `inferAccountKind` is a pure function over the registry's wire event, an available-limit flag, `hasLast4` and an optional explicit kind. Order: explicit kind; available-limit balance or `cc_payment` -> `credit`; `bnpl_installment` -> `bnpl`; `wallet_topup` -> `wallet`; `fx_conversion` -> `multi_currency`; card events (`card_purchase`, `card_purchase_fx`, `atm_withdrawal`, `pending_auth`, `settled`) with last4 -> `debit`; anything else -> `account`. The app has no dependency on the parsing package, so the event travels as its wire string and T-046 maps it. Inference never changes an existing account's kind (the user's choice wins).

**4. Default cash (FR-ACC-03).** `ensureDefaultCash(currency, label)`: read; insert if none; on unique/PK violation re-read. The schema index is global (`is_default_cash = 1`), not per currency (the Lead's brief said per currency; the stored schema, which T-017 froze, is one row). Cash in other currencies is a balance row of the same account, and transactions carry their own currency. The kind of the default cash cannot be changed and it cannot be merged away (`ACC_DEFAULT_CASH`); it can be a merge target.

**5. Balances (FR-ACC-02, 06).** `recordBalance(balance?, available?, asOf, sourceTxnId?)`: currency comes from the `Money` values (both must agree, else `ACC_INVALID`; at least one required), so nothing is ever converted. One statement, `INSERT ... SELECT ... WHERE EXISTS(live account) ON CONFLICT(account_id, currency) DO UPDATE ... WHERE excluded.as_of >= as_of`, so two writers cannot lose a newer value: an older message changes nothing and returns `false`. An equal `as_of` applies (the parsing doc says `>=`). Both fields are replaced as given (a stale partner value under a newer `as_of` would mislead). Zero changed rows: a read tells "no such account" / "merged" from "older". `totalsByCurrency()` sums `balance` per currency over live accounts of asset kinds (not credit/bnpl, whose "balance" is a liability or a limit); hidden accounts count (D-69); no cross-currency sum.

**6. Merge and hide (FR-ACC-04).** `merge(sourceId, targetId)` in one DB transaction: both live, different, source not default cash, else `ACC_NOT_FOUND`/`ACC_MERGED`/`ACC_INVALID`/`ACC_DEFAULT_CASH`. Re-link `transactions.account_id` (soft-deleted rows too, so Undo still works) and `recurring_items.account_id`; repoint accounts already merged into the source to the target (chains stay one hop); move balance rows per currency (the target's row wins unless the source's is strictly newer; never summed); set `merged_into_id` on the source. All-or-none. `setHidden` only changes the flag; lists skip hidden by default, totals do not.

**7. Edit.** `update(id, AccountEdit{label, kind, creditLimit, statementDueDay})`: credit limit must be >= 0 and in the account's currency; due day 1-31; kind of default cash fixed.

**8. Errors and logs.** `AccountsException` codes only (`ACC_NOT_FOUND`, `ACC_INVALID`, `ACC_MERGED`, `ACC_DEFAULT_CASH`, `ACC_CORRUPT_ROW`); DB errors stay code-only `DbWriteException`/`DbReadException`. Nothing logs; no exception carries a label, last4 or amount (a sentinel test).

**9. Tests.** Encrypted DB, as T-050: concurrent resolve (20 callers, one winner, one row), both digit systems, merged-card follow, inst-only deterministic id, default-cash race, stale/equal/newer balances (and a concurrent pair), per-currency independence, merge moves all transactions (incl. soft-deleted), balance merge, chain repoint, refusals, hide still counted, sentinel.

**As built (implementer, 2026-11-11): differences from the note above.**
- None in behaviour. Additions: the institution-only account id is `inst:<code>`; `AccountKind.isAsset` (credit and bnpl stay out of `totalsByCurrency`); `AccountsDao` gained `byInstitutionLast4`, `listLive`, `balancesOfLive`, `updateById`, `inTransaction`, `upsertBalanceIfNotOlder` (one conditional upsert statement), balance move/delete and the re-link statements.
- Default cash is one row for the whole database (the T-017 index is global, not per currency); `ensureDefaultCash(currency, label)` takes the label from the caller (no user-facing string in data).
- The caller (T-046) maps the template event to its wire string and calls `inferAccountKind`; the result goes into `AccountHint.kind`.
- Residuals: no UI to create an account by hand (not in the ACs); the same installation/institution-only rule relies on the primary key, so a user-created institution-only account with another id is found, not duplicated.
- Evidence: `app/test/features/accounts/{domain,data}/` (32 repository tests on an encrypted DB, 8 domain tests). Negative proofs run locally: dropping the `as_of` guard turns 3 balance tests red; removing the duplicate re-read turns the 3 concurrency tests red.

## Description
Apple lifecycle events update Gold.

## Technical details
- Read only `signedPayload`; verify the x5c chain to Apple Root CA G3, the signature, `bundleId` and `environment`, then the nested `signedTransactionInfo` / `signedRenewalInfo` JWS; nothing is written before all pass (`401` otherwise).
- Open envelope: unknown fields ignored, never stored or logged; DTOs list exactly the fields read (no `[JsonExtensionData]` / `JsonElement` / dictionary rest); `x-third-party-body: true`.
- Dedupe `notificationUUID`; return 200 after storing the extracted columns plus `payload_digest`; handle `SUBSCRIBED`, `DID_RENEW`, `DID_FAIL_TO_RENEW` (grace), `EXPIRED`, `GRACE_PERIOD_EXPIRED`, `REFUND`, `REVOKE`, `DID_CHANGE_RENEWAL_STATUS`; `Get Notification History` reconciliation. Production and sandbox URLs.
- State changes write `purchase_events` (`assn:<type>`); a notification never moves a seat.

## Design note
*solution-architect (Opus), 2026-11-11. Inputs: backend-api §1, §4.3 (iOS), §4.5; backend-schema `purchases`, `purchase_events`, `store_notifications`, grants; T-131 design note and as-built code (`AppleJwsVerifier`, `AppStoreVerification`, `AppStoreStateMapping`, `AppleCallBudget`, `PurchaseWriter`, `GrantMatrix`); T-130 design note §1–3; T-131 reviews (FU-092 items 1, 2, 3, 8 owned here); error-handling-and-observability §2. Apple facts checked 2026-11-11 on developer.apple.com: "Responding to App Store Server Notifications" (V2 retries 5 times at 1, 12, 24, 48, 72 h; 200–206 is success, 40x/50x are retried; sandbox sends once, no retries), `responseBodyV2DecodedPayload` (exactly one of `data`, `appData`, `summary`, `externalPurchaseToken`, `unclaimInfo`), `data` (`bundleId`, `environment`, `status`, `signedTransactionInfo`, `signedRenewalInfo`), `NotificationHistoryRequest` (`startDate`/`endDate` required, `onlyFailures`; history kept 180 days in production, 30 in sandbox).*

**0. Model in one line.** The notification is a **signed trigger, not the source of state**: the endpoint verifies and stores extracted columns, answers 200, and a worker re-reads the purchase from the App Store Server API (the same read and the same state table as verify, T-131 §3.5) and writes it under the monotonic `last_verified_at` guard. Out-of-order, duplicate and late notifications therefore converge on Apple's current state, and verify and notifications can't overwrite each other with older reads.
- **Rejected:** applying the notification's own signed `status`/transaction/renewal data. It is authentic, but it describes state at its `signedDate`, notifications arrive out of order, and history replays can be 180 days old; ordering logic would then live in our code. One extra Apple call per notification is cheap at our volume.
- **Not T-134:** seats (a notification never moves one; the DB enforces it, §5), entitlement tokens (T-132), `last_payment_at` (verify only, T-131 §4), Google RTDN (T-133), `CONSUMPTION_REQUEST` answers (PO question 3).

**1. Endpoint `POST /v1/notifications/apple`** (API process, `app_rw`; both App Store Connect URLs point here; the environment comes only from the signed payload). Order; each step only if the previous passed; nothing is written before step 6.
1. **Transport:** existing 256 KB body cap and `application/json` (413/415). Rate limit: a dedicated policy `notifications-apple`, 1 200 requests/min per /24, separate from app buckets (429 is a 4xx, so Apple retries). No bearer token is accepted.
2. **Envelope:** deserialize the body with a dedicated source-generated context (`UnmappedMemberHandling.Skip`, `AllowDuplicateProperties = false`, strict numbers) into `AppleNotificationRequest { string? SignedPayload }`. This bypasses the global unknown-field rejection (`x-third-party-body: true`). Not JSON, not an object, duplicate keys, or `signedPayload` missing / not a string → `400 VALIDATION_FAILED`. Every later failure → **`401`** (generic problem, no detail on which check failed).
3. **Outer JWS:** new `IAppleJwsVerifier.VerifyNotification(signedPayload, now)`, the same pipeline as T-131 §2 (shape, `alg` = ES256 only, forbidden headers, exactly-3 `x5c` chain built offline to the pinned G3 root, both OIDs, P-256, 64-byte P1363 signature, duplicate JSON members rejected), with two differences:
   - **size cap 65 536 chars** for the notification (it embeds two JWSs with their own chains, about 20 KB in practice; the 16 384 cap stays for transaction and renewal JWSs);
   - **validation time = the payload `signedDate`**, bounded by `signedDate ≤ now + 5 min` (new `JwsSource.Notification`, same rule as `App`). Apple's retries and history entries keep their original signature, so validating at `now` would reject genuine late deliveries after an intermediate expires; this is safe because state is always re-read (§0).
4. **Notification claims** (DTO fields read: `notificationType`, `subtype`, `notificationUUID`, `version`, `signedDate`, `data.{bundleId, environment, status, signedTransactionInfo, signedRenewalInfo}`; nothing else, including `appData`, `summary`, `externalPurchaseToken`, `unclaimInfo`):
   - `version == "2.0"`; `notificationUUID` parses as a UUID (stored canonical lower-case); `notificationType` and `subtype` match `^[A-Z0-9_]{1,64}$`;
   - **freshness:** `signedDate ≥ now − 10 days`. Apple's last retry is about 157 h (6.5 days) after the first attempt, and the history job (§4) looks back 7 days. **Invariant:** acceptance window (10 d) < `store_notifications` retention (90 d), so every acceptable replay still hits the dedupe key;
   - if `data` is absent (only `RENEWAL_EXTENSION/SUMMARY`, `EXTERNAL_PURCHASE_TOKEN`, `UNCLAIM_SEATS` and app-transaction types; none is a Gold event): **200, not stored**, `outcome=ignored_no_data`;
   - `data.bundleId == Purchases:Apple:BundleId`, else 401;
   - `data.environment ∈ {Production, Sandbox}`, else 401. Sandbox while `AllowSandbox = false`: **200, not stored**, `outcome=ignored_sandbox` (authentic, and sandbox never retries anyway).
5. **Nested JWSs** (when present), `VerifyTransaction(…, JwsSource.Notification, now)` and `VerifyRenewalInfo(…, JwsSource.Notification, now)` (the renewal method gains a `source` parameter; existing callers pass `Api`):
   - transaction `bundleId` and `environment` equal `data`'s; `originalTransactionId` and `transactionId` match `^[0-9]{1,32}$`; renewal `originalTransactionId` (when present) equals the transaction's and its `environment` (when present) equals `data`'s. Any mismatch → 401;
   - transaction `productId` not in `Purchases:Apple:Products` → **200, not stored**, `outcome=ignored_product` (alerted: our config is behind Apple).
6. **Store:** `INSERT … ON CONFLICT (store, external_id) DO NOTHING` (`app_rw` already has INSERT). Columns: `id` (v7), `store='app_store'`, `external_id` = UUID, `type`, `subtype`, `product_id` (transaction's), `store_key` = `originalTransactionId`, `environment`, `event_time` = notification `signedDate`, `payload_digest` = **SHA-256 of the UTF-8 `signedPayload` string** (not the HTTP body, so the history job computes the same value), `attempts = 0`. Types outside the **reconcile set** (§2), and reconcile-set rows without a `signedTransactionInfo`, are inserted with `processed_at = now()` (and `last_error = 'NO_TRANSACTION'` for the latter) so the worker never sees them. Never stored: `transactionId`, `appAccountToken`, `status`, `bundleId`, any JWS text.
7. **Answer 200** after commit, whether inserted or a duplicate (`outcome=stored|duplicate`). A database failure → 500/503 and Apple retries. Nothing in the request path calls Apple.

**2. Processor (`AppleNotificationProcessorService`, Workers, `worker_rw`).** One instance across replicas via `pg_try_advisory_lock('apple-assn-processor')` on a dedicated connection (the T-130 sweeper pattern); polls every 5 s when idle.
- **Reconcile set** (constant): `SUBSCRIBED`, `DID_RENEW`, `DID_FAIL_TO_RENEW`, `EXPIRED`, `GRACE_PERIOD_EXPIRED`, `REFUND`, `REVOKE`, `DID_CHANGE_RENEWAL_STATUS` (the task's eight) **plus** `REFUND_REVERSED`, `RENEWAL_EXTENDED`, `DID_CHANGE_RENEWAL_PREF`, `OFFER_REDEEMED`, `ONE_TIME_CHARGE` [doc change]. All of them can change state, expiry or plan, and with the re-read model each costs one call. `TEST` and every other type are recorded and ignored.
- **Pick:** `SELECT … FROM store_notifications WHERE store='app_store' AND processed_at IS NULL AND (next_attempt_at IS NULL OR next_attempt_at <= now()) ORDER BY next_attempt_at NULLS FIRST, received_at LIMIT 50` (new partial index, §5). No transaction held.
- **Per row:**
  1. `SELECT id, product_id, plan, environment FROM purchases WHERE store='app_store' AND store_key=@k`. No row → done, `last_error='NO_PURCHASE'`, no Apple call. The worker **never inserts** a purchase: verify inserts (it alone knows the buying install, and `install_id` is insert-only), and the app's verify reads fresh state itself, so a notification that beats verify loses nothing.
  2. `purchases.environment ≠ row.environment` → done, `ENV_MISMATCH`, alerted, no write.
  3. `readAt = now`, then the read on lane `Notification`, base URL of the row's environment:
     - lifetime (catalog type `NonConsumable` for the row's `product_id`): `Get Transaction Info(store_key)` → verify (`Api`) → same `originalTransactionId`, bundle, environment, product in catalog → `AppStoreStateMapping.MapLifetime`;
     - subscription: `Get All Subscription Statuses(store_key)` through **`AppleSubscriptionReader`**, extracted unchanged from `AppStoreVerification.ReadSubscriptionAsync` (verify then calls the shared reader; its tests stay green) → `(latestProductId, plan, MapSubscription(...))`.
  4. Unknown mapping → failure `UNMAPPED` (retry, §3). Never a write on doubt.
  5. **Refund floor:** for `REFUND`/`REVOKE`, a mapped state other than `refunded`/`revoked` is treated as Apple's eventual consistency → failure `REFUND_NOT_REFLECTED` for the first 4 attempts (about 40 min); after that Apple's answer is applied (an older period may have been refunded while the current one is paid) and `zaghlol.assn.refund_not_reflected` fires an alert for a human look.
  6. **Write, one short transaction** (`IAppleNotificationStore.ApplyAsync`): `SELECT … FOR UPDATE` on the purchase, then the **worker statement** (FU-092 item 1, §5)
     ```sql
     UPDATE purchases SET state=@state,
            expires_at = CASE WHEN @keep_expires THEN expires_at ELSE @expires END,
            product_id=@product, plan=@plan, last_verified_at=@read_at
     WHERE id=@id AND last_verified_at < @read_at
     ```
     a `purchase_events` row `cause = 'assn:' || type` when the state changed, and `UPDATE store_notifications SET processed_at=now(), last_error=NULL` in the **same** transaction. Guard lost (a newer verify or sweep read is stored) → still marked processed, `outcome=superseded`.
- **Never written by the worker:** `install_id`, `obfuscated_install_ref`, `environment`, `acknowledged`, `last_payment_at`, account and support columns, `purchase_seats`. `revoked`/`refunded` are **not sticky**: Apple's current answer wins, so `REFUND_REVERSED` restores the state (this closes the T-131 §9 question for iOS).
- **Expected outcomes** (the test table, not code paths; the write is always Apple's current answer):

  | Notification (subtype) | Typical re-read → `purchases.state` |
  |---|---|
  | `SUBSCRIBED`, `DID_RENEW`, `OFFER_REDEEMED`, `REFUND_REVERSED`, `RENEWAL_EXTENDED` | `active` (expiry advanced) |
  | `DID_CHANGE_RENEWAL_STATUS` (`AUTO_RENEW_DISABLED` / `_ENABLED`) | `canceled_active` / `active` |
  | `DID_CHANGE_RENEWAL_PREF` (`UPGRADE`) | `active`, `product_id`/`plan` of the new product (`DOWNGRADE`: unchanged until renewal) |
  | `DID_FAIL_TO_RENEW` (`GRACE_PERIOD` / none) | `in_grace` / `on_hold` |
  | `GRACE_PERIOD_EXPIRED` | `on_hold` (status 3) or `expired` |
  | `EXPIRED` (any subtype) | `expired` |
  | `REFUND` (subscription or lifetime) | `refunded` |
  | `REVOKE` | `revoked` |
  | `ONE_TIME_CHARGE`, lifetime | `active` (usually `NO_PURCHASE` before verify) |

**3. Retries and dead letter** (error-handling §2: "up to 10 times").
- **Counted failures** (`attempts += 1`): `STORE_ERROR` (5xx, timeout, `client_error`), `STORE_AUTH` (401, alerted), `NOT_FOUND` (`4040010` for a known purchase: eventual consistency), `JWS_API` (an Apple API JWS failed: alerted, as in T-131), `UNMAPPED`, `REFUND_NOT_REFLECTED`, `CONTRADICTION`. `next_attempt_at = now + min(1 min · 3^(attempts−1), 8 h)` ± 10 % jitter: 1 m, 3 m, 9 m, 27 m, 81 m, 4 h, 8 h, 8 h, 8 h → the 10th failure arrives about 30 h after the first.
- **Not counted** (the event isn't at fault): `rate_limited` → `next_attempt_at = now + clamp(Retry-After, 1 min, 1 h)`; `budget_denied` / `circuit_open` → `now + 1 min`. On any of these the run **stops** (the rest of the batch would fail the same way).
- **Dead letter:** at `attempts = 10`, `processed_at = now()`, `last_error = <code>`, `zaghlol.assn.processed{outcome=dead_letter}` and an alert. The hourly expiry sweep (§4) still repairs subscriptions; a dead-lettered lifetime `REFUND` is the case the alert exists for.
- `last_error` holds only these codes (the existing `^[A-Z0-9_]{1,64}$` CHECK). Exception messages are constants (`SafeException`), so nothing from Apple reaches a log.

**4. Reconciliation (Workers, two jobs, advisory locks).**
- **History, daily** (`apple-assn-history`): for `Production`, and `Sandbox` when `AllowSandbox`, `POST /inApps/v1/notifications/history` with `{startDate: now − 7 d, endDate: now − 5 min, onlyFailures: true}`, following `paginationToken` while `hasMore`, at most 20 pages per environment (more → alert `assn_history_truncated`). DTO fields read: `notificationHistory[].signedPayload`, `hasMore`, `paginationToken`. Each `signedPayload` goes through **the same ingest function as the endpoint** (§1 steps 3–6, shared `AppleNotificationIngest` in Application with an `IStoreNotificationInbox` port implemented on both logins), so dedupe is the same `ON CONFLICT`. An entry failing verification is skipped and alerted (it came from Apple's API). `zaghlol.assn.reconcile{step=history, outcome}` and a `recovered` counter (inserted rows; alerted when > 0, because it means delivery is failing). Needs worker `INSERT` on `store_notifications` (§5).
- **Expiry sweep, hourly** (`apple-expiry-sweep`): up to 100 rows `store='app_store' AND plan <> 'lifetime' AND state IN ('active','in_grace','canceled_active') AND expires_at BETWEEN now() − 7 d AND now() − 10 min AND last_verified_at < expires_at`, oldest `expires_at` first; each re-read and written exactly as §2 steps 3–6 with `cause = 'sweep'` and no notification row. It catches renewals or expiries Apple never reported as failed, and production rows with `environment = sandbox` whose notifications go to the sandbox URL (PO question 1). No new index: the table is small; add one if the plan shows a sequential scan.

**5. Grants and schema (migration `AppleNotifications`)** [doc change]
- **FU-092 item 1, decision: a worker-specific statement plus a narrow grant.** `UpdateAppleSql` stays verify-only on `app_rw`. The worker uses the statement in §2 and gets `UPDATE (product_id, plan)` on `purchases` (an upgrade notification re-plans the row, as verify does). It does **not** get `environment`, `obfuscated_install_ref`, `install_id` or `last_payment_at`: those belong to verify's binding and new-payment rules (FU-092 item 4 / security L-3). Rejected: granting everything `UpdateAppleSql` writes (the worker would gain the binding column for no need); a worker that never re-plans (Gold plan stays wrong until the next verify).
- Worker `INSERT` on `store_notifications` (history job). Worker keeps `SELECT` only on `purchase_seats`, so "a notification never moves a seat" is enforced by the database as well as by code.
- `store_notifications.next_attempt_at timestamptz NULL` (worker-written; no `ops_ro` grant, following `ack_next_attempt_at`), index `ix_store_notifications_due ON store_notifications (store, next_attempt_at NULLS FIRST, received_at) WHERE processed_at IS NULL`, and CHECKs `type ~ '^[A-Z0-9_]{1,64}$'`, `subtype IS NULL OR subtype ~ '^[A-Z0-9_]{1,64}$'` (T-133 reuses all three).
- Each list is a new frozen list in `GrantMatrix`, merged into `Current`; the golden SQL and the `relacl`/`attacl` Testcontainers test cover it.

**6. Budget and resilience** (FU-092 items 2, 3, 8).
- **Item 8:** rename `StoreLane.Rtdn` → `StoreLane.Notification` (7 references; T-133 has no code yet).
- **Partition instead of a soft reserve:** the worker process gets its own Apple bucket, `Budget:WorkerShare` (default 0.2) of the configured total; each API process gets `total × (1 − WorkerShare) / Replicas`, where `Replicas` now counts **API** replicas only [doc change]. The API bucket refuses lane `Notification` (programming error) and the worker bucket refuses every lane except `Notification`, which the history job also uses. The 20 % "notification reserve" check inside the API bucket is removed: the partition reserves it across processes, which the per-process check never did.
- **Item 2:** in `AppleCallBudget.TryAcquire`, the restore checks and both acquisitions run under one `lock`; inside it, the restore reserve and the restore sub-bucket's `CurrentAvailablePermits` are checked first, then the shared permit is taken, then the restore permit. Only `TryAcquire` consumes and replenishment only adds, so a check under the lock cannot be invalidated, and a failed shared acquire never spends a restore permit.
- **Item 3:** the retry strategy's `ShouldHandle` no longer handles a 429 whose `Retry-After` exceeds 5 s (or a 503 with the same); the response returns at once and the client throws `RateLimited` with Apple's value (clamped to 1–300 s for verify, 1 min–1 h for the worker). `Retry-After` ≤ 5 s is still honoured inside the 20 s total.
- **Call cost:** 1 Apple call per reconcile-set notification, 1 per history page, at most 100 per sweep hour.

**7. Metrics and logs** (constant tag sets; never `notificationUUID`, transaction IDs, `appAccountToken`, JWS text, Apple bodies).
- `zaghlol.assn.ingest{env=production|sandbox|none, outcome=stored|duplicate|unauthorized|ignored_no_data|ignored_sandbox|ignored_product|bad_request}`;
- `zaghlol.purchase.jws{source=notification, outcome=…}` (new source value; failures here are not alerted, they are attacker-controlled input; `api` stays alerted);
- `zaghlol.assn.processed{type=<reconcile-set name|test|other>, outcome=applied|unchanged|superseded|no_purchase|env_mismatch|retry|deferred|dead_letter}`;
- `zaghlol.assn.lag` histogram (`received_at` → processed, seconds); observable gauge `zaghlol.assn.backlog{age=lt_1h|ge_1h}` (alert on `ge_1h > 0`);
- `zaghlol.assn.reconcile{step=history|expiry, outcome}`, `zaghlol.assn.recovered`, `zaghlol.assn.refund_not_reflected`;
- `zaghlol.store.call{api=…+notification_history}`. Logs carry only `store_notifications.id`, `purchases.id` (after the write) and enum codes.

**8. Threats.** Forged or tampered payload: the T-131 verifier on all three JWSs, nothing written. Replay: dedupe within the 10-day window, and a replay only triggers a fresh read (state can't be pushed backwards). Another app's genuine notification: bundle check → 401. Sandbox in production: `AllowSandbox` gate, `env` tag. DoS: rate limit, size caps before decode, a bounded 3-certificate chain per JWS, and no Apple call in the request path (an attacker can't spend our Apple budget; the worker only calls Apple for a UUID that passed full verification and maps to a known purchase).

**9. Tests** (xUnit; `AppleTestPki` + `AppleWireMock`; Testcontainers Postgres; `FakeTimeProvider`).

- **Grants (negative proofs, worker login):** the §2 statement succeeds; T-131's `UpdateAppleSql` fails with `42501`; `UPDATE purchases SET last_payment_at` / `obfuscated_install_ref` fail; any `purchase_seats` UPDATE fails; `INSERT INTO purchases` fails.
- **Retries:** 503 → `attempts = 1`, `next_attempt_at` per schedule; 429 `Retry-After: 120` → exactly one HTTP attempt, deferred ≥ 120 s, `attempts` unchanged, batch stops; budget denied → deferred, uncounted; crash between pick and write (cancel mid-call) → row picked again; two processors → only the advisory-lock holder runs.

Expiry sweep selects exactly the qualifying rows, caps at 100, writes `cause = sweep`.
- **Budget:** 64 parallel `TryAcquire(Verify)` and `TryAcquire(Restore)` on a 100-permit API bucket: restore never exceeds its share, a failed shared acquire leaves the restore sub-bucket unchanged; API bucket refuses `Notification`, worker bucket refuses `Verify`.
- **Vectors:** synthetic notifications under the test PKI (one per reconcile-set type), plus one **recorded sandbox `TEST` notification** (from `Request a Test Notification`, PO question 2) checked against the real root at its `signedDate`; a dynamic skip until it exists. An env-gated live test (`[Trait("live","appstore")]`) requests a test notification and polls `Get Test Notification Status`; it reports skipped when unconfigured.

## Implementation notes (T-134)
*backend-engineer (Opus), 2026-11-11, branch `task/T-134-assn` (from `task/T-134-design-note`).*

**What was built (by design-note section).**
- §1 endpoint: `POST /v1/notifications/apple` (`Api/Endpoints/V1/AppleNotificationEndpoints.cs`): 256 KB cap and `application/json` (413/415, shared `StrictJson.ReadBodyAsync(context, maxBytes)`), the envelope `AppleNotificationRequest { SignedPayload }` read through its own source-generated context (unknown members skipped, duplicates refused, case-sensitive) → 400 `VALIDATION_FAILED`; every later failure a generic 401 `UNAUTHORIZED`; 200 with no body otherwise. No install/account token; own per-/24 bucket `RateLimits:AppleNotifications` (1 200/min) used *instead of* the general per-network bucket. **Deviations from the design note** (for the reviewers).
1. **Alerts are Prometheus rules on the new counters**, not `IAlertSignal` audit alerts: those need a purchase UUID, and most ASSN conditions (ignored product, history invalid entry/truncated, recovered) have none.
2. **Sentinel scan (AC 3)** queries every text-like and bytea column of every `zaghlol` table for the sentinel instead of `pg_dump --data-only` (same coverage, no client binary needed in the test image). Spans are captured with a process-wide `ActivityListener` (raw tags and events, before the redacting processor). HttpClient logs are not part of it: the request path makes no outbound call.
3. **No env-gated live test** that calls `Request a Test Notification` / `Get Test Notification Status`: those two endpoints are not in `IAppStoreServerApi`. The recorded-vector test is in (skipped until the file exists). Follow-up candidate for go-live (PO question 2).
4. **Renewal without a transaction**: when `signedRenewalInfo` is present but `signedTransactionInfo` is not, the renewal's `originalTransactionId` has nothing to be compared with; the payload is still authenticated and stored processed (`NO_TRANSACTION` for reconcile-set types).
5. **Expiry sweep failures** are counted on `zaghlol.assn.reconcile{step=expiry, outcome=failed}` and skipped (no per-row retry state; the next hour re-selects the row).
6. **The intermediate-expired-at-now case** is tested at the verifier level (`AppleNotificationVerifierTests.ARetryUnderAnIntermediateThatHasSinceExpiredVerifiesAtItsSignedDate`), not end to end: the API fixture's PKI is shared by every test class.
7. Also fixed a formatting glitch the design-note commit left in backend-schema.md (the grants comment and the "only these extracted columns" comment had run together on one line).

## Builder self-check (docs/workflow/self-check.md)
1. **Never destroy data on doubt — applies.** The worker never deletes or inserts purchases; an unknown mapping, a JWS/contradiction from Apple, a refund Apple doesn't reflect yet, any store error → retry code, no write. The dead letter only sets `processed_at` and keeps the row (and the hourly sweep still repairs subscriptions). Writes are guarded by `last_verified_at`. Tests: unmapped → dead letter with no event; refund floor; superseded.
2. **Concurrency — applies.** Three advisory locks (one processor, one history job, one sweep across replicas; DB test `OnlyOneHolderOfEachAdvisoryLock`, unit `OnlyTheAdvisoryLockHolderRuns`). The write is `SELECT … FOR UPDATE` + guarded `UPDATE` in one short transaction with the processed mark; no connection held across an Apple call; verify vs worker ordering by `readAt` (DB test stale/superseded). Duplicate deliveries race on the unique key (`ON CONFLICT DO NOTHING`, tested across both logins). Budget: checks and acquisitions under one lock, 64-way contention test.
3. **Untrusted input — applies.** Body cap 256 KB before parsing; outer JWS ≤ 65 536 chars and nested ≤ 16 384 before any decode; 3-certificate chain bounded (4 KiB each); duplicate members refused at both levels; `notificationUUID` must parse; type/subtype `^[A-Z0-9_]{1,64}$` (and DB CHECKs); transaction IDs `^[0-9]{1,32}$` (Arabic-Indic digits refused, test `tx_original_id`); 10-day window; history ≤ 20 pages. Errors never echo input: 400/401 problems carry only the code; 401 doesn't say which check failed.
4. **Fail closed — applies.** Missing/invalid `Purchases:Apple:*` stops API and worker outside Development/Testing (worker newly covered); `WorkerShare` outside (0, 1) stops startup everywhere; an empty bundle accepts nothing; unknown environment (`Xcode`, missing) → 401; the API partition can't spend the worker's lane and vice versa; mixing partitions in one process throws.
5. **Secrets and logs — applies.** Logs carry counts and exception type names only; metric tags come from fixed sets (`AssnTags`, unknown notification types tagged `other`); `last_error` holds constant codes; `Sensitive<T>` for every JWS, transaction ID and pagination token; spans use URL templates. AC 3 sentinel test covers DB, logs and activities (CI).
6. **Docs match the code — applies.** Contract changes written into backend-api §1/§4.5, backend-schema, deployment, error-handling §2/§4 and the OpenAPI operation; deviations listed above, including what the sentinel test does not cover.

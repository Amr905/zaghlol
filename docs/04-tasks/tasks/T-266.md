## Scope (design note first; data migration)
1. Schema: `accounts.linked_account_id` (nullable, FK to accounts, only for card-kind accounts; a credit card can't be linked). Drift migration with tests (`app/tool/generate_drift.sh`, schema version bump, migration test from the previous version; backups/restore include the column).
2. Behaviour: a linked debit card has no balance of its own — its transactions count against the linked account's balance; an SMS balance on a card message updates the linked account; account resolve by (bank, last-4) still finds the card; totals, budgets and transfers never double count (card ↔ its own account is not a transfer).
3. Suggest the link when a card and an account of the same bank exist and the SMS shows the same balance sequence, or when the user opens the card: "Is this card on your <bank> account?" — never auto-link.
4. UI: card detail → "Linked account" (pick / unlink); account detail lists its cards and lets the user set the **current amount** (existing balance edit if present, as-of now); unlinking keeps history and gives the card its own balance again from that moment.
5. Strings ar/en; goldens via app-regen only.

## Acceptance criteria
Migration tests; ledger tests (linked card purchase lowers the account balance once; SMS balance lands on the account; unlink); widget tests ar/en.

## Design note (builder)

**Schema v6 (additive, no rebuild).** `accounts.linked_account_id TEXT REFERENCES accounts(id) CHECK (linked_account_id IS NULL OR (linked_account_id <> id AND kind = 'debit'))`, added last, plus the partial index `ix_accounts_linked (linked_account_id) WHERE linked_account_id IS NOT NULL`. SQLite's `ALTER TABLE … ADD COLUMN` accepts the FK (default NULL) and the CHECK (tested against existing rows: all NULL). The step is frozen in `core/db/migrations/v6_linked_account.dart`; dump `drift_schema_v6.json`; test `migration_v6_test.dart` (v5 file → v6 through the opener, every row kept, shape = fresh = dump, failing step restored byte for byte). Backups carry the column with the `accounts` table (no backup code names columns); a v5 backup restores through the same migration.

**Rules (repository + `AccountLinks`, one transaction each).**
- Only a live `debit` card can be linked, only to a live `account`, `wallet` or `multi_currency` account (never a card, cash or BNPL; never itself). Re-linking to another account is unlink + link. Never automatic: the only writer is the user's tap.
- **Link:** set the column; the card's stored balance rows and typed balances move to the account per currency, newer instant wins (the merge rule): a debit card message's balance *is* the account's balance. The card keeps its id, its (bank, last-4) and all its transactions (resolve still finds the card).
- **While linked** (net worth / Money tab / card detail all read one breakdown): the card has no line of its own; the account's line = its anchor + the counted transactions of the account **and its linked cards** after the anchor (one SQL, `account_id IN (…)`), so a card purchase lowers the account once. A balance from a card message is written to the account (one SQL statement resolves the target, so it can't race a link). `totalsByCurrency` skips linked cards.
- **Unlink:** where a linked card's transactions after the account's anchor counted in a currency, the account is re-anchored at its current figure as a typed balance as of now (so unlinking doesn't move the account's balance), then the column is cleared. From then on the card's transactions count on the card, whose balance is unknown until a message or the user sets it ("own balance again from that moment").
- **Transfers:** a card and its linked account are one ledger for pairing: a transfer leg on the card never auto-pairs with a leg on its account (or another card on it), and a manual link between them is refused like a same-account link.
- **Merge:** cards linked to a merged-away account follow it to the target when the target can hold cards, else they are unlinked (no re-anchor; the merged figures are already a new state). Changing a linked card's kind away from debit, or an account with cards to a kind that can't hold them, is refused with `ACC_LINKED` (unlink first).
- **Suggestion:** card detail (debit, not linked) asks "Is this card on your <bank> account?" when a live eligible account of the same bank exists; when several, the one whose latest reported balance equals the card's (same currency) comes first. Tap = link; nothing is linked without the tap.

**UI (card detail = S-41, used for cards and accounts).** Debit card: a "Linked account" row (pick / change / unlink) or the suggestion question; when linked the header shows "Balance on <account>" with the account's figure. Account: "Cards on this account" list and a "Set current amount" action (the T-199 typed balance sheet, as of now) always available, not only when the balance is unknown.

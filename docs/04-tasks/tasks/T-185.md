## Description
Restore Gold on a new phone only for a genuine app on a genuine device, bound to this install and this body, under the one-phone rules.

## Technical details
- **1. Strict parse and binding (R2-1, R2-6, R3-8):** parse the body once with `JsonDocumentOptions.AllowDuplicateProperties = false` (.NET 10; or an equivalent `Utf8JsonReader` pre-pass) plus a lone-surrogate check → `400 VALIDATION_FAILED`; bind the DTO from the same object; `bodyHash = SHA-256("zaghlol-restore-v1" ‖ 0x00 ‖ installId ‖ 0x00 ‖ JCS(body without "attestation"))` with `installId` from the **install token** only.
- **2. Attestation (required):** Android → T-181 Play Integrity with `requestHash = b64u(bodyHash)` (`device` or `basic` proof level); iOS → `clientDataHash = SHA-256("zaghlol-restore-attest-v1" ‖ 0x00 ‖ bodyHash ‖ seatKeysDigest)` (T-182 digest of `attestation.seatKeys` public keys in order), register `attestationObject` on a key's first use, verify the assertion. Failure → `422 DEVICE_ATTESTATION_FAILED`, nothing written; upstream failure → `503 UPSTREAM_UNAVAILABLE` with `Retry-After`.
- **Seat-key parse (T-182 design note §3):** call `SeatKeyParser.Parse(restore, …)` in step 1 (structural failure → `400 VALIDATION_FAILED` before any App Attest work); step 2 uses its `Digest()` (or `SeatKeysDigest.Empty`); step 2b calls `Verify`.
- **2b. Seat keys (iOS):** `attestation.seatKeys` verified by T-182 over `op = restore`, `challenge = bodyHash` (invalid → `400 VALIDATION_FAILED`; Android `seatKeys` → `400`). **Element-0 check after App Attest, in the same transaction as the counter update (R5-6):** mismatch → `400 SEAT_KEY_MISMATCH` and the transaction rolls back (counter included). A first element 0 registers **trusted** (R5-2) via T-184's `AppAttestVerified` capability.
- **3. Store verification** of each item (T-130/T-131) without the install-binding check.
- **4. Account rule:** account-linked purchase without a valid account token for that account → item `account_required` (no account revealed).
- **5. Seat** via T-184 (same holder; rebind/over-cap; move; cooldown → claimant).
- **6. Basic integrity:** `proof = basic`, token `exp ≤ iat + 2 d` (T-132).
- **Aggregate:** precedence `active > pending > account_required > expired > refunded > invalid`; `restoredCount`; `movedFromOtherPhone`; merged entitlement or `null`; the only 422 is `DEVICE_ATTESTATION_FAILED`; the only 409 is `MOVE_COOLDOWN` (when nothing is `active`/`pending` and at least one item was refused for the cooldown) with the earliest stored hour-rounded `nextMoveAt`.
- **Limits:** 5/hour per install; 10 attempts/day per purchase (keyed by SHA-256 of token / `originalTransactionId`); shared outbound Play/App Store budget reserving capacity for verify and the ack sweeper (restore gets `503` when short).
- Signed 200 with `timeNonce` echo (T-123 filter). Alerts: `MOVE_COOLDOWN` spike, attestation-failure spike by reason, `seat_rebind` (from T-184).

## Design note
Written by the implementer (PO 2026-11-13: Sonnet builds this C4; the contract is already in backend-api §4.3 and ADR-012, so this note only fixes the build decisions).

1. **Parse once, bind once, hash once.** `RestoreRequestParser` (Application) parses the body into one `JsonDocument` (`AllowDuplicateProperties = false`, depth 32), checks every string and member name for lone surrogates, binds the request model by hand from that same element tree (platform schema, patterns and counts of the OpenAPI; an undeclared member at any depth is `400 UNKNOWN_FIELD`, everything else `400 VALIDATION_FAILED`), and writes RFC 8785 JCS from the same tree minus the top-level `attestation`. `bodyHash` uses the `installId` of the install token only. No crypto is written: SHA-256 over the documented message; the vectors in `restore-binding-v1.json` are the test.
2. **Order in `RestoreService`** (nothing is written before its guard passes): seat-key structure (iOS) -> attestation -> per-purchase limit -> store verification (no transaction open) -> one seat transaction -> merged entitlement. Android: Play Integrity (T-181) with `requestHash = b64u(bodyHash)`. iOS: one seat transaction holds the optional `attestationObject`, the assertion over `clientDataHash` (with the `seatKeys` digest), `SeatKeyProofVerifier.Verify` (400), the element-0 registration with the `AppAttestVerified` capability (R5-2; `Mismatch` rolls the transaction back, counter included: `400 SEAT_KEY_MISMATCH`, R5-6) and the limit charge, and only then commits.
3. **Failures:** attestation `Failed` -> `422 DEVICE_ATTESTATION_FAILED` (counted by reason); `Unavailable` -> `503` with `Retry-After`; a store failure aborts the whole call (`502`, or `503` for our own outbound budget) before any seat is touched. A store `Invalid`/`Expired`/`Refunded`/`Pending` result is an item outcome, never a 4xx.
4. **Seats (FU-112, T184-I3):** only `Active` items with a written purchase reach `SeatService.RestoreAsync`, de-duplicated and in **ascending purchase id**, in one App-login transaction, so two restores over the same purchases lock in the same order. A cooldown refusal commits (claimant row) and then answers `409` when no item is `active`/`pending`; `nextMoveAt` is the earliest stored value.
5. **Aggregate:** precedence `active > pending > account_required > expired > refunded > invalid`; `restoredCount` = distinct purchases the caller holds; `movedFromOtherPhone` = a `Moved` outcome that took the seat from another install (a vacant seat is not "from another phone": open question Q1); `entitlement` = the merged token when its status is `active` or `grace`, else `null`.
6. **Limits:** 5 an hour per install is a sliding-window partition in the existing per-token limiter chain (keyed by install id, so a rotated token doesn't reset it), declared by endpoint metadata. 10 attempts a day per purchase (`IRestoreAttemptLimiter`, SHA-256 of the Play token or of the original transaction id of a JWS that verifies) is **in process memory**, like the other buckets: with N API instances the effective limit is up to N times higher (open question Q2: a shared table would need a migration). The shared outbound budget is the existing `StoreLane.Restore`, which the Play and App Store budgets deny first; the Play Integrity call is capped by these two limits (T-181 Q2).
7. **Wiring (FU-120):** `Program.cs` calls `AddZaghlolAttestation()` and `AddZaghlolRestore()`; the error mapping is in `RestoreEndpoints`.

## Acceptance criteria
- [ ] **R3-8:** every `invalid` vector of `restore-binding-v1.json` posted to `/v1/purchases/restore` through the real pipeline gets `400 VALIDATION_FAILED` (endpoint test; review owner T-132, implemented here after the split).
- [ ] R2-6: the hashed object and the bound DTO come from one parse (test: a body with a nested duplicate never reaches binding).
- [ ] R2-1: a valid proof for install A replayed with install B's token and the byte-identical body → `422` (test).
- [ ] Android: stale (> 5 min), replayed, wrong-hash and no-label tokens → `422`; basic-only → `proof = basic` and a 2-day token (tests with T-181 fakes).
- [ ] iOS R4-1(3): a request whose `seatKeys` public keys were reordered or one replaced after the assertion was made → `422` (test).
- [ ] **R5-6:** an iOS restore with a valid assertion and an element 0 that isn't the registered key → `400 SEAT_KEY_MISMATCH`, and the App Attest counter, seat, claimants and events are unchanged (test reads the stored counter before/after).
- [ ] **R5-2:** a restore that passes App Attest registers element 0 with `seat_key_trusted = true`; a restore whose element 0 matches an already registered untrusted key upgrades it to trusted (test).
- [ ] D-63/D-65(a): third same-iPhone restore within 30 days on the holding iPhone → seat passes, window restarts, `seat_rebind` metric emitted (test).
- [ ] `MOVE_COOLDOWN` body carries a whole-hour `nextMoveAt`; the caller becomes a claimant; nothing affecting Gold is written (test).
- [ ] `account_required` precedence and no account disclosure (test).
- [ ] Rate limits: 6th restore in an hour from one install → `429`; 11th attempt per purchase per day across installs → `429` (tests).
- [ ] Upstream decode failure → `503 UPSTREAM_UNAVAILABLE` with `Retry-After`, never `422` (test).
- [ ] R4-2: the 200 echoes `timeNonce` and is signed.
- [ ] FU-011: live response-vs-spec test including `400 UNKNOWN_FIELD`.
- [ ] DoD (CLAUDE.md §7): analyze clean, formatted, tests added, no hard-coded strings, RTL verified where UI, no `double` money, no raw SMS in logs.

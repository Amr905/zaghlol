## Description
Optional account that only carries Gold: verified sign-in that links and protects purchases, moves seats under the one-phone rules, and never loses the link on a refused move.

## Technical details
- **Verification:** Google (`aud` ∈ our client IDs, `iss`, `exp`, JWKS) and Apple (`aud` = Services ID or bundle ID, `iss = https://appleid.apple.com`). Apple `authorizationCode` → encrypted refresh token used only to revoke on deletion.
- **Nonce and replay (R2-9, ADR-016 am. 2/3):** raw nonce required for both providers (`^[A-Za-z0-9_-]{22,128}$`); constant-time compare of `hex(SHA-256(nonce))` with the token's `nonce` claim; missing nonce or claim → `422 ID_TOKEN_INVALID`; `iat` > 10 min old → `422`; single use via `replay_guard`. **The `replay_guard` insert is committed on its own, before and outside the account and seat transaction (R3-5).** An `Idempotency-Key` replay returns the stored result before this check.
- **Element-0 check (§4.6 step 5, R4-1(1)):** an iOS `seatKeys` whose element 0 isn't this install's registered key → `400 SEAT_KEY_MISMATCH`, checked before step 1 so nothing is linked; Android `seatKeys` → `400 VALIDATION_FAILED`; proofs verified by T-182 (`op = signin`, `challenge = SHA-256(nonce)`). A first valid element 0 registers **untrusted** (R5-2).
- **After verification, one transaction that always commits steps 1–4 (R3-5):** (1) upsert account; (2) link install; (3) **attach** (D-54): `account_id` + `account_linked_by = 'signin'` only on purchases with no account and `purchases.install_id` = this install; (4) seat at attach time: if the holder isn't linked to the account, the **account-attach reclaim** once per purchase (`attach_reclaim_used_at IS NULL`; sets it, counts as the move, `seat_move:account_attach`; never cleared, D-58/R3-3), else an ordinary step-5 move; (5) seat moves for account-linked purchases via T-184: same-iPhone rebind within the D-63 cap; over the cap the D-65(a) over-cap rebind **only when `device_key_trusted`**, otherwise an ordinary move with `restoreSuggested: true` (R5-3(b)); otherwise a move under the cooldown (`proof = account`).
- **Refused move (R3-5):** this install becomes a pending claimant (`channel = signin`); response **200** with `accountToken`, `moveRefused: true`, `nextMoveAt` (earliest refused), `restoreSuggested` when applicable, and an entitlement without those purchases. Sign-in never answers `409 MOVE_COOLDOWN`.
- `409 INSTALL_LINKED_TO_OTHER_ACCOUNT` with `replaceLink: true` confirmation (EC-46). Account JWT `{sub, iid, iat, exp: +30 d, kid}`.
- **Account token validity (R3-6):** a token whose account no longer exists, or whose install is no longer linked, → `401 ACCOUNT_TOKEN_EXPIRED` even before `exp` (shared auth handler).
- **Sign-out (D-61(c)):** unlinks the install, doesn't move seats; returns **200 signed** `{entitlement, serverTime, timeNonce}` with account-linked purchases now `paused` here.
- **Delete account:** removes account and links, revokes the Apple token, deletes every `idempotency_records` row with this `account_id` (R3-6); purchases keep seats and `attach_reclaim_used_at`; `account_id` and `account_linked_by` become NULL.
- **Android Apple callback (CR-05, FU-008):** `POST /v1/apple/android-callback` (`form_post`), per-field patterns (`400` otherwise), drop `user` unread, `303` to `intent://callback?…#Intent;package=<applicationId>;scheme=signinwithapple;end` built with a URI builder; body and `Location` never logged.
- Sign-in and sign-out 200s are signed and echo `timeNonce` (T-123 filter).

## Design note (builder, T-135)

- Flow: verify ID token (RS256, single aud from `Accounts:*` config, 60 s exp skew) -> nonce claim = hex(SHA-256(raw nonce)), `iat` within 10 min -> `replay_guard` insert committed on its own -> seat-key proof -> Apple code exchange (refresh token sealed with the envelope cipher) -> one transaction (lock install, upsert account, 409 unless `replaceLink`, link, attach purchases bought by this install only, `SeatService.SignInAsync` per entitling purchase) -> signed entitlement + 30-day account token.
- `moveRefused` is always 200 (R3-5); `restoreSuggested` per R5-3(b); `SEAT_KEY_MISMATCH` per R5-6. Option R5-3(a) is not implemented.
- Delete: Apple revoke first (fail closed: 503 and the account kept, except `invalid_grant`), then one SQL transaction: unlink purchases (reclaim marker untouched), delete idempotency rows for the account, delete the account. Hard delete, no tombstone (FU-015: SQL only). A later request with that account token gets 401 `ACCOUNT_TOKEN_EXPIRED` (R3-6).
- `ACCOUNT_TOKEN_EXPIRED` applies to signout/delete only; sync/verify/entitlement treat a bad account token as absent (purchase `paused`).
- Negative proofs: (1) replay row spent after the transaction opens fails `TheReplayRowIsSpentBeforeTheTransactionOpens...`; (2) dropping the nonce check fails 3 `ABadClaimOrAgeIsRefused...` cases.
- Config the PO supplies: `Accounts:Google:ClientIds`, `Accounts:Apple:{ServicesId,BundleId,TeamId,KeyId,PrivateKey}`, `Accounts:AndroidPackage` (or `Purchases:Google:PackageName`).

## Fix round 25k: delete never blocked by Apple (Lead decision, 2026-11-15)

Batch-25a review finding 2 (permanent Apple failure blocked deletion forever) is resolved so that **the user's right to delete is never blocked by Apple**:

- `DELETE /v1/accounts/me` always deletes the account, its links, its purchase links and its sign-in idempotency rows in one transaction and answers 204. The `503` of the earlier design is gone for this endpoint (OpenAPI updated).
- Apple revoke first. `Revoked` (success or `invalid_grant`) queues nothing. Any other outcome, an exception, or an unreadable key: the refresh token is re-sealed under the constant context `pending-apple-revocation` (the provider subject is gone with the account) and inserted into `zaghlol.pending_apple_revocations` in the **same transaction** as the delete. Columns: `id`, `sealed_blob`, `attempts`, `created_at`, `next_attempt_at`, `expires_at`. No account, install, subject or e-mail reference.
- Migration `20261115120000_PendingAppleRevocations` (plain SQL, model snapshot unchanged; grants in `GrantMatrix.PendingAppleRevocations`): `app_rw` INSERT only; `worker_rw` SELECT, DELETE and UPDATE(`attempts`, `next_attempt_at`); no operator role.
- Worker `AppleRevocationRetryService` (every 15 min, runs `AppleRevocationRetryJob`): drops rows past `expires_at` (30 days), revokes due rows (success or `invalid_grant` deletes the row), otherwise `attempts + 1` and back-off 15 min doubling, capped at 24 h. A blob that no longer opens is dropped.
- Operator must give the **worker** the same `Kms:*` ring and `Accounts:Apple:*` settings as the API (the worker now calls `AddZaghlolKms` and reads `AccountsOptions`).
- Review minor 1: sign-in locks the union of the buying install's unlinked purchases and the account's purchases in one ascending-ID statement (`LockPurchasesAsync`) before attaching; delete locks the account's purchases in ascending ID before its UPDATE. Review minor 3: `RevokeAsync` also catches `CryptographicException` and `InvalidOperationException`. Nit 4: an unreadable sealed token logs a fixed warning.
- Tests: `AccountLifecycleServiceTests` (Apple down or throwing: deleted and the sealed token queued; revoked: nothing queued), `AppleRevocationRetryJobTests` (success removes, back-off, gives up after the window, success after failures), `AccountEndpointTests` (Apple down: 204, account gone, one sealed pending row with 7 columns; invalid_grant path: no row), `AccountPurchaseLockOrderTests` (union locked up front), `GrantTests` deny probes. DB-backed tests run on the GitHub backend-ci run (Docker).

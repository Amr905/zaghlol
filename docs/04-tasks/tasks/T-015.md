## Description
Generate and protect K_db on first launch.

## Technical details
32 random bytes via Random.secure; flutter_secure_storage (Android Keystore-wrapped AES; iOS Keychain first_unlock_this_device, not synchronizable); detect missing/invalidated key vs first run (never silently create a new DB over an existing file); key never logged or persisted elsewhere.

## Design note
Required — solution-architect (Opus) writes it before implementation (C4).

## Acceptance criteria
- [ ] First run creates key; second run reads same key
- [ ] Existing DB + missing key → KeyInvalidated failure (not a new key)
- [ ] Key absent from logs, prefs and files (scan)
- [ ] DoD (CLAUDE.md §7): analyze clean, formatted, tests added, no hard-coded strings, RTL verified where UI, no `double` money, no raw SMS in logs.

## Testing requirements
- Unit tests with fake storage
- Device test on Android + iOS

## Review follow-ups (added by Lead)
- From the T-165 design note: at startup, detect a DB that exists without its key (OEM transfer or leaked restore). Wipe it and start in first-launch state with the restore offer; never half-open it. Never store app data in `UserDefaults` or SharedPreferences in plaintext.

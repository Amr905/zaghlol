## Description
Generate and protect K_db on first launch.

## Technical details
32 random bytes via Random.secure; flutter_secure_storage (Android Keystore-wrapped AES; iOS Keychain first_unlock_this_device, not synchronizable); detect missing/invalidated key vs first run (never silently create a new DB over an existing file); key never logged or persisted elsewhere.

## Design note
Status: written by solution-architect (Opus), 2026-11-10. Inputs: security-model §3/§7, FR-SEC-04/05 (D-50), ADR-002 + T-007 harness (`sqlite3mc_contract.dart`), FU-050 (T-007 security I-2, L-3), T-165 cross-task requirement and review F6, platform-channels §1.3/§5/§6.

**1. Key material.** `K_db` = 32 bytes from `Random.secure()` (OS CSPRNG; it throws `UnsupportedError` if none, which maps to `KEY_STORE_FAILED(generate)`). Reject an all-equal-bytes result as a broken generator. Applied as the T-007 **raw key** `PRAGMA key = "x'<64 lowercase hex>'"` with `cipher='sqlcipher'`, `legacy=4`: SQLCipher 4 raw-key semantics, no PBKDF2 at open; the per-file salt sits in the DB header. *Rejected:* a passphrase key (PBKDF2-SHA512 256k costs 140–240 ms per open, ADR-002 finding 5); a 96-hex key-plus-salt (no benefit, the file salt is already random).

**2. Storage: decision = native Pigeon channel, no `flutter_secure_storage`** (**deviation from ADR-002 / architecture §7 / platform-channels §5, needs PO approval, see Q1**). New `app/pigeons/secret_store_api.dart` → `SecretStoreHostApi`:
```dart
enum SecretSlot { dbKey }                        // T-148 adds backupKey
enum SecretStatus { found, notFound, unusable, unavailable }
class SecretRead { SecretStatus status; Uint8List? value; int attempts; }
@HostApi() abstract class SecretStoreHostApi {
  @async int acquireBootstrapLease(int timeoutMs); // process-wide; lease expires after 30 s
  @async void releaseBootstrapLease(int lease);
  @async SecretRead read(SecretSlot slot);
  @async Uint8List createIfAbsent(int lease, SecretSlot slot, Uint8List candidate); // returns the stored value (winner)
  @async void delete(int lease, SecretSlot slot);  // this slot only, never deleteAll
}
```
Why not the plugin: (a) since 10.0 `flutter_secure_storage` sets `resetOnError` to **true** by default (it deletes stored values on read errors), and 11.0 makes data saved with removed algorithms unusable; both are wrong for the one key whose loss erases all user data. (b) F6 needs exact classification (alias missing vs AEAD tag failure vs transient Keystore error); the plugin flattens these into strings. (c) Its Android store is SharedPreferences, against the T-165 policy. (d) We already need native Keystore/Keychain code for `K_spool` (platform-channels §1.3), so the extra code is ~150 lines per platform, with **no new pub or native dependency and no lockfile change**. The channel must be registered in every engine that opens the DB, including the Android headless engine (T-008).

*Android* (`app.zaghlol.platform.keys`, shared later with T-008's spool key): Keystore AES-256-GCM key `zaghlol_db_kek_v1`, non-exportable, `setUserAuthenticationRequired(false)`, `setUnlockedDeviceRequired(false)` (background capture), StrongBox if available and TEE otherwise. Blob `noBackupFilesDir/keys/db_key_v1.bin` = `0x01 ‖ iv(12) ‖ ct(32) ‖ tag(16)`, AAD `"zaghlol/k_db/v1"`, written as tmp, then fsync, then rename. Every create makes a **fresh** wrapping key (stale alias deleted first). It reads back and unwraps (constant-time compare) before it returns. Read classification: blob absent → `notFound`; blob present + alias absent, `AEADBadTagException`, malformed blob, `KeyPermanentlyInvalidatedException`, or API 33+ `KeyStoreException` with `ERROR_KEY_DOES_NOT_EXIST`/`ERROR_KEY_CORRUPTED` → `unusable`; `isTransientFailure()` true, `IOException`, or **any other exception** → `unavailable` after 3 attempts (100/300/900 ms).
*iOS* (`Runner/Platform/Keys/`): generic password, service `app.zaghlol.keys`, account `db_key_v1`, `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`, `kSecAttrSynchronizable = false` set explicitly, default access group (Runner only: the Share Extension never opens the DB). Queries always name service+account and never touch the D-62 seat-key items. `errSecSuccess` with 32 bytes → `found`, with another length → `unusable`; `errSecItemNotFound` (−25300) → `notFound`; `errSecInteractionNotAllowed` (−25308) and **every other status** → `unavailable`.
**Rule: only positive evidence of absence or corruption is `notFound`/`unusable`. Unknown errors are `unavailable` and never lead to a wipe.**

**3. Flow** (`KeyBootstrap.obtain()`, pure Dart, `core/db/key_bootstrap.dart`). Take the lease (timeout 10 s, else `KEY_UNAVAILABLE(leaseTimeout)`). `dbPresent` = any file of `DbFileSet` exists (`zaghlol.db`, `-wal`, `-shm`, `-journal`, restore/migration temp names; T-015 defines the set and T-016 owns the path). Then `read(dbKey)`:

| read | DB absent | DB present |
|---|---|---|
| `found` | delete + create → `KeyCreated(rotatedNoDb)` (iOS Keychain outlives uninstall; T-165) | `KeyReady` (lease released) |
| `notFound` | create → `KeyCreated(firstRun)` | `KeyInvalidated(missing)`: **no key written, no file touched** |
| `unusable` | delete + create → `KeyCreated(rotatedNoDb)` | `KeyInvalidated(unusable)` |
| `unavailable` | `KeyUnavailable(transient)` | `KeyUnavailable(transient)` |

`KeyCreated` and `KeyInvalidated` **return holding the lease**. T-016 creates and verifies the new DB under it, or wipes on orphan and then calls `bootstrap.recreateAfterWipe(lease)` → `KeyCreated(afterWipe)`, then releases. This serialises the main engine and the headless engine (an SMS arriving during first run, or after "Delete everything"), so one engine never rotates or wipes under another's DB. `createIfAbsent` also returns the existing value if one appeared. A DB file is never created before its key is stored and read back. **T-016 hook:** if the open sequence's verify fails with SQLITE_NOTADB (26) on the first page read, T-016 calls `bootstrap.reportRejected()` → `KeyInvalidated(rejectedBySqlite)` (F6 "SQLCipher key error"). Any other SQLite code (BUSY, IOERR, FULL, CANTOPEN) is transient and never wipes.

**4. Failure behaviour (what the user sees).** `KeyInvalidated` (OEM transfer, a leaked restore, a lost Keystore key, a corrupt page 1, which can't be told apart from a wrong key): T-016 wipes the DB file set, spool, temp, guard config and the `dbKey` slot (never the iOS seat keys), then starts first-launch with the restore offer (D-50, FR-SEC-05). No crash, no loop, nothing partly opened. `KeyUnavailable` in the foreground: a blocking "couldn't open your data, try again" gate with Retry (UI and strings belong to the startup-gate owner; **T-015 ships no UI**). After 3 failed retries the gate shows the support code. It never wipes. In the background: abort the job and leave spool entries (ack-after-commit); WorkManager or the next launch retries. `KeyStoreFailed` on first run: same gate; no DB is created.

**5. Memory lifetime and zeroization.** `DbKeyMaterial` wraps the `Uint8List`, `toString()` → `DbKeyMaterial(<redacted>)`, no `==`/`hashCode` on the bytes, `zeroize()` fills with 0. The hex `String` is built only inside drift's `setup` closure and passed straight to the `_rawExecSecret` pattern. The caller zeroizes right after the first successful open. **No provider, field or cache holds key bytes or the hex.** *Limits, accepted and documented:* Dart `String`s are immutable and can't be zeroed. GC may leave copies. `createInBackground` copies the closure into the DB isolate. The Pigeon codec and `package:sqlite3`'s native UTF-8 buffer are freed but not wiped. sqlite3mc keeps the key schedule for the connection's lifetime (it needs it). Only root can read these (security-model §1, out of scope). *Future hardening (not now):* `sqlite3_key_v2` through FFI with a zeroed native buffer.

**6. Riverpod (ADR-001).** `secretStoreProvider` → `SecretStore` (pure Dart interface; `PigeonSecretStore` in `core/platform/`; `FakeSecretStore` in tests). `dbFileSetProvider`. `keyBootstrapProvider` → `KeyBootstrap(store, files, KeyGenerator(Random.secure()))`, keepAlive and **stateless** (never caches the result or the key). Only T-016's `appDatabaseProvider` calls `obtain()`. If `flutter_riverpod` isn't in `pubspec.yaml` yet, T-015 adds it (already justified, architecture §7).

**7. Error codes and logging (FU-050).** Dart: sealed `KeyBootstrapOutcome` above; diag codes `DB_KEY_CREATED`, `DB_KEY_ROTATED`, `DB_KEY_INVALIDATED`, `DB_KEY_UNAVAILABLE`, `DB_KEY_STORE_FAILED`, fields only `{reason enum, platform, attempts}`. They are emitted once T-021 exists; **until then nothing is logged**. Native: `PlatformException(code, message: null)` with new §6 codes `KEY_STORE_FAILED` and `LEASE_TIMEOUT`. Exception messages and causes are dropped at the boundary. No `Log.*`, `print`, `NSLog` or `os_log` in the keys packages (CI grep). `PRAGMA key`/`rekey` go only through the `_rawExecSecret` pattern, because `SqliteException.causingStatement` holds the key (I-2(1)). Drift `logStatements: false` in every flavor, asserted by a test (I-2(3)). Keys never appear in test names, `reason:` strings or assertion messages. The next edit of `db-platform.yml` adds `trap … EXIT` cleanup for the interop key (L-3). L-1/L-2 (mobile binary attestation) stay with T-171.

**8. Threats.** *Root/jailbreak:* the Keystore can be used as an oracle and memory can be read. Out of scope (§1); FR-SEC-07 warns. An offline copy of the blob is useless without the non-exportable Keystore key. *OS backup extraction:* Android `allowBackup=false` plus the blob under `noBackupFilesDir`. iOS `ThisDeviceOnly` items restore only to the same device, and the DB is excluded (T-165), so the result is "key present, DB absent", which rotates. *Device transfer:* an Android OEM tool copies DB and blob but not the Keystore alias → `unusable` → wipe (D-50). iOS direct transfer has been reported to carry `ThisDeviceOnly` items across (Apple DTS found it surprising and suggested the unwrap may fail). If the key does arrive usable and a DB leaked too, the same user's data opens on their new phone (residual, no third party). Otherwise the orphan or first-run path applies. T-165-device step 5 records it. *Reinstall:* Android drops the key and the files → first run. iOS keeps the Keychain item → rotate. *Developer leakage:* §7 rules.

**9. Tests → AC.**
- **AC1 (create then same key):** unit tests with `FakeSecretStore` + fake `DbFileSet` cover every cell of the §3 table, lease handling, `createIfAbsent` winner semantics (two concurrent `obtain()` calls get one key) and the generator rejecting all-equal output. Integration (`app/integration_test/db_key_test.dart`, added to the db-platform API 35/API 26/iOS-sim legs; the host leg runs the unit tests only): bootstrap → open with the T-007 open sequence → write a sentinel → close → new `ProviderContainer` → bootstrap → `KeyReady` → the sentinel reads back.
- **AC2 (existing DB + missing key → `KeyInvalidated`):** unit: `notFound`/`unusable` with the DB present → `KeyInvalidated`; the fake records **zero** create/delete calls; the DB file bytes are unchanged (SHA-256 before and after). `unavailable` → `KeyUnavailable` with nothing written. Integration, three variants: Android deletes only the alias (F6); Android flips one blob byte (AEAD); iOS deletes the item. Each → `KeyInvalidated` with the DB untouched. Native unit tests: Kotlin JVM test of the exception → status mapping (unknown → `unavailable`); XCTest for OSStatus mapping and the item attributes (`kSecAttrAccessible` = AfterFirstUnlockThisDeviceOnly, not synchronizable).
- **AC3 (key absent from logs, prefs and files):** the integration test injects a **fixed synthetic test key** through `KeyGenerator`, so the host knows the needles without moving a secret. Needles: raw bytes, lower/upper hex, base64. The in-app scan walks the whole sandbox (Android `dataDir` incl. `shared_prefs`, `files`, `no_backup` [the blob must be ciphertext], `cache`, `code_cache`, `databases`; iOS container `Library`, `Documents`, `tmp`, `Preferences` plists) → 0 hits. A positive control writes the needle to a temp file, the scanner finds it, the file is deleted. The host greps `adb logcat -d` / `simctl spawn log show` for the needles → 0 hits, with a fixture-file positive control for the grep. Unit: `DbKeyMaterial.toString()` and every outcome's `toString()` hold no hex; `logStatements` false.
- **Negative proofs** (throwaway branches, as T-007; runs recorded in `implementation-status.md`): (a) bootstrap writes a new key when the DB exists → AC2 red; (b) `debugPrint` of the hex → log scan red; (c) iOS accessibility changed to `AfterFirstUnlock` → attribute XCTest red.
- **Device (T-171 checklist):** one mid-range Android with StrongBox and one iPhone: AC1/AC2 plus a reboot followed by a background read before first unlock (iOS → `unavailable`, no wipe).

**Rejected alternatives:** `flutter_secure_storage` (§2); generating `K_db` inside the Keystore (non-exportable, but SQLite needs the raw bytes); quarantining the orphan DB instead of wiping it (useless without the key, contradicts D-50; the strict classification is the guard against false orphans); retrying `unusable` across launches before wiping (an error loop, against FR-SEC-05).

## Implementation notes (T-015, 2026-11-10)
Where the code refines the note (reviewers: check these):
1. **`reportRejected(DbKeyMaterial rejected)`** takes the key SQLite refused and re-reads under the lease: same key + DB present → `KeyInvalidated(rejectedBySqlite)`; a different stored key (another engine rotated it) → `KeyReady(new key)`, so two engines reporting the same failure can't wipe twice.
2. **`recreateAfterWipe(lease)` never releases the lease**, on any outcome: after a failed recreate the caller still holds it, finishes the wipe and retries, so the one-time notice (`restoreNoticeDue`) is not lost.
3. **Retries:** 1 attempt + 3 retries at 100/300/900 ms (`attempts` = 4 when all fail), on both platforms.
4. **`createIfAbsent` refuses** (`KEY_STORE_FAILED`) when the slot holds an unusable or unknown secret: only `delete` clears it, and the Dart flow deletes only when no database exists. A write with a lease that is not current fails with `LEASE_TIMEOUT`.
5. **Open path in `lib/`:** `core/db/encrypted_open.dart` (`openEncryptedExecutor`, `applyEncryptedOpenSequence`, `DbOpenException extends SafeException`, `dbOpenExceptionOf`, `driftLogStatements = false`) carries the T-007 open sequence with the `_rawExecSecret` rule, so T-016 opens through it. SQLITE_NOTADB from any post-key statement is `DB_KEY_REJECTED` (`PRAGMA journal_mode` already reads page 1). The app now depends on `zaghlol_domain` (path) for `SafeException`.
6. **`DbFileSet`** = bases `zaghlol.db`, `zaghlol.db.restore.tmp`, `zaghlol.db.migrate.tmp` × suffixes `''`, `-wal`, `-shm`, `-journal`. It lists the directory: absent only on positive evidence (directory missing, or listed without error); an unreadable directory is `KeyUnavailable`.
7. **AC2 "SHA-256 before/after"** is a byte-for-byte comparison of every file (stronger; no `crypto` dependency).
8. **Riverpod:** `flutter_riverpod` 3.x with plain providers (no generator yet); `dbDirectoryProvider` throws until T-016 overrides it.
9. **iOS project:** the generated `SecretStoreApi.g.swift` and the `Platform/Keys/*.swift` files are added to the Runner target (the older T-004 `.g.swift` files are still not in the project; their APIs are empty).
10. **Hand-off:** T-008 must call `SecretStoreRegistration.register` in the headless engine (Android) / every engine (iOS). T-016 records `restoreNoticeDue` in the new DB; the startup screen reads and clears it (D-70).

## Review follow-ups (added by Lead)
- From the T-165 design note: at startup, detect a DB that exists without its key (OEM transfer or leaked restore). Wipe it and start in first-launch state with the restore offer; never half-open it. Never store app data in `UserDefaults` or SharedPreferences in plaintext.
- From the T-165 security review F6: orphan detection must key on the key being unusable: the alias is missing, unwrap fails, or SQLCipher open fails with a key error. A wrapped-key blob being present does not mean the key is usable. On orphan, wipe the DB, spool, temp files and wrapped blobs. On iOS, never delete the D-62 seat keys.

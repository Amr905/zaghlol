## Description
Typed sealed `Plan` classes for every variant, parsed from the reply JSON; constants generated from the pinned schema (`planVersion = 1`, plan names, enums, ranges, allowed blanks per plan) by a script with a regen check. `PlanValidator` applies §2.4 steps 1–6 on the phone, plus the phone-only check that no string names an account/card/bank from the user's registry or the mask sources in plain text (takes a `MaskSources`-like lookup).

## Acceptance criteria
1. All shared vectors pass with the same outcome as the .NET validator (T-330).
2. Phone-only check: a plan with `account:"CIB"` in plain text or a `ref` not in the sent text → fallback; `mention:"Carrefour"` for "how much on groceries?" → fallback.
3. Regenerating constants from the schema produces no diff (test or script check).
4. Template grammar rejects every §2.3 class (same list as T-330) in both languages.
5. Pure Dart, no `double`; `dart analyze`, `dart format`, package tests green.

## Notes for the builder

## Design note (builder, Sonnet)
- **Generated constants vs hand-written types:** both. `tool/gen_plan_schema.dart` writes `plan_schema.g.dart` from the pinned schema and the shared vectors: `planVersion`, `planNames`, `planCategorySlugs`, `planTemplateBlanks`, currency exponent sets, and the schema JSON itself (without `$schema/$id/$comment`). Step 1 is a small interpreter of exactly the keyword subset the schema declares (type incl. lists, properties, required, additionalProperties:false, enum, anyOf, `$ref`, pattern, min/max, minItems/maxItems), so the phone cannot drift from the backend's schema. The sealed `Plan` classes in `plan.dart` are hand-written and built only after steps 1-5 pass; a test ties their enums to the schema enums and every plan name to a class.
- **Regen check:** `dart run tool/gen_plan_schema.dart --check` and a unit test compare the committed file with the generator output.
- **Steps 2-6** are a port of the vectors' reference rules (foldKey, canonical decimal equality, whole-word number words, ordered template rules). Phone-only additions: `ref` must be in the question's `MaskMap` (`REF_NOT_IN_MAP`), `mention` and template text must not name a user account, institution alias or merchant (`PLAIN_NAME`, `TEMPLATE_PLAIN_NAME`), the fraction rule also runs for a null currency against `primaryCurrency`, and `target.currency` null is also enforced inside PL-INVEST's nested what-if (stricter than the backend reference; the phone only falls back more).
- **NFC:** the SDK has no normaliser and no dependency was added, so `isLikelyNfc` rejects any text with a composable combining mark (U+0300..036F, U+0653..0655) or U+212A/212B/2126. Safe side: a template is dropped, the plan stays.
- The validator never throws (any internal error is `SCHEMA_INVALID` step 1) and never logs; `toString` of filters, templates and balance refs is redacted.

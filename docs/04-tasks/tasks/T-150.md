## Description
Backups in the user's hidden Drive folder.

## Technical details
google_sign_in drive.appdata scope; upload to temp name then rename; list/download/delete; quota/network errors; cross-platform restore.

## Design note
Written by the implementer (C4, PO cost rule 3: no separate architect note outside crypto/keys). Scope: Drive transport, naming, upload verification, retention pruning, download for restore. Not here: schedules, Free/Gold slot choice, reminders (T-152), restore UI duties (FU-139), iCloud (T-151), account sign-in (T-147).

**1. Layers.**
- `data/drive_files.dart`: a narrow port `DriveFiles` (list one page of `appDataFolder`, create with media, get metadata, rename, download, delete) and `GoogleapisDriveFiles` over `googleapis` Drive v3. Every call is pinned to `spaces=appDataFolder` / `parents=[appDataFolder]`; errors are mapped to `DriveBackupException` codes (never the server message).
- `data/drive_auth.dart`: `DriveAuthorizer` (`accessToken(interactive)`, `clearToken`) and `GoogleSignInDriveAuthorizer` (google_sign_in 7: lightweight sign-in, else `authenticate` only when interactive; then `authorizationForScopes([drive.appdata])`, else `authorizeScopes` only when interactive). Client IDs come from `--dart-define` (`ZAGHLOL_GOOGLE_IOS_CLIENT_ID`, `ZAGHLOL_GOOGLE_SERVER_CLIENT_ID`); missing → `notConfigured` (fail closed). Only the `drive.appdata` scope is requested, so the token cannot reach any file outside the hidden app folder.
- `data/drive_store.dart`: `DriveBackupStore` owns names, listing, upload + verification, pruning, download and delete. One operation at a time per instance (`busy`).
- `application/drive_backup_service.dart`: `backupNow` (snapshot → encrypted temp file → `verifyFile` → upload → persist `seq` → prune) and `download` for `BackupSnapshotService.restore`.

**2. Names.** Final: `zaghlol-backup-<seq>-<createdAtMs>.zaghlol.enc`; in flight: the same + `.partial`. Strict ASCII regexes; anything else in `appDataFolder` is not ours and is never renamed, downloaded or deleted. `appProperties` carry `seq`, `createdAtMs`, `platform`, `schema` copied from the file's header: **labels only** (unauthenticated until chunk 0 verifies, T-148 security I-3); the restore list must present them as file metadata.

**3. Upload (AC "partial upload never replaces the previous backup").** The encrypted stream is written to `<temp>/zaghlol_backup_upload/<random>.zaghlol.enc` (ciphertext only; temp is OS-backup-excluded and cleared by the orphan wipe), `verifyFile` decrypts it once (T-148 §6), and its size and MD5 are computed. Upload is a Drive **resumable** create under the `.partial` name (Drive creates nothing until the last byte). The create response's `size` and `md5Checksum` must equal the local ones, else the just-created partial (ours, provably bad) is deleted and the upload fails `uploadUnverified`. Only then is it renamed to the final name, and the rename response is checked again (id, name, size, MD5). No existing file is ever overwritten: each backup is a new file; a Free "replace" is upload-then-prune with keep 1. The temp file is deleted in `finally`.

**4. Pruning (self-check §1).** Runs only after step 3 succeeded, with the verified file as `protect`. It re-lists all pages (≤ 20 pages × 100); any list error, a missing/renamed `protect` or a page cap hit → no deletes (`pruneSkipped`). Candidates are our **final** names only, sorted by Drive's server `createdTime` desc (tie: id). Kept: `protect`, every file created at or after `protect` (another phone's newer upload, two actors), and the newest `keep` overall. The rest are deleted one by one; a 404 counts as gone; any other error stops pruning (reported, never retried blindly). Our `.partial` files are deleted only when their server `createdTime` is ≥ 24 h before `protect`'s (no device clock; a running upload on another phone is never swept). Because every phone keeps everything at or after its own upload, two phones pruning at once with keep 1 leave at least the newest backup.

**5. seq.** `secure_state` `backup.seq.v1` (8-byte big-endian; device state, never in a snapshot). Next = max(stored, highest `seq` label among our final files) + 1, so a restored phone continues above the old phone's numbers. Stored after the rename; a failed store is reported (`seqStored = false`), never fatal (the next listing recovers it).

**6. Download.** Only an entry from our own listing with a final name. Refused above `maxBackupFileBytes` (1 GiB, also enforced on upload). The stream is capped at the listed size (more bytes → `corruptDownload`, fewer → `corruptDownload`), with a 60 s idle timeout per event. The crypto layer authenticates the content.

**7. Errors and time limits.** `DriveBackupErrorCode`: `notConfigured`, `signInRequired`, `signInCancelled`, `authorizationDenied`, `network`, `quotaExceeded`, `rateLimited`, `serverError`, `notFound`, `uploadUnverified`, `tooLarge`, `listTooLong`, `corruptDownload`, `notOurFile`, `busy`, `io`. A 401 clears the token and retries the operation once. Metadata calls time out at 30 s; uploads at 60 s + 1 s per 25 KB. No logging; exceptions carry the code only; the access token is never stringified (google_sign_in's `GoogleSignInClientAuthorization.toString()` prints it, so it is never passed to string interpolation).

**8. Residuals / PO.** (a) Retention by count can delete a backup made under an old passphrase (Free keep 1 always replaces); T-148 Q1's "delete old-passphrase backups only after the user confirms" is read as applying to a deletion *because of* a passphrase change, which only the settings UI triggers through `delete`. (b) The iOS reversed-client-ID URL scheme and the Google Cloud OAuth clients (Android SHA-1, iOS, web/server) are not configured yet (PO); without them sign-in fails with `notConfigured`/`authorizationDenied`. (c) A rename that fails after a verified upload leaves a complete `.partial`; it is swept after 24 h and the previous backup is untouched.

## Implementation notes (T-048)

**Where:** `app/lib/features/capture/domain/scan_plan.dart` (pure rules), `application/scan.dart` (`InboxScanner`), `application/inbox_scan_service.dart` (`InboxScanService`: first run, catch-up, one-institution re-scan; the production `CatchUpScheduler`), `data/scan_sources.dart` (senders, watermark). `kInboxCatchUpEnabled` is now `true`.

**Behaviour.**
- The scan pages `queryInbox` (first page 100 rows, then 500), ingests every 100 messages in one `IngestStore.ingest` transaction (same `IngestRawMessages` as the spool, origin `inboxScan`), and publishes `ScanProgress` (scanned, imported, skipped, institutions found, restarts, code). Dedupe is `body_hash`, so a re-run and a live+scan overlap store once. Guard drops and ignore rules (EC-62) count as skipped. A hard failure ends as `failed` with a code; the request stays.
- `INVALID_ARGUMENT` (allowlist changed between pages): the scan re-reads the senders and restarts from the first page, at most 3 times (FU-109). `IO_ERROR` on a page: 2 retries. Transient write failure of a batch: 3 retries.
- **Senders.** Registry exact senders (regex-only senders are not scannable, Lead decision 6) plus the user's SMS senders (always-capture rows, custom-template senders). **FU-109 M-1 (PO):** a user-added phone-number sender (`isPhoneNumberSender`: 6 to 15 digits, optional `+`, separators and Arabic digits allowed; 5 digits or fewer are service short codes) is never asked for unless the setting `capture.scan_personal_senders` is on, and then only back to `max(since, now - 3 months)`. Its messages get origin `inboxScanPersonal`: the Guard's "not financial" drop is not waived for them, and anything that would end in review (`unrecognized`, generic, direction unknown) is dropped as `personal_unparsed`, never stored, never in the review queue. A generic auto-save does not apply to them either.
- **Catch-up** (`requestIfPending`, called by T-047 after every drain while live SMS is active; returns at once, the scan runs in the background): once per app start (Q7) and whenever a request is stored. `since = min(watermark, firstMissedSmsAtMs, capture.catchup.from_ms) - 10 min` (the T-039 note), clamped to `[now - 25 months, ...]`; the watermark is `MAX(received_at)` of `raw_messages` with channel `sms`, clamped to now. A null watermark with no request never scans (FU-085). A completed scan clears the stored request only if it still equals the one served (`AlertStore.clearCatchUp`); a failed scan retries after 5 minutes.
- **First run** (`startFirstRun`, for T-056 after the permission): depth = `scan_depth_months` (default 6, max 24). **Re-scan** (`rescanInstitution(code)`, FR-CAP-07).

**Deviations.** (1) No separate Dart isolate: the scan awaits platform calls (native reader runs off the UI thread) and the Drift database already runs on its own isolate, so nothing blocks the UI isolate; the scan yields between pages. The 10k benchmark runs 11.9 s on the host. (2) Progress UI (T-056, T-173) is not part of this task; the service exposes `progress`. (3) The Guard's live-capture exemption for user senders ("not financial" is waived) is unchanged; the PO decision asks for a financial-looking filter on live capture of phone-number senders too, which is T-040/T-047 work (see the report).

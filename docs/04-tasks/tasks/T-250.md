Source: FU-295 (m-2) in `docs/implementation-status.md`; D-83.

Before batch 67, a CIB due reminder or statement could be auto-saved as an expense. Re-parse (registryVersion bump) now reads those raw messages as notices, but the old transactions stay.

## Scope (Lead assumption, PO asked to assume rather than block: nothing is deleted without the user's tap)
1. On re-parse, when a raw message that now parses as a `ParseNotice` is linked to a transaction that is machine-made and never edited by the user (no user edit, not user-verified, not split, not paired/linked to a refund or transfer, not in a closed/exported period if such a concept exists), add one review item per such transaction: "ده كان تذكير بميعاد سداد، مش مصروف — نشيله؟" / "This was a payment-due reminder, not spending — remove it?" with **Remove** and **Keep**.
2. **Remove** soft-deletes the transaction the way the normal delete does (same undo/trash path, totals and budgets recalc); **Keep** marks it user-verified so it is never offered again. The notice itself is then applied to card dues through the T-245 hook.
3. User-edited or user-verified transactions are never touched and never offered.
4. Idempotent: running re-parse twice offers once.
5. Design note first (C4); 2–3 negative proofs max: a user-edited transaction is never offered; nothing is deleted without the tap.

## Design note (builder)
Safety property: a stored transaction is only ever removed by the user's tap on **Remove**, through the normal delete path; re-parse itself only adds a question.
- **No schema change.** The offer is an existing `low_confidence` review item with `txn_id` + `raw_message_id` and payload `{"reason": "oldDueNotice"}` (`ReviewReason.oldDueNotice`). The `review_items.kind` CHECK stays as is.
- **Where.** `IngestRawMessages._reparseOne`: a `parsed` raw row that now reads as a `ParseNotice` is stamped (conditional `promoteRaw`, parsed→parsed, notice template id), handed to the T-245 `CardNoticeHook` (newer-wins merge, so an old notice never replaces a newer due), and then asked for offerable transactions. New outcome `ReparseOutcome.offered` / `ReparseSummary.offered`.
- **Who is offered** (`IngestStorePort.oldDueOfferTxns`, one SQL read): transactions with `raw_message_id` = the row that are live (`deleted_at IS NULL`), machine-made (`source` in sms/notification/shortcut/apple_pay), `expense`/`fee`, `is_user_verified = 0` (every user edit, bulk category, review accept sets it), `category_source <> 'user'`, no note, no transfer pair, not internal, no split participants, no offset link on either side, and no review item of reason `oldDueNotice` for that transaction in any state (open or resolved). The last clause makes re-parse idempotent; resolved review items are never purged (`purgeResolvedBefore` has no caller). There is no closed/exported-period concept in the app.
- **Registry bump** (`cib.cc_due.ar` / `cib.cc_statement.ar` and `registryVersion` 9→10, guard bases too): phones that already ran a batch 67–69 build have these rows stamped v9, so without a bump they would never be looked at again.
- **Remove** (`OldDueActions.remove`): re-checks that the item is open, of this reason, and its transaction is still live and unverified; then the shared `TxnBulkActions.delete` (same undo image, `TransactionsChanged` for totals/budgets, pair/offset clean-up as the detail screen's delete), then resolves the item `removed`. Undo = `TxnBulkActions.undo(batchId)`; the item stays resolved, so it is not offered again.
- **Keep** resolves the item `kept` and marks the transaction user-verified (one transaction, conditional resolve).
- **Screen**: new `OldDueCardModel` / card with the question, the amount line and the date, **Remove** and **Keep**. Swipe-to-dismiss only resolves the item (transaction untouched). Card hidden when the transaction is gone or already verified.
- **Negative proofs (3):** (1) a user-verified (edited) transaction gets no item; (2) after re-parse with no tap the transaction is still live and in totals; (3) re-parse twice (row re-stamped old) gives one item.

## Acceptance criteria
App tests: old auto-saved CIB due (fixture case 7) → after re-parse one review item, transaction still present; Remove → gone from totals, undo works; Keep → stays, never offered again; edited transaction → no item. Strings ar (Egyptian colloquial) + en.

Source: FU-295 (m-2) in `docs/implementation-status.md`; D-83.

Before batch 67, a CIB due reminder or statement could be auto-saved as an expense. Re-parse (registryVersion bump) now reads those raw messages as notices, but the old transactions stay.

## Scope (Lead assumption, PO asked to assume rather than block: nothing is deleted without the user's tap)
1. On re-parse, when a raw message that now parses as a `ParseNotice` is linked to a transaction that is machine-made and never edited by the user (no user edit, not user-verified, not split, not paired/linked to a refund or transfer, not in a closed/exported period if such a concept exists), add one review item per such transaction: "ده كان تذكير بميعاد سداد، مش مصروف — نشيله؟" / "This was a payment-due reminder, not spending — remove it?" with **Remove** and **Keep**.
2. **Remove** soft-deletes the transaction the way the normal delete does (same undo/trash path, totals and budgets recalc); **Keep** marks it user-verified so it is never offered again. The notice itself is then applied to card dues through the T-245 hook.
3. User-edited or user-verified transactions are never touched and never offered.
4. Idempotent: running re-parse twice offers once.
5. Design note first (C4); 2–3 negative proofs max: a user-edited transaction is never offered; nothing is deleted without the tap.

## Acceptance criteria
App tests: old auto-saved CIB due (fixture case 7) → after re-parse one review item, transaction still present; Remove → gone from totals, undo works; Keep → stays, never offered again; edited transaction → no item. Strings ar (Egyptian colloquial) + en.

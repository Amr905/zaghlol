## Description
New tier after keyword: `aiSuggestionFor(merchantNorm)` (state `unconfirmed` only; confirmed/corrected are user rules already). When a suggestion arrives, the recategorizer sets `category_id` + `CategorySource.ai` on that merchant's `needs classification` rows only, and future rows get it through the tier. A later catalog hit replaces an unconfirmed suggestion. Nothing with a user-set, rule, catalog or keyword category is touched.

## Design note (builder)

**"Needs classification"** = a live, non-internal, not user-verified row with `category_source = 'none' AND category_id IS NULL`. That is the only state the AI ever writes into.

1. **Parsing package (pure):** `CategorySource.ai('ai')`, `CategorizeTier.ai`, port `AiSuggestionPort.aiSuggestionFor(merchantNorm) → categoryId?` (unconfirmed suggestions only), optional `CategorizerPorts.ai`. The tier runs last, after keywords, on a valid merchant key only, and needs a live category; rules, own-account, event (cash/InstaPay), p2p stop, catalog and keywords all decide first, so an `ai` decision is only ever produced where the chain would otherwise say "needs classification". `confirmed`/`corrected`/`no_answer` rows return null (confirmed/corrected are user rules already).
2. **Precedence (`Recategorizer.replaceable`):** user rule / catalog / heuristic may replace `none`, `catalog`/`heuristic` as before **and `ai`** (FU-408: a rule, a confirm/correct rule, a later catalog hit, a keyword or event category all rank above the AI tier); `ai` may replace only `none`, and `apply` also refuses an `ai` decision when the row's old category is not null. Every guard stays in the one conditional UPDATE. `user`, `user_rule` rows are never in any list. CAT-cash / CAT-INSTAPAY guard unchanged. `run()` also scans `ai` rows, so a catalog update replaces them; when a catalog decision replaces an `ai` row, the merchant's `unconfirmed` suggestion is dropped (`deleteUnconfirmed`) in the same DB transaction. Rule apply-to-past (`MerchantRulesDao._eligible`) and the event backfill include `ai` (FU-408).
3. **Applying a suggestion** (`Recategorizer.applySuggestion(merchantNorm, categorizer)`): reads only that merchant's needs-classification rows, runs the full categorizer on each (so a p2p/own-account/event row of the same key stays as it is) and writes through `apply`. `AiSuggestionApplier.accept(...)` (for T-358) = `putAnswer` (never replaces confirmed/corrected) + queue removal + `applySuggestion`, one DB transaction; `noAnswer(...)` = `putNoAnswer` + queue removal. Idempotent: a second call changes nothing. Money columns are never in any statement.
4. **Queue fill** (`LlmCatQueueFiller`, `application/llm_cat_queue.dart`; no network, T-358 sends): gate first — flag `llm_categorise` on (fresh snapshot only, `FlagsService.isOn`), active terms known and `cat.llm_consent` covering them; else nothing is written. Then a full, idempotent recompute: needs-classification rows grouped by `merchant_norm`; a merchant is queued only when (a) the key fits the table CHECK, (b) **every** one of its needs-classification rows derives `LlmPaymentKind.businessPayment` (pure `llmPaymentKindOf`: direction expense/refund, automated source sms/notification/shortcut/apple_pay/share/ocr/pdf, counterparty null or `merchant`, no transfer pair, not internal; anything else, incl. manual/voice/csv entries and unknown codes → `unknown` → refused), (c) `LlmEligibility.check` passes on the key **and** the cleaned raw text has no identifier/person-like refusal, with `triedBefore` = any suggestion row exists, (d) no `merchant_norm` user rule exists. Queued rows get `txn_count` = current count (set, not incremented, so re-runs don't inflate), `first_queued_at` kept; queued merchants that no longer qualify are removed; then cap 100 / 60 days (`trim`). One DB transaction.
5. **Pick for sending** (`LlmCatQueueFiller.pickForSend`): returns at most `min(batchMax, remaining)` due merchant keys, re-checked against eligibility; empty when the flag is off, paused, no consent, or the snapshot says 0 remaining before `resetsAt`. It reads the quota, never writes it: the only counter is the backend's, so nothing is counted twice; a re-run of fill/apply never touches the quota.
6. **Lexicon:** `nameLexiconProvider` loads the three `assets/data/*.txt` files via `rootBundle` into `NameLexicon.fromLines`; a missing list makes eligibility fail closed (`lexiconMissing`).
7. **Privacy:** no logging anywhere; exceptions are the DAO's code-only ones; merchant keys never appear in `toString`.

Deviation: the spec flow queues "after the transaction is saved"; here the queue is a recompute the sender (T-358) calls at app open / before a send, not an ingest hook — same result, no change to ingestion, and it is idempotent and resumable by construction.

## Acceptance criteria
1. Suggestion for Zawya → its 3 uncategorised rows become Dining/`ai`; a 4th Zawya row set by the user stays.
2. A new transaction of the merchant gets the AI category via the tier; a catalog update covering the merchant replaces `ai` with the catalog category.
3. **Negative proof 1:** fixture with rows of every source (user, rule, catalog, keyword, InstaPay seed, cash seed, needs classification): after applying suggestions for all merchants, only `needs classification` rows changed (byte comparison of the rest).
4. **Negative proof 2:** suggestion states `confirmed`, `corrected`, `no_answer` never change a row through this tier.
5. Budgets and charts count unconfirmed AI categories (existing aggregation tests extended with one `ai` row).

## Integration fix (batch 95): FU-428 as far as queueing goes

`LlmCatQueueFiller` takes `templateEvents` (template id -> registry `TemplateEvent`, built from the bundled registry in `llm_cat_providers.dart`; default empty = fail closed). A row's counterparty kind is derived as `merchant` only from typed evidence: `cardPurchase` / `cardPurchaseFx` on an `expense` row, or `refund` on a `refund` row. Rows whose template event is anything else (transfer, InstaPay, ATM, salary, fee, wallet top-up, cc payment, ...) get payment kind `unknown`. No template or unknown template: kind stays null (the eligibility rule then refuses unless a business word is present). The rule itself is untouched. T-358 only sends what the queue holds.

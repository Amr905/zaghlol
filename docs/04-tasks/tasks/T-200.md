## Description
The PO can't use a cloud provider. Today `Kms:Provider = Local` (key files) is refused outside Development/Testing and no other adapter exists, so the backend can't start in Staging or Production. Decision D-76: ship a **hardened file provider** now (option B) and move to self-hosted **OpenBao Transit** (T-201) before real users pay for Gold.

## Technical details
- New provider name (e.g. `Kms:Provider = File`), separate from the dev `Local` provider; `Local` stays Development/Testing only.
- Keys are read from a secrets mount outside the app (e.g. `/run/zaghlol-kms`, `Kms:File:KeyDirectory`), same formats as today (P-256 PEM for signing, 32 random bytes for HMAC/envelope), produced by a production key tool (not `dev-keys.sh`) that also prints each signing key's public JWK and the `SeatCheck` value.
- **Refuse to start** (fail closed, like every other guard) when: the directory or any key file is group/world readable or writable, or not owned by the process user / root (POSIX); a key matches a committed dev key or a known test vector; a staging key is reused as a production key (fingerprints differ per environment, recorded in config); any configured key ref is missing.
- Keys are loaded once at start into memory with zeroing on dispose where .NET allows, or per call as `LocalKms` does — the design note picks and justifies.
- The `KmsStartupCheck` (JWK equals key, sign-then-verify, HMAC answers, envelope round-trip) runs unchanged.
- Docs: deployment steps for a single self-hosted server (Docker secrets or a root-owned 0400 mount), backup of the key files offline, rotation procedure (new kid as `Next`, app release pinning both, then `Active`), and the known weakness (a code-execution bug can copy the keys) with the T-201 migration plan. ADR records D-76.

## Acceptance criteria
1. Design note written (Opus) before code, covering the guard list, key loading and the threat model vs T-201.
2. The API and worker start in Staging and Production with `Kms:Provider = File` and correct keys; `Local` is still refused there (tests).
3. Each refusal case above has a test that fails the host start with a clear message and no key material in the log.
4. Production key tool tested; it never writes keys into the repo tree and refuses to run inside it.
5. Code + security reviews APPROVED.

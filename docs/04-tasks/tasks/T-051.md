## Description
Correct cycle totals per currency for Home and budgets.

## Technical details
cycleFor(payday 1–28, A-43 default day 1), mid-cycle payday change (EC-21), spend/income per currency excluding internal/declined, offsets by expense cycle (BR-XFR-07), safeToSpend/idealBurn, cycle_summaries cache invalidated by events.

## Design note
Status: written by solution-architect (Opus), 2026-11-11. Inputs: domain-algorithms §1, §2, §4, §5; BR-BUD-01/03/04, BR-TXN-01/02/03, BR-XFR-03/05/06/07, BR-FX-03, EC-20/21/24, A-16/42/43, D-28/29/68; CLAUDE.md §2.4; T-020 (`payday_day`, `income_target`, `primary_currency`), T-045, T-050, T-019/T-018 tables, T-046 (`TransactionsChanged`, `LocalZone`), `Money.mulDiv(…, floor)` (T-012). Items marked **[doc change]** were applied in the same commit to domain-algorithms §2, database-schema (§2.5 `cycle_summaries`, §2.8 settings) and parsing-engine §6.

**1. Shape.** Pure part in `packages/zaghlol_domain/lib/budget/` (no Flutter, no drift): `CivilDate` (y/m/d over an epoch-day integer; `fromLocalMs(utcMs, offsetMin)` uses floor division; `plusDays`, `difference`, ISO parse and format, own days-from-civil, no `DateTime`), `PaydayEra{CivilDate? from, int day}`, `PaydaySchedule(List<PaydayEra>)` (`cycleOn(CivilDate) → Cycle{start, end, key, length, dayNumber(d), daysRemaining(d)}`), `aggregateCycle(cycle, Iterable<CycleTxn>, Iterable<CycleOffset>) → Map<Currency, CycleTotals>`, `safeToSpend`, `idealBurn`, `burnLine`. `CycleTxn`/`CycleOffset` are plain records (id, direction, status, isInternal, amount `Money`, categoryId, local date; offset: expenseId, sourceId, amount, sourceValid). `CycleTotals{currency, income, spend, pendingSpend, byCategoryMinor}`, all `Money` or `int` minor, never `double`. App side `features/budget/{data,application}`: `CycleRepository` (SQL range read, offsets by join, `cycle_summaries` read/write through the existing DAO), `PaydayScheduleStore` (settings), `CycleOverview` providers. Ports: the existing `Clock` and `LocalZone`.

**2. Cycle boundaries.** Payday is 1-28 (BR-BUD-01, D-68; the settings layer already refuses 29-31), so month-length clamping and the 29-31 case never reach the engine; `PaydayEra` throws on other values. Weekends and holidays never shift a cycle (A-42, EC-20): there is no holiday table. February needs no special case because starts are real dates (payday 1 gives 28/29-day cycles; payday 28 gives 28-31). Schedule rule as in domain-algorithms §2: cycle starts are the union of each era's payday dates in `[from_k, from_(k+1))`. Worked EC-21 cases (payday 25, today 10 Nov): change to 1 gives cycle 25 Oct-30 Nov, next cycle starts 1 Dec; change to 20 gives 25 Oct-19 Nov, then 20 Nov; change on the new day itself (today 10 Nov, new day 10) closes the old cycle on 9 Nov and starts a new one today. Two changes inside one cycle chain correctly (the last era wins). A change on the day an era was created replaces it. **First cycle / first explicit payday:** era `from = null` rewrites all history, so an imported 6-month scan is bucketed with the user's real payday (PO Q1). `PaydayScheduleStore.load()` reads `payday_eras`; if it is empty it returns `[(null, payday_day)]`; if its last era's day differs from `payday_day` (restore, another writer) it appends `(today, payday_day)` and persists once, so the result never depends on when it is read. `setPayday(day)` writes `payday_eras` first, then `payday_day` **[doc change: database-schema §2.8, new typed key `Settings.paydayEras`, additive to T-020]**. Cycle key = start date ISO (`2026-10-25`); the `YYYY-MM` key built by T-046's `cycleKeyFor` can collide after an EC-21 change, so the T-051 implementer replaces it (the T-046 default `CycleKeyOf` calls `PaydaySchedule`) and fixes the `domain_event.dart` comment **[doc change: parsing-engine §6]**.

**3. What counts** (per cycle and per billed currency; `original_*` is never used, BR-FX-03). A row is considered when it is live, not `is_internal` and `posted` or `pending`; `declined` and `reversed` are out (BR-TXN-03). **Spend** = `expense` + `fee` + un-paired `transfer_out` (a transfer to a person is real spend; an own-account transfer is only excluded once pairing sets `is_internal`, which fires `TransactionsChanged` and restates the cycle; PO Q2) minus valid offset links whose **expense** is in the cycle, so a late refund or reimbursement restates the original cycle only (BR-XFR-07). **Income** = `income` + `transfer_in` + `refund` rows, each reduced by the links it funds, counted in its own cycle (BR-TXN-02, BR-XFR-06): a refund fully matched to an expense contributes 0 income and reduces that expense's cycle; an unmatched refund is income-type (BR-XFR-03; PO Q2). A link is valid only if its source is live and `posted`/`pending` (a soft-deleted refund must stop reducing spend until restored). `pending` rows count in spend (the money is held) and are also in `pendingSpend`. `byCategoryMinor` = net spend per `category_id` (offsets reduce the expense's own category, BR-XFR-05), `'_none'` for uncategorized, and always sums to `spend`. Cycle date of a row = its own `occurred_at` + `occurred_tz_offset_min`, never the device zone today (a transaction captured while travelling keeps its wall date).

**4. Formulas, integers only.** `daysRemaining = end − today + 1 ≥ 1`. `safeToSpend = remaining.mulDiv(1, daysRemaining, floor)` with `remaining = max(0, budget − spend)`: minor units, always rounded **down** so the user is never told to spend more than is left; 2,200 EGP left and 7 days = 220 000 / 7 = 31 428 minor (314.28; Home shows whole major units, floored, which gives the spec's 314; PO Q3). It is `null` when the basis budget is 0 or absent (EC-24) and `0` (not null) when overspent. Basis budget in currency *c*: overall cycle budget (`category_id IS NULL`, period `cycle`) else the sum of category cycle budgets in *c* (A-16); annual budgets and rollover (FR-BUD-05/06) are not part of this task. `income_target` is not a safe-to-spend input (PO Q4); the engine only passes it through as `Money?` for progress UI. **Burn line:** `idealBurn(d) = budget.mulDiv(d, cycleLength, floor)` for `d` in 0..length (day 1 = payday; 0 is the chart origin; `ideal(length) = budget`); `burnLine` returns `[(d, idealMinor, actualCumulativeMinor?)]`, the actual series is cumulative net spend by local day (offsets restated on the expense's day) and `null` after today. "Under the ideal line" (BR-MAS-02) = `spend ≤ idealBurn(dayNumber(today))`. A truncated or extended cycle (EC-21) uses its real length; the budget amount is not prorated (PO Q5). `mulDiv` is BigInt-exact, so no intermediate overflow.

**5. Per currency.** Every result is `Map<Currency, CycleTotals>`; the engine groups by the row's `currency` and has no API that adds two currencies (no `MultiCurrencyTotal.sum` over mixed keys). A GBP row must not change any EGP number. Home ordering (primary first) and the ≈ view (§1 `approx`, display only, never cached) belong to T-052/T-023. `cycle_summaries` rows exist only for currencies that had activity in the cycle; a currency with a budget and no activity yields zero totals on read, not a missing key.

**6. Triggers and cache.** Read path: current cycle always computed live (one indexed range read on `ix_txn_currency_time`/`ix_txn_account_time`, widened by 18 h each side for stored offsets and then filtered by local date; offsets by join, no id lists) and written through; closed cycles come from the cache. Cold start shows the cached current row first, then the live one. Invalidate (delete rows, recompute lazily) on: `TransactionsChanged` (its `cycleKeys`, **which emitters must extend with the cycle of every expense whose offset links changed**: T-077, T-089, T-049 **[doc change: domain-algorithms §2]**), a change of `payday_eras`/`payday_day`/primary currency (all rows), restore and migration (all rows), and on app resume every cycle holding a row with `updated_at` or link `created_at` later than the last foreground time (the headless engine's writes and inbox re-scans reach old cycles without an event in the UI isolate; a full scan of 50k rows is acceptable, no new index). `account_filter` is `'*'` or one account id; multi-card filters are computed live, uncached. Budget changes do not touch the cache (it holds no budget values). A midnight timer (re-armed after firing, because Cairo DST moves the local midnight by an hour and a fired timer can still be on the same civil date) and resume re-evaluate "today" and rebuild the providers.

**7. Determinism.** No `DateTime.now()` in `lib/budget` or `features/budget` (grep test): `Clock.nowUtcMs` and `LocalZone.offsetAtInstant` are injected; `computed_at` comes from the clock. Same inputs give the same result in any zone of the test host (tests run under `TZ=Asia/Tokyo` and `America/Los_Angeles` too). Cairo DST (reinstated 2023; transitions at midnight, so one local day has 23 or 25 hours): rules are never hard-coded, the stored offset (+120 or +180) is the only input; civil-date arithmetic is on epoch days, so a 23/25-hour day cannot shift `daysRemaining`. A transaction at 01:00 local on the spring-forward day (`22:00Z` the evening before) belongs to that local day, which UTC bucketing gets wrong.

**8. Edge cases.** Empty cycle: zero totals; no budget: `safeToSpend` null; `today` on the last day: 1 day remaining; on payday: full length; transaction after today (future-dated manual): counted in its cycle, burn actual is cut at today; expense edited or deleted so links shrink (EC-40): recomputed via event; `amount 0` rows count 0; overflow: sums use `Money +` and propagate `MoneyOverflow` (not caught); year 2100 and leap day work; a cycle in the cache from before a schedule change is deleted by the all-rows invalidation.

**9. Tests.** Unit (spec examples as fixed cases): 2,200 / 7 = 31 428 minor and "314" on Home; payday 25 gives 25 Oct-24 Nov; A-43 default; EC-21 worked cases of §2 (shorter, longer, same-day, double change, null first era); EC-24 null; overspent 0; per row of §3 (declined, reversed, internal, soft-deleted, pending, fee, unpaired transfer_out, partial refund, reimbursement in a later cycle restating the old cycle only, soft-deleted source, income net of reimbursement, KWD 3 and JPY 0 exponents, GBP isolation). DST fixtures with pinned zones (`+120`, `+180`, spring-forward and fall-back days of 2025). **Property tests** (fixed-seed generators as T-046, 200 seeds, or glados if already a dev dependency): (a) every payday 1-28 × every month of 2020-2030 plus 1900/2100 leap years: cycles are contiguous, non-overlapping, length 28-31, start day = payday; (b) random era lists: every date in exactly one cycle and `cycleOn(d).start ≤ d ≤ end`; (c) conservation: Σ over all cycles of spend (income) equals the global net figure; Σ `byCategory` = spend; (d) `safe × daysRemaining ≤ remaining < (safe + 1) × daysRemaining`; (e) `idealBurn` monotone, 0 at 0, budget at length, equal to a BigInt oracle on 2^53 budgets; (f) adding rows of another currency leaves the first currency's totals identical. DB tests (encrypted DB as T-045/T-050): cache hit equals live result; each invalidation trigger in §6; resume sweep; a payday change keeps closed cycles' keys. **Negative proofs** (patch, see red, revert): UTC date bucketing; day count by `Duration.inDays`/ms; `ceil` or half-up instead of floor; days remaining exclusive of today; counting declined/internal/deleted; soft-deleted source still offsetting; reimbursement attributed to the link's cycle; mixed-currency sum; current payday applied to history (EC-21 test); invalidation skipped for `cycleKeys` (cache test); `DateTime.now` in the engine (grep).

**Rejected.** Recomputing every past cycle with the current payday (rewrites history and the `fired_alerts` period keys). A `payday_history` table (a v5 migration for a handful of rows). Shifting paydays 29-31 to month end (not allowed by BR-BUD-01). Stamp-based cache validation (offset-link edits are invisible to `updated_at`). Per-day cache rows (burn actuals are a bounded chart query, T-105). Device-zone or UTC bucketing. `double` or rational safe-to-spend.

**Questions for the PO** (provisional defaults are used in code and tests until answered):
- **Q1** The first time a user sets a payday (after using the default day 1), should all past data be re-bucketed with it (*provisional*), or should the change be treated like a mid-cycle change (EC-21), leaving past cycles on day 1?
- **Q2** Un-paired `transfer_out` (for example InstaPay to a person) counts as spend and un-paired `transfer_in` as income; `fee` is spend; an unmatched refund counts as income. Right? (*Provisional: yes.* Otherwise most InstaPay spending would vanish from Home.)
- **Q3** Safe-to-spend: show whole pounds rounded down (314, *provisional*) or with piastres (314.28)?
- **Q4** With no budget set, should "safe to spend" fall back to the income target or the cycle's income so far? (*Provisional: no, hidden as in EC-24.*)
- **Q5** After a mid-cycle payday change the cycle may be 10 or 40 days. Keep the full budget for it (*provisional*) or prorate by length?

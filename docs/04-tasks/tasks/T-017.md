## Design note
Status: written by the implementer (Opus, flutter-core-engineer) at the Lead's request, 2026-11-11, before implementation. Inputs: this file (incl. "Input from T-016"); database-schema §0, §2.1–2.3, §3, §4; T-012 note (money CHECKs); FU-071 m-3; the T-016 code in `app/lib/core/db/`.

**1. Version.** A real `schemaVersion = 2` with a `stepByStep` `from1To2` step (not a regenerated v1): it exercises the T-016 safety net (pre-migration copy, FK check, restore) on a real step, and keeps the rule "every schema change bumps the version". v1 dump stays as committed; v2 dump and the generated `stepByStep` helper are added by `app/tool/generate_drift.sh`. The step creates the new entities explicitly in dependency order: tables → FTS tables → view → indexes → triggers.

**2. Where the DDL lives.** The new entities are written in SQL in `app/lib/core/db/schema/financial.drift`, included by `AppSchema` (`@DriftDatabase(include: …)`): partial indexes, FTS5 tables, triggers and CHECKs are plain SQL there. The codegen script copies `*.drift` as well as `*.dart`; `build.yaml` enables the `fts5` module. Row classes are named `…Row` (`AS TransactionRow`, etc.) like `DbMetaRow`.

**3. Tables.** As §2.1–2.3, with these tightenings (all CHECKs, no behaviour the spec forbids):
- every `id TEXT PRIMARY KEY` is `NOT NULL` (SQLite otherwise accepts NULL in a non-integer PK);
- 0/1 flags have `CHECK (x IN (0,1))`; `accounts.label` 1–30 chars; `last4` 2–4 ASCII digits; `merged_into_id <> id`; `is_default_cash = 1` only for `kind = 'cash'`, plus the partial unique index `ux_accounts_default_cash` that §3 already names ("one default cash");
- `occurred_tz_offset_min` within ±18 h; `parse_confidence` NULL or 0..1 (REAL is not money); `body_hash` 64 lowercase hex chars;
- `transfer_pairs.in_txn_id <> out_txn_id`; `offset_links.expense_txn_id <> source_txn_id`.
- **`categories` is created here** (exactly the §2.4 DDL plus `NOT NULL` id and 0/1 CHECKs), because `transactions.category_id REFERENCES categories(id)` needs its parent, and adding an FK later means rebuilding `transactions` with its FTS triggers. T-018 owns its DAO, seeds and every other §2.4 table; noted in T-018.

**4. Money CHECKs (T-012 request, CLAUDE.md §2.4).** Let `M = 9007199254740991` (2^53−1). Every amount column has `typeof(x) = 'integer' AND x BETWEEN -M AND M` (or `x IS NULL OR (…)` when nullable), so a REAL or text amount is rejected (`BETWEEN` instead of `abs()`: `abs(-2^63)` raises instead of failing the CHECK). Sign rules: `transactions.amount_minor`, `original_amount_minor`, `accounts.credit_limit_minor`, `split_participants.share_minor` ≥ 0; `offset_links.amount_minor` > 0; balances and `balance_after_minor` signed. Every currency column has `GLOB '[A-Z][A-Z][A-Z]'`. The one nullable pair, `original_amount_minor`/`original_currency`, has `(a IS NULL) = (b IS NULL)`. Columns without their own currency use the row's currency (`balance_after_minor`, account balances) or the expense's (`offset_links`, `split_participants`), as §2.3 says. Mapping rows ↔ `Money` is in `app/lib/core/db/money_columns.dart` (`Money.fromStorage`; a half-NULL pair or an unknown code is `CorruptMoney`); the schema folder never imports the domain.

**5. Search (FR-TXN-01, T-016 §8(b)).** `transactions_fts_src` is a real table `(id INTEGER PRIMARY KEY, txn_id TEXT NOT NULL UNIQUE, merchant, counterparty, note, amount_text)`: an `INTEGER PRIMARY KEY` keeps the FTS rowids stable across `VACUUM` (the implicit rowid of `transactions`, a TEXT-PK table, is not). Both FTS5 tables are external-content over it (`content_rowid='id'`): `transactions_fts(merchant, counterparty, note, amount_text)` with `trigram remove_diacritics 1`, and `transactions_fts_short(merchant, counterparty)` with `unicode61 remove_diacritics 2, prefix='1 2'` (T-016 proposal, 20.7 ms p95 vs 497 ms LIKE). Triggers on `transactions` (after insert; after update of `id`, merchant, counterparty, note, amount or currency; after delete) maintain the src row from the view `transactions_fts_row`; triggers on the src table maintain both FTS tables with the external-content `'delete'` command. `merchant` = `merchant_raw` and `merchant_norm` (when different), `counterparty` = `counterparty_value`. `amount_text` = the amount formatted with the currency's exponent, in Latin and Arabic-Indic digits (`1250.50 ١٢٥٠٫٥٠`, no grouping; the search layer strips grouping from queries). The exponent comes from a `CASE` on the ISO table's non-2 exponent codes (0: 17 codes, 3: 7, 4: 2); a test checks the SQL against `Currency.all` for every currency, so a table refresh that changes an exponent fails CI until a migration updates the view. Soft-deleted rows stay indexed (Undo); queries filter `deleted_at IS NULL`. `TransactionsDao.search` sends 1–2 character queries to the short table as a quoted word prefix and longer ones to the trigram table as a quoted phrase; the query is bound, never interpolated, length-capped and its `"` doubled.

**6. Offset invariants (BR-XFR-06, FR-XFR-07).** `BEFORE INSERT` and `BEFORE UPDATE` triggers on `offset_links` `RAISE(ABORT, '<code>')` with fixed codes: `OFFSET_EXCEEDS_EXPENSE` (Σ per expense > expense amount), `OFFSET_EXCEEDS_SOURCE` (Σ per source > source amount), `OFFSET_CURRENCY_MISMATCH` (source currency ≠ expense currency), `OFFSET_PARTICIPANT_MISMATCH` (participant of another expense). A `BEFORE UPDATE OF amount_minor, currency ON transactions` trigger aborts with the same codes when an edit would break an existing link. The update triggers exclude the row being updated from the sums. `OffsetLinksDao` maps these to a typed `DbConstraintException(code)`; messages carry the code only.

**7. DAOs (`app/lib/core/db/daos/`).** Thin, plain classes over `AppDatabase` (no `@DriftAccessor`, so no codegen outside `schema/`): `AccountsDao` (insert, by id, upsert per-currency balance), `RawMessagesDao` (insert-or-ignore on `body_hash`, reporting duplicates; by id), `TransactionsDao` (insert, by id, search), `OffsetLinksDao` (insert/update in a transaction, typed errors). Repositories (T-045, T-050) build on them. Nothing in them logs.

**8. Schema shape and CHECKs (FU-071 m-3).** `schemaShapeOf` gains one line per CHECK clause per table, extracted from `sqlite_schema.sql` with a small scanner that respects quoted strings and balanced parentheses, whitespace-normalised and with identifier quotes dropped; so a migrated table whose CHECK differs from a fresh one is a mismatch. Tests: a negative proof that a changed CHECK changes the shape; the existing dump comparison now covers CHECKs.

**9. Migration tests.** (a) v1 file (built from the committed v1 dump's `fixed_sql`, populated `db_meta`) → v2 through `openAppDatabase` on a real encrypted file: copy made and deleted, `db_meta` rows kept, live shape = fresh v2 shape = v2 dump, `foreign_key_check` empty, new tables usable (FTS + offset trigger); (b) a v1 file whose step fails (a stray `accounts` table) → `DB_MIGRATION_FAILED(restored)`, files byte-identical; (c) the T-016 harness fake becomes `FakeNextDatabase` (current version + 1) so its safety-net tests keep running against the real latest schema (host and the device suite).

**10. Test plan → AC.** AC1 CHECK/unique: `financial_schema_constraints_test.dart` (one case per CHECK, each with a passing control row; partial unique indexes incl. their WHERE). AC2 over-allocation: `offset_triggers_test.dart` (insert, update, transaction-amount edit, per expense, per source, currency, participant; DAO maps codes; sums exactly equal pass). AC3 FTS: `transactions_dao_test.dart` (partial Arabic and English, 1–2 char prefix, amounts in both digit systems, update/delete keep FTS in sync, `"`/`*`/`NEAR` in queries are literal, soft-deleted hidden). DAO tests run on an encrypted database file (sqlite3mc, synthetic key); an in-memory database is not encrypted by sqlite3mc, so "encrypted in-memory" is met by a temp encrypted file. No raw message bodies in test output; fixtures synthetic.

**As built (implementer, 2026-11-11): differences from the note above.**
- §1: the step runs the v2 dump's statements in the dump's order (tables and their indexes interleaved; the view before the triggers), frozen in `app/lib/core/db/migrations/v2_financial_a.dart` without `IF NOT EXISTS` (a stray object fails the step and is rolled back). drift_dev's generated `Schema2` omits `transactions_fts_src`, `transactions_fts_short` and the view, so it is used for dispatch only.
- §2: `.drift` quirks: `"replace"(…)` (a drift keyword) and `format` instead of `printf`. The codegen script now fails on any drift_dev analysis warning (a warning silently dropped the view in a first run). The FTS tables' generated row classes keep drift's default names.
- §7: DAO errors go through `guardWrite` (`daos/write_errors.dart`), which maps every `SqliteException` to `DbWriteException` (also `DB_CONSTRAINT_*` and `DB_WRITE_FAILED`), because the raw exception carries the bound values (a test shows the raw drift error contains a body sentinel).
- §8: the normalised CHECK text also drops whitespace before `(`.

## Input from T-016 (2026-11-10)
- **Short-query FTS (T-016 design note §8(b)).** Measured on the host (debug, encrypted, 50k rows, median of 3 passes after a warm-up): `like_short_ms` p95 **497 ms** (the LIKE fallback misses FR-TXN-01) vs `short_prefix_ms` p95 **20.7 ms** with a second FTS5 table (build 141 ms). Emulator figures: db-platform run on `ci/T-016` (`ZAGHLOL_DB_BENCH` line, `short_prefix_ms`). Proposed DDL for §2.2, kept in sync by the same triggers as `transactions_fts`: `CREATE VIRTUAL TABLE transactions_fts_short USING fts5(merchant, counterparty, tokenize='unicode61 remove_diacritics 2', prefix='1 2');` queried with a quoted word prefix (`"ab"*`) for 1–2 character searches. Digit-only short queries (e.g. `١٢`) find nothing there (no amounts in the table); Search should send them to `transactions_fts`/amount filters.
- **Schema versioning.** T-016 shipped `schemaVersion = 1` with `db_meta` only, dumped in `app/drift_schemas/app_database/drift_schema_v1.json`. Adding tables means either `schemaVersion = 2` with a `stepByStep` migration (exercises the T-016 safety net), or, since no build has shipped, regenerating v1; the architect's design note should pick one. Code generation runs through `app/tool/generate_drift.sh` (drift_dev can't resolve in the workspace; see `tools/drift_codegen/pubspec.yaml`). Put every drift-annotated file in `app/lib/core/db/schema/` and import only `package:drift` and siblings there (the generator copies that folder).
- **Migration tests.** drift_dev's `SchemaVerifier` / `validateDatabaseSchema()` are unavailable at runtime for the same reason; use `schemaShapeOf` (`lib/core/db/schema_shape.dart`) and the dump's `fixed_sql`, as in `test/core/db/app_database_test.dart`, and the safety-net patterns in `test/core/db/migration_harness_test.dart`.

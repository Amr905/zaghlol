## Description
Change many transactions at once with one Undo (D-36).

## Technical details
Single DB transaction; before-image to undo_batches; category/account/delete; optional 'always use for these merchants' rules; undo restores and removes created rules; 24 h expiry.

## Design note
Written by the implementer before coding (C3; no separate architect note was supplied).

- **Shape.** `BulkEditUseCase` (`features/transactions/application/bulk_edit.dart`) with `apply(ids, SetCategory | SetAccount | DeleteTransactions)` and `undo(batchId)`. It takes the `AppDatabase` and uses the existing DAOs; no schema change (`undo_batches` exists, T-019). No provider yet: T-079 wires the UI and can add one (kept out of shared provider files).
- **All or none.** One DB transaction per call. Any id that is not a live row fails the whole call (`BULK_NOT_FOUND`); duplicate ids count once; 1..1000 ids. Category must exist and be unarchived; the account must exist. Amounts and currencies are never written.
- **Before-image** (`before_json`, v1): per row only the fields the change touches (category: `category_id`, `category_source`, `is_user_verified`; account: `account_id`; delete: nothing but the stamp) plus the row's old `updated_at`; the batch's `at` stamp and target; ids of rules created; `{id, from}` of existing rules re-pointed. Written in the same transaction as the change.
- **Category change** sets `category_source='user'`, `is_user_verified=1` (domain §14 step 3). Rules (option): one per distinct merchant, catalog merchant id when present, else a canonical `merchant_norm`; rows with neither get none. An existing rule for the same key is re-pointed (old category kept in the image), not duplicated.
- **Undo restores exactly, never over a later edit.** Each row is restored by a conditional UPDATE that requires the batch's `updated_at` stamp and the field the batch set; the row gets its old values and old `updated_at` back. A row edited, re-batched or purged since is skipped and counted (`UndoResult.skipped`), not overwritten. Created rules are deleted only while still pointing at the batch's category; re-pointed rules are restored only while still at the batch's category.
- **One winner.** `undo` consumes the batch row inside its transaction (`deleteById` must return 1). A second or concurrent Undo gets `BULK_UNDO_NOT_FOUND` and changes nothing.
- **Expiry.** 24 h: a batch with `created_at <= now - 24h` is refused (`BULK_UNDO_EXPIRED`) and kept; `apply` and `purgeExpired()` delete expired batches (same boundary). A corrupt or unreadable image fails with `BULK_UNDO_CORRUPT` before any write and keeps the batch.
- **Residuals.** Account change does not recompute internal-transfer pairing or check the account's currency (a KWD row can move to an EGP account; the row keeps KWD). "Emit events" is covered by Drift table watchers; no separate event bus. Two batches written in the same millisecond on the same row can mask each other's conflict check.

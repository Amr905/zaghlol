## Description
Tamper-evident encrypted backup stream.

## Technical details
Header CBOR (magic, versions, kdf params, wrapped K_bk); Argon2id m=64MiB t=3 p=1; chunk nonces with counter; AAD = header ‖ index ‖ isLast; streaming encrypt/decrypt; passphrase change re-wraps.

## Design note
*solution-architect (Opus), 2026-11-11. Inputs: ADR-011, security-model §3 (`K_bk`, `KEK_pass`) and §5, architecture §7, platform-channels §5 (`SecretStoreHostApi`), T-015 design and implementation notes, D-70, FR-BAK-01/03/06/07, EC-26/27, A-23/24. Library facts checked 2026-11-11 on pub.dev: `cryptography` 2.9.0 and `cryptography_flutter` 2.3.4 (dint.dev, both 2025-11-21; `FlutterAesGcm` uses the OS AES-GCM on Android and iOS, about 50× faster than `DartAesGcm`; Argon2 is not accelerated); `hashlib` 2.4.2 (bitanon.dev, about 4 months old; pure Dart, no FFI; only runtime dependency `convertlib`; Argon2id at RFC 9106's second recommended option, 64 MiB / t = 3 / p = 4, is published at 192 ms on an Apple M3 Pro).*

**0. Scope.** T-148 is a pure crypto and format module (`app/lib/features/backup/crypto/`): key setup, passphrase unlock and change, header encode/decode, streaming encrypt/decrypt, and verify-after-write. **Not here:** what goes into the stream and the restore swap (T-149: snapshot, `K_snap` use, schema migration), upload and listing (T-150), UI and copy. Everything except the `SecretStore` and `TextNormalizer` adapters is pure Dart (no Flutter imports) and runs in host tests.

**1. Libraries** (architecture §7 [doc change]).
- **AES-256-GCM, HKDF-SHA256:** `cryptography` + `cryptography_flutter` (already the §7 choice). `FlutterAesGcm` uses `javax.crypto` on Android and CryptoKit on iOS; host tests fall back to `DartAesGcm` automatically, and the same vectors run on both paths (that is the cross-platform proof, A-24).
- **Argon2id: `hashlib`**, not `cryptography`'s `DartArgon2id`. Both are pure Dart, but `hashlib` publishes Argon2id timings at our exact memory/time cost and checks against RFC 9106; `cryptography` publishes none for Argon2. One small pure-Dart package, no native code and no network.
- **Rejected:** libsodium bindings (`sodium_libs`): about 5× faster Argon2, but a second native crypto stack and large binaries for a cost paid only at setup and restore; `pointycastle` AES-GCM (pure Dart, too slow for 100 MB files on low-end phones); a CBOR package (we need about 150 lines of strict, deterministic CBOR for one fixed schema, §2; a general decoder accepts much more than we want).
- No new native dependency. One new Pigeon method for NFC normalization (§4).

**2. File format v1** (`.zaghlol.enc`, all integers big-endian) [doc change: replaces the security-model §5 block]
```
file   = prefix ‖ header ‖ chunk_0 ‖ … ‖ chunk_{n-1}
prefix = "ZGLB" (4 bytes) ‖ formatVersion u8 = 0x01 ‖ headerLen u16 (1..4096)
header = deterministic CBOR map (RFC 8949 §4.2.1), integer keys, exactly these keys in this order:
  1 kdf        {1 alg: 1 (=argon2id v0x13), 2 salt: bstr 16, 3 mKiB: uint, 4 t: uint, 5 p: uint}
  2 wrap       {1 alg: 1 (=AES-256-GCM), 2 nonce: bstr 12, 3 ct: bstr 48}   -- K_bk ‖ tag
  3 kbkId      bstr 16   -- HKDF(K_bk, salt = "", info = "ZGLB v1 key-id", 16): a non-secret fingerprint
  4 fileId     bstr 16   -- random per file
  5 noncePrefix bstr 8   -- random per file
  6 chunkSize  uint      -- 1 048 576 in v1 (reader accepts powers of two 65 536..4 194 304)
  7 createdAt  uint      -- Unix ms
  8 seq        uint      -- per-K_bk backup counter on the writing device (§6)
  9 schemaVersion uint   -- DB schema of the snapshot (T-149 decides restore vs EC-26)
 10 contentsVersion uint -- layout of the plaintext stream (T-149), 1
 11 platform   tstr      -- "android" | "ios"
 12 appVersion tstr      -- ≤ 32 chars
headerBlock = prefix ‖ header          (the exact bytes as read from the file)
K_chunk  = HKDF-SHA256(IKM = K_bk, salt = fileId, info = "ZGLB v1 chunk", L = 32)
nonce_i  = noncePrefix ‖ u32(i)                     -- derived, never stored
AAD_i    = headerBlock ‖ u32(i) ‖ u8(isLast)        -- isLast ∈ {0x00, 0x01}
chunk_i  = AES-256-GCM(K_chunk, nonce_i, plaintext_i, AAD_i) = ct_i ‖ tag_i (16 bytes)
```
- **Chunking:** every chunk except the last holds exactly `chunkSize` plaintext bytes; the last holds 1..`chunkSize` (0 only when the whole payload is empty, one chunk). At most 65 536 chunks (64 GiB) per file; the writer refuses more.
- **What the header reveals** (it sits unencrypted in the user's Drive/iCloud): times, versions, platform, a counter and random values. Never a device name, account, count of records or anything financial.
- **Changes from security-model §5** [doc change]: the prefix sits outside the CBOR so a reader can dispatch on the version before parsing; `K_chunk` is per file (HKDF over `fileId`), because `K_bk` is reused by every backup and random 8-byte prefixes alone would leave a birthday bound across files; nonces are derived, not stored (one fewer malleable field); the wrap has its own AAD (§3); "contents manifest digest" is dropped (the header is written before the stream, and the AEAD already authenticates every byte; the manifest stays inside the stream, T-149); `seq` and `kbkId` are added.
- **`K_snap`** for T-149 = HKDF-SHA256(`K_bk`, salt = `fileId`, info = "ZGLB v1 db-snapshot", 32), exposed as `BackupKeys.snapshotKey(fileId)`.

**3. Keys and the wrap.**
- `K_bk`: 32 bytes from `Random.secure()`, all-equal output rejected (T-015 rule).
- `KEK_pass` = Argon2id(password = `P` (§4), salt = `kdf.salt`, m = 65 536 KiB, t = 3, p = 1, tag length 32, no secret, no associated data, version 0x13).
- `wrap.ct` = AES-256-GCM(`KEK_pass`, `wrap.nonce` (random 12), `K_bk`, AAD = "ZGLB v1 wrap" ‖ canonicalCBOR(`kdf` map) ‖ `kbkId`). This binds the KDF parameters and fingerprint to the wrapped key without depending on the full header (which contains the wrap).
- After unwrap, recompute `kbkId` from the unwrapped key and compare in constant time; mismatch → `keyMismatch`.
- **Key slot** = the `{kdf, wrap, kbkId}` triple. It is not secret (it is in every file), and it is reused byte for byte in every file written with that `K_bk`, so automatic backups never need the passphrase (ADR-011). Reusing it is not a nonce reuse: it is the same ciphertext, never a new encryption.
- **Storage** [doc change, security-model §3 and platform-channels §5]: `K_bk` in `SecretStoreHostApi` slot **`backupKey`** (32 bytes, the same native rules as `dbKey`: Android Keystore-wrapped blob `noBackupFilesDir/keys/backup_key_v1.bin` under its own Keystore key `zaghlol_bk_kek_v1`; iOS item `app.zaghlol.keys`/`backup_key_v1`, `AfterFirstUnlockThisDeviceOnly`, not synchronizable). Writes take the bootstrap lease like `dbKey`. The key slot is kept in the encrypted DB (`secure_state` key `backup.key_slot.v1`, CBOR), which T-149 **excludes from the snapshot** (it is device configuration; restore writes the restored file's slot).
- **Recovery without a new key:** if `backupKey` reads `notFound`/`unusable` while the slot exists (Keystore invalidated), the next manual backup asks for the passphrase, unwraps the local slot and stores `K_bk` again; old backups stay readable. `unavailable` → the backup job is skipped and retried later, never re-keyed.
- **Passphrase change rotates `K_bk`** [doc change: security-model §3 said re-wrap only]. Anyone with an old file and the old passphrase can recover `K_bk`, so re-wrapping the same key would leave every future backup readable with a leaked old passphrase. `changePassphrase(new)` = `createKey(new)` (new `K_bk`, new salt, new slot), stored by `delete` + `createIfAbsent` under the lease, and the new slot replaces the old one in one DB transaction **after** the secret write is read back. Order on crash: secret written, slot not yet → `kbkId` mismatch at next backup → passphrase prompt, nothing written with a wrong pairing. Old files stay openable with the old passphrase (PO question 1).
- **Zeroization:** `K_bk`, `KEK_pass` and `K_chunk` bytes live in `Uint8List`s wrapped like `DbKeyMaterial` (redacted `toString`, no `==`, `zeroize()`), zeroed right after use; `SecretKeyData.destroy()` for `cryptography` objects. The passphrase is a Dart `String` and can't be zeroed (accepted limit, as in T-015 §5).

**4. Passphrase input `P`.** UTF-8 of: the typed string → Arabic-Indic `٠-٩` (U+0660–0669) and Extended `۰-۹` (U+06F0–06F9) digits to ASCII → every Unicode space separator to U+0020 → **NFC**. No trimming, no case folding. NFC is needed because Android and iOS keyboards may produce different code-point sequences for the same Arabic letter with hamza or madda, and a cross-platform restore must give the same bytes. Dart has no normalizer, so a new `TextNormalizationHostApi.nfc(String) → String` (Android `java.text.Normalizer`, iOS `precomposedStringWithCanonicalMapping`) [doc change, platform-channels §5]; a mismatch between the two platforms is caught by a shared vector list (§9). The minimum is 8 characters after normalization (security-model §5); strength guidance is UI.

**5. Argon2id budget.**
- **Parameters fixed for v1:** 64 MiB, t = 3, p = 1 (ADR-011). Above OWASP's minimum (19 MiB, t = 2). p = 1 because pure Dart runs one thread; p only changes the result, not the speed.
- **Expected time:** `hashlib` does 64 MiB / t = 3 in 192 ms on an M3 Pro (p = 4, same memory passes). A Cortex-A53-class phone is roughly 10–20× slower single-core, so **about 2–4 s** is expected. **Budget: p50 ≤ 4 s, p95 ≤ 8 s on the reference low-end Android** (PO question 2), measured by a T-171 device benchmark (10 runs, release build). If p95 > 8 s, the fallback is t = 2 at 64 MiB (memory is kept; it is the GPU-resistance factor), recorded in the header and ADR-011, never chosen per device silently.
- **Runs only in the foreground** (backup setup, passphrase change, restore, re-unlock), always in `Isolate.run`, so the UI keeps animating; never in automatic backups (no KDF there, §3).
- **Memory:** one 64 MiB block in the isolate, released when it returns; a failed allocation (`OutOfMemoryError`) → `kdfOutOfMemory`, a retryable error that asks to close other apps.
- **Restore-side bounds** (a hostile header must not exhaust the phone): accept `mKiB` 19 456..262 144, `t` 1..10, `p` 1..4, `alg` 1 only; anything else → `unsupportedKdf` **before** running the KDF.

**6. Encrypt (streaming).** `Stream<List<int>> encrypt(BackupKeys k, HeaderMeta meta, Stream<List<int>> plaintext)`:
- Builds the header (fresh `fileId` and `noncePrefix`, `seq` = stored counter + 1, persisted only after the upload succeeds, T-150), emits `headerBlock`, then rebuffers the input into `chunkSize` pieces, holding one piece back so that it knows which one is last; emits `ct ‖ tag` per piece.
- Peak memory ≈ 2 chunks + the platform-channel copies, under 8 MiB. The output is never assembled in memory; T-150 writes it to an encrypted-temp location (spool key rules) or streams it.
- **Fail closed:** any error cancels the stream with a `BackupCryptoException(code)`; callers delete partial output; there is no unencrypted fallback and no partial upload.
- **Verify after write:** `verifyFile(Stream<List<int>> file, BackupKeys k)` decrypts every chunk and discards the plaintext (no KDF, about 1 s per 100 MB with OS AES). T-150 runs it on the written file before upload and deletes the file on failure.

**7. Decrypt and restore-time verification order** (`DecryptSession open(Stream<List<int>> file, String passphrase, {required int maxSchemaVersion})`); each step only if the previous passed:
1. **Prefix:** first 4 bytes ≠ "ZGLB" → `notABackup`. `formatVersion` > 1 → `newerFormat` (update the app, EC-26 wording); 0 → `corruptHeader`. `headerLen` 0 or > 4096 → `corruptHeader`.
2. **Header decode, strict:** definite lengths only, shortest-form integers, no floats, tags, duplicates or unknown keys, every key present with its exact type and length, keys in canonical order, no bytes left over inside `headerLen`. Any violation → `corruptHeader`. Then value checks: `chunkSize` allowed, KDF bounds (§5) → `unsupportedKdf`.
3. **Cheap refusals before the KDF** (the header isn't authenticated yet, so these can only refuse, never accept): `schemaVersion > maxSchemaVersion` → `newerSchema` (EC-26); `contentsVersion` unknown → `newerFormat`.
4. **Passphrase:** normalize (§4), Argon2id in an isolate, unwrap. GCM failure → **`wrongPassphrase`** (the clear error of security-model §5). A corrupted wrap reads the same, which is acceptable. Then the `kbkId` check → `keyMismatch`.
5. **Stream:** derive `K_chunk`; read `chunkSize + 16` bytes at a time; a chunk is last exactly when the stream ends right after it (a short read is always last). Decrypt with `AAD_i`. Any tag failure, a short chunk that is not at the end, a chunk shorter than 17 bytes, or more than 65 536 chunks → **`corruptData`**. Plaintext is yielded chunk by chunk.
6. **Contract with T-149:** yielded plaintext is **untrusted until the session completes with `done`**. The consumer writes only to a temp location, and commits nothing (no swap, no settings applied) before `done`. On any error the consumer deletes the temp output. This is what makes truncation, reordering and swapping harmless even though earlier chunks were already yielded.
7. `done` returns the authenticated header metadata (`createdAt`, `seq`, `schemaVersion`, `platform`, `appVersion`) and the key slot, so T-149 stores `K_bk` + slot after the swap.

**Why each attack fails:** truncation at a chunk boundary turns a non-last chunk into the apparent last (its AAD had `isLast = 0`); a truncated mid-chunk gives a bad tag; dropping, reordering or duplicating chunks changes `i` in nonce and AAD; trailing bytes make the real last chunk non-last; a chunk from another file has a different `K_chunk` and `headerBlock`; header edits change every AAD (and the wrap AAD for KDF fields). **Rollback** (an older genuine backup put in place of a newer one by someone with access to the user's Drive) can't be detected cryptographically without outside state: the restore list shows the authenticated `createdAt` and `seq`, not Drive's metadata, and on the writing device a file with a lower `seq` than the last uploaded one shows a warning. Full rollback protection would need server state (the backend holds no backup data; not proposed).

**8. API and errors.** Riverpod: `backupCipherProvider` → `BackupCipher(secretStore, normalizer, random, clock)`, stateless (never caches keys). Errors: sealed `BackupCryptoException` with `code ∈ {notABackup, newerFormat, newerSchema, corruptHeader, unsupportedKdf, wrongPassphrase, keyMismatch, corruptData, kdfOutOfMemory, keyUnavailable, io}`. The crypto layer holds no strings for users; the UI maps codes to copy. Diag codes (T-021) carry `{code, formatVersion, chunks}` only: never key bytes, passphrase, header bytes, `fileId` or plaintext; no `print`/`debugPrint` in the module (CI grep).

**9. Tests.**
- **Vectors** (`app/test/fixtures/backup/zglb-v1-vectors.json`, synthetic): fixed passphrase (Arabic, with ٣ and a hamza sequence), salt, `K_bk`, wrap nonce, `fileId`, `noncePrefix`, `createdAt`, and a deterministic payload of 2.5 chunks at `chunkSize` 65 536 (plus one at 1 MiB). Expected: `P` bytes, `KEK_pass`, `wrap.ct`, `kbkId`, `K_chunk`, `K_snap`, `headerBlock` hex, the first and last chunk, SHA-256 of the whole file. **Produced by an independent implementation** (`app/tool/backup_vectors.py` with Python `cryptography` and `argon2-cffi`, committed with its output; CI checks only the Dart side). Plus library sanity vectors: RFC 9106 §5.3 Argon2id, NIST GCM test case 16, RFC 5869 case 1. The same vector test runs in the db-platform device legs (Android, iOS) to prove the platform AES and NFC give identical bytes.
- **AC 1 (truncated, reordered, swapped):** for a 4-chunk file: truncate at every chunk boundary and at ±1 byte of each; drop chunk 1; swap chunks 1 and 2; duplicate chunk 2; append one byte; append a chunk from another file under the same `K_bk`; replace chunk 2 with the same index from another file; flip one byte in each chunk and each tag. Each → `corruptData`, and the consumer saw no `done`.
- **AC 2 (wrong passphrase):** wrong passphrase → `wrongPassphrase` raised at unwrap, with **zero chunks read** (a counting stream proves it); a case-changed or trailing-space passphrase is wrong; `٣` and `3` are the same passphrase; a decomposed hamza sequence opens a file written with the precomposed one.
- **Header:** each header byte flipped → one of `corruptHeader | unsupportedKdf | newerSchema | wrongPassphrase | corruptData`, never another exception type; `m` = 4 GiB → `unsupportedKdf` with no allocation; `formatVersion = 2` → `newerFormat`; non-canonical CBOR (long-form integer, reordered keys, unknown key 13) → `corruptHeader`.
- **Fuzz:** `package:test` property loops with a fixed seed, run in CI: 10 000 random byte strings and 10 000 mutations of a valid header into the CBOR decoder (only `corruptHeader` or success, no hang, bounded allocation); 2 000 random truncation offsets and 2 000 random byte flips over a small file (only typed errors). Slow-mode counts (10×) behind a tag for nightly runs.
- **Keys:** create → slot round-trip; `changePassphrase` gives a new `kbkId`, the old file still opens with the old passphrase only; a crash between secret write and slot write → `keyMismatch` path; `backupKey` `unavailable` → `keyUnavailable`, nothing rewritten; generator all-equal output rejected.
- **Streaming:** a 300 MiB synthetic stream encrypts and decrypts with resident memory growth < 16 MiB (host, `ProcessInfo.currentRss`); verify-after-write catches a flipped byte.
- **Negative proofs** (throwaway branches, results recorded in implementation-status): drop `isLast` from the AAD → the boundary-truncation test goes red; drop `i` → the swap test goes red; drop `fileId` from the HKDF → the cross-file substitution test goes red; log `K_chunk` with `debugPrint` → the CI grep goes red.
- **Device benchmark (T-171):** §5 Argon2id timing on the reference low-end Android and one iPhone, recorded with the device model.

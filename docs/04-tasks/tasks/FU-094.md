# FU-094: cross-connection writers fail with SQLITE_BUSY after ~70 ms

Class C4 (data safety under concurrency). Owner area T-016 / T-017. Found by the T-074 code review ("Busy-timeout experiment").

## Problem
Two connections on the same encrypted file, both opened through `openEncryptedExecutor`, both reading `PRAGMA busy_timeout` = 5000. While connection A held a write transaction, connection B's `BEGIN IMMEDIATE`, and also a lone `INSERT`, failed with SQLITE_BUSY after about 70 ms instead of waiting up to 5 s. The headless ingestion engine and the UI engine each hold a connection (T-008 / ADR-005, T-016 design note §5), so writes would fail at random.

## Root cause
The cause is not in the open sequence, the executor or the cipher. It is how SQLite's built-in busy handler sleeps inside a Dart VM.

- The bundled SQLite3MultipleCiphers 3.54.0 (sqlite3 3.9.1 prebuilt) sleeps through the unix VFS `xSleep`, which calls `nanosleep` once and ignores EINTR. `sqliteDefaultBusyCallback` counts every delay in its schedule (1, 2, 5 … 100 ms) as fully slept and stops once the counted total passes the timeout.
- The Dart VM's sampling profiler sends `SIGPROF` (`SI_TKILL`, about every 1 ms) to every thread that has an isolate entered, including a thread blocked in an FFI call to SQLite. It is on in JIT/debug, in profile builds and in `flutter test`.
- `strace -f` of the reproduction showed every busy sleep (`clock_nanosleep` 1 ms … 100 ms) ending `ERESTART_RESTARTBLOCK (Interrupted by signal)` followed by `--- SIGPROF ---`. So the "5000 ms" budget was used up after about 30 to 70 ms of real time. A raw `sqlite3` connection without encryption, drift or a second isolate showed the same result (2000 ms timeout, failure after 32 ms).
- Ruled out: the busy handler being reset (the PRAGMA read back 5000), foreground versus background executors (both failed), the `journal_mode` switch or WAL checkpoint (the failure is on the WAL write lock, and the handler was called), and a same-thread deadlock (A ran on its own isolate). Drift starts transactions with `BEGIN IMMEDIATE` (`Sqlite3Delegate.transactionDelegate`), so drift transactions never hit the WAL read-to-write upgrade, which returns SQLITE_BUSY at once by design.

## Fix
`applyBusyTimeout` (`app/lib/core/db/encrypted_open.dart`) no longer sets `PRAGMA busy_timeout`. It installs a Dart busy handler through `sql.Database.busyHandler`:
- It measures real elapsed time per wait with a `Stopwatch` that restarts when SQLite's `count` is 0, so a cut-short sleep can't use up the budget.
- It sleeps with `dart:io` `sleep`, which retries after EINTR, using SQLite's own delay schedule, capped by the time left.
- It gives up after `dbBusyTimeout` (5 s, now a public constant). The statement then fails with SQLITE_BUSY, which `guardWrite` maps to `DbWriteException(DB_WRITE_FAILED, sqliteCode: 5)`.

The handler is installed in drift's `setup` on the connection's own isolate (`NativeCallable.isolateLocal` in the sqlite3 package). It runs on the blocked thread, the same place SQLite's handler ran.

Consequence: `PRAGMA busy_timeout` now reads 0 on app connections (`sqlite3_busy_handler` clears it). A guard test fails if anything in `lib/` sets that PRAGMA, because doing so would put the broken built-in handler back.

No retry-on-BUSY helper was added. With the handler working and drift using `BEGIN IMMEDIATE`, SQLite's own wait covers both the transaction case and the lone-statement case. If a writer still holds the lock past 5 s, the result is a clean `DB_WRITE_FAILED` and nothing is half-applied.

## Evidence
- Regression test `app/test/core/db/busy_wait_test.dart`. Connection A runs on its own isolate, opens a raw connection with the app's open sequence, takes the write lock (`BEGIN IMMEDIATE` and an insert), holds it with a blocking sleep and commits. Connection B is the app's `AppDatabase`:
  - B on the background and on the foreground executor, each with a drift transaction and with a lone statement: B waits (more than 200 ms) and succeeds, and both rows are present (4 tests).
  - A holds for 6.5 s: B fails with `DbWriteException` `DB_WRITE_FAILED`, `sqliteCode` 5, after at least 4.95 s and before A releases, with nothing written. B's next write succeeds (2 tests: background transaction, foreground lone statement).
  - No `busy_timeout =` in `lib/` (1 test).
- Before the fix all 6 behavioural tests failed (B gave up after about 65 ms). Negative proof on the final code: putting `PRAGMA busy_timeout = 5000` back turns all 7 tests red. The new test passed 5 runs in a row (about 15 s each).
- `app_database_test.dart` PRAGMA read-back now expects `busy_timeout` = 0, with a comment.
- Local checks: `flutter pub get --enforce-lockfile`, `dart format --set-exit-if-changed app packages tools` (0 changed), `flutter analyze` clean, `flutter test` all passed.

## Real devices
Release builds (AOT product mode) have no VM profiler, so the built-in handler probably worked there. Debug and profile builds on device run the profiler and were affected like the tests. Any other signal (for example, ART on Android) could also cut a sleep short. The new handler is correct in all of these cases. Not verified on a device. Residual: SQLite's internal WAL retry sleeps (`walTryBeginRead`, used during WAL recovery or under heavy checkpoint contention) use the same interruptible `xSleep` and do not go through the busy handler. Under the profiler they can give up sooner, with SQLITE_PROTOCOL; this is rare and only in debug/profile builds.

## Description
MonsterASP.NET runs the API on Windows/IIS in a shared host. The File KMS (T-200) refuses to start off Linux (no `prctl`, no POSIX modes) and OpenBao (T-201) needs a server we control. Add a `Kms:Provider = HostSecrets` provider that reads the same key ring (signing ES256 JWKs, HMAC keys, envelope keys, same JSON shapes and kids as the File KMS) from **secret settings injected by the host** — environment variables set in the site's `web.config` `<aspNetCore><environmentVariables>` (never committed; created at deploy from GitHub environment secrets) — and keeps every T-200 behaviour that does not depend on the OS: kid rules, rotation (active + verify-only), constant-message refusals, no key material in logs/exceptions/health, keys never written to disk by the app.

Shared hosting is a weaker custody model (the host's staff and a host compromise could read the settings). It is accepted only by an explicit `Kms:AcceptSharedHostCustody = true`; without it the provider refuses to start in Production. ADR-026 records the trade-off and the exit path (move to OpenBao / File KMS on a server we control before scale or if the host is compromised; HMAC and envelope keys move by the existing BYOK import, signing keys by rotation).

## Acceptance criteria
1. `HostSecrets` implements `ISigningKeyProvider`, `IHmacProvider`, `IDataKeyProvider`; reads `ZAGHLOL_KEYS__…` settings (one per key, base64url JSON in the File KMS format); works on Windows and Linux.
2. Startup refusals (constant messages, no key bytes): missing/invalid key, duplicate kid, wrong curve/length, key material found in `appsettings*.json`, provider used in Production without `AcceptSharedHostCustody`.
3. `Zaghlol.Workers --generate-keys --format host-secrets` prints the settings to stdout once (for pasting into GitHub environment secrets) and never writes files; File KMS key directories can be converted (`--from-dir`).
4. Same kids and HMAC outputs as the File KMS for the same key bytes (test), so a later move to OpenBao keeps hashes valid.
5. 2–3 negative proofs: refusal without the custody flag in Production; no key bytes in logs/exception messages/health output.
6. ADR-026 + deployment.md section "MonsterASP.NET + Aiven".

## Design note (implementer, written before the code)

**Seam.** `HostSecretsKms` is one more `IKmsBackend` behind `KmsServiceCollectionExtensions.SelectProvider` (`Kms:Provider = HostSecrets`). `Signer`, `KeyedHasher`, `EnvelopeCipher`, `KmsStartupCheck` and `SeatKeyStartupCheck` are unchanged and still run after it. No Api/Workers hosting change: both already call `AddZaghlolKms`.

**Same key format and key references as the File KMS.** HostSecrets is a different *source* of File-format keys, not a new key format:
- Key references stay `file:<name>`; signing kids, `Signing:Keys`, `Kms:HmacKeys`, `Kms:Envelope:*` are byte-for-byte the File ring. The envelope wrap is `FileKms.Wrap` (same AAD `"zaghlol-file-wrap-v1" ‖ 0x00 ‖ keyRef`), so HostSecrets and File open each other's envelopes, and the T-201 OpenBao legacy route (`file:` in `PreviousKeyRefs` → imported `file-<name>`) works unchanged. HMAC is plain HMAC-SHA256 with the same bytes, so hashes match File and OpenBao after the BYOK import (AC4).
- Pins reuse the File settings: `Kms:File:Fingerprints:<name>`, `Kms:File:OtherEnvironmentFingerprints:<n>`, `Kms:File:NoOtherEnvironment`. Moving File ↔ HostSecrets changes only `Kms:Provider` and where the key bytes come from. Pins are public, so they may live in a committed `appsettings.<env>.json`; the key bytes may not.

**Setting format.** One setting per key: `ZAGHLOL_KEYS__<name>` (environment variable; config key `ZAGHLOL_KEYS:<name>`; `-` may be written `_`, matching is case-insensitive as in all .NET configuration; both spellings present = refusal). Value: unpadded base64url of the UTF-8 JSON `{"zaghlol":"host-key-v1","name":"<name>","pem":"<the .pem file text>"}` (signing key) or `{…,"key":"<the .key file text: base64 of 32 bytes>"}` (HMAC/KEK). Exactly these three members in this order; `name` must equal the setting's name (catches a value pasted into the wrong secret). The fixed first member gives every value the same 32-character base64url prefix, so a pasted key is recognisable in any file (`HostSecretsKms.ValueMarker`). base64url keeps PEM newlines out of `web.config`.

**Guards (constant messages, no key bytes, names or values; all at host start).** All T-200 guards that don't depend on the OS: key-ref rule and one-role-per-symmetric-key (G7/G15), committed-key denylist, tiny scalar, degenerate secret, named P-256 only, explicit curve refused (G10/G7), fingerprint pin per key (G11), other-environment list + required list-or-`NoOtherEnvironment` outside Dev/Testing (G12), year-0000 kids outside Dev/Testing (G13), same bytes under two names (G15); on Linux also non-dumpable outside Dev/Testing (G14). New:
- H1 missing/undecodable/oversized (> 16 KiB) setting, wrong JSON shape, wrong `name`, `pem` for a symmetric ref or `key` for a signing ref.
- H2 both `<name>` and `<name with _>` set (duplicate).
- H3 key material in a file: any `ZAGHLOL_KEYS` value served by a file configuration provider (`appsettings*.json`, any JSON/INI/XML file source), or an `appsettings*.json` file in the content root or app base directory that contains `ZAGHLOL_KEYS` or `ValueMarker` (catches files the host doesn't load in this environment too).
- H4 outside Development/Testing (Staging and Production — both run on the shared host), `Kms:AcceptSharedHostCustody` must be `true`; any other value refuses the start.
The shared check code is moved out of `FileKms` into helpers that take the provider's messages, so File keeps its exact messages and tests.

**Memory and disk.** Each value is decoded into a pinned buffer, parsed with `Utf8JsonReader` (`CopyString` into pinned buffers), then zeroed; keys are held exactly as in `FileKms` (one `ECDsa` per kid with a lock, pinned 32-byte arrays zeroed on `Dispose`). The app writes no key file. Residual (ADR-026): the setting strings stay in the process environment block and `IConfiguration` (immutable strings can't be zeroed), and on Windows there is no `prctl` equivalent (IIS/WER dumps are a host-side setting).

**Key tool.** `Zaghlol.Workers --generate-keys --format host-secrets --environment Staging|Production (--kid …|--secret …)… | --from-dir <File key dir>`: prints the `ZAGHLOL_KEYS__…` lines (private, marked as such), then public lines (`Kms__Provider=HostSecrets`, `Signing__Keys__…` for new kids, `Kms__File__Fingerprints__…`, `Kms__HmacKeys__SeatCheck`), once, to stdout; never writes a file; runs on Windows and Linux; refuses to run inside a source tree (so `> file` can't land in a checkout); `--from-dir` reads `*.pem`/`*.key` (≤ 8 KiB, no links, `kms.env` refused) and refuses committed or degenerate keys. `--format` with any other value is a usage error; without `--format` the T-200 file tool is unchanged.

**Exit path** (ADR-026): to File KMS — write each `key`/`pem` field to `<name>.key`/`.pem` with the T-200 modes, same ring and pins, change `Kms:Provider`; to OpenBao — do that, then the existing `--openbao-keys` BYOK import (HMAC + envelope), signing keys by rotation.

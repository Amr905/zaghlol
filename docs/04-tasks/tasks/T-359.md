## Description
`confirm(merchant)` → user merchant rule through the existing rule service (removes the AI chip on all its rows) + suggestion state `confirmed` + outbox `llmCatConfirmation`. `correct(merchant, chosenCategory)` → rule + state `corrected` + outbox `llmCatCorrection` with `userCategory` = system code or `custom`. Picker cancelled → nothing changes. `undo()` within 5 s removes the rule, restores the previous state and deletes the outbox row. The sync request includes up to 50 feedback items from the outbox while the flag is on and consent is present; accepted items are removed.

## Acceptance criteria
1. Right on Zawya → rule saved, chip gone on all 3 rows, one confirmation outbox row; sync body carries it once, then it is removed.
2. Wrong groceries → Education → rule + correction row; a custom «كتب» → `custom`, and «كتب» appears nowhere in the sync body (test).
3. Undo within 5 s → no rule, no outbox row, rows back to `ai`/unconfirmed; after 5 s Undo is gone.
4. Flag off or consent cleared → feedback stays local, not sent; more than 50 items → sent across calls.
5. Body items contain only the five closed fields.

## Design note (builder)
- `LlmCatFeedback` (`application/llm_cat_feedback.dart`) does confirm / correct / undo in ONE DB transaction through the existing `RulesRepository` (`save` + `applyToPast`) plus `AiMerchantSuggestionsDao.decide`, then queues the outbox row. Only an `unconfirmed` suggestion with a category can get feedback (so only eligible, AI-answered merchants; person payees never have a row).
- `applyToPast` skips rows already in the rule's category, which would leave the AI chip on after Right; the service flips those rows to `user_rule` with the same guards.
- Undo: the receipt (in memory, 5 s, single use) holds the merchant's transaction columns (`category_id`, `category_source`, `updated_at`), the previous rule row (or none) and the outbox id; undo restores them in one transaction and never overwrites a row the user changed since.
- Sending: `SyncOrchestrator` gets `llmCatFeedbackConsent` and `sendLlmCatFeedback` (default `kSendLlmCatFeedback = false`). Off means the outbox rows stay and `llmCatFeedback` is absent from the body.

## For the PO (FU-412; sending stays OFF until approved)
Sending is behind `const bool kSendLlmCatFeedback = false` in `sync_orchestrator.dart`. To enable: set it `true` and add `llmCatFeedback` to the allow-list in `app/test/privacy/support/br_sync_03.dart` (one line each), after the wording below is approved.
- **Sent, per item** (OpenAPI `LlmCatFeedbackItem`): `merchantNorm` (the normalised shop name, same form as the names sent for guessing), `verdict` (`right` or `wrong`), `aiCategory` (the system category code Zaghlol guessed), `userCategory` (the system code the user picked, or the word `custom` for a user's own category), `source` (`llm`, `cache` or `catalog`: where the guess came from). `source` is not named in D-96; the OpenAPI spec and the backend table carry it, so the SRS line should name it.
- **When:** only while the `llm_categorise` flag is on AND the auto-category consent is on (the same consent as the names, OQ-LCAT-04); at most 50 items per sync, oldest first, the rest on the next syncs. Flag off or consent off: items stay on the phone, unsent.
- **Never sent:** amount, date, account or card, institution, transaction ids, message text, the name or id of a custom category, anything about person payees (they never get an AI guess, so never feedback). Undo within 5 s removes the item before it can be sent.
- **Wording to approve (BR-SYNC-03 / privacy screen):** "When you tap Right or Wrong on a guessed category, the shop name, Zaghlol's guess, your category (or 'custom') and where the guess came from are sent with the next sync, only while auto-categories are on. Nothing else." Note the shop name travels together with the anonymous install ID in the sync request (the point raised in FU-412).

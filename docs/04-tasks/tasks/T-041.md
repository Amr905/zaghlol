## Description
Background processing of the spool within 10 s.

## Technical details
Expedited work; reuse cached engine if app alive else start headless engine at ingestionMain; wait for Dart completion (≤ 60 s); re-enqueue with back-off if spool non-empty; EventChannel onSpoolChanged for foreground.

**3. Work requests (fixes FU-081 F5) [doc change ADR-005, platform-channels §2].** Two unique works, both `IngestionWorker`, **no constraints**:
- **Live** `zaghlol.ingest`: `setExpedited(RUN_AS_NON_EXPEDITED_WORK_REQUEST)`, `APPEND_OR_REPLACE`. Enqueued by `afterSpoolWrite()` (also after a refused write) and `scheduleIngestionNow`. **Never returns `Result.retry()`**, so the head is never parked in back-off and a new SMS never waits behind one (F5). It can only append behind a *running* head (≤ 60 s budget).
- **Retry** `zaghlol.ingest.retry`: not expedited, `ExistingWorkPolicy.KEEP`, `setInitialDelay(min(10 s × 2^(n−1), 15 min))`, input `attempt = n` (a number, no content). A run that ends `RETRY`/`TIMEOUT`/spool-unavailable enqueues retry `n+1` (n from its own input, 1 for a live run) and returns `success`; after attempt 8 it stops (the next live enqueue or app open resumes). Any run that ends with `pending == 0` cancels `zaghlol.ingest.retry`.
- Outcomes: `OK` + empty → success; `OK` + only stuck entries (T-046 `stuck > 0`, pending unchanged) → success, no retry; `NO_DATABASE`, `DEFERRED` → success, no retry (the UI engine drains at start); `RETRY`, `TIMEOUT`, or `OK` with nothing drained while `pending > 0` and no UI engine (claim held elsewhere or entries `Unavailable`) → retry work.
- A process-wide `Mutex` lets one worker run at a time (a live and a retry run never interleave cycles).
- **Expedited vs foreground.** API 31+: WorkManager runs expedited work as an expedited JobScheduler job (standby-bucket quota; out of quota → regular job); `getForegroundInfo()` is not called; we **never call `setForeground`** (background FGS starts throw on 12+), so no FGS type is declared and API 34+ type rules do not apply. API 26–30: WorkManager falls back to a foreground service and calls `getForegroundInfo()` → the existing low-importance notification, `VISIBILITY_SECRET` on the notification **and** `lockscreenVisibility = VISIBILITY_SECRET` on the channel (FU-093 N1). Rejected: `dataSync`/`shortService` FGS (Play declaration, per-type timeouts, nothing gained over a job).
- **Time limits.** The loop budget is 60 s, far below JobScheduler's 10-minute stop. On stop (quota, 10 min, cancel) the coroutine is cancelled: a `NonCancellable` `finally` posts `engines.headless.shutdown()` (never `destroy`) and returns; WorkManager reschedules stopped work itself.

Headless engine (from the spike, `ShutdownSequence` kept).** One process-wide `FlutterEngineGroup`, one engine at a time, entrypoint `ingestionMain`, `automaticallyRegisterPlugins = false`, allowlist: `JniPlugin`, `JniFlutterPlugin`, `SecretStoreRegistration`, `AndroidCaptureHost` (headless: `inbox = null`, `guardWriter = null`: no Guard writes, no inbox reads from the background, FU-088), and the new ingestion Pigeon APIs (§7). **Reuse:** a cycle reuses a live engine; a shutting-down engine is never reused (wait for `gone`, then start fresh). **Linger** `LINGER_MS = 10_000` (provisional; Lead may tune from the device rows), then `shutdown()`; also on `onTrimMemory`/`onLowMemory` when no claim is held. **Teardown order (unchanged, F1):** pending drain answered → Dart `close` (awaits the DB close) → `FlutterEngine.destroy()`, exactly once; bounds 55 s (drain) and 5 s (close) only for a hung isolate (FU-093 N4: a cycle hung past 55 s can be destroyed; nothing acked is lost). **Change:** `close` now also means *stop after the current batch* (Dart sets a stop flag checked before each `drainSpool`), and `ShutdownSequence.request()` sends `close` at once even while a drain is pending (state `CLOSING`, bound = drain + close). The drain reply still arrives first (Dart's close awaits the running cycle). Effect: a UI engine waits at most one batch (≤ 20 entries), not a 50 s cycle. `teardown` → `host.detach()` (claim released) → `notifyUiIfAttached()` if `pending > 0`.

**6. **7. Dart entrypoint and control channel [doc change platform-channels §2].** The spike `BasicMessageChannel zaghlol/spike_metrics` command protocol becomes a Pigeon contract `app/pigeons/ingestion_api.dart`:

```dart
class IngestCycleReport { IngestOutcome outcome; int drained; int inserted; int stuck; int held; String? code; }
@FlutterApi() abstract class HeadlessIngestionApi {
  @async IngestCycleReport drain();
  @async void close();          // stop after the current batch, await the DB close
}
@HostApi() abstract class HeadlessIngestionHostApi { void ready(); }  // handler installed
```

5. T-046's `ingest_poison_test` "unstorable stays stuck" now expects the entry held; the old path is kept as the hold-failure case.

### Self-check (docs/workflow/self-check.md)
1. **Never destroy data on doubt:** applied. Hold is a rename (same bytes, same AAD), never a delete; release only on a proven version change (absent/unreadable version file → release, which deletes nothing); the headless engine is destroyed only after the drain and close replies (bounds only for a hung isolate; nothing acked is lost).

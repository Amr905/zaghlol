## What exists
`device-flows` already sends a few synthetic SMS through the emulator modem (`adb emu sms send`, with a `content insert` inbox fallback) and checks that the real app saved them (`app/integration_test/sms_device_test.dart`, `.github/scripts/device-flows.sh`). Nothing checks what the charts show from SMS.

## Scope
1. **Scenario file** `app/test/fixtures/sms/scenarios/month_story.json` (synthetic only, built from the existing per-bank fixture templates so the parser really matches them): about 40–60 SMS over the current period and the two before it, across at least 4 banks/wallets (e.g. CIB, NBE, QNB/HSBC, InstaPay, a wallet), covering: card purchases at known merchants in several categories (groceries, food delivery, fuel, telecom, pharmacy), one unknown merchant, salary/income, an ATM cash withdrawal and later cash spending, a self-transfer between own accounts (must not count as spending), a refund, a foreign-currency purchase (USD), a declined/OTP/promo message (must be ignored), a bill payment. Each entry: sender, body, date (epoch ms), and the expected result (kind, amount minor units, currency, merchant, category or "ignored").
2. **Expected numbers** computed by a small pure Dart helper from the scenario's expected results (not from the app): per-period spend per currency, per-category totals, top merchants + Other, income, saved per month, day-by-day totals; they follow the app's documented rules (transfers excluded, refunds net, cash-covered rule, per currency, never summed).
3. **Delivery to the emulator:** extend `.github/scripts/device-flows.sh` with a `scenario` phase: past-dated entries go into the system inbox with their dates (`content insert ... date`), then the first-run scan; a few current ones arrive live via `adb emu sms send` while the app runs. Logs show sender ids and counts only, never bodies.
4. **New integration test** `app/integration_test/sms_charts_device_test.dart` (real app, real DB, devSms flavor): after delivery, assert (a) each scenario entry produced the expected transaction (or was ignored), with amount, currency, merchant and category; (b) the Insights v2 screens show the expected numbers: Overview hero spend, Where it went rows, Saved each month bars' values (via semantics labels), Categories tab totals and share, Trends heatmap totals for 3 sample days, merchants chart incl. Other; (c) Home's recent list shows the live ones. Take screenshots of each tab (Arabic and English) to `device-shots/<sha>/scenario/`. Pin "now" to a fixed date inside the scenario's current period if the app supports a clock override in integration tests; otherwise generate the scenario dates relative to the device clock at run time (document which).
5. **CI:** run it as its own job in `device-flows` (within the 60-minute job limit); report the run id.

## Acceptance criteria
1. Every scenario entry checked; mismatches listed by entry id with expected vs actual (no bodies in logs).
2. Chart numbers asserted against the independent expected numbers, per currency, ar and en.
3. Green `device-flows` run on `ci/T-233` with screenshots published; any real app bug found is fixed with a unit test (or, if large, filed as an FU with the failing entry id and the job skipped for that check only, with the reason).
4. `dart analyze`, `dart format`, fixture tests (`test/fixtures` parser coverage) green.

## Design note (builder, 2026-11-24)
- **Scenario** `month_story.json` (47 entries, format in `scenarios/README.md`): 38 inbox (3 months), 4 live, 1 manual cash. Dates are relative to the device clock (`monthsAgo` + `day` + `time`); the app has no clock override in integration tests. Main period under test = last month (closed, so the numbers do not depend on today); the current month holds only the live entries.
- **Expected numbers** `app/test/support/scenario_expected.dart`: pure Dart from the entries' `expect` blocks (never from the app), with a unit test. Rules as in the README.
- **Delivery**: `device-flows.sh` phase `scenario`: `jq` computes epoch ms per entry; inbox rows by `content insert ... date`; live via `adb emu sms send`. Logs: entry id + sender only.
- **Test** `sms_charts_device_test.dart`: first-run scan, wait for the live ones, check each entry (transactions table by amount+currency+day), then read the Insights v2 providers/semantics for lastMonth and thisMonth; shots to `ci_screens` (pulled to `device-shots/<sha>/scenario/`).
- **CI**: own job in `device-flows.yml`.

## Build result (2026-11-24)
Green `device-flows` run **45369489896** on `ci/T-233` (commit 003bb22c): scenario job, 44 of 44 entries matched, 0 problems. Screenshots: `device-shots` branch, `003bb22ce30ad158675465b33e8195e8fa541613/scenario/` (Overview, Categories, Trends in en and ar, Home).

Deviations: (1) dates are relative to the device clock (no clock override). (2) Past messages are delivered through the modem with the device clock set to each entry's time (root, auto time off, restored after): `content insert` cannot carry ':' and direct sqlite rows are invisible to apps (probe run on `ci/T-233-probe`). (3) The scenario reaches the test as the `SCENARIO_JSON` dart-define. (4) Merchants chart "Other" is checked as the expected remainder in the log and the top-5 against the repository; the UI shares are checked through the chart query (not as UI text). (5) The refund (InstaPay, no merchant) links to nothing, so "refund nets" is not exercised.

App bug found and fixed: SMS-ingested transfer legs were never paired (no ingest hook), so a transfer between two own accounts counted as spend and as income. Fix: `TransferPairingHook` in `buildIngestRawMessages`, unit test `test/features/transactions/application/transfer_pairing_hook_test.dart`. Not a bug: identical SMS text from one sender is deduped by `body_hash` by design (scenario bodies now differ by balance).

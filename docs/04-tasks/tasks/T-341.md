## Description
Expose two calls (or verify they already exist): Android `integrityToken(requestHashB64u)` using a prepared standard token provider (prepare once, re-prepare on expiry); iOS `appAttestAssertion(clientDataHash)` with the install's existing App Attest key, returning `{keyId, assertion, attestationObject?}`. Contract defined in Dart first and documented.

## Acceptance criteria
1. Kotlin unit test with a fake manager: the `requestHash` is passed through verbatim; provider expiry triggers one re-prepare.
2. Swift test with a fake service: assertion uses the given hash; `attestationObject` only on first use of a key.
3. Neither hashes, tokens nor assertions are logged (log capture).
4. `platform-channels.md` updated; Dart contract test green; iOS checked on `ci/T-341`.
5. If the existing channel already does all of this, the task closes as verified with the test references.

## Notes for the builder
- No new key generation: reuse the restore flow's App Attest key. If that is impossible, stop and report (Opus escalation).

## Design note (builder, 2026-11-26)
Decision: **existing channel, no new method.** `AttestationHostApi` (platform-channels §4a, T-178) already takes a caller-supplied 32-byte hash and never builds or sees its meaning: Android turns it into an unpadded base64url `requestHash` for a standard Play Integrity request on a prepared, cached token provider (one re-prepare on `INTEGRITY_TOKEN_PROVIDER_INVALID`, then transient); iOS signs exactly those bytes with the install's one Keychain App Attest key and returns `attestationObject` only when a key was newly generated (first use, `forceNewKey`, or `invalidKey`). ask-llm §5 needs only a different hash: Dart passes `bodyHash` (Android) or `clientDataHash = SHA-256("zaghlol-ask-attest-v1" || 0x00 || bodyHash)` (iOS) built by T-340's binding code. Nothing about the question text crosses the channel except that hash. No new key material, no Opus escalation, no manifest/entitlement/Info.plist change, no new permissions, no store-policy change.

## Description
Shared normalizer for parsing, voice, OCR and search.

## Technical details
Arabic-Indic/extended digits → ASCII; ٫/٬ separators; invisible marks; tatweel/diacritics (matching only); Arabic letter folding for keys; amount parser for 1,234.56 / 1.234,56 (eu locale flag) / 1,23,456.78 with currency exponent validation (no silent rounding).

## Design note
Author: solution-architect (Opus). Status: ready for implementation.

**Layout and API** (pure Dart, `packages/zaghlol_parsing/lib/normalize/`; add `zaghlol_domain` workspace dep for `Money`, `Currency`, `Result`, `ParseFailure`; no other deps). Export through `zaghlol_parsing.dart`.
- `text_normalizer.dart`: `String normalizeText(String)` (display-safe), `String foldForMatching(String)`, `String foldKey(String)`.
- `amount_parser.dart`: `enum NumberLocale { standard, eu }`; `Result<Money, ParseFailure> parseAmount(String token, {required Currency currency, NumberLocale locale = standard})`; `Result<Money, ParseFailure> parseMoneyText(String text, {Currency? fallback, NumberLocale locale})` (finds symbol/ISO code before or after the number, then calls `parseAmount`).
- `currency_markers.dart`: const table symbol to code. `$ £ € ₹ ₺` map to USD GBP EUR INR TRY. `﷼` and `$` are ambiguous across currencies, so the symbol is used only if `fallback` agrees or is null (USD for `$`); `﷼` with no `fallback` fails. A 3-letter code resolves through `Currency.tryOf`. Arabic names (`جنيه`, `ج.م`) are template data, not here.
- Every function is pure, total and never throws; failures never carry the input text (NFR-SEC-03).

**Character maps** (applied in one pass over code units)

| Input | Output | Level |
|---|---|---|
| U+0660-0669, U+06F0-06F9 | `0`-`9` | normalizeText |
| U+066B `٫` | `.` | normalizeText |
| U+066C `٬` | `,` | normalizeText |
| U+00A0, U+202F, U+2009 | space | normalizeText |
| U+200B-200F, U+202A-202E, U+2066-2069, U+061C, U+FEFF | removed | normalizeText |
| runs of whitespace | one space, trimmed | normalizeText |
| U+0640 tatweel; U+064B-0652, U+0670 harakat | removed | foldForMatching |
| `أ إ آ ٱ` to `ا`; `ى` to `ي`; `ة` to `ه` | folded | foldKey only |

The Arabic comma `،` is not mapped (it is prose punctuation). Folding is for matching and keys only: the stored body, display strings and merchant display names never go through `foldForMatching` or `foldKey`. `foldForMatching` = `normalizeText` + tatweel/harakat. `foldKey` = `foldForMatching` + letter variants + lowercase ASCII. All three are idempotent.

**Amount grammar** (input is the numeric token after `normalizeText`; sign is stage 3's job, so `-` or `+` fails):
`number = D ( sep D )*`, where `D` is one or more digits. A leading or trailing separator fails. The segments between separators must fit one pattern:
1. no separator: `\d+`;
2. Western grouping: `\d{1,3}(,\d{3})+`, optionally followed by one decimal part;
3. Indian grouping: `\d{1,2}(,\d{2})+,\d{3}`, optionally followed by one decimal part;
4. decimal only: `\d+` + decimal separator + `\d+`.
Space is not a thousands separator, so `1 234` fails.

**Locale disambiguation.** The thousands and decimal characters come only from the `NumberLocale` flag (`standard`: `,` thousands, `.` decimal; `eu`: swapped). Digit counts are never used to guess. Consequences:
- `1,234` (standard) is 1234 for every currency, including KWD.
- `1.234` (standard) is a decimal, so it is 1.234 KWD. For EGP it fails with `excessPrecision`; it is never read as 1234.
- Under `eu` the two cases swap.
- `1.234,56` under `standard` fails (malformed), because EU is allowed only when the template declares `locale: eu`. `1,234.56` under `eu` fails likewise.
- A repeated decimal character (`1.234.567` in standard), grouping out of pattern (`1,2345`, `12,34,5`) and a mixed order all fail.

**Exponent validation.** Split into whole and fraction digits, then check `fraction.length` against `currency.exponent`:
- Trailing zeros beyond the exponent are dropped, because that is lossless (`JPY 1500.00` gives 1500; `EGP 12.500` gives 12.50).
- Any other digit beyond the exponent returns `Err(ParseFailure(ParseFailureReason.excessPrecision))`. There is no rounding anywhere.
- Short fractions are padded (`KWD 12.3` gives 12300 minor).
- Then call `Money.tryParse(canonicalString, currency)`; a null result (out of range, over `maxMinor`) returns `malformedAmount`.
- Do not use `double` or `num.parse` for money.

**Edge cases:** empty input; token length over `Money.maxParseLength`; digits plus Latin text such as `12abc`; `0` and `0.00` (valid; the caller decides whether zero is plausible); `٫٥٠` (no leading digit, fails); mixed Arabic-Indic and ASCII digits in one token (accepted, as digits are mapped first); amount touching a sentence full stop (`EGP 150.` fails, so template regexes must exclude the trailing dot).

**Test plan** (`packages/zaghlol_parsing/test/normalize/`, no new dev deps; seeded `dart:math` Random)
- Table-driven, one row per format: the AC cases (`١٬٢٥٠٫٠٠` to 1250.00 EGP; `KWD 12.345` to 12345); `$ £ € ₹ ₺ ﷼`, ISO code before and after; `1,234.56`; `1.234,56` (eu); `1,23,456.78`; exponent 0, 2 and 3 currencies; extended digits; the full ambiguity matrix above (standard x eu x EGP/KWD/JPY); failure rows asserting the reason. Normalizer rows cover every mapping in the table, including a tatweel and harakat case and an RTL-mark-wrapped number.
- Property (round-trip): for 2,000 random (currency from `Currency.all`, minor in `[0, maxMinor]`, style in {ascii-western, arabic-indic, extended, indian, eu, no grouping}, symbol position) cases, `parseMoneyText(format(m)) == m`. The test-only formatter lives in `test/support/`. Negative property: exponent+1 digits with a non-zero last digit always gives `excessPrecision`.
- Fuzz: random Unicode strings never throw; normalizers are idempotent; `foldKey` output contains no code point from the removed or folded sets; failure `toString` never contains the input.

**Rejected:** heuristic separator guessing from digit count (silent misreads such as `1.234` EGP); one monolithic normalizer (the display and matching levels would blur); a `double` intermediate; a third-party intl parser (locale tables are too permissive, and it adds a dependency).

**Open question (non-blocking):** `ParseFailureReason` (T-014, `packages/zaghlol_domain/lib/core/failure.dart`) has no precision reason. `Failure` is sealed, so the parsing package cannot subclass it. Implementer adds one enum value, `excessPrecision` (code `PARSE_EXCESS_PRECISION`), in this task and fixes any exhaustive switches. Syntax, grouping, locale and range errors reuse `malformedAmount`.

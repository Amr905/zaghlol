**PO, 2026-11-28 19:21:** "the vibration is pretty weak and not felt". Target: Duolingo-like — clearly felt, crisp, never buzzy.

## Likely causes (check each, write findings in the task file)
1. The Dart beat table (`app/lib/core/ui/z_haptics.dart`) uses low intensities (ticks at 30–60 %), and `PRIMITIVE_TICK` at scale 0.3–0.6 is barely felt on most phones.
2. Android `HapticsPlan.kt` waveform pulses are 15/25/45 ms — too short for many ERM/LRA motors to spin up.
3. `VibrationAttributes`/`AudioAttributes` usage: if the vibration is played as USAGE_TOUCH it is scaled by the user's (often low) "touch feedback" intensity; check what `HapticsRegistration.kt` uses and pick the usage that is felt but still respects the user's settings (Android 13+: `VibrationAttributes.USAGE_MEDIA` or `USAGE_ALARM` are not appropriate; prefer `USAGE_HARDWARE_FEEDBACK`/`USAGE_PHYSICAL_EMULATION` only if they apply; document the choice).
4. iOS `HapticsHost.swift` intensities/sharpness too low.

## Scope
- Raise the table: tick ≥ 70 %, click 90–100 %, thud 100 %; prefer CLICK/HEAVY over TICK for the payday coin beats (keep the rising feel by intensity 70→100); birdTap = one crisp CLICK at ~80 %; saved = CLICK 90 + CLICK 100; oops = two THUD 100.
- Android: Composition primitives with scale ≥ 0.7 (use `PRIMITIVE_QUICK_RISE`/`PRIMITIVE_THUD` for the payday "pop" if supported); waveform fallback pulses ≥ 30/45/80 ms with amplitude ≥ 180 (or DEFAULT_AMPLITUDE when the phone has no amplitude control); on phones without amplitude control use `createOneShot`/`EFFECT_HEAVY_CLICK`/`EFFECT_CLICK` predefined effects rather than returning false.
- Dart fallback (`HapticFeedback`): map tick→`mediumImpact`, click→`heavyImpact`, thud→`heavyImpact` (light impacts are too weak).
- iOS: intensity 0.7–1.0, sharpness 0.5–0.8 per strength; impact generator style `.medium`/`.heavy`/`.rigid`.
- Keep: «الاهتزاز» setting off → nothing; reduce motion → one beat; system touch feedback off → silent.
- Kotlin/Swift compile only in CI: push the same commit once to `ci/T-300` (don't wait).

## Acceptance criteria
- Dart test: every beat ≥ 70 %; fallback mapping as above.
- `HapticsPlanTest.kt`: scales ≥ 0.7, waveform pulse lengths and amplitudes as above, predefined-effect path for no-amplitude phones.
- Device feel check owed to the PO (write the steps).

## Design note (builder)
Findings per suspected cause:
1. Confirmed. Ticks were 30-60 %, birdTap 60 %, oops 60 %. New table: every beat 70-100 %; payday coins are CLICKs rising 70 to 96, pop THUD 100, tail click 75 + tick 70; saved 90/100; oops 100/100; birdTap click 80. Dart fallback: tick medium, click and thud heavy.
2. Confirmed. Pulses were 15/25/45 ms at amplitude pct*2.55. Now 30/45/80 ms, amplitude floor 180. Primitive scale floor 0.7 (`HapticsPlan.MIN_SCALE`).
3. Usage: `play` calls `vibrate(effect)` with no attributes, i.e. USAGE_UNKNOWN, which the system does not scale by the "touch feedback" intensity; the user's touch-feedback switch is still read by hand (`HAPTIC_FEEDBACK_ENABLED`, off means silent). So this was not a cause and I left it unchanged. USAGE_TOUCH was not adopted because it would bring back the low-intensity scaling the PO complained about; USAGE_MEDIA/ALARM are inappropriate. Not verified on a device (no device here).
4. Confirmed. iOS intensity is clamped to 0.7-1.0, sharpness 0.5-0.8 (tick 0.8, click 0.65, thud 0.5), impact fallback tick medium, click rigid, thud heavy.
No-amplitude phones: single beat uses `createPredefined` (EFFECT_CLICK for tick, EFFECT_HEAVY_CLICK otherwise, API 29+); multi-beat uses on/off timings; it no longer returns false while a vibrator exists.

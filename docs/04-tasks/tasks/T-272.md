## Description
Write the shared, versioned contracts first so backend and app lanes can build in parallel against fakes:
1. `backend/contracts/ask-plan-v1.schema.json`: envelope `{v, plan, p, t}`; `p` an `anyOf` of one closed object per plan (all fields required, `null` for unused, `additionalProperties:false`), common types Period/Filter/Amount, placeholder pattern with U+27E6/U+27E7.
2. `backend/contracts/cat-result-v1.schema.json`: `{"r":[{"i":int,"c":<enum>,"p":0..100}]}`; the `c` enum is injected at runtime from the live system categories + `unknown` (documented in the file).
3. Vectors: `vectors/ask-plan-v1.json` (valid and invalid plans, each with the sent question text, `lang`, expected outcome, and for invalid ones the failing §2.4 step and reason code; include text-normalisation cases for the `mention` substring rule); `vectors/ask-binding-v1.json` and `vectors/cat-binding-v1.json` (installId + body → JCS bytes hex, `bodyHash`, Play `requestHash` b64u, App Attest `clientDataHash`).
4. OpenAPI: `POST /v1/ask/plan`, `POST /v1/categorise`, sync request `llmCatFeedback`, sync response `config` block, problem extensions `quota` and `providerId`, codes `LLM_QUOTA_EXHAUSTED`, `LLM_CONSENT_REQUIRED`, `LLM_SERVICE_PAUSED` (plus existing `DEVICE_ATTESTATION_FAILED`, `RATE_LIMITED`, `UPSTREAM_UNAVAILABLE`). Regenerate DTOs with the in-repo generator.
5. Fake-backend fixtures `backend/contracts/fixtures/ask-plan-responses-v1.json` and `categorise-responses-v1.json`: one 200 per plan variant and per categorise status, one problem body per error code. Used by backend tests, app fakes and device E2E.

## Acceptance criteria
1. A contract test validates every valid vector against the schema and rejects every schema-level invalid vector (§2.4 step 1); vectors cover every plan in §2.2's table, every §2.3 rejection class and the §10 examples of the SRS (PL-COMPARE, PL-AVERAGE, PL-WHATIF-CUT percent 150 → invalid, unknown plan `PL-TRANSFER` → invalid, plain `account:"CIB"` → invalid, `⟦CARD_2⟧` not in the sent text → invalid).
2. The schema uses only keywords accepted by OpenAI strict structured outputs, Vertex `responseJsonSchema` and Anthropic structured output; any exception is listed in the file's `$comment` with the adapter workaround.
3. Binding vectors are reproducible: a .NET test recomputes every vector from its inputs byte-exactly (JCS per RFC 8785).
4. OpenAPI request bodies are closed (`additionalProperties:false`); `q` 1…300, `merchants` 1…20 unique 2…64 chars, `llmCatFeedback` ≤ 50; the DTO regeneration check is green and the generated Dart/.NET files are committed.
5. Every fixture response validates against the OpenAPI schema (test).
6. All data in vectors and fixtures is synthetic.

## Design note (provider keyword subset, as built)
- Used keywords only: `type` (incl. `[T, "null"]`), `properties`, `required`, `additionalProperties:false`, `enum` (single-value enum instead of `const`), `anyOf` (nullable objects and the `p` union), `$defs`/`$ref`, `pattern`, `minimum`/`maximum`, `minItems`/`maxItems`. Not used: `oneOf`, `allOf`, `not`, `if/then/else`, `const`, `uniqueItems`, `minLength`/`maxLength`, `format`. Root is an object. Source: OpenAI strict structured-output docs (read 2026-11-26): `anyOf`, `pattern`, number bounds and `minItems`/`maxItems` supported, root `anyOf` and `allOf`/`not`/`if` unsupported, 10 levels and 5 000 properties.
- Exceptions (also in the schema `$comment`): Anthropic ignores numeric bounds and `minItems`/`maxItems` and budgets 16 union parameters (schema exceeds it; not a launch provider); Gemini documents no `pattern`; OpenAI does not document `minLength`/`maxLength`, so mention length is a bounded-repeat pattern and template length/lang/NFC are step 6 rules (a bad template must drop only `t`).
- The `anyOf` cannot tie `plan` to `p`, so step 5 requires `p` to validate against `$defs/P_<plan>` (`PLAN_MISMATCH`).

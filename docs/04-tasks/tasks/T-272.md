## The PO's case
Salary arrives in USD (income in USD, D-85). He spends in EGP after exchanging. Today the EGP side shows spending with almost no income, because (a) the USD salary lives on the USD page only and (b) an exchange pair is excluded from income and spending in both currencies (FR-CUR-06), and bank FX-conversion messages have no handler (`fx_conversion` "until T-089").

## Scope
1. **Month "money in" per currency** (domain, pure): income + **exchanged in** (the receiving leg of an exchange pair in that currency) − nothing else; "money out" = spending + **exchanged out** shown separately, never as spending. An exchange is never income and never spending in reports by category; it is a third kind ("exchange"). Totals reconcile: per currency, opening + in − out = closing.
2. **Home/month read model** for the primary currency: money in = income + exchanged in; "left" grows by the EGP received. A typed budget is unchanged (Q1).
3. **Ingest:** handle the `fx_conversion` event (two legs in one multi-currency account, `transfer_pairs.kind = fx_conversion`, FR-PAR-12) instead of "no handler"; keep amounts exact in each currency; store the bank's rate when the message gives it (derive from the two amounts otherwise) without a schema change if the pair/transaction already has a place for it — if a column is needed, stop and write why.
4. **Cross-bank / exchange-office exchanges:** when a USD transfer out and an EGP credit appear within 3 days and the implied rate is plausible (within a wide band around the last known rate, or any band when no rate is known), raise ONE review suggestion "Is this EGP x the USD y you exchanged?" (existing `cross_currency` pair kind and suggestion machinery); accept pairs them, decline never asks again for that pair. Never auto-pair across banks (Q4).
5. **Manual "I exchanged money"** (data + minimal entry point in the Add sheet list if a slot exists; otherwise a repository method with tests and note the UI for T-273): from account/currency/amount → to account/currency/amount, date; creates the pair.
6. Payday/salary logic unchanged (D-85). Zakah/net worth unchanged (balances already per currency).
7. Strings ar (Egyptian colloquial; the period is شهر) + en for any new label.

## Acceptance criteria
Domain tests for the PO's story (plan §2 numbers): USD 1,000 salary → USD income 1,000; exchange USD 600 → EGP 29,700: EGP month money in 29,700, USD exchanged out 600, USD left 400; no income/spending category total changes; nothing counted twice. Ingest test for an `fx_conversion` SMS fixture (synthetic). Suggestion test (offer once; accept; decline). Existing transfer-pairing, budget and charts tests stay green. Max 3 negative proofs (an exchange never appears as income or spending; unpaired legs are not silently counted as both).

## Design note (builder)

**Where an exchange lives.** An exchange is a complete `transfer_pairs` row of kind `fx_conversion` (same institution, one message) or `cross_currency` (two accounts, linked by the user or by an accepted suggestion). Both legs stay `is_internal = 1`, so every existing spend/income/category/chart query that excludes internal rows keeps excluding them (no change there). No schema change: the bank's rate is the ratio of the two stored legs (`impliedRateE9(sent, received)`, integer, 1e-9 units), so it is exact and needs no column. `original_amount` is not reused for it.

**Cycle engine (pure, `zaghlol_domain`).** `CycleTxn.isExchange` marks a leg of a complete exchange pair. `aggregateCycle` adds, per currency, `exchangedIn` (live posted/pending `transfer_in` legs) and `exchangedOut` (`transfer_out` legs). A leg counts as exchange only when it is internal **and** in a complete exchange pair; an unpaired leg stays ordinary income/spend (as today) and is never counted twice. New derived figures on `CycleTotals`: `moneyIn = income + exchangedIn`, `left = moneyIn − spend − exchangedOut`. `income`, `spend`, `byCategoryMinor` are untouched by an exchange. A currency whose only activity is an exchange now gets a totals entry (zeros plus the exchange). Per currency: opening + moneyIn − (spend + exchangedOut) = closing, all in that currency.

**Data.** `CycleRepository.loadRows` reads `is_exchange` with an `EXISTS` on `transfer_pairs` (complete pair, kind in the two exchange kinds). The `cycle_summaries` cache has no column for it, so cached (closed) cycles get the exchange figures overlaid from a small live query of exchange legs only; old cache rows therefore need no invalidation or migration.

**Home.** `HomeCurrencyFigures`: the income KPI shows `moneyIn`, with one muted line «منهم {amount} من تحويل عملة» when `exchangedIn > 0`; the spent KPI keeps spending and gets a muted «وحولت {amount}» line when `exchangedOut > 0`; "left" (`net`) is `left`. Budget, safe to spend and the budget bar are unchanged (Q1). Progress without a budget uses `moneyIn`. Cards, the per-currency view and the ≈ line are T-273.

**Ingest.** `fx_conversion` gets a handler (`ExchangeEvent` disposition). Contract (as both shipped templates already capture it): `amount`/`cur` = money sent, `oamount`/`ocur` = money received. One raw row, two legs in the one resolved account (kind `multi_currency` when new), one `fx_conversion` pair written in the same savepoint (both internal). Missing received amount or the same currency on both sides → review (`unrecognized`), nothing stored as money. A possible cross-channel duplicate of the sent leg is stored with a `possibleDuplicate` review item (never merged, so no leg is lost); user-confirmed input with a match returns `IngestPossibleDuplicate` as for other events. Re-parse turns old `reparse_pending` conversions into exchanges.

**Suggestions (cross-bank, Q4).** The existing `fx_pair_suggestion` path keeps "suggest, never auto-pair". Band: with a known rate the amounts must agree within **15 %** (was 3 %); with no rate at all any amount qualifies; window stays 3 days. One open item per leg pair (existing), accept = `acceptFxPair` → `cross_currency` pair, dismiss is remembered (existing).

**Manual exchange.** `TransferPairingUseCase.recordExchange(...)`: in one DB transaction inserts the `transfer_out` and `transfer_in` legs (source `manual`, user-verified) and the pair (`fx_conversion` when one account, else `cross_currency`); different currencies and positive amounts required. The Add-sheet entry and form are left to T-273 (no free slot without redesigning the sheet that T-264 is changing).

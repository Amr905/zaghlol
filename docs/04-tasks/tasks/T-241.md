## Design note (builder)
Core safety property: a due reminder or statement is **never** a transaction and never auto-saved, whatever path read it.
- **Type-level separation.** New sealed result `ParseNotice` (kind `ccDue` / `ccStatement`, last-4, amount due, minimum due, due date, statement date, source template or generic). `ParseParsed` is never produced for `cc_due`/`cc_statement`; the pipeline turns those template events into `ParseNotice`. Every exhaustive switch over `ParseResult` in the app had to be extended, so no path can fall through to "save".
- **Registry.** Events `cc_due`, `cc_statement` (must declare direction `neutral`, lint-enforced); groups `mindue`, `duedate`, `stmtdate` (`amount` = total due); `date.yearPolicy: nearest_future` applies to `duedate` only, `date`/`stmtdate` stay nearest past.
- **Generic notice gate** (before amount ranking, after the decline check): future-deduction / due / statement cues, evaluated on the text with boilerplate tails cut (`يمكنك الاطلاع`, `للمزيد اتصل`, `please ignore if paid`). Gate hit gives `ParseNotice` (best effort last-4, amount only when unambiguous). A gate cue next to a strong past-tense purchase cue is `genericNoticeConflict` (unrecognized, review), never saved either way. Past-tense `تم الخصم ... لسداد` has no gate cue and stays a payment.
- **Eligibility.** `genericAutoSaveEligible` takes a `ParseResult` and is false for anything that is not a `ParseGeneric`.
- **Ingest.** `ParseNotice` stores a raw row (status `parsed`), writes no transaction, no review item, and calls `CardNoticeHook` (no-op default; T-245 implements) inside the message savepoint. New outcome `IngestNotice`. Reparse of a stored row never converts a notice into a transaction.
- **Negative proofs (3):** (1) eligibility false for a CIB due notice read generically; (2) ingest of cases 7, 8, 12 writes zero transactions; (3) a gate-shaped generic message with a purchase cue never reaches auto-save.

## Builder assumptions
- A gate cue beside a strong purchase cue goes to review (`genericNoticeConflict`), not to a notice: a possibly real transaction is never silently swallowed, and never saved.
- Generic notices have no due date (only templates read dates); the amount is set only when exactly one distinct amount is found.
- A stored review row that is now read as a notice stays in review (reparse stamps it); only new messages follow the notice path.
- Notice kept as raw `parsed` with no review item; the dues layer (T-245) owns surfacing it.

## Problem
On `main`, CIB's due reminder (case 7) and statement (case 8) come back from the generic reader as an expense with a direction, an amount and a last-4, which `genericAutoSaveEligible` (`packages/zaghlol_parsing/lib/generic/generic_policy.dart`) accepts, so they can be auto-saved as spending. HSBC's statement (case 12) is unrecognized. Undated due dates get the past year (2025-11-25).
## Scope (plan §4.1)
1. New template events `cc_due` and `cc_statement` (registry schema, models, lint, guard export). Parsed fields: card last-4, amount due (total), minimum due, due date, statement date, currency. New named groups as needed (`due`, `mindue`, `duedate`, `stmtdate`).
2. A **notice gate** in the generic reader before amount ranking: future deduction cues (`سيتم خصم`, `will be debited`, `payment due`, `pay by`, `موعد السداد`) or statement cues (`كشف حساب … هو`, `statement date`, `total amt due`, `min. amt due`, `الحد الادني للسداد`) → a notice result, never a transaction. `genericAutoSaveEligible` returns false for notices. Watch for real transactions that share wording ("تم الخصم … لسداد" past tense stays a payment).
3. Templates: `cib.cc_due.ar` (case 7), `cib.cc_statement.ar` (case 8), `hsbc.cc_statement.en` (case 12). Boilerplate tails (`يمكنك الاطلاع…`, `please ignore if paid`) are not part of any field.
4. Date year policy `nearest_future` for due dates (template `date.yearPolicy`); statement and transaction dates stay `nearest_past`.
5. Ingest: a notice result is stored as a raw message with status parsed and **no transaction**; the parsed due is handed to the dues layer through a new hook that T-245 implements (here: a no-op default plus a test that no transaction row is written). Existing per-bank due/statement **drop** patterns for these banks are removed so the messages arrive.
6. `registryVersion` bump.
## Acceptance criteria
PO cases 7, 8, 12 pass (pending markers removed); ingest test: each of the three gives zero transactions and is never auto-saved; a past-tense CIB card payment fixture still saves as `cc_payment`; negative proofs (max 3): an auto-save eligibility test for a due notice from a known bank returns false; registry lint green; `dart test` in the package and the ingestion tests in `app` green.

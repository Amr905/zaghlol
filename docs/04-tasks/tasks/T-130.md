## Description
Server-side verify and acknowledge Android purchases, plus the live Play order-ID lookup used by support.

## Technical details
- **Verify (Android, §4.3):** product table lookup (`422 PURCHASE_WRONG_APP`); subscriptions → `purchases.subscriptionsv2.get`, lifetime → `purchases.productsv2.getproductpurchasev2` (v1 `products.get` not used); product ID returned by Play must match (`422 PURCHASE_TOKEN_INVALID`); `ACTIVE | IN_GRACE_PERIOD` or `PURCHASED` only (pending → `pending`, no Gold); `environment = sandbox` from `testPurchase` / `testPurchaseContext`; `obfuscatedExternalAccountId == StoreBindingRef(installId)` (verify only; `PURCHASE_NOT_OWNED`; design note §5); upsert by token, recording `linked_purchase_token`; acknowledge via `purchases.subscriptions.acknowledge` / `purchases.products.acknowledge` with the Play-returned product ID; 15-min sweeper; alert at 48 h unacked; Polly resilience (`502 STORE_UNAVAILABLE` on open circuit, per OpenAPI; Lead decision 1 below).
- Exposes a `IStoreVerification` result consumed by T-132 (seat at verify, entitlement) and T-185 (restore re-verification without the install-binding check).
- **Ownership lookup for support (D-57, §5.3):** `IPlayOrderLookup.CheckAsync(orderId, purchase)`:
  - **First confirm** that Play Developer API `orders.get` is available to the app's developer account and returns `purchaseToken` (record the evidence in the task file). If yes: the order's `purchaseToken` must be the purchase's token or one in its `linkedPurchaseToken` chain, and its `state` not `CANCELED`, `REFUNDED` or `PENDING_REFUND`.
  - **Fallback (R4-7, R5-8)** if not: compare the order ID with `subscriptionsv2` **`lineItems[].latestSuccessfulOrderId`** of the purchase's token and of each token in the `linkedPurchaseToken` chain (subscriptions), or the `productsv2` order ID (lifetime), together with the purchase state. **The deprecated `latestOrderId` is never read.**
  - Outcomes `pass | fail | unavailable`. The order ID is a `[Sensitive]` value: held in memory for the call only, never stored, logged, traced or put in an exception message.
- **Play Integrity decoding is not here**: it moved to T-181.

## Design note
*solution-architect (Opus), 2026-11-11. Inputs: backend-api §1, §4.3, §4.5, §5.3, §6; backend-schema `purchases`, `idempotency_records`; ADR-012 Part A; error-handling-and-observability §2–4; T-124 security review S-2…S-6 (FU-052); OpenAPI `verifyPurchase`.*

**0. Scope and boundaries.**
- **T-130 owns:** the `POST /v1/purchases/verify` route (Android branch) with `WithIdempotency`; the Play client; product allow-list; install-binding check; `purchases` upsert; inline acknowledge; the ack sweeper (Workers); the 48 h alert; the shared Play call budget; `IPlayOrderLookup`; the idempotency S-2 fix.
- **Not T-130:**
  - seat decision and entitlement token: T-132 through T-184, via a port;
  - iOS: T-131 (`platform: ios` returns `503 UPSTREAM_UNAVAILABLE` until T-131 registers its verifier);
  - RTDN receiver and voided reconciliation: T-133 (reuses the Play client and `PurchaseWriter`);
  - restore: T-185 (calls the verifier with `BindingCheck.Skip`);
  - support endpoints and audit rows: T-186 (calls `IPlayOrderLookup`);
  - Play Integrity: T-181.
- **Ports (Application/Purchases):**
  ```csharp
  public interface IStoreVerification {            // one per store; T-131 adds AppStore
    Task<StoreVerificationResult> VerifyAsync(StorePurchaseRef r, InstallId caller, BindingCheck b, CancellationToken ct); }
  public enum BindingCheck { RequireCaller, Skip }   // Skip only from restore (T-185)
  public sealed record StoreVerificationResult(
    VerifyStatus Status,            // Active | Pending | Expired | Refunded | Invalid
    string? ProblemCode,            // PURCHASE_TOKEN_INVALID | PURCHASE_NOT_OWNED | PURCHASE_WRONG_APP | null
    Guid? PurchaseId, Plan Plan, DateTimeOffset? ExpiresAt, StoreEnvironment Environment,
    Guid? PredecessorPurchaseId,    // linkedPurchaseToken names a known purchase -> T-184 "new payment" rule
    bool Acknowledged);
  public interface IVerifyGrant { Task<VerifyGrantResult> ComposeAsync(StoreVerificationResult v, VerifyContext c, CancellationToken ct); }
  ```
  - The default `NullVerifyGrant` returns `entitlement: null` and no seat change, following T-128's `NullSyncEntitlementBlock` pattern.
  - A startup check refuses Production while `NullVerifyGrant` (or no iOS verifier) is registered, so verify can't ship without T-132.
  - Store failures throw `StoreUnavailableException` (a `SafeException`); they are never a result value.

**1. Verify procedure (Android).** Each step runs only if the previous one passed. Nothing is written before step 5.
1. **Request checks:** the OpenAPI shape, plus `purchaseToken` matching `^[A-Za-z0-9._-]{1,512}$`.
   - Longer than 512 or another character: `422 PURCHASE_TOKEN_INVALID` with no Play call. The schema caps `store_key` at 512 (OpenAPI says 2048; doc fix below).
   - The token is always URL-escaped into the path.
2. **Allow-list:** `Purchases:Google:PackageName` and `Purchases:Google:Products` (`productId → {type: subscription|onetime, plan}`), bound from config and validated at startup.
   - Exactly the three IDs; Production refuses an empty list or a test package.
   - An unknown `productId` is `422 PURCHASE_WRONG_APP`. The package name never comes from the request.
3. **Play read:** subscriptions call `subscriptionsv2.get`; lifetime calls `productsv2.getproductpurchasev2`. The v1 `products.get` and `subscriptions.get` are not in the client at all, so they can't be called.
   - DTOs (source-generated System.Text.Json) declare only the fields we read: `subscriptionState`, `lineItems[].{productId, expiryTime, latestSuccessfulOrderId}`, `linkedPurchaseToken`, `acknowledgementState`, `testPurchase`, `externalAccountIdentifiers.obfuscatedExternalAccountId`, `startTime`; and `productLineItem[].productId`, `purchaseStateContext.purchaseState`, `testPurchaseContext`, `orderId`, `obfuscatedExternalAccountId`, `acknowledgementState`, `purchaseCompletionTime`.
   - `latestOrderId` is **not** declared.
   - **Play answers:**
     - `400`, `404` or `410`: `422 PURCHASE_TOKEN_INVALID` (a final result, stored);
     - `401` or `403`: our credential or permission is wrong. That is `502 STORE_UNAVAILABLE` plus `zaghlol.store.call{outcome=auth_error}` (alerted), **never** a 422 that blames the user;
     - `408`, `429`, `5xx`, timeout or open circuit: `502 STORE_UNAVAILABLE` with `Retry-After`, not stored.
4. **Match, binding and state:**
   - The Play product ID must equal `productId`; otherwise `422 PURCHASE_TOKEN_INVALID`.
   - **Binding (`RequireCaller`):** `obfuscatedExternalAccountId` must equal `StoreBindingRef(callerInstallId)` (§5), compared in constant time. If it is absent or different: `422 PURCHASE_NOT_OWNED`.
   - **State mapping:**

     | Play state | `purchases.state` | Verify status |
     |---|---|---|
     | `ACTIVE` | `active` | Active |
     | `IN_GRACE_PERIOD` | `in_grace` | Active |
     | `CANCELED` with `expiryTime > now` | `canceled_active` | Active |
     | `PENDING` | `pending` | Pending, no Gold |
     | `ON_HOLD` / `PAUSED` | `on_hold` / `paused` | Expired |
     | `EXPIRED` | `expired` | Expired |
     | `PENDING_PURCHASE_CANCELED` | not upserted | Invalid (`PURCHASE_TOKEN_INVALID`) |
     | products `PURCHASED` | `active` | Active |
     | products `PENDING` | `pending` | Pending |
     | products `CANCELLED` | `refunded` | Refunded |
     | anything unknown or unspecified | not written | `502`, never a grant |

   - The `CANCELED` and unexpired row extends §4.3 step 3 (doc fix below). `environment = sandbox` iff `testPurchase` / `testPurchaseContext` is present.
5. **Upsert (one short transaction, `app_rw`):** `INSERT … ON CONFLICT (store, store_key) DO UPDATE`, with a monotonic guard `WHERE purchases.last_verified_at < @readAt`. `@readAt` is taken **before** the Play call, so a slower read never overwrites a newer RTDN/T-133 read.
   - Writes `linked_purchase_token`, `obfuscated_install_ref`, `state`, `expires_at`, `environment` and `last_verified_at`.
   - Writes `install_id` **only on insert**: verify never changes the buying install.
   - Writes `acknowledged = true` when Play already says `ACKNOWLEDGED`.
   - Adds a `purchase_events` row (`cause = verify`) when the state changes.
   - Resolves `PredecessorPurchaseId` from `linked_purchase_token`. It never edits the predecessor (T-133 and T-184 own that).
6. **Acknowledge,** only for Active rows not yet acknowledged, outside any DB transaction:
   - `purchases.subscriptions.acknowledge` or `purchases.products.acknowledge`, with the **Play-returned** product ID (never consume).
   - On success, set `acknowledged = true` and record `time_to_ack` (from `startTime` / `purchaseCompletionTime`).
   - On failure, Gold is still granted: the purchase is valid and ack is our duty. The sweeper retries.
   - An ack error answer triggers a re-read; `ACKNOWLEDGED` counts as success.
7. **Grant:** `IVerifyGrant` (T-132) builds `{status, entitlement, seatHeldElsewhere, accountRequired, nextMoveAt}`. The signing middleware signs it, and the T-123 filter echoes `timeNonce`.

**2. Resilience and budget.**
- **Pipeline:** `Microsoft.Extensions.Http.Resilience` (Polly v8, 10.x; one new dependency, the in-box .NET standard pipeline).
  - Attempt timeout 5 s; 3 retries, jittered exponential from 400 ms, honouring `Retry-After` on 429/503.
  - Retries only on 408/429/5xx/`HttpRequestException`/timeout. Never on other 4xx.
  - Circuit breaker: failure ratio 0.5, minimum 10 calls per 30 s, break 30 s.
  - Total timeout 20 s.
  - Acknowledge is safe to retry (a repeat is resolved by the re-read).
- **Budget:** `IStoreCallBudget`, a `System.Threading.RateLimiting` token bucket with lanes `verify`, `ack`, `rtdn`, `support`, `restore`.
  - `restore` may use at most 30 % and is denied first, which gives restore `503 UPSTREAM_UNAVAILABLE` (§4.3).
  - When `verify` or `ack` is denied: verify gets `503 UPSTREAM_UNAVAILABLE` + `Retry-After`; the sweeper skips to its next run.
  - The bucket size is config, sized under the Play Developer API daily quota (200 K/day by default, PO question 4).
- **Never grant on doubt:** an exception, unknown enum, timeout or open circuit leaves the row unchanged and grants nothing.

**3. Ack sweeper (`PlayAckSweeperService`, Workers, `worker_rw`).**
- Every 15 min it takes `pg_try_advisory_lock('play-ack-sweeper')` on one dedicated connection (a single sweeper across replicas; if the lock is busy, it skips).
- It reads up to 200 rows from `ix_purchases_unacked`, due rows only (`ack_next_attempt_at` NULL or passed), ordered `(state = 'pending'), ack_next_attempt_at NULLS FIRST, created_at`, in a short read with no transaction held.
- A row the run can't finish (still pending, skipped for an unknown product/state or mismatch, or a failed Play call) is deferred: `ack_next_attempt_at = now + clamp(age / 4, 15 min, 2 h)` (24 h past 72 h). Fix round for security M-1: stuck rows can't starve newer ackable ones.
- Per row, outside any transaction:
  - re-read Play;
  - if the state is now purchased or active, acknowledge;
  - if Play already shows `ACKNOWLEDGED`, set the flag;
  - if pending, wait;
  - if cancelled, refunded or expired, write the state and don't acknowledge.
  - Then a short update with the same monotonic guard.
- **Alert:** an observable gauge `zaghlol.purchase.unacked{age=lt_48h|ge_48h}`, recomputed each run from `created_at` of rows in an ackable state younger than 72 h (pending rows are excluded, their 3-day clock starts when they become purchased; rows past 72 h are excluded because Play has already refunded them). Any `ge_48h > 0` alerts and also fires `AlertFired("purchase_unacked_48h")`.
- `worker_rw` already has UPDATE on `state`, `expires_at`, `acknowledged`, `last_verified_at` and `linked_purchase_token`; migration `PurchaseAckNextAttempt` adds UPDATE on `ack_next_attempt_at` (no `ops_ro` grant, like `claim_id`).

**4. Idempotency fix (FU-052 S-2, with S-3, S-4, S-6).** The cause: the session holds a pooled connection, transaction and advisory xact lock while the handler opens a second connection and waits seconds on Play, so a full pool deadlocks.

**Decision: option (b), claim rows with a lease.** No connection is held while the handler runs.
- **Rejected (a), sharing the connection:** it still pins a connection and an open transaction through 5–20 s of Play calls, and the seat service's `FOR UPDATE` locks would be held as long.
- **Rejected (c), a separate pool:** it only moves the ceiling.

- **Migration:**
  - `idempotency_records` gains `claim_id uuid NULL`.
  - `status` CHECK becomes `status = 0 OR status IN (200..299, 409, 422)`, with `CHECK ((status = 0) = (claim_id IS NOT NULL))`.
  - `response_body_enc` may be empty when `status = 0`.
  - Grants are unchanged (app_rw SID; no UPDATE needed).
- **`TryClaimAsync`** (transaction 1, milliseconds), on `(install, op, key)`:
  1. Delete rows with `expires_at <= now`. A stale claim from a crashed request is taken over.
  2. `INSERT … SELECT … WHERE EXISTS (SELECT 1 FROM installs WHERE id=@i AND deleted_at IS NULL) ON CONFLICT DO NOTHING`, with `status 0`, `claim_id = new`, `body_sha256`, `expires_at = now + 60 s`. The EXISTS clause fixes S-4.
  3. If nothing was inserted, read the row:
     - a final row: compare the hash, then replay or `409`;
     - `status 0`: `429 Retry-After: 1`;
     - no install: `401`.
  4. Commit.
- **Handler:** runs with a hard `CancellationTokenSource` of 30 s, less than the 60 s lease, so a live handler never loses its lease.
- **`CompleteAsync`** (transaction 2):
  - `DELETE … WHERE claim_id=@mine AND status=0`, then, only if 1 row was deleted, `INSERT` the final row with the same EXISTS guard, `expires_at = now + 24 h`.
  - 0 rows (lease lost) means the result is returned but not stored, and `idempotency.claim{outcome=lease_lost}`.
- **`ReleaseAsync`** on 429, 5xx or an exception: `DELETE WHERE claim_id=@mine`, best-effort; lease expiry backs it up. A retry runs again at once.
- **S-6:** the envelope context becomes `idem/v2/<installId>/<op>/<b64u(SHA-256(key))>`. No production rows exist yet, so there is no v1 read path.
- **S-3:** idempotent handlers never take `IInstallTokenRotator` (architecture test). The filter also scans the captured top-level JSON: a non-null `rotateInstallToken` is not stored; it throws in Development/Testing and logs `errorType` in Production.
- `FindLive` / replay requires `status <> 0`. The existing `TryBeginAsync` and `Session` are removed, and `POST /v1/accounts/signin` (T-135) inherits the fix.

**5. Store binding value.** "HMAC(installId)" is not defined anywhere, and the app must compute it. The definition:
- **`StoreBindingRef(id)`** = the first 16 bytes of `HMAC-SHA256(key = ASCII "zaghlol-store-binding-v1", msg = lower-case 36-char installId)`, with RFC 9562 version 8 and variant bits set, formatted as a lower-case hyphenated UUID.
- **Uses:** Play `obfuscatedAccountId` (≤ 64 chars, not PII) and Apple `appAccountToken` (must be a UUID).
- **The key is a public domain separator; secrecy adds nothing.** The check compares the value against the install that the **token** authenticates, so knowing someone's ref doesn't let you act as them. Stamping someone else's ref onto your own purchase only gives them Gold you paid for.
- **Shared vectors:** `backend/tests/Zaghlol.Contract.Tests/vectors/store-binding-v1.json`, used by T-145 (Dart), T-131 and T-130.

**6. Ownership lookup (`IPlayOrderLookup`, D-57).**
- **`orders.get` evidence:**
  - Google's reference documents `orders.get`, with an `Order` that carries `purchaseToken` and `state ∈ PENDING | PROCESSED | CANCELED | PENDING_REFUND | PARTIALLY_REFUNDED | REFUNDED`. Orders calls count toward the Play Developer API quota (developers.google.com/android-publisher/api-ref/rest/v3/orders, read 2026-11-11).
  - **Account availability is not yet confirmed.** The implementer runs one `orders.get` with the production service account on a license-tester order and records the outcome here (AC 5).
  - **Evidence (implementer, 2026-11-11): not confirmed, not refuted.** No Play Console service account, credential or license-tester order exists yet (PO questions 1 and 5), so the live call could not be made from the implementation workspace. Both paths ship behind `Purchases:Google:OrderLookup`, default `fallback`, which needs only `subscriptionsv2`/`productsv2` (already required by verify). Whoever runs the live smoke test (PO question 5) runs one `orders.get` on the tester order and records here: HTTP status, whether `purchaseToken` is present, and the `state` value; only then may `OrderLookup=orders` be set.
  - Until then the code ships both paths behind `Purchases:Google:OrderLookup = orders|fallback` (default `fallback`).
- **`orders` path:**
  - pass when `purchaseToken ∈ chain(purchase)` and the state is not `CANCELED`, `REFUNDED`, `PENDING_REFUND` or `PENDING`;
  - `PARTIALLY_REFUNDED` passes (the task excludes only the listed states).
- **`fallback` path:**
  - walk `chain` = the purchase's token plus `linked_purchase_token` from the DB and each Play read, at most depth 10, with cycle detection;
  - pass iff some `lineItems[].latestSuccessfulOrderId` (subscriptions) or the `productsv2` `orderId` (lifetime) equals the order ID, in constant time, **and** that read's state is Active.
- **Outcomes:** a Play 404 on the order is `fail`. A Play 5xx, timeout, open circuit or an exhausted `support` budget is `unavailable`.
- **Order ID handling:**
  - the order ID is a `Sensitive<string>` that lives only in the call frame;
  - the outbound URL template is `/orders/{orderId}`;
  - no exception message, retry log or span attribute carries it.

**7. Credentials and config.**
- **Credentials:** `Google.Apis.Auth` (1.7x, maintained; used only to mint OAuth tokens for scope `androidpublisher`). The Play client itself is a plain typed `HttpClient`, not `Google.Apis.AndroidPublisher.v3`, which gives:
  - DTOs with only the fields we read;
  - control of the URL redaction;
  - a configurable base URL for WireMock;
  - one dependency instead of two.
- **Credential source,** in order: workload identity federation or the platform identity (preferred, no key); otherwise the service-account JSON from the secrets manager (`Purchases__Google__Credential`), never a file in the repo.
- **Startup checks in Production:** the credential, package, products and Play base URL = `https://androidpublisher.googleapis.com` must be set; the fake client is refused; and nothing is echoed.
- **Service account permissions:** only what get, acknowledge and orders need (PO question 1).

**8. Logging and metrics.**
- **Never logged:** purchase tokens (only `tokenHash8`), order IDs, `obfuscatedExternalAccountId`, Play response bodies, the `Idempotency-Key` and the time nonce.
- **Outbound spans and Polly logs** use the templates `…/subscriptionsv2/tokens/{token}`, `…/productsv2/tokens/{token}`, `…/orders/{orderId}`.
- **Play errors** become `PlayApiException(api, outcome)`, a `SafeException` with constant messages; the response body is never read into the exception.
- **New instruments, each tag from a constant set:**
  - `zaghlol.store.call{store=google_play, api=sub_get|prod_get|sub_ack|prod_ack|orders_get, outcome=ok|client_error|auth_error|rate_limited|server_error|timeout|circuit_open|budget_denied}`;
  - `zaghlol.purchase.ack{channel=verify|sweeper, outcome=acked|already|failed|not_ackable}`;
  - `zaghlol.purchase.unacked{age}`;
  - `zaghlol.purchase.ownership_check{path=orders|fallback, outcome=pass|fail|unavailable}`;
  - `zaghlol.idempotency.claim{outcome=claimed|replayed|reused|in_progress|taken_over|lease_lost}`.
- **Existing instruments:** `zaghlol.purchase.verify{store, outcome, code}`, with `code` from `ErrorCodes` or `none`, and `time_to_ack`.

**9. Threats.**
- **Replay across installs:** the binding check returns `PURCHASE_NOT_OWNED`, and nothing is written.
- **Forged token:** never parsed locally; Play is the only judge (`400`/`404` → invalid).
- **Another app's or product's token:** the package is fixed server-side, plus the allow-list and the product match.
- **Sandbox token in production:** recorded as `environment = sandbox`; the policy is PO question 3.
- **Refund or chargeback:**
  - products `CANCELLED` or subscription expiry is caught at verify and in the sweeper;
  - voids and refunds come through T-133 RTDN and the daily `voidedpurchases.list`;
  - offline Gold is bounded by the entitlement `exp ≤ iat + 3 d` (T-132).
- **Verify racing a refund:** the monotonic `last_verified_at` guard.
- **Path injection through the token:** the regex plus escaping.
- **Quota exhaustion with junk tokens:** per-install and IP rate limits, the global budget with lanes, and the circuit breaker.
- **Credential theft:** least privilege, no key file where workload identity federation is possible, and the alert on `auth_error`.
- **Promo-code or out-of-app purchases have no binding:** verify gives `PURCHASE_NOT_OWNED`, and the app falls back to restore (attested, T-185).

**11. Rejected alternatives.**
- `Google.Apis.AndroidPublisher.v3`: a heavier surface, every response field deserialized, harder URL redaction.
- Acking only from the sweeper: it adds up to 15 min of delay and risk for no gain.
- Trusting `testPurchase` absence alone for production: the environment is recorded, not used as a gate.
- Storing order IDs to speed up support checks: forbidden by D-57.

**12. Doc fixes for the Lead.**
- (a) Task text and error-handling §2 say `503 STORE_UNAVAILABLE`, but OpenAPI maps `STORE_UNAVAILABLE` to **502**. This note follows OpenAPI: 502 for Play failures, 503 `UPSTREAM_UNAVAILABLE` for our own budget, KMS or DB.
- (b) The OpenAPI `purchaseToken` `maxLength: 2048` and the DB `store_key ≤ 512` disagree. Align OpenAPI to 512.
- (c) backend-api §4.3 step 3 should add "`CANCELED` with `expiryTime > now` → active (`canceled_active`)".
- (d) Define `StoreBindingRef` (§5 above) in backend-api §4.3, T-145 and T-131.

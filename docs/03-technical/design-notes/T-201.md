# T-201 design note: OpenBao Transit KMS (`Kms:Provider = OpenBao`, D-76 step 2)

Class C4 (keys, entitlements). Written before the code. Scope: the third KMS adapter, behind the T-200 seam (`IKmsBackend`, `SelectProvider`), so the API and the worker never hold a signing, HMAC or key-encryption key; the one-time migration from the T-200 `File` keys; the OpenBao server set-up; CI against a real OpenBao. ADR-023 records the decision; `deployment.md` §3 "OpenBao Transit KMS" holds the operator steps.

Sources checked (2026-11-20): OpenBao API docs (`/docs/api/secret/transit/`), the Transit and BYOK pages, and the OpenBao source (main branch, 2.7 line) (`sdk/helper/keysutil/policy.go`, `internal/builtin/logical/transit/path_{import,sign_verify,hmac,keys,decrypt}.go`). Facts the design depends on, all read from the source:

- `sign` with `marshaling_algorithm=jws` returns `vault:v<n>:` + **unpadded base64url** of `r‖s` (32 + 32 bytes, left-padded): IEEE P1363, what `Signer` already uses. With `prehashed=true` and `hash_algorithm` `sha2-256` (URL segment) the input is our SHA-256 digest.
- `hmac` returns `vault:v<n>:` + standard base64. For a key of type `hmac` the MAC key **is** the key; for any other type (e.g. `aes256-gcm96`) it is a separate random companion key of that version.
- `import` (`keys/:name/import`) accepts `type=hmac` (32–512 bytes, used as-is) and `aes256-gcm96` (raw 32 bytes). The ciphertext is `RSA-OAEP(SHA-256, label "")(ephemeral 32-byte AES key)` (512 bytes, 4096-bit wrapping key from `GET wrapping_key`) followed by `AES-KWP(ephemeral, key)` (RFC 5649), base64. .NET 10 has both (`RSA.Encrypt` with `OaepSHA256`, `Aes.EncryptKeyWrapPadded`).
- `decrypt` for AES-GCM keys splits `vault:v<n>:` + base64 into `nonce(12) ‖ ciphertext ‖ tag(16)` and authenticates `associated_data` (base64) as GCM AAD. That is **exactly** the T-200 File wrap (`nonce ‖ ct ‖ tag`, AAD `"zaghlol-file-wrap-v1" ‖ 0x00 ‖ keyRef`), so a File-wrapped data key opens in Transit once the File KEK is imported (§5).
- `GET keys/:name` returns `type`, `exportable`, `allow_plaintext_backup`, `deletion_allowed`, `latest_version`, `imported_key`, `soft_deleted`, `key_size` (hmac) and, for ECDSA, `keys.<version>.public_key` (PEM `PUBLIC KEY`). Never private material.
- Errors: JSON `{"errors":[…]}`. A sealed server answers `503`; a missing token, a bad token or a policy denial `403`; a bad request `400` (a missing key on `decrypt`/`hmac` is `400 "encryption key not found"`, a failed GCM tag `400 "cipher: message authentication failed"`).
- `seal "static"` (32-byte AES-256-GCM key from `file://…`, given raw, hex or base64, told apart by length) exists since OpenBao 2.4.0. We write it as 64 hex characters: a raw binary key may lose a leading or trailing white-space byte to trimming. Audit devices are declared in the server configuration (`audit "file" …`); creating them through the API is off unless `unsafe_allow_api_audit_creation = true`.

## 1. Where it plugs in

- `SelectProvider` gets one more case, `OpenBao` → `OpenBaoKms` (an `IKmsBackend`). The three ports, `Signer`, `KeyedHasher`, `EnvelopeCipher`, `KmsStartupCheck` and `SeatKeyStartupCheck` keep their contracts.
- Key references: `openbao:<name>`, `<name>` = the Transit key name (`[a-z0-9][a-z0-9-]{0,62}`, the File name rule). Signing kids are their own Transit keys (`openbao:s2027a`). The legacy envelope reference `file:<name>` is accepted **only** in `Kms:Envelope:PreviousKeyRefs` and is served by the imported Transit key `file-<name>` (§5). Any other prefix, or `file:` anywhere else, refuses the start.
- A provider-specific startup check, `OpenBaoStartupCheck` (a hosted service registered just before `KmsStartupCheck`, a no-op for other providers), proves the key attributes and the fingerprint pins before the generic ring check runs (§6).
- **Scope (new, `Kms:Scope = Full | Envelope`, default `Full`).** The worker only opens sealed Apple refresh tokens (T-135), so its OpenBao identity may only use envelope keys. With `Envelope`, `KmsStartupCheck` skips the public-key comparison, the signing probes and the HMAC probes (the envelope round trip stays), `OpenBaoStartupCheck` checks only envelope keys, and `OpenBaoKms` refuses `sign`/`hmac`/public-key calls with a configuration error. `Local` and `File` ignore the scope apart from the startup probes. The API keeps `Full` (a `SeatCheck` under `Envelope` fails, so a wrong API scope can't start).

## 2. Calls (all `POST` unless noted; `<m>` = `Kms:OpenBao:Mount`, default `transit`)

| Port | Request | Pinned fields | Answer used |
|---|---|---|---|
| login | `auth/approle/login` `{role_id, secret_id}` | – | `auth.client_token`, `auth.lease_duration` |
| `GetPublicKeyAsync` | `GET <m>/keys/<name>` | version `1` | `keys."1".public_key` → named P-256 → `04‖X‖Y` |
| `SignDigestAsync` | `<m>/sign/<name>/sha2-256` `{input, prehashed:true, marshaling_algorithm:"jws", key_version:1}` | key v1 | `signature` = `vault:v1:` + 86 base64url chars → 64 bytes |
| `HmacSha256Async` | `<m>/hmac/<name>/sha2-256` `{input, key_version:1}` | key v1 | `hmac` = `vault:v1:` + base64 → 32 bytes |
| `GenerateDataKeyAsync` | `<m>/datakey/plaintext/<name>` `{bits:256}` | latest | `plaintext` (32 bytes, decoded straight into the `DataKey` buffer), `ciphertext` (`vault:v<n>:…`, ASCII, stored as the wrapped key) |
| `DecryptDataKeyAsync` (`openbao:`) | `<m>/decrypt/<name>` `{ciphertext}` | – | `plaintext` (32 bytes) |
| `DecryptDataKeyAsync` (`file:`) | `<m>/decrypt/file-<name>` `{ciphertext:"vault:v1:"+b64(wrapped), associated_data: b64(File AAD)}` | v1 | `plaintext` |

- **Every signing and HMAC call names `key_version = 1`.** A kid is one Transit key at version 1; an accidental `rotate` can't change what signs (the startup JWK check and the per-signature verify catch a wrong key anyway) or which HMAC key hashes (stored hashes stay valid). Envelope keys may rotate inside Transit (new data keys use the latest version; old `vault:v<n>` wraps keep opening).
- Each answer is checked: exact prefix `vault:v1:` where pinned, exact decoded lengths (64, 32, 32), `ciphertext` ASCII starting `vault:v`, at most 1 KiB. Anything else → unavailable (never a partial value).
- Wrapped keys handed back to `decrypt` are checked locally first: an `openbao:` wrap must be ASCII `vault:v<digits>:<base64>` ≤ 1 KiB; a `file:` wrap must be 60 bytes. Otherwise `CryptographicException` (provably not a wrap we made; same rule as `FileKms`).

## 3. Transport, TLS and timeouts

- `Kms:OpenBao:Address`: absolute URI, no user-info, query or fragment, path empty or `/`. `https` everywhere; `http` only in Development/Testing (CI live tests with a local server). One `HttpClient` per provider over a `SocketsHttpHandler` with **`UseProxy = false`** (the KMS is never reached through a proxy), no redirects, no cookies, `ConnectTimeout` = the call timeout, pooled connections recycled every 5 minutes.
- **Pinned CA.** `ca.pem` in the credential directory (§4) is the *only* trust anchor: the certificate callback builds a chain with `X509ChainTrustMode.CustomRootTrust` over the certificates in that file (system roots ignored, revocation not checked: a private CA has no CRL), and refuses any name mismatch or missing certificate. A certificate from another CA, even a public one, is refused. TLS 1.2 and 1.3 only.
- Response bodies are read to at most 64 KiB into owned (not pooled) buffers, parsed with `JsonDocument` in place; the buffers are zeroed after use, request bodies too (best effort: .NET may keep other copies; the `string` token and `secret_id` can't be zeroed). No response text, error text, URL, key name or token ever reaches an exception message or a log.
- **Timeouts and 503.** Every adapter call runs inside the existing `KmsCall` (2 s per attempt, one retry, never cached). The adapter maps:

| OpenBao answer | Adapter throws | Caller sees |
|---|---|---|
| connect/TLS/IO error, timeout, `429`, `5xx` (sealed `503` included), `400`/`404`/other, malformed answer | internal transient error | after the retry `KmsUnavailableException` → `503 UPSTREAM_UNAVAILABLE` + `Retry-After: 5` (`ResponseSigningTests`) |
| `403` | re-login once (only if the token used is still the current one), then the same request once; a second `403` → transient | as above |
| `decrypt` `400` whose only error is `cipher: message authentication failed` | `CryptographicException` | `EnvelopeDecryptionException` |

**Never destroy on doubt (self-check §1).** `AppleTokenVault.OpenAsync` returns `null` on `EnvelopeDecryptionException`, and the T-135 retry job then **deletes** the pending revocation row. So only a proven bad tag is a decryption failure. A missing key (`encryption key not found`), a too-new version (a restored older snapshot), a denied policy, a sealed or unreachable server are all "unavailable": the row is kept and retried. A negative proof covers it (§9). *(Review S1.)* The same rule now holds one level up in `EnvelopeCipher` for every provider: a blob whose key reference isn't configured (e.g. `PreviousKeyRefs` forgotten at the switch) is `KmsUnavailableException`, not a decryption failure (`OpenBaoRevocationRetryTests.AForgottenPreviousKeyRefKeepsThePendingRevocation`, through the real T-135 job). Residual: a key deleted and **re-created under the same name** while the API runs answers a bad tag for old envelopes (they are then truly unopenable); the pin of every key (§6) refuses such a key at the next start, the API policy can't delete or re-create keys, and keys are created with `deletion_allowed=false`.

## 4. Authentication

**Chosen: AppRole, `role_id` + `secret_id` read from files, login in-process; no response wrapping, no token file.**

- Credential directory `Kms:OpenBao:CredentialDirectory` holds `role-id`, `secret-id` and `ca.pem` (each ≤ 8 KiB; any other entry must pass the same checks). It gets the **T-200 guards unchanged** (same code): absolute canonical path with no symbolic link, directory 0700/0500 and files 0400/0600 owned by the process user or root, safe parents, no symlink/subdirectory/special entry, not in a source tree / the content root / the app folder, no `kms.env`. Same mount pattern as T-200 (`/etc/zaghlol/openbao-api` → `/run/zaghlol-openbao:ro`, uid 1654).
- `role-id` and `secret-id`: 1–256 printable ASCII characters without spaces (one trailing newline allowed). Read at **each** login (so a rotated `secret_id` is picked up without a restart) with the same checks.
- Token: kept in memory; re-login when two thirds of `lease_duration` have passed (`0` = no expiry) or after a `403` (above). One login at a time (`SemaphoreSlim`); concurrent callers wait for it. Login counts toward the 2 s call budget. *(Review nit.)* A `403` forces at most one login per 5 s: callers whose token was already renewed reuse the new one, and a token refused again within the interval (a policy denial) is "unavailable" without another login.
- *(Review C2.)* A credential read that fails at a run-time login (a `secret-id` being replaced, a mode briefly wrong) is "unavailable" (503), not a configuration error; at start it still refuses the start.
- Role settings (setup script): `token_ttl=1h`, `token_max_ttl=4h`, `token_type=service` (revocable with `bao lease revoke -prefix auth/approle/login`), `secret_id_num_uses=0`, `secret_id_ttl=0`, `secret_id_bound_cidrs` and `token_bound_cidrs` = the docker network of the stack, `token_policies` = one policy, `token_no_default_policy=true`.

Why not response-wrapped `secret_id`: a wrap is single use, so every container start (crash, `restart: unless-stopped`, host reboot) would need a fresh wrap from a trusted orchestrator. This deployment has none (one server, docker compose); either the restart fails (outage) or a long-lived unwrap credential sits next to it (no gain). CIDR binding gives the property that matters: a copied `secret_id` is useless off the box. Why not a token file: a periodic token on disk is the same exposure without the CIDR binding, and needs an external renewer (OpenBao Agent) per process. Incident response: destroy the `secret_id` (`secret-id/destroy`), revoke the role's tokens, issue a new one into the mount; no app release.

**Policies (least privilege, generated by `setup.sh policy api|worker|keytool` from the key lists, so they name each key):**
- `zaghlol-api`: `update` on `<m>/sign/<kid>/sha2-256` for each kid; `update` on `<m>/hmac/<name>/sha2-256` for the three HMAC keys and each envelope key (pins, §6); `update` on `<m>/datakey/plaintext/<envelope>` and `<m>/decrypt/<envelope>`; `update` on `<m>/decrypt/file-<name>` for imported legacy keys; `read` on `<m>/keys/<name>` for each of those keys (attributes and public keys). Explicit `deny` on `<m>/export/*`, `<m>/backup/*`, `<m>/restore*`, `<m>/keys/+/config`, `<m>/keys/+/rotate`, `<m>/keys/+/import*`, `<m>/wrapping_key`, `<m>/datakey/wrapped/*`, `sys/*`.
- `zaghlol-worker`: only the envelope part (datakey, decrypt, hmac pin and `read` on envelope keys, decrypt on `file-<name>`), same denies.
- `zaghlol-keytool` (operator, short-lived token for §5 only): `read` `<m>/wrapping_key`, `create`/`update` `<m>/keys/+/import`, `read` on the keys, `update` on `hmac` and `decrypt` of the imported keys (to verify the import). Issued with `ttl=15m`, `num_uses=40`, revoked after use.

## 5. Migration from T-200 (one time, per environment)

1. **Signing: rotated in, not imported.** *(Review C1.)* After the switch the T-200 kids stay in the ring as `Retired` entries with `KeyRef=file:<kid>`: the adapter treats them as **verify-only** (role `VerifyOnly`): never signed with, no Transit lookup, `KmsStartupCheck` skips the public-key comparison for them (`IVerifyOnlySigningKeys`), and their pin `Kms:OpenBao:Fingerprints:<kid>` is the T-200 one, computed from the configured JWK and checked like every other pin (denylist and other-environment lists included). So the JWKS keeps them and account tokens they signed still validate (`OpenBaoKmsTests.C1_TheDocumentedSwitchOverKeepsT200TokensValidAndSignsWithTheNewKids`). A `file:` kid that is `Active` or `Next` is refused. `setup.sh` creates `ecdsa-p256` keys named by the new kids (e.g. `s2027a`, `e2027a`), `exportable=false`, `allow_plaintext_backup=false`. The key tool (below) prints their ring entries (`Status=Next`, public JWK) and pins. Ship an app release that pins the old `file:` kids **and** the new ones; once it is the minimum supported version, flip the new kids `Active` and the old `Retired` (the T-200 rotation rule). Until then the old kids keep signing from the File provider, i.e. **the provider switch happens at the flip**, when the ring no longer needs a `file:` signing key: `Kms:Provider=OpenBao` refuses `file:` signing references. Retired `file:` kids stay published as JWKs only; their `.pem` files are destroyed with the File key directory after the switch.
2. **HMAC keys: imported (BYOK), so every stored `install_hash`, `device_key_hash`, audit hash and the log pseudonym stay valid.** `seat`, `audit`, `install-pepper` become Transit `hmac` keys of the same names, imported from the File key files. Proof that the import is the same key: the File fingerprint is `HMAC-SHA256(key, "zaghlol-kms-file-fingerprint-v1")`, and the OpenBao pin of an `hmac` key is that same MAC computed **by Transit** (`hmac` at `key_version 1`). So `Kms:OpenBao:Fingerprints:seat` must equal the T-200 `Kms:File:Fingerprints:seat`; the tool refuses to finish when it differs, and the API refuses to start on a wrong pin. `Kms:HmacKeys:SeatCheck` stays unchanged and is re-proved at every start.
3. **Envelope: the File KEK is imported as `aes256-gcm96` key `file-<name>` (decrypt-only by policy); no re-wrap job, no File decrypt path.** Old envelopes carry `file:envelope` and a File-format wrap; with `Kms:Envelope:PreviousKeyRefs:0=file:envelope` the adapter sends that wrap to Transit `decrypt` with the File AAD (§1, facts). New envelopes use a new Transit key (`openbao:envelope-2027`). Rejected alternatives: a re-wrap job (rewrites every row with both keys in one process; a crash or a bug mid-way loses Apple refresh tokens, self-check §1) and a read-only File decrypt path (keeps a KEK on the API disk, the exposure T-201 removes). The legacy key is deleted (`deletion_allowed` set by the operator, then `DELETE`) only after no row references `file:` (query in `deployment.md`); idempotency rows expire in 24 h, Apple refresh tokens live as long as the account.
4. The **key tool** `dotnet Zaghlol.Workers.dll --openbao-keys …` (in the release image, like `--generate-keys`) does steps 1–3's OpenBao side: reads the File keys through the T-200 checks (format, denylist, degenerate), wraps each with a fresh ephemeral AES key under the OpenBao wrapping key (RSA-4096 checked), imports it (`exportable=false`, `allow_plaintext_backup=false`, `allow_rotation=false`), verifies it (HMAC: Transit pin = File fingerprint; legacy KEK: Transit opens a File-format wrap of a random test key the tool made), and prints only public values: `Kms__OpenBao__Fingerprints__<name>` for every key, the `Signing__Keys__<n>__…` entries of the new kids. A key that already exists is not imported again; it is verified (re-runnable). Refuses: `http` outside Testing/Development, an unknown option (not echoed), a token file that isn't private, a key name outside the name rule, any mismatch (exit 1, nothing printed but the reason).

## 7. The OpenBao server (`backend/deploy/openbao/`)

- `openbao.hcl`: `storage "raft"` (single node, snapshots for backup), `listener "tcp"` with TLS (`tls_min_version = "tls12"`, cert/key from the OpenBao container's own mount), `seal "static"` with `current_key = "file:///openbao/unseal/unseal.key"`, `audit "file"` to `/openbao/audit/audit.log` (fields HMAC'd, the default), `disable_mlock = true` (raft requirement; swap off or encrypted as in T-200), `ui = false`, no `unsafe_allow_api_audit_creation`.
- `setup.sh` (runs in a one-off container of the OpenBao image on the `kms` network, `BAO_ADDR=https://openbao:8200`, with an admin token and a writable output mount; `ZAGHLOL_BOUND_CIDRS` required (review S2); `policy` prints a policy without needing a server): enables the Transit mount, creates the signing keys and the new envelope key (non-exportable, no plaintext backup, deletion not allowed), writes the three policies, enables AppRole and creates `zaghlol-api` / `zaghlol-worker` with the §4 settings, writes `role-id`/`secret-id` for each into an output folder (umask 077; never printed), creates the key-tool token into a file, and checks that an audit device is enabled (fails otherwise). Re-runnable: existing keys are kept (never re-created), existing roles updated.
- `docker-compose.openbao.yml`: the `openbao` service (pinned image, non-root, `cap_drop: [ALL]`, read-only root, `ulimits: core 0`, no published port; reachable only on the stack network) and the `api`/`worker` credential mounts.

**Static-seal custody.** The unseal key is 32 random bytes (written as 64 hex characters) in a file on the host (`/etc/zaghlol/openbao/unseal/unseal.key`) owned by OpenBao's uid 1655 with mode 0400 (OpenBao must read it), in a folder whose parents only root controls; it is mounted read-only **into the OpenBao container only** (never the API, the worker or the one-off set-up container), and the server's routine backup set must not contain it. Two offline encrypted copies (the T-200 backup procedure). `bao operator init` with static seal returns recovery keys (3 shares, threshold 2) and a root token: the recovery shares go to three named people offline; the root token is used for `setup.sh` and the import, then revoked (`bao token revoke -self`); a new one is generated from the recovery shares when needed (`bao operator generate-root`). Rotation: new key file with a new `current_key_id`, old one as `previous_key`, restart. Residual (unchanged from T-200 §6): root on the server can read the unseal key and the raft data, so it gets every key. What T-201 adds: a code-execution bug in the API or worker can use the keys while it lasts (sign, MAC, unwrap) but can't take them away; closing the hole and destroying the `secret_id` ends it, with no app release.

**Backup / restore.** `bao operator raft snapshot save` daily into the server's normal backup set (encrypted under the seal key, useless without it) plus the unseal key's offline copies. Restore: new OpenBao with the same `openbao.hcl` and unseal key, `bao operator raft snapshot restore -force`, restart; the API's pins prove the same keys are back. Losing both the unseal key copies and the recovery shares loses every key (same consequence as losing the T-200 offline backup).

## 8. CI (real OpenBao)

New job `openbao-live` in `backend-ci.yml` (same triggers): runs the pinned `ghcr.io/openbao/openbao` image with the **production** `openbao.hcl` (raft, static seal, TLS from a CA made in the job, audit file) rather than `-dev` (dev mode keeps everything in memory, so it can't prove "stable across restarts" or the static unseal). Steps: CA + server certificate (openssl), unseal key, start, `operator init` (recovery 1/1 in CI only), `setup.sh`, T-200 key tool → File keys, OpenBao key tool → import + pins, `dotnet test --filter Category=OpenBaoLive` phase 1, `docker restart` (auto-unseal), phase 2. Live tests skip when `ZAGHLOL_OPENBAO_ADDR` is unset. The image is pinned by tag and multi-arch index digest (T-192).

## 9. Tests

- In-process **stub OpenBao** (`OpenBaoStub`, Kestrel over TLS with a test CA): the endpoints of §2 plus login, `wrapping_key` and `import`, with real crypto (ECDSA P-256 JWS marshaling, HMAC with companion keys for non-`hmac` types, AES-256-GCM with AAD, RSA-OAEP + KWP unwrap), `vault:v<n>:` prefixes, OpenBao's error JSON and status codes, sealed `503`, `403` on policy denial / expired or revoked token, delays; policies are parsed from `setup.sh policy …` output, so the stub enforces the committed policies.
- `OpenBaoHostStartupTests` (API) and `OpenBaoWorkerTests` (worker binary): the real `Program` starts with OpenBao in Staging/Production and refuses a sealed server; the worker starts with `Kms:Scope = Envelope` and stops with the full scope (its policy can't read signing keys).
- `OpenBaoKmsTests`: starts in Staging/Production/Testing and serves every port; the request fields of §2 (`prehashed`, `jws`, `key_version`); TLS pinning (other CA refused); every guard of §6 with its message and no secret in messages or logs (sentinels: `secret_id`, token, key bytes); worker scope; token expiry/revocation re-login; two actors and one login; sealed and timeout → `KmsUnavailableException`; decrypt classification (bad tag → decryption failure; missing key, denial, sealed → unavailable).
- `OpenBaoKeyToolTests`: imports the File keys, pins equal the T-200 pins, `SeatCheck` still passes, old File envelopes open through OpenBao, re-run verifies without re-importing, no key byte in stdout/stderr, refusals.
- `OpenBaoLiveTests` (CI only): sign/verify, JWK = published key, HMAC = HMAC of the File key bytes before and after a restart, envelope (new and legacy) round trip across the restart, sealed/unreachable → unavailable.
- Negative proofs (run locally, reverted): (1) decrypt classification widened to every `400` → `OnlyAProvenBadTagIsUndecryptable` and `AVersionTooNewIsUnavailableNotUndecryptable` go red; (2) the TLS callback ignoring chain errors → `AnotherCaIsRefused` and `TheToolTrustsOnlyTheGivenCa` go red (an accept-all callback doesn't even compile: analyzer CA5359); (3) the `exportable` check removed → `O2_…(exportable)` and `AnExportableSigningKeyIsRefused` go red.
- HTTP mapping: the adapter's failures surface as `KmsUnavailableException`; `ResponseSigningTests.AKmsOutageIs503WithRetryAfterAndNoBody` already proves that exception becomes `503 UPSTREAM_UNAVAILABLE` with `Retry-After: 5`.

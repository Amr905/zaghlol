# T-137 design note: `zaghlol-ops` (C3, written by the implementer)

Scope: the operator CLI on top of the admin API (`backend/openapi/zaghlol-v1.yaml`, tag Admin). This note fixes the three parts the task asks for: sign-in, where the token lives on each OS, and how the order ID is read. Everything else (commands, runbook) follows the OpenAPI file and T-186.

## 1. Sign-in (R3-9), independent of the IdP

The identity provider is not chosen yet (T-136 Q1), so the CLI knows only OIDC. Settings (all public values, read from `ZAGHLOL_OPS_*` variables or a JSON file; the variable wins; no flag takes a secret): `apiUrl`, `issuer`, `clientId`, optional `scopes` (default `openid email`), `tokenUse` (`id_token` default, or `access_token`), `redirectHost` (`localhost` default, `127.0.0.1`), `tokenCache` (`os` default, or `memory`), optional `clientSecret`.

Flow (RFC 8252, RFC 7636):
1. Fetch `{issuer}/.well-known/openid-configuration` over HTTPS. The document's `issuer` must equal the configured one (mix-up defence); `authorization_endpoint` and `token_endpoint` must be HTTPS. Nothing else in the document is read, so a `device_authorization_endpoint` is never used. A test serves one as bait and asserts it is never requested and that `grant_type` is always `authorization_code`.
2. Open a TCP listener on `127.0.0.1` with an OS-chosen port (best effort on `::1` too). The redirect URI is `http://{redirectHost}:{port}/callback`. Entra accepts any port for a registered `http://localhost`; Google desktop clients accept both hosts. A raw listener instead of `HttpListener` avoids the Windows URL-ACL problem for non-admin users.
3. Make `state` (16 random bytes), `nonce` (16) and a PKCE verifier (32 random bytes, base64url, 43 characters); the challenge is `S256`. Open the system browser (`xdg-open`, `open`, shell execute; no shell string on Unix) and always print the URL (`--no-browser` skips the launch).
4. The listener answers only `GET /callback` once with matching `state`; anything else gets 404 and is ignored. It reads at most 8 KiB of request head, has a 3-minute overall deadline, and closes after the first valid hit. `error=` from the IdP ends the login with the error code (fixed character set), never its description.
5. POST the form `grant_type=authorization_code`, `code`, `redirect_uri`, `client_id`, `code_verifier` (and `client_secret` only when configured; Google's desktop client type needs one that Google itself calls non-confidential). Response capped at 256 KiB. The ID token's `iss`, `aud`, `nonce` and `exp` are checked locally (it came straight from the token endpoint over TLS; the API still verifies the signature). No `offline_access` scope, so no refresh token exists to protect.
6. The token that goes to the API is the one `tokenUse` names. The API origin is fixed by config; redirects are not followed, so the bearer token cannot be sent to another host. HTTPS is required for the API except for loopback hosts (development).

## 2. Token storage on Windows, macOS and Linux

Rule: the token is held **in memory or in the OS credential store, never in a plain file**, and never printed or logged. Only the short-lived (at most 60 minutes) token plus its expiry are stored; no refresh token exists. An entry past `exp` minus 60 s is treated as absent and removed.

| OS | Store | How the secret travels |
|---|---|---|
| Windows | Credential Manager, generic credential `zaghlol-ops/{key}`, `CRED_PERSIST_LOCAL_MACHINE` (kept per user, protected by DPAPI) via `CredWriteW`/`CredReadW`/`CredDeleteW` (advapi32) | In-process API call. A blob holds at most 2560 bytes, so a token is split over up to 4 entries `{key}#0..3`; a longer token is not persisted (memory only) |
| macOS | Keychain through `/usr/bin/security -i` (commands read from **stdin**) | The token is written to the child's stdin, never to its arguments, because arguments are visible to every user in `ps`. It is only used if it matches `[A-Za-z0-9._-]+` (a JWT does), so nothing can break out of the command line; otherwise it is not persisted |
| Linux | Secret Service (GNOME Keyring, KWallet) through `secret-tool store/lookup/clear` | `store` reads the secret from stdin; the attributes (service, account) are public |

Fallback: if the tool or service is missing (headless server, no D-Bus session), or `tokenCache=memory`, the CLI keeps the token in memory for this process only and says so once on stderr; the next run signs in again. The CLI never falls back to a file. `logout` deletes the entry; a failed delete is reported, not hidden.

Accepted residual (stated in the runbook): any process of the same OS user can read the credential store, as it can read the CLI's memory. The store protects against disk images, backups, copied home directories and other users. The 60-minute lifetime and the IdP's phishing-resistant MFA for support roles bound the rest. The credential store never holds the order ID.

Code shape: `ITokenStore` with `MemoryTokenStore`, `WindowsCredentialStore`, `ProcessTokenStore` (macOS and Linux share the process plumbing through an `IProcessRunner` that never uses a shell and passes arguments as a list). Tests use a recording runner (the secret appears only in stdin, never in an argument), a fake `secret-tool` script through the real runner on Linux, and the memory store. The Windows store compiles everywhere but can only run on Windows (stated in the report).

## 3. The order-ID prompt (D-57)

- The three commands (`support move|detach|unfreeze`) have no order-ID option and read no environment variable for it. The parser has an explicit option list per command; any other option is a usage error that prints no part of the offending argument beyond the option name. A test lists the options and asserts none mentions order or ownership, and another sets plausible variables (`ZAGHLOL_OPS_ORDER_ID`, `ORDER_ID`, `OWNERSHIP_CHECK`) and asserts the sentinel never reaches the request.
- The prompt reads the terminal key by key (`Console.ReadKey(intercept: true)`, which keeps the terminal in no-echo mode on every OS), so nothing is echoed, not even `*`. Backspace edits, Enter ends, Escape and Ctrl-C cancel. If input is redirected (a pipe, a file, `<<<`) the command refuses with exit 2: a script feeding the prompt would be keeping the order ID somewhere (history, a file). Input is checked as typed against the order-ID pattern `^[A-Za-z0-9.-]{6,64}$`; excess characters are dropped and a bad final value is not echoed in the error.
- The characters live in a `char[]` that is cleared as soon as the request body is built; the body is built as UTF-8 bytes straight into a buffer that is cleared after the call. .NET `HttpClient` may keep copies and the runtime does not guarantee wiping, so this is best effort and is described as such.
- The value is sent only in the request body of the one call. It is not written to history (never on the command line), config, log, audit output or any error text; the CLI prints API problems as status and `code` only, from a fixed character set.
- Tests: a fake key source for the prompt (no echo output, backspace, redirected refusal, over-length), and full runs of all three commands with a sentinel order ID through success, 409, 422, 503 and a network error, capturing stdout, stderr and a logging sink, asserting the sentinel appears in none of them and appears exactly once in the one request body.

## 4. Command surface

Every operation of the OpenAPI Admin tag has one command (table in the runbook). A test reads the spec and fails if an `adminXxx` operation has no command, so a new admin operation cannot be forgotten. Output is JSON on stdout (the response body as received, re-indented); errors go to stderr as `error: <status> <CODE>`. Exit codes: 0 ok, 1 API refused (4xx/5xx), 2 usage, 3 sign-in or role failure (401, 403, login failed), 4 network or timeout.

`catalog import <file>` is client-side: it reads a JSON file of entries and applies them in order with the same `POST`/`PUT` calls as the single commands, stops at the first failure and says how many were applied. It has `--dry-run` (validates the file only). Nothing is published until `catalog publish`.

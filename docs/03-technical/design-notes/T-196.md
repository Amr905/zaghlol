# T-196 design note: recurring every 1, 3, 6 or 12 months becomes a bill (C3, written by the implementer)

Scope: D-72 (supersedes the confirm-first rule of BR-SUB-01 for these cadences). Domain rules in `packages/zaghlol_domain/lib/recurring/recurring_rules.dart`; storage, detection and undo in `app/lib/features/recurring/`; schema v5.

## 1. Cadences

`RecurrenceCadence` gets `quarterly` and `semiAnnual` (stored codes `quarterly`, `semi_annual`), each with `monthsPerCycle` (monthly 1, quarterly 3, semiAnnual 6, yearly 12). `advanceDue` adds that many months to the date just paid and clamps the anchor day to the month end (31st becomes 30/28/29). Yearly stays year + 1 with the same clamp. `yearlyOf` multiplies by 12 / 4 / 2 / 1; `monthlyOf` divides the yearly figure (rounded half up, integers only). The insights `annualCost` and the chart repository switch get the same two cases (the Dart switch is exhaustive, so a missed one does not compile).

## 2. Detection rules (pure, domain)

`detectRecurring(charges, today:, exclude:, excludedCategoryIds:)` replaces `detectSubscriptions` (removed; no other caller).

- Group by (merchant key, account, currency) as before. A chain never mixes currencies or accounts. Zero amounts and unstorable merchant keys are ignored. Charges whose category is in `nonRecurringCategoryIds` (the seeded codes groceries, dining, transport, cash, income, where the same merchant repeats by coincidence; the app passes a user subcategory as its top-level code; `instapay` is NOT excluded because rent and bills are often paid that way; a test checks every id is a seeded code) are dropped first. Lead decision 2026-11-20: rent, utilities, bills, installments, education, insurance and subscriptions are NOT excluded and do auto-add (Q-25's essential set is about roasting, not bills).
- For the group's latest charge, walk back while the gap to the previous charge is inside the cadence window and the amount is within 10% of the previous one. The cadence is fixed by the latest gap; the windows do not overlap:

| Cadence | Gap window (days) | Minimum chain |
|---|---|---|
| monthly | 25..35 (unchanged) | 3 |
| quarterly | 84..97 (3 months is 89..92) | 3 |
| semi-annual | 176..189 (181..184) | 2 |
| yearly | 360..371 (365..366) | 2 |

  Monthly goes from 2 to 3 charges because a bill is now created without asking (task text). A walk that mixes windows stops at the first gap outside the window of the latest gap.
- Stale chains are not added: `nextDue` earlier than `today - 10 days` means the chain stopped (a cancelled yearly plan seen 18 months later, a monthly one silent for 3 months). A longer look-back (760 days) would otherwise resurrect them.
- Output carries cadence, amount (the latest charge), the anchor day (most common day of month, ties to the later, FU-143), `nextDue = advanceDue(last)`, annual cost and the chain ids.
- `exclude` holds dismissal keys and existing items' keys (`merchant|account|currency`). An existing item with a merchant key but no account (typed by hand) also blocks the same merchant and currency on every account (`merchant||currency`).

## 3. Storage: schema v5

Two changes, one version (`appSchemaVersion` 5), because SQLite cannot widen a CHECK:

1. `recurring_items` is rebuilt (create `__v5`, copy by column name, row count equal, drop, rename, indexes) with `cadence IN ('monthly','quarterly','semi_annual','yearly','weekly','custom_days')` and a new nullable `auto_added_at INTEGER` (epoch ms, set only by automatic detection). Old rows keep their values (no stored value needs rewriting: existing codes stay valid); `auto_added_at` is NULL for them.
2. New table `recurring_dismissals (dismissal_key TEXT PRIMARY KEY, dismissed_at INTEGER)`. `dismissal_key` is the detection key. No foreign key, so a later account removal can never block or silently drop a dismissal.

A new frozen step file `migrations/v5_recurring_cadence.dart` (own rebuild type: v4's temp name is hard-wired to `__v4`), wired as `from4To5`; the v5 dump and `app_schema.steps.dart` come from `app/tool/generate_drift.sh`. The step is checked against the v4 and v5 dumps like v4 was.

Pending `suggested` rows from before stay as they are (the user can still confirm or dismiss them in the review queue); only new detections are auto-added.

## 4. Auto-add, undo, notification

`RecurringRepository.detectAndAutoAdd` (the old `detectAndSuggest` is removed; the housekeeping step keeps its name `recurring_detect`): one transaction scans posted, non-internal, non-deleted expenses in the last 760 days (cap 20 000 as now), loads dismissal keys and existing item keys, runs the domain rule and inserts each chain as `kind = subscription`, `status = active`, `auto_added_at = now`, the chain's cadence, due day, next due date, amount (integer minor units, the chain's own currency). No review item is created for auto-added bills. It returns the new ids. Idempotent: the inserted item blocks its own key on the next run; with two engines at once SQLite serialises the write transactions: the second either sees the first's row and skips the key, or fails with a busy error and retries on the next run, so no duplicate is inserted (a test runs two repositories on one database; a true two-connection race is not tested).

Undo, `notABill(id)`: in one transaction, only if the row is active and `auto_added_at` is set: insert the dismissal key (`INSERT OR IGNORE`) and set the item `dismissed` (kept, with its occurrences). The bills snackbar offers Undo for 6 seconds: `undoNotABill(id)` (only for a `dismissed` row with `auto_added_at`) forgets the key and makes the item active again; after that, a dismissal stays. `deleteItem` of any kind with a merchant key writes the same dismissal first (BNPL installments included). `updateManual` writes the old key when it changes (account or currency), so the edited item is not re-added as a duplicate. Editing clears `auto_added_at`.

One notification per run when at least one bill was added, type `subscriptionRenewal` (its toggle and channel already exist, unused so far), subject `auto_added`, period key = today, so a second run on the same day is silent. Body: the name for one bill, a count for several; redacted variant has no amount. Tap opens `/insights` (bills live in the Insights tab; the route allow-list has no bare `/recurring`).

## 5. UI

Bills list rows for an auto-added item show a small "اتضافت لوحدها" badge and a "مش فاتورة" text button (one tap, no dialog; a snackbar confirms). Strings in `app_ar.arb` / `app_en.arb`, Egyptian colloquial. The edit screen's cadence chips gain 3 and 6 months. Reminders need no change: `dueReminders`/`overdueReminders` read `next_due_date` and are cadence-blind; `markPaidManual` and `autoMarkPaid` use `_cadenceOf`, which learns the two codes (an unknown code there silently stopped an item, so a test covers all six).

## 6. Tests (map to the acceptance criteria)

1. Domain: monthly, quarterly, semi-annual, yearly chains; near misses (gaps outside the window, amount outside 10%, different merchant, different currency, excluded category, one charge only, two monthly charges, stale chain); advanceDue for each cadence at month ends; determinism under input order.
2. Repository (in-memory DB): detection adds active auto bills; second run adds nothing; `notABill` then detection adds nothing; hand-delete then detection adds nothing; existing dismissed/manual key blocks; currency separation; `shouldStop`; reminders and auto-mark for a quarterly item.
3. `yearlyOf`/`monthlyOf` for all codes; chart `annualCost`.
4. Migration v4 to v5 through the opener on an encrypted file (rows kept, CHECK widened, new column NULL, dismissals table usable, schema equals fresh and the dump, frozen step equals the dumps).
5. ar/en goldens of the bills list with an auto-added row.

## 7. Accepted residuals

- After the 6-second Undo, a dismissal is permanent; there is no "bring it back" button (add the bill by hand).
- The excluded-category set is a parameter (`excludedCategoryIds`); a custom category with a name outside the set is never excluded.
- The badge stays until the user edits the item or undoes it.

# T-195 design note: salary as income, manual or from the SMS (C3, written by the implementer)

Scope: D-71. Domain rules in `packages/zaghlol_domain/lib/salary/salary_rules.dart`; storage, matching and nudge in `app/lib/features/salary/`. **No schema change: no v6** (section 4).

## 1. Matching rule (pure, domain)

- Window of a payday date P: local civil dates P-3 .. P+5 (9 days; monthly windows never overlap). Payday day is 1..28, so P always exists.
- A captured credit is a candidate when it is live, `posted`, direction `income` or `transfer_in`, `is_internal = 0` and not in a transfer pair, `source` is not `manual`, and it is not already tied to a salary entry or declined (below). Its local date comes from `occurred_at + occurred_tz_offset_min`.
- It matches a salary anchor (a payday P, or the date of a manual entry) when (a) the **currency is the same** (never converted, never compared across currencies), (b) its date is inside the anchor's window, and (c) its amount is within 15 % of the expected or manual amount (integer test: `|c - e| * 100 <= 15 * e`) **or** its description (merchant, counterparty, note; never the raw SMS body) contains salary, payroll, مرتب, راتب or رواتب. Keyword plus right currency and window is enough even when the amount differs (a raise, a partial).
- Two or more possible anchors or candidates never get guessed: with two manual entries in reach nothing merges; with two candidate credits the first one that arrives takes the expected item and the second stays a plain income.

## 2. Where the expected salary lives, and the order cases

- `settings` key `salary.plan` (JSON: amount minor, ISO currency, payday day 1..28, optional account id). Absent: the feature is off. Backed up with the other settings; no new table.
- `settings` key `salary.state` (JSON, at most 16 KiB, pruned to the last 8 entries and 16 declined ids): `entries` (txn id, `manual` or `captured`, anchor date, optional merged manual txn id and its amount) and `skipped` (anchor dates). Read and written only inside a database transaction, so the UI engine and the background engine serialise.
- The **expected item is never a transaction row**; it is derived: plan + today + state. It is open for a payday P when P <= today and P is not skipped and no live transaction is tied to P. It shows from P until the next window starts. Deleting the tied transaction reopens it.
- **SMS after the expected item (no manual entry):** the post-persist hook tags the captured transaction (an entry anchored at P, category `sys:income` when it has none) and so closes the item. Nothing is inserted or deleted.
- **SMS after a manual entry:** the SMS transaction is the survivor; the manual row is soft-deleted in the same transaction (its note is copied when the SMS has none), and the captured entry keeps the manual id and amount. **Undo** (transaction detail, "ارجّع المرتب اللي سجلته"): restore the manual row, drop the link and remember the SMS id as declined so it is not merged again. Undo only works while the soft-deleted row is still restorable (30 days).
- **Manual entry after the SMS:** `SalaryService.recordManual` first looks for a captured credit that matches by the same rule; if found it returns `FoundExisting` and the UI asks (same one: close the item with it; another income: record anyway). Nothing is written until the user answers.
- Reconciliation also runs from housekeeping (a credit that arrived before the plan existed, or when the hook failed), so both arrival orders end at one counted income.

## 3. Totals ignore unconfirmed expected income

Home, budgets, safe-to-spend and charts read `transactions` (and `cycle_summaries` built from it). The expected item has no row, so it is in no total by construction. It becomes income only through a real transaction (manual or captured). A test builds the cycle summary with an open expected item and checks income is unchanged. Double counting is prevented by soft-deleting the manual row on merge (soft-deleted rows are in no total); a test sums income per currency after every order and expects one salary. A `TransactionsChanged` event for both rows' cycles is published after a merge or undo.

## 4. Schema impact

None. Plan and state are two `settings` rows; tagging uses the existing `sys:income` category plus the state entries; the manual row is an ordinary `manual` income. No new column, no rebuild, no new dump: `appSchemaVersion` stays 5. (A dedicated Salary category would be a catalog change, not a migration; raised as a PO question.)

## 5. Nudge and UI

- Home tap target: the nudge's payload is `/home` (a new `HomeTarget` in the notification route allow-list).
- Housekeeping step `salary_check`: reconcile, then for the latest payday P whose window has ended (today >= P+6, within 20 days) and is still open, one local notification "المرتب نزل؟" (type `upcomingDue`, so its toggle, channel and quiet hours apply; no amount in the text; subject `salary_check`, period key P: `fired_alerts` makes it once per payday). Tap opens Home, where the expected row has the three actions: نزل (records it as manual income on the plan's account, dated P), لسه (hides nothing, no write), تخطي الشهر ده (skipped).
- Home: one row "المرتب — متوقع" with the amount through `ZMoneyText`. Settings (preferences, under payday): "مرتبي" with amount, currency, payday day, account, and Remove. Add flow: a "مرتب" switch on the income form. Transaction detail: the undo line after a merge.
- Strings in both ARB files, Egyptian colloquial.

## 6. Tests (map to the acceptance criteria)

1. AC1: manual salary with no SMS is income in the cycle summary and Home read model.
2. AC2: both orders, amount drift (within and outside 15 %), early (P-3) and late (P+5) arrival, outside the window, two currencies (the other currency never merges), two credits, undo, one-counted-income assertion per case; negative proof that the other-currency credit stays separate.
3. AC3: nudge once per payday (second run silent), none when the period is closed, none when `notif.upcoming_due` is off.
4. AC4: ar/en goldens of the expected row and of the nudge preview; RTL; l10n key parity.
5. Settings codec round trips; backup restore keeps plan and state (settings rows).

## 7. Accepted residuals

- A `transfer_in` credit is offered to the matcher only when it is not internal and not paired at that moment (the salary hook runs after the pairing hook). If it is paired later, the merged manual row stays soft-deleted and the pair is internal, so that month's salary is not counted until the user restores the manual row (undo) or the pair is unlinked. Rare (a pair needs an own transfer-out of a similar amount).
- The "It arrived" confirmation looks for a received credit more loosely than the automatic match: any credit of at least half the plan, same currency, inside the window, is offered with "is that your salary?" (never tied silently), because the plan amount may be out of date.
- No dedicated Salary category; the tag lives in the state.

# T-200 design note: hardened file KMS (`Kms:Provider = File`, D-76 option B)

Class C4 (keys, entitlements). Written before the code. Scope: a key-file provider that is allowed in Staging and Production, the guards that make it refuse to start, the production key tool, and what stays weak until T-201 (OpenBao Transit). ADR-023 records the decision; `deployment.md` §3 holds the operator steps.

## 1. Where it plugs in (the seam T-201 reuses)

- The three ports stay as they are (`ISigningKeyProvider`, `IHmacProvider`, `IDataKeyProvider`, `KmsPorts.cs`). Callers (`Signer`, `KeyedHasher`, `EnvelopeCipher`, `KmsStartupCheck`, `SeatKeyStartupCheck`) do not change.
- `KmsServiceCollectionExtensions` gets one selector, `SelectProvider`, that switches on `Kms:Provider` and returns an internal `IKmsBackend` (the three ports in one object). Each port is registered as a forward to that one instance. `Local` keeps its rule (Development/Testing only); `File` is new; T-201 adds `OpenBao` as one more case. An unknown name is refused, as today.
- `File` uses its own key-reference prefix `file:<name>` (`[a-z0-9][a-z0-9-]{0,62}`), so a `local:` ring can never be pointed at the File provider by accident and an envelope's stored keyRef says which provider wrapped it (T-201 needs that, §8).
- File formats are the ones `dev-keys.sh` writes today: `<name>.pem` is a P-256 private key (PKCS#8 or SEC1 PEM), `<name>.key` is 32 random bytes in base64 with an optional trailing newline. The envelope wrap is AES-256-GCM like Local, with associated data `"zaghlol-file-wrap-v1" ‖ 0x00 ‖ keyRef` (a different label from Local's, so a Local-wrapped key never unwraps under File).

## 2. Key loading: once, at start

Chosen: **load every configured key once when the provider is built** (at host start, before any request), check it, keep it in memory, and refuse to start on any failure. Not per call as `LocalKms` does.

Why:
- The guards (permissions, owner, denylist, fingerprints) then check exactly the bytes that sign. Per-call reads would re-open the file on every response signature, so a file replaced at run time would be used without any check, and an I/O error mid-traffic would turn into 503s instead of a refused start.
- The secrets mount is only needed at start. Rotation already needs a restart (the ring is configuration), so nothing is lost.
- Memory exposure is the same either way against the threat that matters (§6): a process that can run code as the app user can read the files too.

How it is held:
- Signing keys: one `ECDsa` per key ref (OpenSSL keeps the private scalar in native memory; `Dispose` frees it). Signing takes a per-key lock: .NET does not document `ECDsa` instances as thread-safe, and one signature costs well under a millisecond.
- Symmetric keys: `GC.AllocateArray<byte>(32, pinned: true)`, so the GC never copies them; zeroed by `Dispose`. HMAC and AES-GCM are computed from that array; the `AesGcm` and HMAC objects are created per call and disposed.
- File bytes, decoded base64 and PEM characters are read into buffers that are zeroed right after parsing (`CryptographicOperations.ZeroMemory`). The PEM import needs `char`s; those go into a plain `char[]` that is cleared after import. Residual: .NET does not guarantee that no other copy exists (the OpenSSL import, the kernel page cache); this is best effort and documented as such.
- The provider is a DI singleton; the container disposes it at shutdown.

Only keys named in configuration are loaded (every `Signing:Keys:n:KeyRef`, the three `Kms:HmacKeys`, `Kms:Envelope:KeyRef` and `PreviousKeyRefs`). A configured key whose file is missing refuses the start. Other files in the directory are not read, but they are permission-checked (§3), and a `kms.env` there is refused (§4).

## 3. Refusal guards (all fail closed, all at host start)

Every guard throws `KmsConfigurationException` with a **constant message** that names the guard and the setting, never a path, key name, file content, fingerprint value or OS error text (the exception from `File.Open` carries the path; it is dropped). Each has a test that starts the services and asserts the message and that a sentinel planted in the key bytes appears in no log line or exception text.

| # | Guard | Environments |
|---|-------|--------------|
| G1 | `Kms:Provider = Local` outside Development/Testing (unchanged) | all but Dev/Testing |
| G2 | File provider on a non-Linux OS (no POSIX owner/mode to check) | all |
| G3 | `Kms:File:KeyDirectory` unset, relative, not canonical (contains a symlink, `..`, a trailing separator), not a directory, or a symlink | all |
| G4 | Key directory mode has any group/other bit (`mode & 0o077 != 0`), or owner is neither the process's effective uid nor root | all |
| G5 | Any ancestor of the key directory is not owned by root or the effective uid, or is group/other-writable without the sticky bit (so nobody else can swap the directory) | all |
| G6 | Any entry in the key directory is a symlink or not a regular file (subdirectories included); any regular file has a group/other bit or a setuid/setgid/sticky bit, or is owned by neither the effective uid nor root | all |
| G7 | A configured key ref is not `file:<name>`, or its file is missing, unreadable, larger than 8 KiB, or not the expected format (a named-curve P-256 private key in PEM, explicit curve parameters refused; base64 of exactly 32 bytes) | all |
| G8 | Key directory inside a source tree (an ancestor holds `.git` or `Zaghlol.sln`), inside or equal to the content root or the app base directory, or one of their ancestors | all |
| G9 | Directory contains `kms.env` (always written by `dev-keys.sh`) | all |
| G10 | A key is in the **committed-key denylist** (§4), a signing key has a private scalar below 2^64 (review S4; d = 1 would make the public key the generator), or a symmetric key is degenerate (fewer than 16 distinct byte values; a random 32-byte key has about 30, so a false refusal has probability about 3·10⁻¹⁷, 2⁻⁵⁴·⁸, computed exactly) | all |
| G11 | A key's fingerprint does not equal `Kms:File:Fingerprints:<name>` (missing value included) | all |
| G12 | A key's fingerprint is listed in `Kms:File:OtherEnvironmentFingerprints:<n>`, or Staging/Production sets neither that list nor `Kms:File:NoOtherEnvironment=true` | list: all; required: Staging/Production |
| G13 | A signing kid with year `0000` (the dev `s0000d`/`e0000d`, test `s0000t`, catalog seed `s0000a`) outside Development/Testing | all but Dev/Testing |
| G14 | *(review S2)* The process can't be marked non-dumpable (`prctl(PR_SET_DUMPABLE, 0)`, called before the first key byte is read) | all but Dev/Testing |
| G15 | *(review S3)* One symmetric key reference in two roles (two of the HMAC keys, or an HMAC key and an envelope key), or the same key bytes under two names (equal fingerprints) | all |

Then, unchanged: `KmsStartupCheck` (JWK equals key, sign-then-verify, every HMAC answers, envelope round-trip) and `SeatKeyStartupCheck` (`SeatCheck`).

**Reading a file safely (G6/G7).** Per entry: `statx(AT_SYMLINK_NOFOLLOW)` on the name (refuse symlinks, non-regular files, bad mode/owner); open read-only; `statx(AT_EMPTY_PATH)` on the open descriptor; refuse unless device and inode equal the first look and mode/owner still pass; read at most 8 KiB + 1 bytes from the descriptor. So the bytes read come from the file that was checked.

**Linux mechanics.** .NET exposes the mode (`File.GetUnixFileMode`) but not the owner, so the provider P/Invokes glibc `statx` (Linux 4.11+, glibc 2.28+; Ubuntu Noble chiseled image has both) with the fixed 256-byte `struct statx`, which has the same layout on every architecture, and `geteuid`. The configured path must equal its `Path.GetFullPath` form (no `..`, `.`, double or trailing separator), and an `lstat` walk from `/` down refuses any component that is a symbolic link or not a directory (no `realpath` call). A missing symbol or a `statx` error refuses the start (fail closed), message without errno detail.

**Windows and macOS.** The File provider refuses to start (G2) in every environment. Windows has ACLs, not POSIX modes; checking "only this account can read" there needs a full DACL walk (inheritance, groups, SYSTEM, Administrators) that we would test on no production machine, since the server is Linux. A half check would be worse than a clear refusal. Development on Windows uses `Local`. Tests that need the File provider are Linux-only (`[LinuxFact]`); one test on non-Linux asserts the refusal (skipped on Linux, run by the PC runner).

**Docker note.** The container runs as uid 1654. A root-owned 0400 file is unreadable to it, so the files are owned by uid 1654 (mode 0400, directory 0500) on the host and the directory is bind-mounted read-only; owner = euid passes G4/G6. Docker secrets are not used: Docker creates `/run/secrets` itself (root, 0755, refused by G4) and swarm's default file mode is 0444 (`deployment.md` §3).

## 4. Dev and test key detection (G8–G10, G13)

Recognising "any key `dev-keys.sh` could have produced" is impossible: it makes fresh random keys with OpenSSL, indistinguishable from production keys. Instead the provider refuses what can be known:

1. **Committed private material.** Keys whose private half is in the repository: the catalog dev seed key `s0000a` (`tools/catalog_build/dev/dev_signing_key.json`), the `s2026a` key in `tools/catalog_build/test/catalog_build_test.dart`, and the fixed `K_seat` of the vectors (bytes `00 01 … 1f`, `seat-key-hash-v1.json`, `FakeKms.FixedSeatKey`). Their fingerprints are embedded in `KnownTestKeys`. Signing keys are compared by the fingerprint of the public key, so the private scalar never needs to be in the product.
2. **Committed public test keys.** Every public JWK in `backend/tests/Zaghlol.Contract.Tests/vectors/*.json`. Their private halves were discarded, so a match is practically impossible, but the check is free and catches a regenerated vector file whose key someone kept.
3. **Coverage test.** `KnownTestKeysTests` scans those files (linked into the test output) and fails if a key there is missing from the denylist, so a new committed key forces a denylist update. The RFC 4231 keys in `keyed-hash-v1.json` are not 32 bytes and can't be loaded (G7).
4. **Where dev keys live.** `dev-keys.sh` writes into `backend/.dev-keys/` inside the repo (G8) together with `kms.env` (G9) and uses kids `s0000d`/`e0000d` (G13). Copying the `.pem`/`.key` files alone elsewhere, with a new kid, passes these three; G11/G12 then still demand that the operator wrote the fingerprints that the production tool printed for this environment, and the deploy runbook says to create keys only with the production tool.

Residual: a developer who copies fresh dev keys out of the repo, renames the kids and writes their fingerprints into production config defeats the detection. That is a deliberate operator act, not an accident, and is out of reach of any file check.

## 5. Fingerprints and the staging/production split (G11, G12)

- Fingerprint of a signing key: lower-case hex SHA-256 of the DER SubjectPublicKeyInfo. Of a symmetric key: lower-case hex HMAC-SHA256(key, `"zaghlol-kms-file-fingerprint-v1"`). Both are one-way and public (same standing as `SeatCheck`).
- `Kms:File:Fingerprints:<name>` pins every loaded key (G11). A replaced, recreated or swapped key file stops the start. It generalises the T-182 `SeatCheck` to all keys.
- `Kms:File:OtherEnvironmentFingerprints:<n>` lists the other environment's fingerprints (production lists staging's and, once it exists, staging lists production's). A key whose fingerprint is there, or a pin that equals an entry there, refuses the start (G12). In Staging and Production one of the list or `Kms:File:NoOtherEnvironment=true` (the explicit "there is no other environment yet") must be set, so the check can't be forgotten silently.

## 6. Threat model: File (T-200) vs OpenBao Transit (T-201)

| Threat | File provider | OpenBao Transit (T-201) |
|--------|---------------|-------------------------|
| Key file readable by another local user or container | Refused at start (G4–G6) | Keys never on the API's disk |
| Key committed / dev key in production | Denylist, repo-tree, `kms.env`, kid 0000, fingerprints (G8–G13) | Same pins; key created inside OpenBao |
| Staging key reused in production | G12 | Separate mounts; same G12 idea on the public fingerprints |
| Backup of the app container or image leaks keys | Keys are mounted, not in the image; the mount is excluded from image builds | Same |
| **Code-execution bug in the API or worker** (RCE, deserialisation, a malicious dependency) | **Attacker copies the keys** (they are in process memory and readable by the uid). They can forge entitlements until rotation **and** every app release that pins the keys is replaced | Attacker can sign/HMAC while the bug is live, but **can't take the keys away**; closing the hole and revoking the token ends it, no app release needed |
| Crash dump, core file, swap | Process non-dumpable in Staging/Production (G14); `ulimits core: 0`, no .NET minidumps, no or encrypted swap (`deployment.md` §3) | Keys not in the API process |
| Server root compromise | Keys taken | Keys taken too unless the unseal key is offline (T-201 custody); still raises the bar |
| Key loss (disk failure) | Offline backup (§7) | OpenBao snapshot + unseal key custody |

So T-200 is acceptable for staging and for a production that sells no Gold to real users yet (D-76); T-201 must land before that.

## 7. Production key tool and rotation

Tool: the worker binary, `dotnet Zaghlol.Workers.dll --generate-keys …`, so it ships in the release image and needs no SDK or OpenSSL on the server. Logic in `Zaghlol.Infrastructure.Kms.FileKeyTool` (tested directly).

```
--generate-keys --environment Staging|Production --out <new dir> [--kid s2026a]… [--secret seat]…
```

- Refuses (exit 2, nothing written) when: any component of `--out`'s parent is a symbolic link or not a directory (review C1/S1: the source-tree check is lexical, so the path must be real); something exists at `--out` (checked with `lstat`, so a dangling link counts); the current directory or `--out` is inside a source tree (an ancestor holds `.git` or `Zaghlol.sln`) or the application folder; `--out` already exists (empty or not) or its parent doesn't; not on Linux; a kid doesn't match `^[se][0-9]{4}[a-z]$` or has year 0000; a name repeats; nothing to generate; an unknown option.
- A failure while writing removes only the files this run created and the folder it created, then exits 1.
- Creates `--out` with mode 0700 (umask-independent: `Directory.CreateDirectory(path, UnixFileMode.UserRead|UserWrite|UserExecute)` then an explicit `SetUnixFileMode`) and each file with `FileMode.CreateNew` and `UnixCreateMode = 0400`, so a key is never briefly world-readable. Then sets the directory to 0500.
- Prints to stdout **public values only**, as lines that are valid env-file entries and safe to `source` in a POSIX shell (a `-` in a key name is printed as `_`; the settings accept both spellings): the `Kms__File__Fingerprints__<name>` lines, the `Signing__Keys__n__…` ring entries with each public JWK (status `Next` for signing keys; the operator flips to `Active`), `Kms__HmacKeys__SeatCheck` for a secret named `seat` or `seat-*`, and a short reminder of the next steps (backup, mount, status). The files belong to the user that ran the tool, so it is run as uid 1654 (below). Never a private value: a test captures stdout/stderr and asserts no key byte (base64, hex, PEM body) appears.
- Run on the server, inside the image, with no network and as the app uid, e.g. `docker run --rm --network none --user 1654:1654 -v /etc/zaghlol/kms-production:/out zaghlol:<tag> dotnet /app/worker/Zaghlol.Workers.dll --generate-keys --environment Production --out /out/new --kid s2026a --kid e2026a --secret seat --secret audit --secret install-pepper --secret envelope`.

Rotation (signing keys, yearly or on suspicion): generate `--kid s2027a` into a new directory; copy the `.pem` into the key directory (0400, owner 1654); add the ring entry as `Next` with its fingerprint; ship an app release that pins both kids; after that release is the minimum supported one, flip the new kid to `Active` and the old to `Retired`; drop the retired kid in a later release. HMAC keys: no scheduled rotation (stored hashes would be orphaned; `K_seat` has the T-182 emergency procedure). Envelope KEK: new `--secret envelope-2027`, set as `Kms:Envelope:KeyRef`, old ref moves to `PreviousKeyRefs` until its rows are gone.

Backup: right after generation, copy the directory to two offline encrypted media (e.g. `age`/GPG-encrypted file on USB in two places), never to the repository, cloud drive or the server's backup set; record fingerprints, not keys, in the runbook.

## 8. Input to T-201

- Signing: new kids are created in OpenBao (non-exportable) and rotated in; the File signing keys are retired, not imported.
- HMAC: must be imported once (BYOK) so existing hashes stay valid; the `Fingerprints` pins and `SeatCheck` prove the import is the same key.
- Envelope: blobs carry `file:<name>` and the File wrap format, which Transit `decrypt` can't open. T-201 needs either a one-time re-wrap job or a read-only File decrypt path for `file:` refs until those rows age out (Apple refresh tokens can be long-lived). Decide in the T-201 design note.

## 9. Tests

- Infrastructure (`Kms/FileKmsTests`, Linux-only where they touch modes): correct keys start through `AddZaghlolKms` + `AddZaghlolSeatKeys` in Staging, Production and Testing and serve every port; 0600/0500 accepted; two actors sign at once; one or more tests per guard G1, G3–G13 (each asserts the constant message, and that no directory, key file name or key byte appears in the exception or the captured logs); the `SeatCheck` still runs. `FileKmsPlatformTests` asserts G2 off Linux (skipped on Linux). Owner tests (`chown`) run when the tests run as root (CI containers); otherwise they return early.
- `Kms/KnownTestKeysTests`: the denylist covers every JWK private scalar in the source tree, every public JWK in the shared vectors, and every 32-byte `keyHex`; the degenerate rule.
- `Kms/FileKeyToolTests`: modes 0400/0500, no private byte in stdout/stderr, the printed lines start Production; refusals inside the repository, into a source tree or the app folder, into an existing folder, bad arguments, an unknown argument not echoed; a rotation key alone.
- API (`FileKmsHostStartupTests`): the real `Program` starts in Staging and Production with `File` (database unreachable on purpose), refuses a group-readable key without key material in the logs, and still refuses `Local` in Production.
- Worker (`FileKmsWorkerTests`): the shipped `Zaghlol.Workers.dll --generate-keys` output starts the worker in Staging and Production; a group-readable key stops it; the tool refuses to run inside the repository.
- Negative proofs (run locally, reverted): G6 mode check removed, G10 denylist removed, G12 both other-environment checks removed (each alone is covered by the other; review C3), the key tool's symlink check removed, the non-dumpable call removed, the explicit-curve check, the tiny-scalar check and the duplicate-fingerprint check removed; the matching tests go red.
- Review fixes: `FileKeyToolTests.ASymlinkedParentPointingIntoTheRepositoryIsRefused` (the reviewer's repro), `…ASymlinkedAncestor…`, `…ADanglingSymlinkAtOutIsRefused`, `…ThePrintedLinesAreSafeToSourceInAShell`; `FileKmsDumpableTests` (reads `PR_GET_DUMPABLE` back; Testing leaves it alone); `FileKmsTests.G7_…(explicit)`, `G10_ASigningKeyWithATinyScalarIsRefused`, `S3_…`, `C7_AShellSafePinNameIsAccepted`.
